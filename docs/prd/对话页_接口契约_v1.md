# 对话页 · 接口契约 v1

> 版本：v1 · 2026-07-31
> **定位**：客户端（SwiftUI）↔ `dialogue` Edge Function ↔ 数据库，三者之间**传什么、什么时候传、失败了怎么办**。
> **上位**：`对话页与成长层_需求设计_v1.md`（做什么）+ `对话页_Prompt设计与全文_v1.md`（模型侧契约）。本文只管**接口**。
> **既有范式**：鉴权、CORS、错误返回全部照抄 `get-tab2-home/index.ts`，不另发明。

## 〇、先说一个必须现在解决的矛盾

**验收标准要求流式播报（"生成出第一句就开始出声"），但模型的输出是一整个 JSON。** 这两件事天然打架——JSON 要等最后一个 `}` 才算完整，而等它完整就没有流式可言了，整轮延迟会退回 2.5 秒。

这不是实现细节，**是必须在写代码之前定死的架构选择**。三条路：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A · 等 JSON 完整** | 最简单 | **流式播报直接作废**，E1a 验收标准第②③条不可能达标 |
| **B · 拆成两次调用** | 第一次只要 `reply`（流式）；第二次在后台补记账字段 | 成本翻倍、两次调用可能对同一句话理解不一致 |
| **C · `reply` 放第一个字段 + 增量解析** ✅ | 流式接收，一边收一边找 `"reply"` 的字符串闭合引号，**一拿到就发给客户端开始播**，其余字段收完再处理 | 需要写一个容错的增量提取器（约 30 行），且依赖模型遵守字段顺序 |

**选 C。** 理由：

- `reply` 被硬性限制在 ≤30 词（prompt §2.1），**它是整个 JSON 里最短的部分**，而记账字段才是大头。把它放第一个，等于把用户能感知的那部分延迟压到最低。
- 成本不变，一次调用。
- **不需要完整解析 JSON 就能拿到 `reply`**——只要找到 `"reply":"` 之后到下一个未转义 `"` 之间的内容即可。这个提取器很小，而且失败时可以安全退化成方案 A（等完整 JSON），**不会崩**。

**因此输出 schema 的字段顺序是接口的一部分，不是随便排的。** `reply` 必须第一个。这条要写进 prompt 的 OUTPUT 段和本文 §3.3。

> **给 Claude Code 的明确指令**：实现增量提取时，**必须保留"解析失败就退化为等完整 JSON"的兜底路径**。不要写一个只在理想情况下工作的解析器。

## 一、函数怎么划分

### 1.1 一个 `dialogue` 函数，内部按 `action` 路由

仓库现有惯例是**一个功能一个函数**（`generate` / `get-materials` / `get-tab2-home` …）。对话页**刻意偏离这个惯例**，理由：

四个动作（开场 / 一轮 / 兜底 / 结束）共享同一套东西——session 校验、seed 装配、ledger 查询、prompt 常量、模型客户端。**拆成四个函数就要把这些复制四遍**，而它们一定会随 prompt 迭代一起改，四份不同步只是时间问题。

```
POST /functions/v1/dialogue
  body: { "action": "start" | "turn" | "fallback" | "end" | "resume", ... }
```

> 这是有意的偏离，**要写进代码注释**，否则下一个人会以为是没遵守惯例。

### 1.2 客户端配置

`SupabaseConfig.swift` 加一条，与现有写法一致：

```swift
// MARK: - 对话页（E1）
static var dialogueFunctionURL: URL {
    projectURL.appending(path: "functions/v1/dialogue")
}
```

### 1.3 鉴权：照抄，不要改

**完全复用 `get-tab2-home/index.ts` 的 `getAuthUserId`**——走 `/auth/v1/user` 让 Supabase 验签，**不在本地解 token**。拿不到 uid 直接 401。

这是 `CLAUDE.md` 里写明的"已验证的安全范式"。`dialogue` 涉及用户的口语记录，是目前最敏感的数据，**更不能在这里自创写法**。

## 二、五个动作

### 2.1 `start` —— 进页，拿开场白

**客户端什么时候调**：进入对话页后立即调，**不等待，页面先渲染骨架**（`需求设计 v1 §4.3`：先进页后出声）。

**请求**

```jsonc
{
  "action": "start",
  "scene_category": "工作与学业",     // 数据库枚举值（中文），来自 MineRoute 参数
  "client_session_id": "550e8400-…"  // 客户端生成的 UUID，见 §4.1 幂等
}
```

**响应**（流式，见 §3）

```jsonc
{
  "session_id": "…",                 // 服务端 session，后续所有动作都要带
  "reply": "You've got mornings at the office and client calls in here. Which one's on your mind?",
  "candidates": [                    // 前端的兜底 chips（Tab2_v2 拍板 11b：chips 是兜底不是关口）
    { "name": "晨会前", "label": "Mornings at the office" },
    { "name": "客户电话", "label": "Client calls" }
  ],
  "suggestions": []
}
```

> **`candidates` 的 `label` 是英文、`name` 是原始值。** 前端显示 `label`（`CLAUDE.md`：产品 UI 一律英文），回传时用 `name`。**不要让前端去翻译中文子场景名**——那是模型在服务端顺带做的事。

**服务端做什么**

```
1. 校验 uid（401 兜底）
2. 建 dialogue_sessions 行（scene_category，scene_detail 留空）
3. 装配分类级 seed：子场景候选（occurrence_count ≥2，取前 3）+ 每个的一句 quote
4. 查 ledger 候选（该分类下 status=active，优先 spoken_count=0，取 10–15）
5. 调模型，mode=OPENING，流式返回
6. 落 dialogue_turns（role=assistant）
```

**`candidates` 为空怎么办**（新解锁的分类可能没有出现 ≥2 次的子场景）：不报错，照常走。prompt 里已经写了兜底——问他今天过得怎么样，用户答什么就是锚点。

---

### 2.2 `turn` —— 一轮对话

**请求**

```jsonc
{
  "action": "turn",
  "session_id": "…",
  "turn_id": "6ba7b810-…",           // 客户端生成，幂等键，见 §4.1
  "text": "I set up the room but the projector no work",
  "asr_confidence": 0.82,            // 0–1；系统框架拿不到时传 null
  "duration_ms": 3400,               // 用户这一轮说了多久（§7.4 先攒着）
  "is_first_turn": true              // 第一轮 → 服务端要回填 scene_detail
}
```

**响应**（流式）

```jsonc
{
  "reply": "So you were troubleshooting before the day even started.",
  "suggestions": [
    { "lemma": "run late", "hint": "if things ran behind" }
  ],
  "scene_detail": "晨会前",           // 仅第一轮返回；null = 用户没选
  "spoken_now": ["set up"],          // 本轮记进 spoken_count 的词，供前端做微反馈（可选）
  "breakthrough": ["set up"]         // 本轮首次说出口的词
}
```

> **`correctness.issues` 绝对不返回给客户端。** 它只在服务端写进 `learning_events`。
> 这不只是产品原则（`PRD §6.2.4` 不打断），**更是一道工程保险**：字段不下发，前端就没有任何可能"不小心"把它渲染出来。`Tab2_v2 D-5` 要求纠错必须是组件层面的硬约束——**最硬的约束是数据根本不到前端**。

**服务端做什么**

```
1. 校验 uid + session 归属（session.user_id 必须 == uid，否则 403）
2. 幂等检查：turn_id 已存在 → 直接返回上次结果，不重复调模型、不重复记账
3. 装配上下文（history 最近 6 轮 + seed + ledger）
4. 第一轮：先按 mode=TURN 调用，拿到 scene_detail 后回填 session 并追加子场景级 seed
5. 调模型，流式返回 reply
6. ★ 流式结束后，异步记账（不阻塞响应）：
     - used_entries 二次校验（见 §4.2）→ record_lexicon_dialogue_units
     - correctness.issues → learning_events（asr_confidence 低则丢弃）
     - 落 dialogue_turns ×2（user + assistant）
```

> **第 6 步必须是异步的、非阻塞的**，和 `generate` 的 Stage 3 记账同一个模式。用户不该为了数据库写入而多等。
> **但"异步"不等于"可以丢"**：记账失败要写日志、要能被 §5 的补账作业捞回来。

---

### 2.3 `fallback` —— 母语兜底

**请求**

```jsonc
{
  "action": "fallback",
  "session_id": "…",
  "turn_id": "…",
  "native_text": "投影仪坏了，所以我们晚了十分钟开始"
}
```

**响应**（**不流式**——它是一个弹框，要整块出现）

```jsonc
{
  "translation": "The projector wasn't working, so we started ten minutes late.",
  "key_words": [
    { "word": "projector", "phonetic": "/prəˈdʒektər/" }
  ],
  "hint": "Try saying it."
}
```

**服务端做什么**

```
1. 调模型，mode=FALLBACK
2. 立即写一条 learning_events：event_type='gap', aspect='vocab'
3. ★ 不写 spoken_count、不写 occurrence、不推进任何状态
4. 在 session 上标记"下一轮是兜底后的目标语言表达"
   → 该轮的 occurrence 记 is_known_gap = true
```

> **第 3 步是这个接口的全部意义。** 母语说出来的东西**不算数**（`PRD §6.2.2`）。
> **第 4 步最容易漏**：兜底暴露的缺口是全产品最高价值的语料，如果下一轮不打 `is_known_gap`，这个价值就白丢了。

---

### 2.4 `end` —— 结束，拿总结卡

**请求**

```jsonc
{
  "action": "end",
  "session_id": "…",
  "reason": "user_exit" | "idle_timeout"
}
```

**响应**（不流式，要即时）

```jsonc
{
  "used_words": [                    // 块①：用出了哪些你的词
    { "lemma": "set up", "first_time": true }
  ],
  "to_improve": [                    // 块②：最多 2 条
    { "aspect": "grammar", "suggested": "the projector wasn't working",
      "note": "negation needs a verb" }
  ],
  "progress": [                      // 块③
    { "type": "breakthrough", "lemma": "set up" }
  ],
  "turn_count": 12
}
```

**服务端做什么**

```
1. 幂等：session 已 ended → 直接返回已算好的结果（防止重复调用产生两张卡）
2. 从数据库聚合三块（不调模型！）
3. 写 ended_at + end_reason
```

> **总结卡不调模型，是纯数据库聚合**（`PRD §6.3.2`："把已攒的笔记归类拼卡，不是重新分析整段对话"）。所以它几乎零延迟、零成本，用户点退出的那一刻就能出卡。
> **三块任一为空就不返回该块的数组内容**（返回空数组），前端据此隐藏——"有才出现"（`PRD §6.3.2`）。

**硬规则：`user_exit` 和 `idle_timeout` 走的是同一个 `end`。**
不要为自动收尾另写一条路径（`需求设计 v1 §6.5`）。两条路径必然有一条会漏记账,而漏的那条恰好是用户已经离开、最不会发现的那条。

---

### 2.5 `resume` —— 恢复会话

**什么时候用**：App 被系统回收、用户接了个电话回来、网络断了重连。

**请求**：`{ "action": "resume", "session_id": "…" }`

**响应**：session 状态 + 最近若干轮 `dialogue_turns`，前端重建对话流。

**如果 session 已经 `ended`** → 返回 `410 session_ended`，前端直接回 Tab2，**不要试图接着聊**。

## 三、流式怎么传

### 3.1 传输方式：SSE

用 `text/event-stream`。Supabase Edge Functions（Deno）原生支持，客户端用 `URLSession.bytes(for:)` 逐行读。

### 3.2 事件序列

```
event: session     data: {"session_id":"…"}              ← start 时才有，第一个发
event: reply       data: {"delta":"So you were "}         ← 增量文本，多条
event: reply       data: {"delta":"troubleshooting…"}
event: reply_done  data: {"text":"So you were troubleshooting before the day even started."}
event: meta        data: {"suggestions":[…],"scene_detail":"晨会前"}
event: done        data: {}
```

**客户端的行为：**

| 收到 | 做什么 |
|---|---|
| `session` | 存下 session_id |
| `reply` 增量 | **文字立即上屏** |
| `reply_done` | **交给 TTS 开始播**（整句播，比逐词播自然得多） |
| `meta` | 更新推荐区、话题名 |
| `done` | 解除"AI 正在说"状态，重新开麦 |

> **文字上屏用增量、语音播报用整句。** 这不是不一致——文字增量是给用户"它在回应我"的即时感,而 TTS 逐词播会断断续续、非常难听。**两者的最佳粒度本来就不同。**

### 3.3 字段顺序是契约的一部分

模型输出的 JSON **必须以 `reply` 开头**（§〇 的原因）。这条要同时写在：

- prompt 的 OUTPUT 段
- Edge Function 的增量提取器注释
- 本文

**三处都写是刻意的**——只写一处，下一个改 schema 的人不会知道顺序有意义,而调换字段顺序**不会报任何错**,只会让延迟悄悄退回 2.5 秒。这是最难查的那类退化。

### 3.4 ⚠️ thinking budget：比字段顺序更大的一段延迟

**Gemini 2.5 Flash 默认会先"思考"再输出，思考的 token 产生在正式回复之前。** 这意味着 §〇 那条时间轴的起点可能根本不是 0.0 秒：

```
0.0s  （在思考，一个字都没吐）
1.2s  {"reply":"So you were …          ← §〇 的时间轴其实从这里才开始
1.4s  …reply 完整
```

**如果不管它，我们把 reply 从 1.9 秒省到 0.2 秒的全部优化，会被前面的思考时间吃掉。** 而且这个坑的症状只是"感觉慢"，从 prompt 和流式代码里怎么查都查不出来。

#### ⚠️ 本轮不拍板，先随便给个初始值，跑起来再调

**这个参数没有必要现在定死**——它是一行配置，改起来零成本，而在没有真实延迟数据之前拍的任何值都是猜的。**本节的目的是把坑记清楚，不是给答案。**

初始值就按下表设，**跑起来后按实测调，不需要回来改文档**：

| mode | 初始值 | 备注 |
|---|---|---|
| `OPENING` / `TURN` | 最低 / 关 | 延迟最敏感的两个 |
| `FALLBACK` | 留一点 | 翻译任务，用户面对弹框本来就预期有一拍 |
| `WRAP` | 无所谓 | 异步，不挡任何东西 |

> **要记住的只有一件事：如果对话"感觉慢"，先来看这个参数，别去 debug 流式代码。**

#### 关掉思考的代价，以及它为什么可以接受

同一次调用既要产出 `reply`（要快），又要判语法对错（本来受益于思考）。关掉思考，**正确性判定会变弱——它会少报、报得保守**。

**而这恰好和我们已定的偏向一致**：prompt 里写的是"只报有把握的、最多 2 条、误报远比漏报糟"（`Prompt 文档 §7`）。**一个不那么深思熟虑的模型，天然就更少报。** 我们要的本来就是这个方向。

#### 如果正确性判定弱到不可用，逃生路径是现成的

**把一次调用拆成两次。但切口不能按"用户看不看得见"来划——那是错的。**

看不见的字段里，有一半必须实时。正确的切口是**"影响下一轮" vs "只影响总结卡"**：

```
快调用（每轮、流式、无思考）
  → reply + current_topic + suggestions
    这三个都影响下一轮：推荐要按当前话题重排

慢调用（异步、可开思考、可攒几轮一起做）
  → used_entries + new_expressions + correctness
    这三个唯一的消费者是账本和总结卡，而总结卡在退出时才拼
```

> **`current_topic` 是这个切口的试金石**：用户看不见它，但它必须实时——按"看得见/看不见"划，它会被错误地丢进慢的那半，于是实时推荐永远锚在上一轮的话题上，而且**不会报错，只会慢慢变得不搭**。

**这条路径的关键点是：慢调用完全没有延迟约束**——用户已经在听 AI 说话了，它慢 3 秒也没人知道。所以"开思考"甚至"换个更强的模型"的代价，在这里几乎为零。而语法判定恰好是这两半里唯一真正需要判断力的活。

> **但不要一上来就拆。** 先跑单次调用 + 关思考，拿 `Prompt 文档 §六` 的 12 条回归看实际结果。**很可能够用**，那就省下了两套集成和两套 prompt 的维护成本。

代价是成本翻倍和两次调用可能对同一句话理解不一致。**所以它是逃生路径，不是首选**——但它同时也是 §〇 方案 C（字段顺序）失效时的逃生路径。**两个风险共用同一个后备方案，这让后备方案更值得提前写好。**

> **⏳ 必须实测**：E1a 第 5–6 步跑通后，用同一批输入分别在"开思考 / 关思考"下各跑一遍 `Prompt 文档 §六` 的 12 条回归，比较：① 首字延迟 ② `correctness` 的报出率和准确率。**拿数据定，不要凭感觉定。**

> **顺带一条对照**：Tab1 的 `generate` 是相反的情况——分类 + 转换任务，判卡型确实需要推理，且用户本来就在等一张卡出来。**同一个模型，两个场景该给不同的 thinking 配置。** 不要因为"统一"就把两边设成一样。

## 四、两个必须做对的保护

### 4.1 幂等：`turn_id` 由客户端生成

**为什么必须有**：网络抖动 → 客户端重试 → 同一句话被记两次 → `spoken_count` 虚高 → **北极星指标失真**。这在语音场景里不是小概率，用户经常在信号不好的地方练。

**做法**：客户端每轮生成一个 UUID 随请求发送。服务端拿它当 `dialogue_turns` 的唯一键：

```sql
CONSTRAINT uq_dialogue_turns_turn_id UNIQUE (turn_id)
```

命中已存在 → **直接返回上次的结果，不调模型、不记账**。

> `client_session_id` 同理，防止用户狂点卡片建出五个 session。

### 4.2 `used_entries` 二次校验（宁可漏，绝不多）

`Prompt 文档 §7` 已经点名这是最贵的一种错。**校验放在 Edge Function，不放在 prompt**：

```
对模型返回的每个 lemma：
  能在用户本轮转写文本里找到词形匹配（含常见变形：set up / set it up / setting up）
    → 保留
  找不到
    → 丢弃，并记一条日志（用来观察模型报宽的频率）
```

**规则是不对称的**：宁可漏记几个词，绝不多记一个。多记一次 → `breakthrough` 虚假触发 → 总结卡告诉用户"你第一次说出了 X"，而他根本没说过 → **用户会认定整个产品在糊弄他**。

## 五、错误与失败

### 5.1 错误码

| HTTP | code | 什么情况 | 客户端做什么 |
|---|---|---|---|
| 401 | `unauthorized` | 无 uid | 走登录流程 |
| 403 | `session_forbidden` | session 不属于当前用户 | 回 Tab2，报通用错误 |
| 404 | `session_not_found` | session_id 无效 | 回 Tab2 |
| 410 | `session_ended` | 已结束还想继续 | 回 Tab2 |
| 429 | `rate_limited` | 模型限流 | **提示稍后重试，保留已有对话**，不清空 |
| 500 | `model_failed` | 模型调用失败/超时 | 见 §5.2 |
| 500 | `missing_config` | 环境变量缺失 | 通用错误 |

### 5.2 模型失败时，对话不能死

**这是最重要的一条容错。** 用户说了一句话，模型挂了——**绝不能让这一轮凭空消失**。

```
① 该轮的 dialogue_turns（role=user）照常落库   ← 他说的话不能丢
② 返回 500 + 一句本地兜底提示（前端固定文案，不调模型）
③ 前端保留对话流，允许重说或继续
④ 用户此时选择退出 → end 照常出总结卡（可能只有部分内容）
```

> **原则：任何失败路径都不能丢掉用户已经说出口的话。** 他好不容易开了口，产品把它弄丢了，比报个错严重得多。

### 5.3 断网

- 进页前断网 → 明确提示 + 返回按钮，**不进对话页**（进去也说不了话）。
- 对话中断网 → 保留已有对话流 + toast 提示（`需求设计` 已定：网络错用 toast，不用常驻横幅）。恢复后可继续。
- **已产生但没发出去的轮次**：本地暂存，恢复后带原 `turn_id` 重发（幂等保证不会重复记账）。

### 5.4 记账失败（异步阶段）

模型返回成功、但写数据库失败。用户无感知（他已经收到回复了），但数据丢了。

**对策**：写一条失败日志，靠 `PRD §5.3.1` 已规划的补账/对账作业捞回。**不要在用户面前报错**——他什么也做不了，报了只会制造焦虑。
