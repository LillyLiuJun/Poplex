Poplex · Library · 刀 4 字段规格 v3

每个字段的状态与展示

前提：conversationEnabled = false，对话进不去， 所有以「说过」为前提的字段在 1.0 恒为空。这份规格只用 1.0 真实存在的数据， 逐字段定义取值范围、每种状态的展示、以及不展示的条件。 凡是没在这里定义的状态，实现时不得自行发挥。

术语对齐

三个名字指同一样东西，历史遗留，这里统一。

时间档位（模板与取整规则）

下表里的 {d} 和 {w} 是变量，不是字面量。 d = 本地自然日之差（不是 24 小时之差）： 昨天 23:50 与今天 00:10 相差 20 分钟，但 d = 1。

条件文案实例为什么这样分
d = 0Added todayAdded today一周之内用户还记得具体是哪天，说「天」有意义。
d = 1Added yesterdayAdded yesterday
2 ≤ d ≤ 6Added {d} days agod=4 → Added 4 days ago
7 ≤ d ≤ 13Added last weekd=9 → Added last week 超过一周说「23 days」要用户心算。
取整规则：w = floor(d / 7)，即 d=13→w=1，d=14→w=2，d=23→w=3。
14 ≤ d ≤ 29Added {w} weeks agod=23 → Added 3 weeks ago
d ≥ 30Nothing new in a monthd=200 → Nothing new in a month 不再往上分档：两个月和五个月对用户是同一件事。
句式从「你做过什么」变成「什么都没有」，这是唯一带推动意味的一档。
last_material_at = null整行不渲染— 不写 Never added——那是把「没有这个动作」说成「你没做」。

同一套档位在 Hero 理由行复用，只换句式： d ≥ 30 → Nothing new in a month； 2 ≤ d ≤ 29 → Nothing new in {…}（同上取整）； d ≤ 1 的情况由 new_material_count 接管，见下节。

Hero 理由行：两个字段合成一句话

它是卡上唯一解释「为什么是它」的地方。 new_material_count 优先，为 0 才退到 last_material_at。

条件文案
new_material_count = 1You added something new today
new_material_count ≥ 2You added {n} new bits today
= 0，且 d 有值Nothing new in {时间档位}
= 0，且 last_material_at = nullOnly words so far

⚠️ 口径问题，必须先定：new_material_count 的「今天」是谁的今天？ 数据库是 UTC，用户在本地时区。若后端按 UTC 日切，东八区用户早上 8 点前存的东西会被算成「昨天」。

解法：RPC 增加参数 p_day_start timestamptz，由客户端传入 本地自然日 00:00 对应的 UTC 时刻，后端统计 created_at ≥ p_day_start。 这样 new_material_count 与 Hero 选取规则里的「今天」是同一个今天。

代价：get-tab2-home Edge Function 要计算并透传这个参数， RPC 签名变化。这是刀 4a 的第三项改动，不是一行 SQL 能装下的。

三个数字的口径不一样，这是设计

每条素材带一个粒度标记：word / sentence / passage。 三个上卡面的数字对它的处理各不相同，因为它们回答的是不同的问题。

数字含 word?依据它回答的问题
occurrence_count
（Cooking ×7）		 不含 v5 ②
FILTER (granularity <> 'word')		 你反复在做什么。查 7 个厨房单词不等于做了 7 次饭——含 word 这句话就是假的。
word_count
（40 words）		 含 v5 ①
不加 granularity 过滤		 你在这一类攒了多少词。词库语义，来源无关。
★ new_material_count
（3 new bits today）		 含 本次新定 你今天往这儿放新东西了没有。查词就是放了新东西—— 中午查了三个词、晚上看到「Nothing new in 2 weeks」，用户会觉得 app 眼瞎。

new_material_count 按不同素材去重： 一张照片抽出 8 个词算 1 条，不是 8 条。

时区：1.0 用 B，但把 A 的门留着

存储层已是行业标准（timestamptz，内部 UTC，按用户时区渲染）。 缺的只是「聚合到自然日」这一步该由谁切。

方案做法取舍
B · 1.0 采用 客户端算出「本地今天 0 点 = UTC 的哪一刻」，作为 p_day_start 传入 设备自己知道时区和夏令时，永远算得对；无需时区设置项
A · 将来 服务端存用户时区，自行切日 需上报与保鲜（用户出差即过期）；但服务端主动动作（推送、周报）必须有它

传时刻，不传偏移。p_day_start timestamptz 而不是 p_tz_offset int——存偏移数字的系统每年夏令时会错两次，这是本领域最经典的坑。 同理，将来 A 方案存 IANA 名（Asia/Shanghai），不存 +8。

4a 必须一并写入的兜底（今天不改变任何行为，只是把门留着不锁）：
v_day_start := COALESCE(p_day_start, date_trunc('day', now() AT TIME ZONE COALESCE(v_user_tz, 'UTC')));

迁移到 A 的成本因此是：加一列 + 填值 + 改这一行兜底，客户端零改动。 之所以这么便宜，是因为「今天」只在读取时计算、从不落盘—— 若哪天把每日统计物化成表并按 UTC 分桶，换时区就要重跑全部历史。不要那么做。
