# AI English Learning APP — 数据架构与业务流深度审计报告

> 版本：v1 · 2026-07-04
> 审计人：系统架构师 / 业务分析（Claude）
> 审计范围：Onboarding（Page0）→ Tab1（generate 链路）→ Tab2（Mine 链路），以及方案 B（图片输入）增量迭代。
> 审计基线：本报告不基于 PRD 的"设计意图"，而是基于**仓库中的真实代码与 Schema**（`materials` 迁移、`generate`/`get-materials` Edge Function、`Material.swift`/`AIResponse.swift`/`Message.swift`）。凡代码与 PRD 冲突处，以代码为准并单独标注——**这类"文档—代码漂移"本身就是最高危的技术债来源**。
> 重要前提：审计中发现，`messages` 表、`users/profiles` 表在 `supabase/migrations/` 中**没有任何 DDL 定义**（只有 `materials` 与 `analytics_events` 两张表建表脚本），但 `generate` 函数却在向 `messages` 写数据、Onboarding 依赖 `onboarding_completed_at`/`english_level` 字段。这是贯穿全报告的结构性隐患。

---

## 第一部分 · 全局数据关系与前后端交互契约映射

### 1.1 实体关系模型（ER 逻辑关系）

系统当前**真实存在**的持久化实体只有两张有 DDL 的表，另有两张"被代码引用但无 Schema"的影子实体：

```
┌─────────────────────────────┐
│  auth.users (匿名账号)       │  ← Onboarding 静默创建；PRD 依赖
│  · id (uuid)                │    onboarding_completed_at / english_level
│  · onboarding_completed_at  │  ⚠️ 无迁移文件，字段落点未知（影子实体）
│  · english_level = 'B1'     │
└──────────────┬──────────────┘
               │ 1 : N（应有，实际未连）
               │  user_id 在 materials 中【永远为 null】
               ▼
┌─────────────────────────────┐        ┌──────────────────────────────┐
│  messages（影子实体，无DDL） │  1:0..1│  materials（唯一有DDL的业务表）│
│  · role user/assistant      │────────│  · id (uuid, PK)             │
│  · input_type text/image    │source_ │  · user_id           ← null  │
│  · user_content "[photo]…"  │message_│  · source_message_id ← 从不写│
│  · card_type/card_content   │  id    │  · material_type scene/vocab │
│  · (无 image_url 列)         │(声明未写)│  · status pending/categorized│
└─────────────────────────────┘        │  · scene_category            │
                                        │  · raw_content (jsonb)       │
┌─────────────────────────────┐        │  · related_material_ids[] 预留│
│  analytics_events           │        │  · deleted_at (软删除)        │
│  · 埋点，独立链路            │        └──────────────────────────────┘
└─────────────────────────────┘
        client-only（不持久化）：TimelineEntry(UIImage 仅在内存)
```

**关键结论：三条本应存在的外键关系，实际全部断裂**——

1. `materials.user_id` ← `auth.users.id`：**代码从不写入 user_id**（`generate/index.ts:279-283` 的 INSERT body 无 user_id 字段）。
2. `materials.source_message_id` ← `messages.id`：列已声明（迁移 line 7），`saveMaterial()` **从不填充**。这意味着素材与其来源消息（图片就挂在消息里）之间**没有任何可追溯链路**。
3. `related_material_ids[]`：声明为"词汇→来源场景"的继承链依据，MVP 预留但未写入。

### 1.2 前后端职责边界划分（State Partitioning）

| 数据元素 | 归属 | 是否持久化 | 数据流向 | 备注 |
|---|---|---|---|---|
| `TimelineEntry` 消息流（含 `UIImage`） | **前端视图状态** | ❌ 仅内存 | Client only | **App 重启即丢失**；图片从未落盘 |
| 输入框图片/文字草稿、缩略图 | **前端视图状态** | ❌ | Client only | 56×56 预览 + 1600px 压缩版两条流水线 |
| `MineViewModel.scenes / selectedCategory / isLoading` | **前端视图状态** | ❌ | Server→Client 渲染 | 30s stale 节流 |
| `VocabBookView` 的 `@State vocabs` | **前端视图状态（孤立）** | ❌ | Server→Client | 无 ViewModel，状态孤岛（见 3.2-④） |
| `mine_last_scene_count` 骨架屏数量 | 前端 UserDefaults | ✅(本地) | Client only | 仅体验优化 |
| `materials`（scene/vocab 正文、分类、状态） | **后端持久化实体** | ✅ | Client→(Edge)→DB→(Edge)→Client | 唯一稳固的业务表 |
| `messages`（对话历史） | **后端持久化实体** | ⚠️ 写入无表 | Client→Edge→DB(?) | **无 DDL，写入结果未知** |
| `english_level / onboarding_completed_at` | **后端持久化实体** | ⚠️ 无表 | Client→? | **无 DDL** |
| 图片二进制 | **无归属** | ❌ | Client→Gemini(base64)→丢弃 | **既不在前端持久化，也未上传 Storage** |

**数据流向核心特征**：所有读写都经 Edge Function 中转，且**读写两端都用 Service Role Key**（`get-materials:3` 明确注释"绕开 anon key 权限问题"）。这直接推翻了 `Tab2_数据逻辑梳理_v1.md` 中"客户端使用 anonKey，由 RLS 保护"的表述——**实际实现绕过了 RLS**（见 3.1-①）。

### 1.3 生命周期数据流转机制

```
Onboarding: 静默建匿名号 → english_level='B1'(默认) → Screen4 拍照/选预设卡
            → Screen5 调 generate → 首条 material 落库 → 标记 onboarding_completed_at
                                                            └─(写向无 DDL 的实体)
Tab1:  send(text?, image?) → POST generate
        └ Gemini 生成卡片 → Promise.all[ 写 messages×2, saveMaterial() ]
           saveMaterial: INSERT(status=pending/categorized) →〔scene〕二次 Gemini 分类 → PATCH(categorized)
Tab2:  手动切 Tab（异步，不自动跳转）→ onAppear → loadScenesIfStale(>30s)
        → GET get-materials(全量 scene) + GET get-vocabs(仅取 count)
```

## 第二部分 · 图片功能（方案 B）级联影响评估

### 2.1 图片数据传递链路（实测）

```
[Tab1 输入] UIImage → 压缩 1600px/JPEG0.75 → base64
   ↓ POST generate { text?, image_base64, mime_type }
[Edge] 三分支拼 Gemini prompt（纯图→s4/chinese_original=null/ai_scene_guess；图文→按文字分类）
   ↓ 生成后
   ├─ messages: input_type = image_base64 ? "image" : "text"，user_content = "[photo] …"
   └─ saveMaterial → buildRawContent → materials.raw_content
        ⛔ base64 图片在此处被【丢弃】，从未上传 Supabase Storage
   ↓
[Tab2] get-materials 读 raw_content ——【没有任何图片 URL 可读】
```

**结论：图片是一条"只进不出"的死链**。它只作为 Gemini 的一次性上下文存在，既没进前端持久层，也没进后端 Storage。方案 B 设计文档第七节提议给 `raw_content` 加 `source_image_url`——但**当前没有上传管线、没有 Storage bucket、`source_message_id` 也不写**，该字段无源可填。Tab2 想显示 52×52 缩略图与详情页大图，在数据层完全无法实现。

### 2.2 影响矩阵表（Impact Matrix）

| 受影响对象 | 现状字段/结构 | 图片引入后的影响 | 耦合度 | 风险等级 |
|---|---|---|---|---|
| `materials.raw_content`（SceneRawContent） | `native_english / chinese_original / key_phrases` | 需加 `source_image_url`，但**无上传源**；纯图片时 `chinese_original` 被 `String(null ?? '')` 压成**空字符串**，`ai_scene_guess` **未进结构直接丢失** | 高 | 🔴 高 |
| `materials.source_message_id` | 已声明未写 | 图片挂在 message 上，若不建立此链则素材永远找不回它的图 | 高 | 🔴 高 |
| `messages` 表 | 无 DDL；写 `input_type`/`user_content` | 需 `image_url` 列；`input_type` 对"图文混合"硬编码为 `"image"`（`:391`），丢失图文区分——**方案 B 5.1 节 Plan A/B 之争在代码里已被单方面"选择"且选错** | 高 | 🔴 高 |
| Tab2 纯图片素材呈现 | 无"纯图片"状态位 | 落库后与普通 s4 无法区分（`chinese_original=''`），违背 Tab2"AI 生成 ≠ 用户能说出口"的核心视觉分界 | 高 | 🔴 高 |
| `AIService.generate` | 双方法 text/image | 合并为 `generate(text:?, image:?)` | 中 | 🟡 中 |
| `TimelineEntry.userBubble` | 已支持 `image: UIImage?` | 结构就绪，但重启丢失 | 中 | 🟡 中 |
| Vocab 链路（s1/s3） | 无图片 | 明确不带图，保持"词汇本不假装有场景" | 低 | 🟢 低 |

### 2.3 冗余 / 异步问题

- **无冗余存储**（问题在另一极端：**零存储**）。图片没有任何副本落盘。
- **异步同步延迟**：scene 素材走"INSERT(pending) → 二次 Gemini 分类 → PATCH(categorized)"两阶段写入，叠加 Tab2 的 30s stale 节流。用户在 Tab1 发完图立刻切 Tab2，很可能看到**尚未分类（挂"全部"）或分类为"其他"**的中间态。

## 第三部分 · 逻辑完备性与数据一致性审计

### 🔴 高危（High）

**① 多用户数据隔离完全缺失（安全 + 正确性双重故障）**

- **现象**：`saveMaterial()` 写入时不带 `user_id`（恒为 null）；`get-materials` 用 Service Role Key 读取，**且完全不按 user 过滤**（`get-materials/index.ts:30-34` 只筛 `material_type` 与 `deleted_at`）。
- **风险**：所有用户共享一个全局素材池——**用户 A 会在自己 Tab2 里看到用户 B 的全部素材**。这是隐私泄露级缺陷，同时使 `english_level`、个性化等一切"从你自己生活取材"的产品承诺失效。文档宣称的"RLS 保护"与实现完全相反。
- **重构方案**：(a) `generate` 从 JWT 解析 `auth.uid()` 并写入 `materials.user_id`；(b) 所有 get-* 函数强制 `user_id=eq.<uid>` 过滤；(c) 补 RLS 策略作为纵深防御；(d) 回填/清洗已有 null user_id 脏数据。

**② `messages` 与用户档案表无 Schema 定义（幽灵写入）**

- **现象**：`generate` 向 `messages` 写 6 个字段、Onboarding 依赖 `onboarding_completed_at`/`english_level`，但 `migrations/` 里**没有这两张表的建表脚本**。
- **风险**：若线上表是手工建的，则 Schema 无版本管理、无法复现环境、字段类型无契约；方案 B 要给 `messages` 加 `image_url` 时无迁移可改。这是"数据契约优先"原则的根本性违背。
- **重构方案**：补 `messages` 与 `profiles`（或 `auth.users` metadata）迁移文件，纳入版本管理，字段类型/约束/索引一次定清。

**③ 纯图片素材落库即"失真"，破坏 Tab2 核心分界**

- **现象**：`buildRawContent` 的 s4 分支 `chinese_original: String(content.chinese_original ?? '')`——纯图片时 AI 返回 `null`，被压成 `''`；`ai_scene_guess` 根本不在 `SceneRawContent` 结构里，**直接丢弃**。
- **风险**：Tab2 拿到一条 `chinese_original` 为空、无任何"这是纯图片/AI 猜测"标记的 scene，无法按 PRD 施加"未说出口前模糊/特殊态"处理。且首次体验（Onboarding Screen4 纯图片路径）**第一条素材就命中此 bug**。
- **重构方案**：`materials` 增 `origin_type`（`user_text`/`ai_image_guess`）或让 `raw_content` 保留 `ai_scene_guess` 且 `chinese_original` 允许真 null；Tab2 据此渲染差异化状态。

### 🟡 中危（Medium）

**④ `native_english` / `chinese_original` 语义在三层间漂移**

- **现象**：命名从 AI 层 `native_translation`/`native_polish` → 落库 `native_english` → 前端 `nativeEnglish` 三度改名；更严重的是 s2 分支把 `chinese_original` 填成 AI 的 `chinese_translation`（`generate:200`），即"用户原文"字段里装的其实是"AI 译文"。`Material.swift:50` 注释亦坦承此偏差。
- **风险**：语义污染使 Tab2"用户原话 vs AI 表达"的边界在 s2 类素材上失真；跨层改名增加维护脑力负担。
- **建议**：统一术语表（一个概念一个名字，贯穿 DB/Edge/Swift）；为 s2 区分"用户英文原句"与"AI 中译"两个独立字段，不要复用 `chinese_original`。

**⑤ 乐观删除 fire-and-forget，无失败补偿**

- **现象**：`delete-material` 调用不等结果（Tab2 逻辑文档第五节）；前端已移除 UI。
- **风险**：网络失败时后端未删，下次 `loadScenes` 素材"复活"，用户困惑。
- **建议**：失败回滚 UI 或加重试队列；至少对删除结果做静默校验。

**⑥ VocabBookView 状态孤岛 + `get-vocabs` 双请求**

- **现象**：vocab 的 loading/error/list 全在 View 的 `@State`，与 MineViewModel 脱节；`get-vocabs` 被 MineViewModel（取 count）和 VocabBookView（取全量）各调一次。
- **风险**：删词后徽章不实时更新；同一数据两次网络往返。
- **建议**：vocab 状态上移进 MineViewModel 统一管理。

**⑦ 删除逻辑与 ISO8601 解码器代码重复**

- **现象**：MineViewModel 与 VocabBookView 各拷贝一份删除+Undo 计时器、各写一份日期解码器。
- **建议**：抽公共 service / `JSONDecoder` 工厂扩展，消除"改一处漏一处"。

### 🟢 低危（Low）

**⑧ `related_material_ids` 长期空转**：预留字段未用，词汇→来源场景继承链无数据支撑，随迭代易被遗忘。建议要么排期启用，要么在文档明确标注"MVP 不写入"。

**⑨ 埋点/主流程静默失败**：`saveMaterial`/`insertMessage` 失败仅 `console.error`，主响应照常返回。用户侧无感，但会积累"卡片显示了却没进素材库"的隐性数据丢失。建议加服务端可观测告警。

## 附 · 优先级修复路线图（建议排序）

| 序 | 修复项 | 对应发现 | 阻塞对象 |
|---|---|---|---|
| 1 | 写入并按 `user_id` 过滤 + 补 RLS | ① | **上线前必须**，涉隐私 |
| 2 | 补 `messages`/`profiles` 迁移文件 | ② | 方案 B 图片落库的前置 |
| 3 | 建 Storage 上传管线 + 回写 `source_image_url` + `source_message_id` | 2.1 / ② | 方案 B 切片 1 真正可用 |
| 4 | 纯图片素材 `origin_type` + 保留 `ai_scene_guess` | ③ | Tab2 呈现正确性 |
| 5 | 统一术语 + s2 字段拆分 | ④ | 数据契约健康度 |
| 6 | 删除逻辑/解码器抽公共层、vocab 状态上移 | ⑤⑥⑦ | 可迭代中并行 |

**一句话总结**：产品的**设计文档质量很高**，但**代码实现落后于设计、且已有多处"沉默的契约违背"**——尤其 `user_id` 隔离缺失（①）和图片零持久化（2.1），二者叠加会让方案 B"把图片带进 Tab2"的目标在当前数据地基上**根本无法达成**。建议按上表 1→3 先补齐数据地基，再谈方案 B 的横向铺开。
