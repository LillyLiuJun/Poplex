## 〇、为什么这三块是一条链

一句话：用户输入一段东西 → **① 生成**（变成卡片 / 学习内容）→ **② 提取与判断**（变成账本里的结构化词条）→ **③ 记录与总结**（记下学习历程、归纳呈现）。三块首尾相接，缺一段就断。本文档第一节展开①（输入生成），第二、三节列②③的开放问题。

## 一、输入生成（Tab1）

**重新定义（前提）**：Tab1 = **翻译 / 生成功能**——把用户各种输入形式变成**可用的目标语言素材**。只做内容生成、不做答疑（chat 删除，那类输入按翻译处理）；且从此要关注**内容长短**（影响卡片与排版）。

下面按 **① Prompt → ② 卡片 → ③ 错误状态 → ④ UI 排版** 线性走，每块 = 现状 + 待修改（+ 代码落点）。

### 1.1 Prompt

**现状 · SYSTEM_PROMPT 骨架**（10 块，供统一优化）：
1. 角色 persona（English Buddy）
2. SAFETY RULES（不安全 / 无意义 → error）
3. CARD SELECTION（选 1 类卡；现写"优先 s1–s4，chat 最后手段"）
4. GRANULARITY RULE（有谓语 → 句级，无谓语 → 词级）
5. LANGUAGE INTENT RULE（按意图判中英）
6. SELF-REFERENCE EXTRACTION（抽 `extracted_concept`）
7. OUTPUT SCHEMAS（逐卡字段，含 `scene_trigger`）
8. TONE
9. MULTI-TURN CONTEXT（带 1 轮）
10. 输出 JSON 形状

> **范围（已定）**：本提示词**只管短内容**。长内容不在这里加分支，走独立流程（§1.2.2）；图片（至少纯图）也拆成独立提示词（见下）。

**待修改**：
- **删 chat**（动第 3 块）：CARD SELECTION 去掉 chat 分支 → 一律归入 s1–s4；chat 类输入（问英语学习本身，如 would vs could）**按翻译处理**、无特殊 Q&A（error 仍兜底）。*caveat：纯 meta 问题翻译输出可能略怪，接受的取舍。*
- **追问分化**（动第 7 块 `scene_trigger`）：从统一"warm follow-up"改成分卡型——s2 / s4 追问**场景细节**；s1 / s3 追问**"什么场景遇到 / 会用到"**（各卡交互详见 1.2）。为什么这么分：场景卡本有情境、追问细节是顺势加深；词卡孤立、追问"什么场景"补上处境感，也呼应账本"词 → 场景"继承。
- **图片拆成独立提示词（为稳定性，提案 = minimal）**：纯图（photo → 总是 s4 + `ai_scene_guess`）拆到一个独立的小提示词；**文字-only + 图文混合仍留本（文字）提示词**（图片当上下文）。理由：纯图是确定性任务、也是最"污染"共享提示词的部分，拿掉它文字路更清爽更稳；图文混合本就文字主导，留文字路即可。
  - **影响**：下游数据契约不变（仍出 s1–s4 卡，记账 / Tab2 不动）；Edge 函数加一步"纯图 → 图片提示词"的路由。多轮里图片重放逻辑保留。
  - **待你拍**：**minimal**（只拆纯图，重复最少，我推荐）vs **full**（任何带图都拆、文字路零图片痕迹，但图文混合的分类逻辑要在图片提示词里再写一份）。
- **代码落点**：后端 `supabase/functions/generate/index.ts`——SYSTEM_PROMPT（删 chat 第 3 块、追问第 7 块）；图片拆分涉及 `generate` 里构造 user parts 的三分支（纯图 / 图文 / 纯文）+ 新增一个独立 image 提示词常量 + 路由。前端不动。

### 1.2 卡片（每种卡片的内容与交互）

Tab1 产物是卡片。按 短内容 / 长内容 / 语音 三类，逐类说清**内容（展示什么）+ 交互（用户能做什么）**。

#### 1.2.1 短内容卡 s1–s4（现状主力）

一个原子输入 → 一张卡，4 类（词 / 句 × 中 / 英 的 2×2）：

| 卡（当前标签） | 触发 | 内容（字段） | 交互 |
|---|---|---|---|
| s1 Word | 英文词 / 查词 | 词 + 音标 + 词性 + 释义 + 例句 | 追问 |
| s2 Polish | 英文句 | 中译 + 语法点? + 地道版? + 核心词组? | 追问 |
| s3 Translate | 中文词 → 英 | 中概念 → 英译 + 音标 + 词性 + 例句 | 追问 |
| s4 Moment | 中文句 / 纯图 | 中原文? + AI 场景猜测? + 地道英文 + 核心词组? | 追问 |

（`?` = 可空字段；当前交互只有"追问 `scene_trigger`"一种。输入形态现为**文字 + 图片**，语音见 1.2.3。**4 类对短的原子输入是完备且干净的，够；删 chat 不需补短卡**。）

**待修改**：
- **删 chat 卡**（前后端 + 数据）——代码落点：
  - `Models/AIResponse.swift`：去 `.chat`（decode ~L24 / enum ~L36 / `ChatContent` ~L106–115 / cardTypeName ~L136 / contextRepresentation ~L178–181 / primaryEnglish ~L194 / 注释 ~L199）。
  - `Models/MessageRecord.swift:~41`：去 chat decode。
  - `Today/Components/MessageRow.swift:~112`：去 `.chat → ChatBubbleView` 路由。
  - 删组件 `Today/Components/ChatBubbleView.swift`。
  - **实现注意**：历史 chat 消息 decoder 别删崩（dev 数据可直接清，或降级成普通文本）。
- **追问分化**（交互层）：提示词侧在 1.1；前端字段不变、不用改。
- **长度自适应**：短卡内容长短不一（尤其 s2 多可空字段 → 大块空白），布局要自适应 / 卡片展开（详见 1.4）。

#### 1.2.2 长内容卡 / 报告（提前规划，短期不上线）

**长 / 短分界（已确认）**：不是字数，是**"一个学习单元" vs "一个待开采的素材源"**——短 = 原子表达 → 一张卡；长 = 一大段（粘贴 / 邮件 / 文件 / connector）→ 含很多可学点，得开采出多个单元。**长内容是独立生成流程（独立提示词 / 函数），不复用短内容提示词（§1.1）。**

**处理流程（你给的骨架）**：
1. **先判语言** → 全母语 / 全目标语言 / 中英混合，三种各自产物**待细化**。
2. **生成"报告"**：从这段提取 场景 / 短语 / 句式（等），拆成一组"可学单元"。
3. **交互 · 勾选剔除**：用户勾掉不想要的，只留想学的进账本（"素材是用户的"）。

**待细化**：三种语言情况各自产物；报告呈现形态（列表 / 可勾选卡片组）；connector / 文件怎么进来怎么切；提取粒度（场景 / 短语 / 句式之外是否含单词 / 语法点）。

#### 1.2.3 语音（提前写入，规划占位）

**现状**：语音输入、语音对话都**未上线**；当前输入只有文字 + 图片。
**提前规划（占位，待你给方向）**：语音作为未来输入形式，进 Tab1 后怎么处理还没定——是"转写成文字 → 走同一套 s1–s4 翻译流程"，还是有独立的语音卡 / 交互？*这块我们之前没展开，先占位。*

### 1.3 错误状态（现状 + 修改）

**现状 · 两类错、两条路**：
- **内容错**（AI 判不安全 / 无意义）→ error 卡 → `ErrorBanner` = 页面居中一句灰字（不成卡、割裂）。
- **技术 / 网络错**（请求失败 / 断网）→ `sendFailed`（右对齐"Couldn't send. Tap to retry."重试）；另有常驻 `OfflineBanner`（"You're offline"横幅，Tab1 / Tab2 都挂）。

**修改（决策）**：
1. **删常驻 `OfflineBanner`**（Tab1 + Tab2 都删），**网络错改 toast**（一闪即逝）。
2. `sendFailed`（每条可重试）**保留**——它是"这条没发出去"的补偿，和离线横幅是两回事。
3. 内容错那句灰字怎么改 → UI 阶段（1.4）。
- **代码落点**：删 `Components/OfflineBanner.swift`；`Today/TodayView.swift`（去 `OfflineBanner()` ~L27，`NetworkMonitor` ~L9 留作 toast 触发）；`Mine/MineView.swift`（去 ~L117–118 + animation ~L83）；`Mine/MineViewModel.swift`（去 `isOffline` ~L8/70/74）；`Mine/VocabBookView.swift`（去 ~L8/61–62/66/129/131）；新增 toast（复用 `Mine/Components/UndoToast.swift` 模式）；`Services/NetworkMonitor.swift` 保留。小待定（UI 阶段）：toast 触发范围与样式。

| 字段 | s1 | s2 | s3 | s4 | 不一致点 |

## 二、批次一 · 内容的判断与提取规则（输入 → 结构化词条）

这一批是**输入侧**：把用户说的话 / 输入，变成账本里的结构化、去重、分好类的词条。发生在记账 Stage 3 / dialogue 函数里。开放问题：

- **抽取规则**：从一段话里抽出哪些单元（词 / 词组 / 搭配 / 俚语 / 习语 / 句型）。
- **句型识别**：怎么认出 "Too... to..."、"It takes sb. some time to do sth." 这类骨架。（这批里最难。）
- **判层**：framework（框架词） vs scene（场景词）怎么判（词表 + 跨情境扩散）。
- **规范化去重 + 停用词过滤**：什么进账本、什么不进（lemma 归一、功能词剔除）。
- **义项标注**：为将来一词多义预留（MVP 不分义，字段已留）。
- **已知缺口识别**：母语兜底那句"想说但不会"的，怎么识别并标记。

> 主 PRD 已给的参考方案（词表 + 扩散、抽词 AI 顺带标注等）在 §5；这里列的是仍要敲定的实现逻辑。

## 三、批次二 · 总结与记录（结构化 → 记录与呈现）

这一批是**输出 / 反思侧**：把对话里发生的事记下来，并归纳呈现给用户。发生在 learning_events + 成长页。开放问题：

- **记录逻辑**：对话中怎么判"进步 / 待提高 / 语法错"（learning_events 怎么生成）、"进步翻转"怎么触发。
- **spoken_count 怎么记**：已定原则——记用户**实际说出来**的那句，不判达标（细节实现待定）。
- **呈现的生成**：即时总结卡 + 周期侧写怎么**从数据生成内容**（读账本 / 事件 → 出人话）。
- **呈现的口气**：非评价、"有才出现"、进步正向 / 待提高用邀请式——怎么在生成时把控。
- **§6.9 / §7 凝练**：把"记录"（§6，产生数据）和"呈现"（§7，展示数据）的边界划清，消除即时总结卡与周期侧写的重叠。
