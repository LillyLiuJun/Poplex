## 〇、一句话读懂这份文档

**Tab2 的意义是让用户练习和成长。要练习，先得有一份"练什么"的清单——而现在的代码里，这份清单不存在。**

打个比方：现在的 App 像一个**只会往盒子里扔纸条的机器**。用户每输入一次，它生成一张卡片、往 `materials` 盒子里塞一张纸条。盒子里纸条越来越多，但机器**从来没有统计过"set up 这个词你其实已经用过 7 次了、而且一次都没说出口"**——因为每张纸条是独立的，词埋在纸条内部的文字里，没有被单独拎出来数过。

没有这份清单，"练习"就无从谈起：你不知道该练哪个、不知道哪个已经会了、不知道自己在进步。

所以这份文档的核心，不是加三个花哨功能，而是先补上这个**"词汇账本"（lexicon）数据地基**，让它成为练习清单，再在上面长出练习和成长。

**文档结构：**
1. 先盘点**已经建好了什么**（第二节），避免重复造轮子。
2. 说清**为什么现在这个地基撑不起练习**（第三节）——整份文档的转折点。
3. 给出**架构总图**（第四节）：练什么 / 怎么练 / 练得怎样。
4. 逐层展开（第五、六、七节），第六节按对话时序组织。
5. 处理知识产权（第八节）。
6. 落到**代码整合点**（第九节）、数据模型（第十节）、埋点（第十一节）、待确认（第十二节）、开发计划（第十三节）、变更对照（第十四节）。

## 一、这份文档要解决的问题

原始 agent 规划（《语言学习Agent规划.md》）写了四段：内容来源、内容整理、AI 对话、用户成长。它是一份**思路草稿**——每段都点出了正确方向，但都停在"要做这个"，没有回答"数据怎么存、和现有代码怎么接、MVP 先做哪一刀"。

同时，仓库里已有一套**跑起来的代码**：Tab1 能把输入变成卡片并落库，Tab2 能展示场景卡和词汇本。

**这份文档做的事，就是把"草稿的方向"和"代码的现实"对齐**：保留草稿里对的判断，补上它没说的数据结构，改掉代码里挡路的地方，最后给出一条能一片一片开发出来的路径。

**三个必须记住的代码事实 —— 以及各自该怎么解**

#### (1) 词在系统里没有独立身份

一个"词"目前有两种存在方式：要么是一整行 `vocabulary` 素材（s1/s3 查的词），要么是**埋在某行 scene 素材 `raw_content.key_phrases` 里的一个 JSON 片段**（s2/s4 场景里高亮的词组）。**两种方式都不支持"把同一个词跨内容聚合起来数一遍"**——这正是第三节要解决的根本问题。

**未来输入来源还会变，账本必须和来源解耦。** 已知的变化：加长内容（粘贴 / 邮件 / 文件 / connector）、加语音、**删掉 chat**。如果记账逻辑写成"读 s1/s3 的主词 + 读 s2/s4 的 key_phrases"，每加一种来源就要改一次记账层。

**解法：在生成层和记账层之间定一个稳定的中间契约。** 不管输入从哪来、走哪个 prompt，生成层都产出同一份东西，记账层只吃这份东西：

```
输入来源（短文本 / 图文 / 纯图 / 长文本 / 文件 / 语音 …）
        ↓  各自的 prompt 与生成流程（可以完全不同）
    生成产物（一张卡 / 一份可勾选的报告）
        ↓  统一契约（无论来源，形状一样）
   { 目标语言原文, 语境元数据(情境/来源id), 输入语言, 可学单元[] }
        ↓
    记账层（抽词规范化 → 打标 → 入账）
```

- 加任何新来源，只需要让它**产出这份契约**，记账层零改动。
- 长内容天然是"一次输入 → 多个可学单元"，契约里 `可学单元[]` 是数组，**本来就支持**；长内容的"用户勾选剔除"发生在入账之前，被剔掉的不进契约。
- **删 chat 对账本零影响**：`buildRawContent` 的 default 分支本来就返回 `null`，chat 卡从来没进过 `materials`。

#### (2) 当前 prompt 只产出 1 个 key_phrase —— 这是现状，不是结构限制

**先澄清一个容易混淆的点**：`raw_content.key_phrases` 是 jsonb 数组，**数据库层面不限数量**。受限的是当前的**产出**：

- `SYSTEM_PROMPT` 里 s2/s4 的输出 schema 写的是 **`key_phrase`（单数，object 或 null）**——只让 AI 挑"最地道的那一个"。
- `buildRawContent` 落库时写 `key_phrases: kp ? [kp] : []`——数组里最多一个元素，也可能是空数组。

**所以"一条场景素材最多贡献 1 个词"是今天的事实，不是必须接受的约束。**

**正确的方向：可学单元的数量应当随输入形态而定，不在 prompt 里写死一个。** 短文本一句话可能只有 1–2 个可学点，长文本一段可能有 10 个——数量由输入体量决定才合理。这与 5.1.1"有多少抽多少"是同一件事的两端。

> **这条直接改变了记账的实现路径**：如果主 prompt 按输入形态输出**可学单元数组**，卡片展示取其中主推的 1–2 个、账本吃全部，那就**不需要另跑一次抽词**——零额外 AI 调用。见 9.2 与 §12 问题 3。

#### (3) 两处字段失真 —— 问题在落库映射层，不在 prompt 层

| 失真 | 现象 | 根因在哪 |
|---|---|---|
| s2 的 `chinese_original` 装的是 AI 中译 | `buildRawContent` 填的是 `content.chinese_translation`，不是用户原文 | **落库映射**。prompt 输出的字段名叫 `chinese_translation`，**AI 没错**——错在被填进了名叫"用户原文"的槽位 |
| 纯图素材上下文丢失 | s4 分支 `String(content.chinese_original ?? '')` 把 `null` 压成**空字符串**；`ai_scene_guess` **直接丢弃** | **落库映射**。prompt **确实输出了** `ai_scene_guess`，但 `SceneRawContent` 结构里没有这个字段，写库那一刻就没了 |

**⚠️ 所以：只拆 prompt 修不好这两处。** 拆出独立的图片 prompt 之后，AI 照样输出 `ai_scene_guess`，落库结构不改照样丢。

**拆 prompt 的方向是对的，但必须往前走一步：拆的是"契约"，不只是"提示词"。**

现在的问题正是——3 种输入形态（纯文 / 图文 / 纯图）× 4 种卡片类型，全部挤进 `SceneRawContent` / `VocabRawContent` **两个**结构，压缩过程中就丢信息了。所以每种输入形态要有：**自己的 prompt + 自己的落库结构**。具体到这两处：

- s2 需要一个**独立的**"用户英文原句"字段，不复用 `chinese_original`。
- 纯图需要 `ai_scene_guess` 真正落进结构，且 `chinese_original` 允许真 `null`（区分"用户没写"和"用户写了空"）。

> 这件事的完整设计归《输入到成长_链路现状与待敲定》§1.1（prompt 拆分）——本文档只标明：**prompt 拆分必须连带落库结构一起拆，否则失真不会消失**。而引导页的纯图路径是新用户的第一条素材，第一条就命中这个 bug。

## 三、核心洞察：为什么现在的地基撑不起练习

这一节是整份文档的转折点。请慢读。

### 3.1 "练习和成长"的每一个动作，都要求"能按词聚合"

把 Tab2 的职责逐条翻译成"它需要什么数据能力"：

| Tab2 要做的 | 翻译成数据能力 | 现在能做到吗 |
|---|---|---|
| 告诉用户"该练哪个" | 每个词要有一个状态（练过没有）和一个层级标签 | ❌ 词没有独立身份，无处挂状态 |
| 区分常见词汇（框架）和专业词汇（场景） | 能全局判定并存下来 | ❌ 同上 |
| 展示"这个表达你用过几次" | 要能查"这个词用户一共用了几次" | ❌ 词分散在 N 行素材的 JSON 里，数不出来 |
| 分析用户的表达习惯 | 要能对用户所有词做排序统计 | ❌ 同上 |
| "还有哪些同义表达" | 要能定位一个词、挂上它的同义词 | ❌ 词没有独立身份 |
| 记录"之前不会/错误、现在正确" | 要能对同一个词记录多次使用、每次对错 | ❌ 素材是一次性快照 |
| 对话里实时推荐你的高频可用词 | 要能实时查用户词库里的高频词 | ❌ 没有词库 |

**七条，七个 ❌，卡在同一个点：系统里没有"词"这个独立、可聚合、可累计的对象。**

### 3.2 根因：词汇是"一次性快照"，不是"可累计的账本"

现在的模式是：用户每输入一次 → 生成一张卡 → 存一行素材。这行素材是那一刻的**快照**。同一个 "set up"，用户在"帮妈妈弄手机"的场景里用过一次（埋在 scene A 的 key_phrases）、在"配置新电脑"的场景里又用过一次（埋在 scene B 的 key_phrases），系统里就是**两个毫不相干的 JSON 片段**。

要回答"set up 你用过几次"，得把用户所有 scene 素材拉出来、把每行的 `key_phrases` 解开、逐个字符串比对——既慢又不准（set up / sets up / setting up 算不算一个？），而且**同义扩展、对错记录这些根本无从谈起**。

### 3.3 结论：先补一层"词汇账本"（lexicon），练习才立得住

引入一个**规范化的词汇层**，把"词"从素材里拎出来，变成有独立身份、能累计、能挂状态的对象。它不替代 `materials`（场景素材仍是场景素材），而是**在旁边并行长出一份"用户个人词库"**。

有了这一层，Tab2 的三件事才成立：

- **练什么** = 账本就是练习清单（第五节：怎么正确地记账）。
- **怎么练** = 对话页一边陪练一边往账本记新账、并读账本做实时推荐（第六节）。
- **练得怎样** = 把账本和用户的实际输出对比、找差距（第七节）。

三者是**同一个账本的写入端和读取端**，这就是草稿里"三者耦合"的本质。

## 四、整体架构

> **v2 重写**：v1 把整套东西描述成"三个并列的承载面（Tab1 / 对话 / 成长）"。这个框架被产品负责人纠正——正确的划分是**功能阶段**：**Tab1 的意义是输入生成内容，Tab2 的意义是让用户练习和成长**。对话页不是第三个并列的面，**它是 Tab2 的练习执行页**。

```
   Tab1 · 输入生成（本轮不动）              Tab2 · 练习与成长（本轮范围）
     用户说一段生活                    ┌────────────────────────────────┐
     AI 生成学习卡片          ────▶    │ 练什么   词条账本 = 练习清单     │
     素材落库 + 记账                    │ 怎么练   对话页（练习执行页）     │
                                       │ 练得怎样 成长层（练习结果）       │
                                       └────────────────────────────────┘
            │                                      │
            │        两个入口都往同一个账本记账        │
            ▼                                      ▼
   ╔══════════════════════════════════════════════════════════╗
   ║  词汇账本 lexicon                                          ║
   ║   lexicon_entries      去重后的词条（练什么）               ║
   ║     · tier 框架词/场景词  · total_count 碰过几次            ║
   ║     · spoken_count 说出来过几次 ← 练习状态的来源            ║
   ║   lexicon_occurrences  每次使用的流水（练习证据，只增不改）   ║
   ║   learning_events      弱点 / 错误 / 进步（练习节点）        ║
   ╚══════════════════════════════════════════════════════════╝
```

**读这张图只需记住四件事：**

1. **账本是中心，而且它就是 Tab2 的主视图。** 上面两个入口只管往里写，成长层往外读。
2. **三张表分工明确**：`lexicon_entries` 是"去重后的词"（set up 只有一行），`lexicon_occurrences` 是"每一次用到"（场景 A 一行、场景 B 一行），`learning_events` 是"有意义的学习节点"（犯错、突破）。频率 = 数 occurrences；词本身的属性 = 存在 entry；高光时刻 = 查 events。**这是标准做法：一个"字典条目"配一份"使用流水"再配一份"事件日志"。**
3. **对话页既是写入端也是读取端**——一边把对话里的新词记进账本，一边实时读账本给用户推荐。这就是三层无法拆开的根本原因。
4. **成长层不是账本的镜子，是"账本 vs 用户实际说出来的"的差集。**

> **两处边界备注：**
> 1. **Tab1 本轮不动。** 现有代码只覆盖文字 / 图片的短输入；长内容、语音、connectors 还没规划（见《输入到成长_链路现状与待敲定》）。这不影响账本设计——无论输入来自哪，记账动作是同一套；但账本要能接住新来源。
> 2. **Tab2 的"练习功能"就是对话页，不存在另一个待设计的练习模块。** `Tab2_PRD_v1` §4 写着卡片状态与练习机制"已拆分到《Tab2_卡片状态与练习机制_v1.md》"——**该文件在仓库中不存在**。本文档正式接管这个职责：**练习 = 对话页**（第六节）。

## 五、Tab2 · 练什么 —— 内容整理层 = 记账机制

**这一层的目的：从用户输入里把语言素材提取出来、打上标，好让系统能分析这个用户的语言习惯、进而定制化地提升他的表达能力。** 账本同时是练习清单——它得能回答"我该练哪个"。

整层是一条链——**提取 → 打标 → 累计与再现**。

> 术语：下文"词条"是泛化的**词汇单元**（词/短语/词伙/俚语/习语/句型，见 5.2.5）；"账本" = lexicon 三张表。

### 5.1 提取与清洗

**两个来源，一套提取动作：**
- **Tab1 输入** → 从生成的内容里抽词。
- **对话过程** → 从用户用目标语言产出的话里抽词（见第六节）。

#### 5.1.1 已定：按抽取规则"有多少抽多少"，不设条数上限

**（本轮拍板）** Tab1 卡片的视觉**不动**——卡上仍然只高亮"最地道的那 1 个"。但**账本是另一层**：记账时按抽取规则把这句话里**所有可学单元都抽出来入账**，不设固定条数。

**为什么不能照今天这样只吃 `key_phrases`**：按 2.3(2)，当前 prompt 只产出 1 个。如果账本只吃这一个，会出现：

- 账本一天最多长几行，且**几乎不重复**——AI 每次挑的是"这条里最地道的那个"，天然倾向挑新鲜的。
- 结果 `total_count` 长期是 1，**"按频率排序"和"看见你最常用的表达"这两个体验在数据上是空的**，`All` 镜头、成长层的高频榜、对话里的高频词推荐三个功能同时失效。

**两条实现路径，二选一（见 §12 问题 3）：**

| | A · 主 prompt 输出可学单元数组（**推荐**） | B · 记账时另跑一次抽词 |
|---|---|---|
| 怎么做 | 主 prompt 按输入形态输出 `可学单元[]`，数量随输入体量而定；卡片展示取主推的 1–2 个，账本吃全部 | 卡片产出不变，Stage 3 对生成的目标语言原文再调一次模型抽词 |
| AI 调用 | **零额外**（同一次调用） | 每条素材 +1 次 |
| 与 prompt 拆分的关系 | **天然一致**——本来就要按输入形态分化 prompt，顺手把输出结构一起分化 | 与 prompt 拆分无关，是独立的一步 |
| 代价 | 主 prompt 变复杂；卡片展示与账本入账的筛选标准要在同一次输出里区分（可用"主推标记"解决） | 成本翻倍；但抽词逻辑独立、可单独调优与重跑 |

> 路径 A 同时解决了 2.3(2) 指出的"数量应随输入形态而定"，与《输入到成长》§1.1 的 prompt 拆分是同一件事的两面，**建议合并成一个决策**。

#### 5.1.2 ⚠️ 头号未决问题：什么算"一个可学单元"

**既然是"有多少抽多少"，那"什么算一个可学单元"这条判断标准，就是整条链路的闸门。**

理论上 `I was in meetings all day — completely drained.` 能抽出 `be in meetings` / `all day` / `completely drained` / `drained` / `meeting` ……抽满了，账本会被稀释成一本流水单词表，`For review`（该练什么）就失去意义。

**停用词表只挡得住 the/is/of，挡不住这类"是个词但不值得学"的东西。** 这条标准必须写死，否则账本质量不可控。

> **归属**：这条标准连同抽取的完整规则，写在《输入到成长_链路现状与待敲定》§二 批次一，是那份文档的第一道题。本文档只标明它是本层的前置依赖。

#### 5.1.3 两道清洗（无论抽多少都要过）

1. **规范化（normalization）→ 去重**：入账前统一成一个 `lemma`（转小写、去首尾标点；词形还原：setting up / sets up / set up → `set up`，meetings → meeting）。MVP 用轻量规则 + 抽词那次调用顺带给原形，不追求语言学完美。**目的：同一个东西在账本里只有一行，频率才数得准。**
2. **过滤（停用词）**：纯功能词（the, a, is, of, 的, 了）**不入账**——它们不是学习目标，入账只会稀释一切榜单。
   - *为什么过滤是生死线：* 不过滤的话，"高频词 Top 10"全是 the/is/to，习惯分析直接作废。

### 5.2 打标：决定"分析什么、何时/何地再现"

每个维度存在的唯一理由，都是"它能支撑对用户语言习惯的分析、或决定这个词该在什么场景/时机再现"。

#### 5.2.1 分层：框架词 / 场景词 / 固定句型

依据是这个语言模型假设：

> 人的表达 ≈ **基础高频词（框架，尤其是动词）** + **场景词** + **固定句型**。
> 不会表达时，卡点有三种：不知道用什么**动词**（框架缺口）、不知道用什么**场景词**（场景缺口）、不知道用什么**句型**把意思架起来（句型缺口）。
>
> *假设评估：* **基本成立**——高频核心词覆盖大部分用量、动词是二语学习者最尖的卡点，都有语言学依据。补充：框架侧不止动词，还含搭配 / 介词 / 轻动词；"词都会但不知道怎么搭"归入词伙（collocation）；"固定句型"作为第三支，用 `entry_kind='pattern'` 承载。

**分层有两个作用（不是"框架词少推、场景词多推"的展示开关）：**
1. **在对话中：引导用户输出。** agent 知道用户手上有哪些框架词 / 场景词 / 句型，就能顺势搭台子推着他主动用出来（落地见 6.3.3）。
2. **在成长层：诊断缺口。** 把库存和实际输出一比，看出他偏哪种缺口（如"场景词丰富、但句型单一"）。

- 定义：**框架词** = 跨话题通用词（get, make, set up…）；**场景词** = 绑定领域的词（invoice, marinate…）；**固定句型** = 可复用句子骨架。

**判层方法（v2 修正）：**

> **v1 的问题**：v1 写"静态词表 + **跨情境扩散度修正**"。但扩散度是**后验的**——要等这个词在多个情境出现过才算得出来，而 `tier` 在词条第一次创建时就要写值，此时扩散度恒为 1，提供不了任何信息。

- **MVP 已定：只用静态通用高频词表判 tier**（NGSL / CEFR 之类，静态、零 AI 调用、确定性强、可写单元测试）。
- **跨情境扩散度修正明确标为迭代项。** 启用时必须一并设计重算作业：谁触发、多久跑一次、**重算后用户在 Tab2 看到的分层标签会不会当着他的面跳变**（昨天"场景词"今天"框架词"）。没有这套设计就不要启用。
- 句型识别靠抽词那次调用顺带标注。

#### 5.2.2 情境（scene_category）

继承自来源场景的话题标签（沿用现有 12 类）。它是"在最贴近的场景再现"的直接依据。

**（v2 定死，消解 v1 的自相矛盾）对话中产生的 occurrence，情境按"当前推断话题"记，不按 seed 场景记。**
- *为什么*：6.3.3 的实时推荐本来就要"每隔几轮重新推断当前话题"。既然系统已经在算当前话题，就用它——否则一次对话从"工作"聊到"家庭"，后半段的词全被打上"工作"标签，`By scene` 镜头和情境再现都会错。
- **孤立词**（s1/s3 查的、无场景的词）情境为空，不参与情境再现。它在账本里照样有 entry、照样计频率。

#### 5.2.3 来源 / 继承链（词 → 场景）：记忆锚点

每条 occurrence 带 `source_id`（来源素材 / 对话消息）。于是词能反查"它来自哪些场景"——**这是练习的语境供给：告诉你该在什么处境下把它用出来**。它也补上了 `related_material_ids` 长期空转的洞。

#### 5.2.4 一词多义（sense）：MVP 不做，字段预留

**已定：一词多义（schedule 日程 → 赛程）放到迭代版本，MVP 不做。** 这里说清"以后怎么加不折腾"。

- 数据层：`lexicon_entries` 的唯一键**现在就定成** `(user_id, lemma, sense_key)`，`sense_key` 默认 `'default'`。MVP 抽词不判义项，所有 entry 恒为 'default'——行为和"没有分义"完全一样。
- 迭代开启时：只需打开"判义项 + 义项不一致就新建 sense 的 entry + 一词多义卡呈现"，**不用改表、不用改唯一键、不用回填老数据**。
- *为什么现在就把 sense_key 放进唯一键：* 若 MVP 唯一键只有 `(user_id, lemma)`、以后再加，那是一次约束变更 + 要把已合并的多义词拆开回填，折腾且有风险。

#### 5.2.5 entry_kind：词汇单元类型

word / phrase / collocation(词伙) / slang / idiom / **pattern(固定句型)**，抽词时顺带标注。既是展示筛选维度，也承载 5.2.1 假设的两支：**collocation** 对应"词都会但不知道怎么搭"，**pattern** 对应固定句型（`display_form` 存模板本身）。

> 建模选择（已定）：句型用 `entry_kind='pattern'` 承载、`tier` 默认按框架处理，**不把 tier 扩成三值**——形态归 entry_kind、通用度归 tier，两轴分开、互不污染。

#### 5.2.6 输入语言 与 已知缺口

**记录每条 occurrence 的语言（`input_lang`）**，三个理由：
- **多语言复用**：母语表达是"想说什么"的意图载体，跨目标语言可复用。
- **区分脚手架**：母语轮 vs 目标语言轮本来就要分（6.3.2）。
- **账本过滤**：母语内容不混进目标语言的高频榜。

**"已知缺口（known gap）"**：当用户用母语说了个意思（= 他承认"这句我不会用目标语言说"），对应的目标语言表达同时满足**高动机 + 高缺口**，学习优先级高于系统猜测的泛泛高频词。

> MVP 轻量实现（已定）：在 occurrence 上加 `input_lang` + 一个"来自母语兜底缺口"的布尔标记即可，**不单开 expression_needs 表**。

### 5.3 累计与再现

**累计（记账）：** 每次产生词条，就往 `lexicon_occurrences` 追加一行（带来源、情境、对错、例句）；`total_count` / `spoken_count` 是缓存，真值永远是流水。流水只增不改——它是分析用户语言习惯的**全部证据**。

**记账动作（在 `generate` 新增 Stage 3，见 9.2）：**
抽词（5.1）→ 规范化过滤（5.1.3）→ 顺带取 kind（5.2.5）→ 查该用户是否已有此 lemma+sense：没有则新建 entry（判 tier、存已知的音标词性释义）、有则 `total_count += 1`；无论新旧都 append 一行 occurrence。

#### 5.3.1 ⚠️ 失败与脏数据修复路径（v2 新增，v1 完全缺失）

这是一本**只增不改的流水账**，脏数据会永久沉淀。以下必须实现，不是可选项：

| 情况 | 处理 |
|---|---|
| 抽词的 AI 调用失败 | 记账整体跳过（**不写半条**），落一条服务端告警日志。**不阻塞主响应**——用户照常看到卡片 |
| 记账落库失败 | 同上；`materials` 已经写成功，账本缺这一笔，靠下面的补账作业补 |
| 补账 | 提供一个可手动触发的补账作业：扫描"有 material 但无对应 occurrence"的记录，重跑记账 |
| 归一化错并（把两个不同的词并成一行） | 提供拆分能力：把指定 occurrence 迁到新 entry，重算两边 count。MVP 可以是后台脚本，不做 UI |
| `total_count` / `spoken_count` 与流水不一致 | 提供对账作业：按 occurrences 重算所有 count 并回写。定期或按需跑 |

> *为什么必须现在写：* v1 只写了"失败只告警不阻塞"，但没有任何补救机制。缓存值一旦漂移，Tab2 的排序和成长层的统计就全错，而且**没有任何人会发现**——因为不会报错。

**再现（这层目的的落地，三种交付）：**
1. **对话里实时再现**：聊到某话题时，把该情境下用户的高频可用词推回（6.3.3）。
2. **Tab2 主动再现**：`For review` 把"该练的词"浮到眼前（5.5）。
3. **成长层分析**：把画像和实际输出对比，告诉他习惯与缺口（第七节）。

### 5.4 数据模型（三张新表）

> 术语统一：一个概念只用一个名字，贯穿 DB / Edge / Swift。下面字段名即最终名。

#### 5.4.1 ⚠️ 已知缺口：pos / phonetic / definition_zh 大概率为空

s1/s3 卡片有音标、词性、释义，但 **s2/s4 的 `key_phrase` 只有 `{phrase, note}` 两个字段**，对话里抽的词更是什么都没有。所以账本里**多数词条这三列会是空的**。

**这带来一个必须回答的设计问题：Tab2 词条行没有音标词性时展示什么？** 三条路（待定，见 §12）：
- (a) 只展示 `display_form` + `entry_kind` + 练习状态，不强求音标——**最省，推荐**；
- (b) 记账时对新词补一次轻量查词调用——准确但每个新词多一次成本；
- (c) 用户点开词详情时按需查一次并回写——成本可控但首次点开有延迟。

> 完整的"卡片类型 → 账本字段"映射表写在《输入到成长_链路现状与待敲定》，本文档只标明缺口位置。

### 5.5 Tab2 前端：练习清单长什么样

**主体 = 词条列表 + 顶部一排镜头标签**（不是把页面切块）。

**（硬约束）每一行必须带练习状态：**

```
set up          phr.   ● 说过 3 次      家庭
run late        phr.   ○ 还没说过        工作
invoice          n.    ○ 还没说过        工作
```

`○ 还没说过` 不是装饰，**它就是练习进度**——一份练习清单必须让人一眼看到哪些还没练。这也是 `Tab2_PRD_v1` 第一节要的"让他看见差距，并推他去补上"；没有它，词条列表第一眼就变成"我攒了多少内容"，违反该文档定死的产品根基。

**镜头标签（点哪个就按哪个维度重排同一份列表）：**

| 镜头 | 含义 |
|---|---|
| `For review` | **默认**。策展"现在该练的"：三类缺口都照顾——没用起来的场景词、贫乏/不地道的框架动词、单一的句型 |
| `All` | 全量，按频率 |
| `Not yet` | `spoken_count = 0`，还没说出来的 |
| `Spoken` | `spoken_count > 0`，已经说出来过的 |
| `Recent` | 最近 |
| `By scene` | 按来源场景，展开时复用现有情境 chips |

- `For review` 的具体排序权重是可调细节，上线后按数据 tune（§12）。
- 点一个词 → 词详情：展示它的 occurrences（来自哪些场景/对话）+ 从这里发起练习（6.2）。**场景在这里作为"练习语境"出现，不再是独立可浏览的卡片**——想整段回看某次场景，那是 Tab1 的历史。

## 六、Tab2 · 怎么练 —— 对话页（按对话前 / 中 / 后组织）

> **v2 重组**：v1 把这一层按功能点罗列（入口、语言、时长、推荐、素材、记忆…），同一个用户动作散落在多处。本版按**用户体验时序**重排，读一遍就能知道"用户从进入到退出，系统每一步做了什么"。

**这一层解决的问题：素材躺在库里不等于会说。** 用户需要一个能一来一回、从他自己的经历出发、在他卡壳时接住他的陪练对象——并且这个陪练全程在往账本记账、在记住他的强弱项。

**定位：对话页 = Tab2 的练习功能。** 不存在另一个待设计的练习模块（见第四节备注）。

### 6.0 和 Tab1 生成的界线

| | Tab1 捕获生成（已实现） | 对话页（本文档新增） |
|---|---|---|
| 交互形态 | 单次：输入一条 → 出一张卡 | 连续：一来一回的多轮 |
| 目的 | 把生活片段变成学习素材 | 用已有素材练"说出来" |
| 产物 | materials 卡片 | 一段练习记录；**副产物**是新词条 + 新素材（需确认） |
| 记忆 | 30 分钟短期上下文，**纯内存、App 被杀即丢** | **长期记忆**，落 DB，跨 Session 持续 |

> **关键区分**：Tab1 的 `ConversationSession` 是"工作记忆"（说完就忘、且只在客户端内存里），对话页的记忆是"长期记忆"（记住你哪个词总说错）。**两者都叫记忆但完全不同，不能复用同一套机制**——对话页要跨进程恢复，需要服务端 session。

### 6.1 对话前

#### 6.1.1 从哪发起

**从 Tab2 的词详情发起**：点开一个词 → 看它的来源场景 → 在某个来源场景上"和它聊聊" → `dialogue` 函数拿这个场景内容（native / 中文原句 / key_phrases）当 seed，生成贴合的开场。

*为什么是这个入口：* 话题是用户真事，锚强、有话说；而且它天然承接"我要练这个词"这个意图——从练习清单点进来，练的就是它。

> **v2 修正**：v1 写"冷起手住 Tab1"。**作废**——Tab1 改成"输入即生成"的形态后，结构上不做往复对话。无 seed 的"随便聊聊"起手需要重新安置（§12 待定）。

#### 6.1.2 交互形态

- **独立 chat 流页面**：沉浸、**语音对话（MVP 无文本聊天模式）**、不干扰首页。
- 进入前要处理**麦克风权限**：未授权 / 拒绝态必须有明确的空状态和引导（`CLAUDE.md` 硬约束：每屏定义 loading / empty / error 含权限拒绝）。

#### 6.1.3 开场准备（系统在用户开口前做的事）

- 拿 seed 场景生成开场白。
- 预读账本：挑出这个情境下用户的可用词，供 6.3.3 实时推荐。
- 读成长层的缺口画像（用户偏缺框架动词还是场景词），供推荐加权。

### 6.2 对话中

#### 6.2.1 Agent 用什么语言：全目标语言 + 点击翻译

- **AI 全程用目标语言**（MVP 是英文，但架构 / 文案不写死英文），营造沉浸语境。
- **点击翻译兜底**：用户主动点某句 → 看整句母语译文（默认不显示，保沉浸）。
- **MVP 只做整句翻译**；点单个词弹"单词卡 + 查账本显示'你已经有它'"列为后续增强。

#### 6.2.2 用户用什么语言：母语兜底 + 必须说目标语言才推进

用户可用母语或目标语言。规则：

- **母语兜底**：卡壳时用母语说出想表达的意思 → **弹框实时翻成目标语言，对重点词带音标**（降开口门槛 + 练发音）。
- **必须用目标语言说出来 AI 才推进**：母语轮只给"翻译 + 音标"帮助、不推进剧情、**不计 occurrence**；用户用目标语言说出来（哪怕照译文念）AI 才回复、这轮才计入。**守住"说出来才算数"。**
- **母语兜底的语料是最高价值的"已知缺口"**——用户承认自己不会说、却明确想说的东西，同时满足高动机 + 高缺口。记为 `is_known_gap`，供 6.2.4 推荐和成长层优先攻克。

#### 6.2.3 ⚠️ 划清界线：不判"达标" ≠ 不判"对错"

> **v2 新增。这是 v1 最容易被误读的地方**——v1 §12 把"不判达标"写成了已定死原则，但 §5.4 又保留 `used_correctly`、§6.9 又要检测错误。下一个 agent 读到会困惑，甚至会把 `learning_events` 整张表删掉。

这是**两件不同的事**：

| | **达标判定** | **正确性判定** |
|---|---|---|
| 问的是 | 你说的和 AI 给你的译文一样吗？ | 你说的这句英语，语法 / 用法有错吗？ |
| 状态 | ❌ **已废除** | ✅ **保留** |
| 为什么 | 拿"照不照抄"当标准，既不可靠也违背"用户说什么记什么" | 这是学习产品的基本功能；没有它，`learning_events`、总结卡的"待提高"、成长层的语法薄弱点全部失去数据来源 |

**配套规则：**
- **记用户实际说出来那句**（照译文念也好、说了自己的变体也好、说岔了也好），照样计入 `spoken_count`。AI 译文只是屏幕上的脚手架，不是被记录的内容。
- **不设 `assisted` 字段**（是不是照念既不可靠又不必要）；"用了多少次母语兜底"走 `native_fallback_used` 埋点。

#### 6.2.4 对话中 AI 不打断（本轮拍板）

**AI 在对话进行中绝不纠错、不打断。** 正确性判定在后台默默进行、写进 `learning_events`，但**不给用户任何即时的纠错反馈**。

*为什么：* 即时纠错的收益是反馈快，代价是打断表达欲——而这是一个练口语的产品，"敢开口"比"说得对"优先级更高。纠正统一延后到退出时的总结卡（6.3.2），那时用户已经说完了，接受度也更高。

#### 6.2.5 实时推荐："最需要"的多信号排序

对话中实时给"你手头有这些能用上"（从账本挑，可一键关闭）——这是 5.2.1 分层第一个作用的落地。"最需要"= 综合排序：

1. **动态相关性**：话题随对话进化，**不锚死开场场景**——每隔几轮从最近对话内容重新推断"当前话题"、重排候选。（这个推断结果同时用于 5.2.2 的情境归属。）
2. **已知缺口优先**：刚母语兜底暴露的"想说但不会" → 最高权重（当下正卡在这）。
3. **按 tier 个性化加权**：从成长层拿缺口画像，把他弱的一侧加权。
4. **可激活的闲置储备**：账本里有、最近没用、当下用得上的词，推一把促成复习式产出。
5. **够得着（i+1）+ 多样性**：略高于当前水平不超纲；别老推同几个。

排序：动态相关性 ×（已知缺口 > 闲置储备 > 新词）× tier 缺口加权 × 够得着。

*为什么推自己的词而非通用推荐：* 激活已有、快忘的储备 = 复习式产出；灌通用新词认知负担高、也背离"从你生活取材"。

#### 6.2.6 边聊边记：两种笔记

系统一边听一边记两种笔记，**每一轮顺手记下**（AI 本来每轮就在判断，顺手落成一条 `learning_event`），**不是等对话结束才重新分析整段对话**：

- **待提高**：用户没说出来、或说错的点 → `event_type='gap'` 或 `'error'` + `aspect` 标明是词还是语法；若牵涉某个词，同时在该 occurrence 上标 `used_correctly=false`（**语法类问题不属于某个词，`entry_id` 可空**）。
- **进步**：见 6.3.3 的两级定义。

#### 6.2.7 空闲退出：不设最低时长，做优雅收尾

**最低时长：不做（已定）。** 硬性"聊满 N 分钟才能走"偏暗黑模式、和"有温度、不施压"冲突；收获按"是否产出"而非时长——4 轮产出 2 个表达 = 有收获，10 轮全 yes/no = 没收获。要引导就用**产出型软目标**（"用出 3 个你的词"），完成有正反馈但随时能走。

**空闲退出：做，但优雅。** 不是"逼你留下"，是"你已经走了就体面放手"：
- 空闲一小会先轻推一次（"慢慢来～"），不退；继续空闲（1–2 分钟，阈值待定）→ **优雅收尾：生成总结卡 + 记账落库 + 退出**。
- **对话是语音的**：持续监听麦克风在耗电，所以空闲超时停止监听是**必要的、不是可选的**。
- **硬规则：任何自动结束都必须产出总结卡 + 记账，绝不因用户分心就静默丢掉他练的东西。**

### 6.3 对话后

#### 6.3.1 记账落库

对话产生的词条走同一套记账动作（5.3），`source_type='dialogue'`、`source_id` = 对应 message、`scene_category` = 当前推断话题、`input_lang`、`is_known_gap`、`sample_sentence` = 用户实际说的那句。

**说出来的词额外更新**：`spoken_count += 1`；若是第一次，写 `first_spoken_at` 并生成一条 `breakthrough` 事件（见 6.3.3）。

#### 6.3.2 总结卡

**为什么能即时、成本低：** 它是"把已攒的笔记归类拼卡"，不是"重新分析整段对话"。所以**在用户退出那一刻（主动退出 或 空闲收尾）直接拼卡即可，几乎零延迟、零额外成本**。若想加一句 AI 生成的温暖总结语，那是一次轻量调用，可异步补、不挡卡片先出。

**三块内容（条件展示，"有才出现"）：**

1. **这次用出了哪些"你的词"**：从账本调用了几个已有词条——正向、有成就感。
2. **待提高**：**只给 1–2 条，用「也可以这么说」的口气，不打分、不列错误清单**（本轮拍板）。分两类，**语法是一等公民**：
   - 词 / 表达：想说没说出、或用得不地道。
   - **语法**：时态、单复数、语序、冠词等结构问题。*（语法甚至比词更重要：词错了对方常还能猜懂，语法错了容易听不懂或误解，而"被听懂"是口语第一目标。）*
3. **进步**：见 6.3.3。

**没进步就不显示进步块、没错就不显示待提高块**——避免硬凑空栏，也不给用户"每次都被挑毛病"的压迫感。

#### 6.3.3 "进步"的两级定义

> **v2 修正**：v1 在 §6.9 说"进步 = 先错后对的翻转"、在 §7.2 说"进步 = 从说不出到说出来"——两个完全不同的触发器，混用了。而且如果只用前者，触发条件极窄（要求同一个词在两次对话里都被用到且都被判定过），**北极星指标 `progress_event_created` 可能几个月都是 0**，会让人误以为产品没价值。

拆成两级，分别用 `learning_events.event_type` 承载：

| 级别 | 定义 | 触发器 | 频率 | 用途 |
|---|---|---|---|---|
| **突破** `breakthrough` | 说不出来 → 说出来了 | `spoken_count` 由 0 变 1（写 `first_spoken_at`） | 每次对话都有几个 | **北极星指标**；总结卡的日常正反馈 |
| **纠正** `correction` | 说错 → 说对了 | 同一 entry / 同一 aspect 出现"先错后对"的翻转 | 稀疏 | 总结卡与成长层的**高光时刻** |

*为什么必须分开：* 混成一个数字，你看不出"这周进步 5 次"里是 5 次都是第一次说出口（日常），还是有 1 次真的改对了老错误（里程碑）——两者对用户的反馈方式应该不一样。

> **⏳ 待产品负责人确认**：产品负责人另提出第三种进步——**卡顿 → 流畅**。它不是"词"层面的东西，是"这个人说话的状态"，需要另一套数据（每轮的停顿时长、语速、犹豫次数）。**本文档目前没有任何数据模型支撑它**，要不要做是一个独立决定（§12）。

#### 6.3.4 新素材提取与确认（不自动入库）

对话里冒出值得留存的内容，agent **打包成预览卡问"要不要加入你的素材？"**，确认才入 materials + 记账，否则丢弃。

- **什么值得提**：用户产出的、**账本里还没有的**表达（新词 / 搭配 / 句型）；母语兜底转出的地道英文；纠错后用户采纳的更地道说法；够到"场景级"的完整表达更该存。
- **排除**：AI 单方面说、用户没接住的；纯寒暄；账本已有的重复。
- **为什么必须确认**：延续"素材是用户的"，自动塞会污染库；按一下确认既是筛选、也是"我认领了"的确权。

#### 6.3.5 ⚠️ 删除语义：防复活（v2 新增）

用户可以左滑删除一个**词条**（连词汇都能删），对话确认入库的素材同样能删。但 v1 没有说清后果，这里补上：

- **词条是聚合对象**。删除时：entry 的 `status` 置 `'excluded'`（不是物理删），它的 occurrences **保留**（流水是证据，不能删），只是不再进入任何列表和统计。
- **必须防复活**：如果只是删掉 entry，用户明天再输入同一个词，记账的 upsert 会把它**重新建出来**——用户删掉的东西自己回来了，这是个真实的产品坑。所以记账时必须先查 `status`：命中 `'excluded'` 就**跳过入账**，不重建、不累加。
- 提供撤销（沿用现有 Undo Toast 模式）。

## 七、Tab2 · 练得怎样 —— 成长层

**目的：让用户"知道自己的现状"**——把"用户实际说出来的"和"账本里已经有的"放在一起对比，让他看清自己现在站在哪。它不产生新存储（只读三张表），但比"只读账本"多了一个关键动作：**找差距**。

**入口（已定）**：独立轻量"回顾 / 侧写"页 = 周期性推到首页（像对话总结卡的周度大表哥）+ Tab2 一个安静小入口 + 对话总结卡带链接。**不做第三个底部 tab**（避免"实时记分板"式的刷分心态）。

### 7.1 什么算"用户输出"

= **用户在对话里用目标语言"说出来"的话（口语）**。

- 母语兜底后说出来的（照念也好、说了别的也好）都算——**记的是用户实际说出来那句**，不判达标（6.2.3）。
- **明确不算输出的**：AI 生成的内容、母语原话、查词（s1/s3 被动查询）；以及 **Tab1 打字捕获的英文句子——那是"输入 / 捕获"，不是"说出来的输出"**（打字能绕过"开口"这道坎，对口语产品不算数）。

*为什么收紧到口语：* 产品核心是练口语、对话是语音的，"能说出来"才是成长的度量——守住"AI 生成 / 打字 ≠ 用户能说出来"的边界。

### 7.2 差距分析

**框架：两个视图的差。**

- **输入账本（碰过）** = 全部 active 条目：你收集 / 遇到过的表达（`total_count`）。
- **已使用账本（说过）** = 其中 `spoken_count > 0` 的：你在对话里**实际说出来**过的。

> **v2 修正**：v1 说"已使用账本 ⊂ 输入账本，是同一份 lexicon 的两个视图"。**这个子集关系其实不成立**——用户在对话里说出一个账本里从来没有的词时，记账会新建 entry（`total_count=1`, `spoken_count=1`），于是存在**说过但从没"碰过"**的第三种状态。所以 `origin` 字段（5.4）区分来源，框架重述为**三种状态**：

| 状态 | 判定 | 含义 |
|---|---|---|
| 碰过没说过 | `origin='captured'` 且 `spoken_count=0` | **练习目标**（`Not yet` 镜头） |
| 碰过也说过 | `origin='captured'` 且 `spoken_count>0` | 你真能用的（`Spoken` 镜头） |
| 没碰过直接说出来 | `origin='spoken'` | **他在长新东西**——正向差距的真正来源 |

**两种差距：**

- **正向差距** = `origin='spoken'` 的词条 + `learning_events` 里的 `breakthrough` 事件 → 他在长新东西。
  > **v2 修正**：v1 定义为"用户输出里冒出了账本里没有的表达"。但按记账规则，用户说出的词**立刻就入账了**，等成长层去读时账本里已经有它——**差集永远是空的**。改用 `origin` 字段和事件表来判定，才有数据来源。
- **负向差距** = 账本里有、但没说出来的词（闲置资产）；或反复用错的点（`learning_events` 的 error，按 `aspect` 分——**含语法薄弱点，语法是重点**）。

**（硬原则）成长层只陈述现状，不评价。** 负向差距也只**谨慎地告知现状**，不带评判、不制造焦虑。措辞是"你有这些词还没怎么用起来"，不是"你这些词学得不好"。**目的是让用户认识自己、自己决定要不要提升，而不是让产品替他下判断。**

### 7.3 呈现的五个角度（都是差距分析的切面，全部只读）

1. **高频表达 / 表达习惯**：读 `total_count` → "你最常用的表达"。分框架词 / 场景词展示。
   > ⚠️ 这个角度的数据质量直接取决于 5.1.1 的抽词供给量。如果抽得太少，这里长期是一堆"用过 1 次"。
2. **更地道的说法**：某个高频表达其实不够地道 → 对照历史 `native_polish`，"你常说 X，也有更 native 的 Y 可选"。**给选项，不判优劣。**
3. **同义扩展**：针对高频依赖的词，推它**没用过的**同义词（AI 生成候选，比对账本里没有的），"想说这个意思，你还可以用这些"。
4. **语法 / 结构薄弱点**：读 `learning_events` 里 `aspect='grammar'`（及 pattern）的反复项。**这是待提高的重点**——语法错比词错更影响"被听懂"。谨慎告知、给可练方向，不打分。
5. **闲置与进步**：负向 = 闲置的词（有但不用，谨慎告知）；正向 = 读 `breakthrough` 与 `correction` 事件，"这些是你从说不出到说出来的 / 从说错到说对的"。**用质变叙事，不用进度条 / 打分。**

**呈现原则：** 成长页第一反应应该是"哦，我原来是这样"和"我想再练"，不是"我被评了几分"或"我攒了多少词"。数字只作工具性信息，不作评价指标。

## 八、知识产权保护

原问：**"怎么保护知识产权，对外怎么展示。"** 这里的 IP 有两层含义。

**第一层：用户的个人素材是用户的隐私资产。**
- **默认全私有**：lexicon 和 materials 严格按 `user_id` 隔离，任何情况下不跨用户可见（代码已做，见 2.1）。这是底线，不是功能。
- **图片等原始输入**存私有 bucket、按需签发短期 URL（已实现），不生成公开链接。

**第二层：将来若要"对外展示"（分享/社区），展示什么、不展示什么。**
- **可分享的 = 去人格化的语言产物**：一个词条、一句地道英文、一个语法点——这些是"通用学习内容"，本身不含个人隐私，类似字典条目。
- **不可分享的 = 人格化的场景背景**：照片、中文原话、时间地点、这段经历本身——默认剥离，除非用户逐条主动勾选公开。
- 换句话说：**分享时把"帮妈妈弄手机"这段私事抽掉，只留 "set up" 这个词和它的地道用法。**

**落地：分享功能标为 MVP 后置**，但**数据模型现在就留接口**：给 `materials` 预留 `visibility`（'private' 默认 / 'shareable_derived'），lexicon 天然是去人格化的可共享层。

*为什么现在只留字段不做功能：* 遵循"垂直切片、不提前铺框架"。但 IP 分界的**原则现在就定死**，避免将来做分享时才发现数据混在一起、拆不开。

## 九、与已实现代码的整合改造点

### 9.1 前置：只剩一笔地基欠账

> **v2 更正**：v1 列了两笔欠账，其中"补 `messages` / `profiles` 迁移文件"**已经完成**——仓库里有 `20260704010000_create_messages_table.sql`（含 DDL + 索引 + RLS）和 `20260707000000_create_profiles_table.sql`（含 DDL + `handle_new_user` 触发器 + RLS），之后还有 4 个针对 messages 的增量迁移。**照 v1 施工会去"补"一份已经存在的迁移。**

**剩下的唯一一笔：`source_message_id` 从不写入。**

但这句话背后有两个必须先拍板的实现决定：

| 问题 | 说明 |
|---|---|
| **指向哪一条 message？** | 一次 `generate` 请求写了**两条** message：user 行（原始输入，图片挂在这里）和 assistant 行（AI 卡片，素材由它提取）。指向 user 行能反查原始输入和图片；指向 assistant 行能反查生成的卡片。**必须选一个并写进文档** |
| **怎么拿到 id？** | `insertMessage` 现在用 `'Prefer': 'return=minimal'`，**根本不返回 id**。要回填就得改成 `return=representation`，并把 message 写入从"并行 fire-and-forget"改成"串行等 id"——这会**给主响应加一次 DB 往返的延迟** |

### 9.2 `generate` 函数：新增"记账"阶段（Stage 3）

```
generate（改造后）
├── Stage 1  INSERT materials（raw_content + material_type）   ← 已有
├── Stage 2  scene 打 scene_category，PATCH 回写               ← 已有
└── Stage 3  记账（新增）：
      ├── 取可学单元：
      │     路径 A（推荐）—— 直接读主 prompt 输出的【可学单元数组】，零额外调用
      │     路径 B        —— 对生成的目标语言原文另跑一次抽词
      │     （二选一，见 5.1.1 与 §12 问题3；无论哪条，都按"有多少抽多少"）
      ├── 规范化 lemma + 停用词过滤（5.1.3）
      ├── 顺带取 entry_kind（5.2.5）
      ├── 查 status='excluded' → 命中则跳过（防复活，6.3.5）
      ├── upsert lexicon_entries（判 tier、累加 total_count）
      └── append lexicon_occurrences（source_id、scene_category、input_lang、sample_sentence）
```

**工程要点：**
- **记账层只吃 2.3(1) 定义的统一契约**，不直接依赖某种卡片类型的字段结构。这样加长内容 / 文件 / 语音等新来源时，记账层零改动。
- Stage 3 与主响应**解耦**（用户不必等记账完成才看到卡片），失败按 5.3.1 的路径处理（跳过 + 告警 + 可补账），**不阻塞**。
- **成本**：现在每条素材已经调了 2 次 Gemini（主生成 + 情境分类）。走路径 A **不增加调用**；走路径 B 是第 3 次。
  > 这件事和《输入到成长_链路现状与待敲定》§1.1 的 **prompt 拆分决策强耦合**——路径 A 本质上就是"prompt 按输入形态分化时，顺手把输出结构一起分化"。**两份文档要一起定，不要各定各的。**
- **prompt 拆分必须连带落库结构一起拆**（2.3(3)）：只换提示词、不改 `raw_content` 的结构，s2 的用户原句和纯图的 `ai_scene_guess` 照样会在写库那一刻丢掉。

### 9.3 新增 Edge Functions

| 函数 | 职责 | 备注 |
|---|---|---|
| `dialogue` | 对话陪练主循环：接收对话历史 + 用户输入，返回 AI 回复；内部含母语兜底判定、实时推荐挑词、gap/error/breakthrough/correction 检测 | 对话的记账 + learning_events 写入在这里 |

## 十一、埋点设计

| 事件名 | 触发 | 附加属性 | 能回答什么 |
|---|---|---|---|
| `dialogue_started` | 进入一次练习对话 | `{ seed_type, scene_category?, entry_id? }` | 练习入口有没有人用、从哪个词发起的最多 |
| `native_fallback_used` | 用户切母语兜底 | `{ }` | 卡壳有多普遍、母语依赖度（**取代 per-word assisted**）；也是"已知缺口"产生量 |
| `dialogue_ended` | 一次对话结束 | `{ turns, produced_count, native_fallback_count, known_gap_count, end_reason }` | 每次练习的收获 + 怎么结束的——支撑 6.2.7 用产出而非时长衡量 |
| `vocab_suggestion_shown` / `_tapped` | 实时推荐展示 / 被点用 | `{ entry_id }` | 推荐词有没有真的被用起来 |
| `material_confirmed` / `_discarded` | 对话新素材确认/丢弃 | `{ }` | 确认率——太低说明提议质量差 |
| `tab2_word_tapped` | 点一个词条查看详情 | `{ entry_id, tier, spoken_count }` | 哪类词更被点；**已说过 vs 没说过哪个更吸引点击** |
| `tab2_lens_switched` | 切换顶部镜头 | `{ lens }` | 哪个镜头用得多、默认 For review 够不够用 |
| `growth_viewed` | 打开成长页 | `{ top_word_count }` | 成长页活跃度，作其他埋点分母 |
| `synonym_adopted` | 采纳一个同义扩展 | `{ entry_id }` | 同义扩展有没有价值 |
| **`breakthrough_created`** | 一个词第一次被说出来 | `{ entry_id, tier }` | **北极星指标**：直接度量"说不出→说出来"的质变 |
| `correction_created` | 生成一条"先错后对"翻转 | `{ entry_id, aspect }` | 高光时刻的发生率 |
| `lexicon_entry_excluded` | 用户删除一个词条 | `{ entry_id, reason? }` | 抽词质量的反向指标——删得多说明抽的词不该抽（**直接检验 5.1.2 的判定标准**） |

## 十二、待确认问题清单

### 已定死的原则（不是待定，列此提醒别被改回去）

- **Tab1 = 输入生成内容；Tab2 = 让用户练习和成长。** 对话页是 Tab2 的练习执行页，不是第三个并列的面。
- **Tab2 以词条为中心**（练习的单位是表达），场景降为练习语境，整段回看归 Tab1。
- **词条行必须带练习状态**（`○ 还没说过` / `● 说过 N 次`）。
- **记账按抽取规则"有多少抽多少"**，Tab1 卡片视觉不动。
- **不判"达标" ≠ 不判"对错"**（6.2.3）。正确性判定保留，否则 `learning_events` 整套失去数据来源。
- **对话中 AI 绝不打断**；纠正只在总结卡里给 1–2 条，用"也可以这么说"的口气。
- **母语兜底 gate**：母语轮只给翻译+音标、不推进、不计 occurrence；必须用目标语言说出才计；**记用户实际说的那句、无 `assisted` 字段**。
- **成长层只陈述现状、不评价、不打分。**
- **成长层不做第三个底部 tab。**
- **删除词条 = `status='excluded'` 且记账时跳过，防复活。**

### 已决定"迭代再说"（MVP 不做，字段/接口先留）

- **一词多义分义**（5.2.4）——`sense_key` 预留，迭代开逻辑。
- **跨情境扩散度修正 tier**（5.2.1）——MVP 只用静态词表；启用时必须一并设计重算作业。
- **主动词义扩展**（聊到世界杯主动提醒 schedule 还能表示赛程）——需要额外的词典义项库，和一词多义是一套逻辑。
- **单词级点击翻译 / 单词卡**（6.2.1）——MVP 先整句翻译。
- **IP / 分享功能**（第八节）——数据分界现在定死，功能后置。

```
- 新增 dialogue Edge Function（seed 参数化）+ 独立语音 chat 页（含麦克风权限拒绝态）
- 从 Tab2 词详情的来源场景发起，seed=该场景
- Agent 全目标语言 + 点击整句翻译
- 对话产出走 Stage 3 记账（source_type='dialogue'、input_lang、scene_category=当前推断话题）
- spoken_count / first_spoken_at 写入；首次说出生成 breakthrough 事件
验收：从一个词的来源场景发起对话，来回 3 轮，新词进 lexicon 且 source_type=dialogue；
      第一次说出某个词时 spoken_count 由 0→1 且产生一条 breakthrough
```

**Slice 4 · 母语兜底 + 新素材确认**
```
- 母语兜底：弹框实时翻译、重点词带音标；母语轮不推进、不计 occurrence、触发 native_fallback_used 埋点
- 必须用目标语言说出才推进；记用户实际说的那句、不判达标、无 assisted
- 母语暴露的记为 is_known_gap
- agent 提议新素材 → confirm-material → 确认才入库；确认入库的可删（软删）
验收：母语那轮不产生 occurrence、埋点+1；用户说出来那轮按他实际说的产生 occurrence；
      确认后素材入库且可删，丢弃则无
```

**Slice 5 · Tab2 换成练习清单主视图**
```
- 新增 get-lexicon 只读函数
- MineView 主列表改为词条行（词 + tier/entry_kind + 【练习状态】+ 频率 + 来源提示）
- 顶部镜头标签（For review / All / Not yet / Spoken / Recent / By scene）
- 点词 → 词详情（来源场景 + 发起练习入口）
- 词条删除（status='excluded'）+ Undo；记账侧防复活
- 旧场景卡列表 / 独立词汇本退场；孤立词并入账本；清 vocab 状态孤岛 + 双请求
验收：Tab2 看到带"○还没说过 / ●说过N次"的词条列表；切镜头能重排；
      Not yet 与 Spoken 有真实区分；删掉一个词后再次输入它不会复活
```

**Slice 6 · 对话记忆 + 实时推荐**
```
- 建 learning_events 表；检测 gap/error，翻转生成 correction；结束总结卡汇总本次
- 总结卡：三块条件展示；待提高只给 1-2 条、用"也可以这么说"口气；对话中不打断
- 实时推荐：动态相关性（每几轮重算当前话题）+ 已知缺口优先 + 按 tier 缺口加权（可关闭）
验收：用错一个词→used_correctly=false + gap；下次用对→correction；
      对话进行中无任何纠错打断；推荐随话题变化、且优先母语暴露的缺口
```

**Slice 7 · 成长层**
```
- 扩展 get-lexicon：读用户输出，和账本对照算正/负差距（正向读 origin='spoken' + breakthrough 事件）
- 成长页 5 个角度：高频榜（分层）、更地道说法、同义扩展、语法/结构薄弱点、闲置词 + 进步高光
- 文案全程只陈述现状、不评价、不打分
验收：能看到 Top 高频词、至少一条 breakthrough 高光、一组同义扩展、
      一条语法薄弱点、一组"有但没怎么用"的闲置词，且无任何评价性措辞
```

**Slice 8 · 埋点 + IP 预留**
```
- materials 加 visibility 预留字段（不做分享功能）
- 接入十一节全部埋点，重点是 breakthrough_created 与 lexicon_entry_excluded
验收：analytics_events 能看到全部事件、字段完整
```

**Slice 9 · 一词多义分义（迭代，MVP 不做）**
```
- 字段已在 Slice 1 预留；本片只开启逻辑：判义项 + 义项不一致新建 sense 的 entry + 一词多义卡呈现
- 无需改表 / 改唯一键 / 回填老数据
```

**排序理由：** Slice 0→2 先把账本建好并能正确记账（后端为主，前端零变化，风险最低）；Slice 3→4 长出练习本体并开始产生 `spoken_count`；**Slice 5 此时才换 Tab2，换过去就是完整可用的**；Slice 6→7 补齐记忆与成长；8→9 收尾与迭代。**每一片都不依赖后面的片，可随时停在一个完整可用的状态。**
