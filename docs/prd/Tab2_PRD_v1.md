## 一、页面定位

**Tab2 解决且仅解决一个问题：用户有了素材，但素材还不是他的——这个页面让他看见差距，并推他去补上。**

不是内容管理工具，不是词典，不是进度报表。用户打开这个页面，应该产生的第一反应是"我想把这个说出来"，而不是"我有多少内容"。

产品根基（继承自 PRD.md，Tab2 的所有设计决策不可违反）：
- 有内容不代表是用户的：AI 生成的 ≠ 用户能说出来的。这个区分是 Tab2 最重要的视觉分界线。
- 进步感知的本质是质变（说不出来 → 说出来了），不是数字积累（场景数、词汇数）。
- 场景是根，词汇是叶——词汇脱离场景会失去处境感和记忆价值。

**MVP 决策：Tab1 不放"开始练习"入口。** 所有练习入口统一收敛在 Tab2，这既强化了 Tab2 作为"练习起点"的角色定位，也不需要在 Tab1 卡片上为场景/词汇分别设计不同的 CTA 文案（避免了单个词卡片配"开始练习"这种重承诺感 CTA 的违和感）。用户在 Tab1 只管输入和对话，练习动作发生在 Tab2。**注意**：Page1_PRD_v1.md 模块 B5 目前仍写着"开始练习"入口在 Tab1 出现，需要在下一次更新 Page1 文档时同步修正，本文档先按最新决策记录。

## 二、内容来源

Tab2 的素材完全来自 Tab1，没有独立的内容生产入口（MVP 阶段不做 connectors，不做用户手动整理）。

**流转规则**（继承自 PRD.md 已确认规则）：
1. 判断一条对话要不要提取进 Tab2，标准是"AI 是否已成功生成过至少一层素材"（哪怕只是词汇层），而非"是否走完完整流程"。AI 还在追问、未产出任何素材时用户退出，则不提取。
2. 素材在 Tab1 生成后**立即**在 Tab2 可见（哪怕只是"待整理"状态），不存在延迟。"分类整理"是后续动作，"素材可见"是即时的。
3. 分类由 AI 主导（场景维度 + 语言素材维度：词汇/句子/段落），MVP 不给用户分类自由度。

**素材深度决定它在 Tab2 的归属**（对应 Page1 的 s1/s2/s3/s4 卡片类型）：
- 达到句子/段落层、有完整上下文的素材（s2/s4）→ 进入**场景化素材区**，归入固定场景分类体系。
- 只停在词汇层、没有场景支撑的素材（s1/s3，用户只输入了一个词）→ 进入**零散词汇区（词汇本）**，以词卡形式独立呈现，不假装自己是场景。

这样处理的原因：既不丢弃用户任何产出，又不让零散词汇稀释"场景化"这个核心主张的纯粹性。词汇本的排序方式与复习机制留待后续细化（详见第七节待定问题）。

**分类节奏：内容可见性和情境打标是两件独立的事，不绑在一起。** 素材本身（原文 + native 表达 + 词组高亮）在提取完成后立刻可见于 Tab2，初始挂在"全部"里；给它打情境标签（`scene_category`）这一步可以攒批处理（攒够一定数量或定时跑一次），用轻量模型做，不需要逐条实时跑。分类结果回填后卡片在对应情境标签下自动归位，用户不会感知到这个延迟——他们在意的是"我的内容出现了没有"，不是"这条内容具体几点被打上了哪个标签"。

## 三、内容组织结构

这是 Discussion 中讨论最久、也是分歧最大的问题。最终结论：

**情境（家庭/日常/旅行……）只做顶部筛选标签，不做导航层级；场景卡片直接铺陈在页面主体；词汇附属于场景，不单独开 Tab。**

### 3.0 三个概念的定义

- **情境**：AI 打在场景上的话题标签（"家庭""日常""旅行"……），本身不含内容，只用来筛选。MVP 阶段是固定分类集合，AI 在固定选项内分类，不动态新建。

  **MVP 起始分类清单**（参考 IELTS Speaking Part 1 话题表和主流 CEFR 教材单元、去掉纯访谈型话题后合并简化，供后续细化，非最终版）：家庭与人际 / 工作与学业 / 日常起居 / 饮食 / 购物消费 / 出行交通 / 运动健康 / 休闲娱乐 / 科技数码 / 天气环境 / 情绪社交 / 其他。
- **场景**：一段有完整上下文的具体经历，对应 s2/s4 卡片（句子/段落级，含谓语，能独立成句）。场景是内容的最小完整单元，一张大卡片对应一个场景。
- **词汇/短语**：对应 s1/s3 卡片（词/短语级，不含谓语，不能独立成句）。

**词汇的归属是一条继承链，不是两个并列标签**：场景 → 情境，词汇 → 场景 → 情境。从某个场景内容里提炼出的重点词组（如"set up"来自"帮妈妈弄手机"这个场景）天然继承这个场景的情境标签（"家庭"），不是词汇自己单独被打了情境标签。

**孤立词汇（词汇本里没有场景的单词）不参与情境筛选**，独立于情境标签体系之外。理由：孤立词汇的定位本身就是"查词典"（用户当时只是想知道这个词的意思），不该为了凑情境体系假装它有场景归属——如果强行让 AI 给孤立词汇也打一个情境标签，一是容易猜不准（没有上下文可依据），二是违背了"词汇本不假装自己是场景"这个设计初衷。词汇本应该有自己独立的组织方式（见第七节待定问题 5），不和情境筛选栏绑定，这样也省了一次不必要的 AI 分类调用。

### 3.1 为什么不做"情境优先"的嵌套导航（否决方案）

曾经讨论过让用户先选情境（如"家庭"）、进去再看场景和词汇的方案。否决理由：情境是 AI 自动打的标签，用户对"家庭""日常"这些分类没有强认同感，让用户先选一个自己无感的维度做第一层导航，是不必要的认知负担；而且情境列表会把场景压缩成"家庭 3 个场景"这样的数字，数字是冷的，场景才有温度。

### 3.2 为什么不做"场景/词汇并列 Tab"（否决方案）

曾经讨论过场景 Tab 和词汇 Tab 并列切换的方案。否决理由：词汇一旦从场景里被抽出来单独管理，用户的注意力就从场景转移到了单词本身，处境感变弱——而处境感正是这个产品记忆效果的来源（"set up"这个词用户记得住，是因为记得帮妈妈弄手机那件事）。

### 3.3 最终结构

```
顶部：情境标签筛选（家庭、日常、旅行……，横向可滚动，含"全部"）+ 最右侧词汇本入口（"词汇本 12"轻量胶囊，常驻）
  ↓ 点击某个情境标签后，标签下方出现该情境的词汇汇总条（横向滚动）
    例：set up · be useful · grateful · patient · +8个
中间：场景卡片列表（完整大卡片，见第四节）
  每张卡片直接展示：原文 + native 表达 + 这个场景的重点词汇
  词汇不单独抽离，就嵌在卡片里
点进场景：详情页（见第九节）
点击词汇本入口：词汇本子页面（见第十节）
```

**情境词汇汇总的呈现方式**：选择"方案一——筛选后在列表顶部出现"，而非长按展开浮层。理由：用户点击情境标签时注意力已经在这个话题上，顺势展示词汇汇总不需要用户做额外操作；同时词汇条在上、场景卡片在下，用户往下滚就能看到某个词来自哪个场景，词汇和场景的关联是天然可见的，不需要跳转。

**情境词汇汇总条是视图层聚合，不是重复存储。** 这条词汇条（"set up · be useful · grateful +8个"）是按情境筛选场景后、把这些场景里的核心词组实时拼出来展示，词组数据本身只存一份在场景卡片里，不会被复制写进词汇本这张独立表。词汇本只装真正孤立、没有场景支撑的词（s1/s3 的产出），场景的核心词组不重复计入词汇本，避免同一个词条在两个地方各存一份、边界混淆。

**情境标签只展示用户已经有素材覆盖到的情境，不展示固定分类集合里的全部选项。** 固定分类集合是 AI 打标签用的词典，不是要摆给用户选的菜单——很多类目用户可能完全没有素材，展示出来点开是空的，只会增加无意义的选择负担。筛选栏应该随着用户积累动态生长：有几个情境的素材，就露出几个标签，这个逻辑和第五节"稀疏态自适应"是同一套原则的延伸（内容驱动 UI，不摆冷冰冰的结构）。标签的具体排序方式（按最近活跃 / 按场景数量）留待视觉稿阶段细化。

## 四、卡片设计（本节只讲卡片展示什么内容，不涉及状态/练习）

> 卡片的"未练习/进行中/已完成"状态机、完成判断标准、排序逻辑、练习方式，已拆分到《Tab2_卡片状态与练习机制_v1.md》，作为练习模块立项设计的输入。这里先把卡片本身长什么样、展示什么内容定下来，不被还没设计的练习模块卡住。

### 4.1 词汇本卡片的统一展示格式

s1（英文查词）和 s3（中文查词）来源语言不同，但进了词汇本之后，来源这件事对用户不再重要，统一成一张标准词卡：英文词条做主标题（用户要学的目标语言），音标 + 词性紧跟其后，中文释义/翻译弱化处理（小字灰色，和 s4 卡片"中文原文弱化显示"用同一套视觉语言，不新发明一套），例句双语。

语言展示切换（以后让偏好中文优先的用户把词卡切换成中文为主展示）作为个性化预留项，不在 MVP 做，处理方式和 `reply_style`、`interest_tags` 这些已预留但暂不启用的字段一致。

### 4.2 场景卡片的统一展示格式（s2/s4 进 Tab2 后视觉统一）

s2（英文输入句子分析）和 s4（中文输入场景手帐）在 **Tab1 生成时刻**视觉焦点是不对称的，这是刻意设计：s4 的任务是"生成"，用户写的是中文，交付物是地道英文翻译，所以英文翻译必须是视觉焦点；s2 的任务是"确认/纠错"，用户已经自己写了英文，视觉焦点其实是中文翻译（确认意思对不对）和纠错内容，只有触发纠错时才会多出一段润色版英文（`native_polish`），用户原句已经地道时 `native_polish` 为 null，不会额外突出显示新英文。

但 **s2/s4 流转进 Tab2 场景卡片后，应该统一按"英文优先、中文弱化"展示**，不延续 Tab1 那套不对称逻辑——因为 Tab2 只关心一件事：这段经历能不能被说出来，不管素材当初是 s2 还是 s4 来的，用户要练习的都是同一个目标。

具体规则（复用 Page1_PRD_v1.md 3.3 节已定的 TTS 朗读 fallback 逻辑，不新造一套）：**场景卡片的 native 表达 = 有 `native_polish` 就用 `native_polish`；没有（用户原句已地道）就直接用用户原句本身作为这个场景的英文表达**。中文原文/翻译一律弱化展示（小字灰色），与 4.1 节词汇卡片的视觉语言保持一致。

## 五、冷启动 / 稀疏态方案

**结论：不做"内容积累到一定程度才解锁 Tab2"的门槛机制，做稀疏态设计。**

判断依据（对照已确认的产品原则）：
1. PRD.md 已明确"用户主动点击进入 Tab2（不自动跳转）"——Tab2 入口本身一直开放，是既定原则，锁功能等于新增一条规则去否决它。
2. IOS App 文档已明确 Page0 引导页的兜底设计：用户设定英语水平后（无论走"拍照/相册上传"还是"选预存图"路径），AI 立即生成一段内容并放入 Tab2。也就是说走完引导页后 Tab2 理论上不存在真正的空态，会发生的是"只有 1-2 张卡片"的稀疏态。
3 更根本的原因：锁功能传递的信号是"你不配用"，这和产品根基"有话想说但说不出来，这个产品帮你说出来"是相反的态度。产品应该先给一点甜头，不是攒够了才给看。Tab1 已经用新用户态（快捷示例、破冰引导）示范过这个逻辑，Tab2 应该延续，不应另立门槛逻辑。

**内容少 ≠ 体验差，这是两件事**：真正影响练习体验的是"这个场景是不是用户真心想说的东西"，不是数量。哪怕只有 1-2 个场景，只要是用户自己的真实经历，依然是完整、有温度的练习体验——Discussion 里也提到过反例，场景越多反而越容易让用户迷失，数量从来不是体验的决定因素。

会显得单薄的是**页面结构**，不是练习本身——内容很少时，情境筛选栏、情境词汇汇总条这些结构性 UI 元素会显得形同虚设、页面空落落的。这个用**稀疏态自适应布局**解决：场景数低于某个阈值（如 3 个）时，直接隐藏情境筛选栏和词汇汇总条，页面只保留推荐卡片 + 其余场景 + 练习入口，干净直接；场景数超过阈值后，这些结构性元素再自然出现。这样解决的是真正的问题（视觉单薄），不需要牺牲"即时反馈"和"随时可进入"这两条已定原则。

**极端边界**（引导页那张卡片也被用户删除，真正一张不剩）：需要一个极简空态兜底，引导用户回到 Tab1 输入。这是边界情况，不是常态设计，具体文案留到视觉稿阶段处理。

## 六、与 Tab1 的数据衔接（复用 PRD.md 已定表结构）

Tab2 直接消费 `materials` 表（见 Page1_PRD_v1.md 5.1 节），关键字段：

| 字段名 | 用途 |
|--------|------|
| `material_type` | `'scene'` 进场景化素材区；`'vocabulary'` 进词汇本 |
| `scene_category` | 情境筛选标签的依据 |
| `status` | 现有值 `'pending'` / `'categorized'`——`'pending'` 对应"情境未打标，暂挂在'全部'里"，`'categorized'` 对应"情境标签已回填"。Tab2 展示层还需要另外区分"未练习/进行中/已完成"三态，这三态的定义和数据契约缺口已拆到《Tab2_卡片状态与练习机制_v1.md》 |
| `raw_content` | 卡片正文（native 表达 + 词汇高亮）。s1/s3 存词卡结构（word/phonetic/pos/definition/example），s2/s4 存场景结构（原文/native 表达/key_phrase） |
| `related_material_ids` | 词汇的"来源场景"标注、情境词汇汇总的关联依据（已预留，MVP 存但可能需要开始在 Tab2 用起来） |
| `deleted_at`（新增） | 软删除标记，见第十二节。不做物理删除，置了值的记录不出现在任何列表/聚合查询里 |

**分类批处理**：`scene_category` 的写入不需要跟 `raw_content` 写入同一次调用完成，可以异步攒批用轻量模型处理，不影响素材的即时可见性（见第二节"分类节奏"）。

**练习相关的数据契约缺口**（练习次数、内容完整度判定结果等字段）已整理进《Tab2_卡片状态与练习机制_v1.md》第六节，不在本文档重复维护。

## 七、待确认问题清单

状态机、完成判断、开放式对话验证技术方案这三项已经随第四节一起拆到《Tab2_卡片状态与练习机制_v1.md》第五节，不在这里重复列。以下是仍留在 Page2 PRD 范围内、尚未收敛的问题：

1. **相似内容提示**：用户隔几天输入高度相似的主题（如两次都聊"咖啡续命"），系统是否提示"你之前聊过类似的"。影响产品"是否显得智能"的观感，优先级不高，可以留到 Tab2 v1 上线后再看数据决定。
2. **词汇本的呈现与复习机制**：排序方式（最近添加 / 复习状态）、词汇练习的具体交互（跟读 / 造句）尚未展开讨论，孤立词汇造句后"升级"为场景的具体机制也待细化。

## 九、场景详情页

点击一张场景卡片后进入的页面，**不重新设计，直接复用 Tab1 的 AI 回复卡片组件**，因为这条素材在 Tab1 生成时已经有完整的原文、native 表达、翻译区、音频播放这些字段和交互，数据是同一份，没必要在 Tab2 再造一遍。这样做的好处：开发成本低（复用已有组件），视觉一致（用户在 Tab1 生成时看到的和点进 Tab2 详情页看到的长得一样），也符合"先定数据契约、复用而不是重新设计"的原则。

详情页 = Tab1 AI 回复卡片组件 + 三样新增内容：
1. **情境标签**：小字放顶部，如"来自：家庭"。
2. **场景发生时间**：呼应第十节以外、第四节排序逻辑里"越新越靠前"的时间感（时间机制详见配套的《Tab2_卡片状态与练习机制_v1.md》）。
3. **"开始练习"CTA**：这是新增的核心入口——第一节已经决定这个按钮从 Tab1 挪到这里，所有练习动作从场景详情页发起。

**不在本节展开的部分**：练习本身的交互流程（点击"开始练习"之后发生什么）属于练习模块的设计范畴，本节只定义这个入口存在于详情页、长什么样，不定义点击之后的具体流程。

## 十、词汇本入口与子页面

**入口位置**：不做成和场景列表并列、需要跳转的独立大入口（会让用户误以为词汇本和场景同等重要，违背"场景是根，词汇是叶"的原则），也不直接铺在场景列表下面接着滚动（词汇量一多会被埋没，起不到复习作用）。

**方案**：在情境筛选栏那一行的最右侧，放一个轻量的常驻入口——"词汇本 12"这样的小胶囊（数字是词汇本里的词条总数）。点击后进入一个独立的词汇本子页面（push 进入或半屏弹层，具体交互留视觉稿阶段定）。

**为什么用数字不违反"不用数字做进步感知"的原则**：那条原则针对的是场景"有没有练会"这种成就感（第四节已定不用数字/进度条表达完成度），词汇本的计数是工具性质的信息（"我攒了多少个生词"），不是拿来衡量用户是否进步的指标，两者角色不同，不冲突。

**子页面内部的排序方式和词汇练习交互**（跟读/造句）仍然是待定项，保留在第七节问题清单里，不阻塞入口位置和整体骨架的确定。

## 十一、状态穷举

| 模块 | 状态 | 触发条件 | 展示内容 |
|------|------|----------|----------|
| Tab2 整体 | 加载中 | 首次打开 Tab2，素材还在拉取 | 骨架屏（卡片形状的占位灰块） |
| Tab2 整体 | 极端空态 | 真正一张素材都没有（引导页那张也被删除） | 极简空态文案 + 引导回 Tab1 输入的入口（属边界情况，非常态设计） |
| Tab2 整体 | 加载失败 | 网络错误 | 错误提示 + 重试按钮 |
| 场景卡片 | 未分类 | `scene_category` 还没写入（extract-materials 函数第二阶段尚未完成，通常只有一两秒） | 暂时挂在"全部"筛选下，不出现在任何具体情境标签里，不额外标注"未分类"字样——用户感知不到延迟是最好的效果 |
| 词汇本 | 空态 | 用户从没查过孤立词汇 | 词汇本入口不显示数字，或显示"词汇本"不带计数；子页面内是简单的空态提示 |
| 场景卡片 / 词汇卡片 | 删除确认 | 用户左滑触发删除 | 见第十二节 |

## 十二、删除功能

**交互方式**：场景卡片和词汇卡片都支持标准 iOS 左滑删除；场景详情页里也放一个删除入口，避免用户在详情页想删除却要退回列表才能操作。

**删除方式：软删除，不做物理删除**。给 `materials` 表加 `deleted_at` 字段，删除时置值而非物理清除。理由两点：一是可以配一个"已删除，撤销"的 toast，容错误删；二是以后如果做"相似内容提示"这类分析，软删除的数据还有价值，物理删除就彻底没了。

**关联清理不需要额外处理**：如果删的是一个场景，它的重点词组本来就是从场景实时聚合到情境词汇条里的（第三节已定，视图层聚合不是重复存储），场景一软删，聚合查询自然就不会再捞到它，不需要额外写清理逻辑；如果删的是词汇本里的孤立词，跟其他数据没有关联，直接标记删除即可。

## 十三、情境分类的系统实现（复用 Page1 Function 2，不新建批处理机制）

推翻了之前"攒批处理"的设想。对照 Page1_PRD_v1.md 5.2 节的 Function 2（`extract-materials`）才发现，它本来就是异步触发、一条用户消息对应一次调用，而且已经包含"调用 AI（轻量模型）做 Tab2 场景分类"这一步——现有架构本身不存在"分类调用过于频繁"的问题，不需要另外发明定时批处理、也不需要建队列表，那样反而增加不必要的复杂度。

**调整为两阶段写入，复用同一个函数**：
1. **第一阶段（立即）**：`extract-materials` 把提取出的 `raw_content` + `material_type` 落库，这一步完成后素材立刻在 Tab2 可见（挂在"全部"筛选下）。
2. **第二阶段（紧接着，同一次函数执行内）**：调用轻量模型对这条素材做 `scene_category` 分类（固定选项内），完成后 UPDATE 这条记录。

**前端配合**：通过 Supabase Realtime 订阅 `materials` 表的 UPDATE 事件（不只是 INSERT），`scene_category` 一写入，卡片自动从"全部"归位到对应情境标签下，不需要用户手动刷新，用户几乎感知不到这一两秒的延迟。

**需要同步修正 Page1_PRD_v1.md**：Function 2 的描述需要明确写成"两阶段"（先写可见内容、再补分类），并补充 Realtime 订阅 UPDATE 事件这一条，目前 Page1 文档里对这两步的先后顺序和可见性没有写清楚。

## 十四、埋点事件设计

延续 Page1 的 `analytics_events` 表，Tab2 新增以下事件：

| 事件名 | 触发时机 | 附加属性 | 这条数据能回答什么 |
|--------|----------|----------|----------|
| `tab2_opened` | 用户切到 Tab2 | `{ scene_count: int, vocab_count: int }` | 作为其他埋点的分母，衡量整体活跃度 |
| `scene_card_tapped` | 用户点击一张场景卡片 | `{ material_id, scene_category }` | 除以 `tab2_opened`，算出"打开页面后真的点进去练的比例"——验证卡片设计有没有激起欲望 |
| `context_tag_tapped` | 用户点击情境筛选标签 | `{ scene_category }` | 情境筛选功能有没有人用，用得少说明优先级该往下调 |
| `vocab_book_opened` | 用户点击词汇本入口 | `{ vocab_count }` | 词汇本这个常驻小入口值不值得占位置 |
| `vocab_card_tapped` | 用户在词汇本子页面点击一张词卡 | `{ material_id }` | 配合 `vocab_book_opened` 看，判断词汇本子页面本身设计得好不好 |
| `material_deleted` | 用户删除一张卡片 | `{ material_id, material_type }` | 删除率异常高时，可以顺线排查是不是某类内容生成质量或分类有问题 |
| `practice_button_tapped` | 用户在场景详情页点击"开始练习" | `{ material_id }` | 原记在 Page1（Tab1 卡片底部），入口挪到 Tab2 详情页后一并挪过来；配合 `scene_card_tapped` 算出"看了详情页之后真的去点开始练习的比例" |

这几条串起来是一条完整漏斗：`tab2_opened` → `scene_card_tapped` → `practice_button_tapped`，每一步的转化率掉在哪，就告诉你 Tab2 卡在哪一环。

**需要同步修正 Page1_PRD_v1.md**：`practice_button_tapped` 目前记在 Page1 的埋点清单里（触发位置写的是 Tab1），需要删掉或标注"已迁移至 Page2"。
