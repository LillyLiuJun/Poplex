| 层面 | 问的问题 | 上一轮改动的归属 |
|---|---|---|

| **加载层** | 数据**多快能到手**、从哪来、有没有本地备份 | ❌ 上一轮一行没碰；「新内容冷启动等几秒」属于这里 |

## 二、现状全景

### 2.1 数据怎么展示

```
TodayView
 └─ ScrollView + LazyVStack
     └─ ForEach(viewModel.entries)          ← 一个数组驱动整屏
         └─ TimelineRow（气泡/卡片/日期分隔符/失败行）
```

- `entries` 数组是**全量重建**的：每次拿到记录列表，`buildEntries` 按天分组、插入日期分隔符，**整体替换**旧数组。
- 没有「增量插入」概念：即使只有 1 条新记录，也是整列重建（ID 稳定后视觉无感，但结构如此）。
- 滚动规则（上一轮定）：冷启动瞬间定位底部；被动对齐（进页面/下拉刷新/回前台）只在用户已在底部时跟随、否则不拽；主动发送才动画跟随。

### 2.2 前端缓存四件套（现状）

| 存储 | 存什么 | 谁写 | 谁读 | 持久化？ |
|---|---|---|---|---|
| `LocalCache(.messages)` | **上一次** `get-messages` 全量响应的原始字节 | **只有** `loadHistory` 拉全量成功后写 | **只有** `loadHistory` 冷启动时读 | 是（Application Support 下 JSON 文件） |
| `ImageCache` | 图片，按 storage 路径为键（内存+磁盘） | 图片加载时 + `preloadRecentImages` 预载最近 15 张 | 图片渲染 | 磁盘在 Caches（系统可清，丢了能重下） |
| `PendingRetryStore` | **失败的**尝试（气泡+失败行，照片存 JPEG） | 发送失败时 | `loadHistory` 注入时间线 | 是（UserDefaults + Documents） |
| `OnboardingSeedStore` | onboarding 刚生成的卡（仅预设卡路径） | OnboardingView 完成时 | `loadHistory` 的 defer | **否（纯内存，一次性）** |

**关键空白**：**「生成成功的内容」没有任何本地落脚点**。成功路径只更新内存 `entries`，不写任何持久化。冷启动时本地快照永远比服务器旧「一步」。

### 2.3 后端现状（get-messages）

- **一次返回全量**：内部按 300 行一批循环读取、合并，**直到取完**，再整体返回给 App（`created_at` 升序）。
- 300 是内部读库步长，**不是**给客户端的限量——客户端拿到的永远是全部历史。
- 顺带为所有图片批量签发 1 小时访问链接。
- **无上限**：数据越多响应越大，平台对 Edge Function 响应体有大小上限（几 MB 量级），触顶时请求直接失败。
- 网络往返的实际耗时构成：匿名会话确认（可能含 token 刷新）+ **Edge Function 冷启动**（空闲被回收后首次调用，几秒级，是大头）+ 全量传输 + 图片签名。

### 2.4 冷启动完整时序（现状）

```
冷启动
 ├─ 有缓存：读 LocalCache → 渲染旧快照（快，现在不跳了）
 │              ↓ 同时
 │          网络全量对齐 → 整体替换（几秒后「新内容」才出现 ← 本次反馈的问题）
 └─ 无缓存（首启/刚走完 onboarding）：空屏 → 等网络全量（几秒）→ 内容出现
```

## 三、上一轮改动做了什么（已提交 `9d73a09` + `4a108ae`）

**全部是显示层**，共 4 处，对应「跳一下」的 4 个来源：

| # | 改动 | 解决的问题 |
|---|---|---|
| 1 | 日期分隔符 ID 由日期**确定性派生**（不再每次随机） | 缓存→网络替换瞬间，分隔符被 SwiftUI 判成「删旧插新」→ 整列重排闪烁 |
| 2 | `loadHistory` 全程标记「被动对齐」：仅在用户已在底部时跟随 | 进页面/下拉刷新/回前台时，正在翻历史的用户被拽回底部 |
| 3 | 时间线首次有内容时**无动画瞬间定位底部** | 冷启动「从顶部滑到底部」的多余滑动 |
| 4 | 被动跟随动画调至 0.15s | 新内容到达时跟随拖沓 |

顺带修：跨年同文案日期不再误并成一组。新增 5 个单测锁定，全量 220+ 全绿。
**没碰的**：数据从哪来、多快、有没有本地备份——即加载层原样未动。

## 四、体验问题清单（现象 → 根因 → 层面）

| 问题 | 状态 | 根因 | 层面 |
|---|---|---|---|
| P1 进页面「跳一下」 | ✅ 已修 | 分隔符随机 ID / 强制滚底动画 | 显示层 |
| P2 **新生成的内容冷启动要等几秒才可见** | ❌ 未修 | ①生成成功不落本地（§2.2 空白）②seed 注入排在网络往返之后（defer）③网络往返含 Edge 冷启动 | 加载层 |
| P3 数据量大后：全量拉取变慢、终将顶到平台响应上限 | ⏳ 未发生 | 全量一次返回、无分页（§2.3） | 加载层 |

豆包对比：生成结果直写本地数据库（本地为唯一事实来源），页面永远读本地 → 秒显，网络同步后台化。我们缺的正是「生成时刻写本地」这一步（P2 的根因①）。

## 五、方案分档（成本 × 效益）

### 短期 · 建议现在做（本工作树）

| 方案 | 内容 | 成本 | 解决 |
|---|---|---|---|
| **S1 生成即落本地** | onboarding 完成 / Tab1 发送成功时，把「气泡+卡片」**增量合并**进本地快照（`LocalCache.messages` 或独立增量文件）；冷启动先渲染本地、网络后台对齐 | 中低（一个垂直切片，含单测） | **P2 主解**：新内容冷启动 0 秒可见 |
| **S2 seed 注入提前** | `OnboardingSeedStore` 消费时机从 `loadHistory` 的 defer（网络之后）挪到**网络请求之前** | 极低（几行） | P2 的 onboarding 预设卡路径立即见效 |

S1 与 S2 有重叠：S1 把 seed 持久化后，S2 自然成为 S1 的子步骤。两者合起来 = 一个切片「生成结果本地直达」。

### 长期 · 数据量增长触发（暂不做）

| 方案 | 触发条件 | 成本 | 内容 |
|---|---|---|---|
| **L1 真客户端分页** | 历史上千行，或首次出现响应体过大报错 | 高（独立垂直切片） | 后端游标契约（接受 page/cursor 参数）；`TodayViewModel` 分页状态+页间去重；首屏最新一页、上滚到顶加载更早；分页的 loading/empty/error；`LocalCache` 分页缓存；顶部插入旧记录后的滚动位置保持。**后端 limit 只是其中一环** |
| **L2 本地数据库 SSOT（豆包式）** | L1 + S1 仍不够时再评估 | 最高（架构级） | SwiftData/SQLite 本地库，页面永远绑本地，网络只做后台同步 |

### 成本效益排序（推荐顺序）

1. **S1+S2**（低—中成本，直接治 P2）→ 2. **L1**（等数据量触发）→ 3. **L2**（观察再说）
