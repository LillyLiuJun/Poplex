## 0. 一句话目标（用户视角）

断网 / 弱网时打开 App，仍能看到我**之前加载过的**学习内容（Tab2 的素材、Tab1 的历史对话），而不是白屏或「加载失败」。

## 1. 产品哲学约束（L0）

- 兼容「用户内容是用户的」——断网不该让个人内容消失。
- 不与「服务器为正本」冲突：本地只是镜像，冲突时以服务器为准。
- 不与已有「乐观删除 + 4 秒撤销」冲突：删除必须同步落到本地缓存，否则会出现「幽灵素材」（服务器删了、本地又读出来）。乐观删除的数据前端不得展示。

## 2. 用户怎么用它（L2 交互 / 状态机）

- **触发**：进入 Tab2 / Tab1 时。
- **过程（stale-while-revalidate，先旧后新）**：
  1. 打开页面 → **先读本地缓存并立即渲染**（有缓存就不再是空白/骨架）。
  2. 同时后台向服务器请求最新数据。
  3. 请求成功 → 用新数据替换列表 + 覆盖本地缓存。
  4. 请求失败（断网）→ **保留本地内容继续展示**，不弹「加载失败」；仅用一个轻量「You're offline.」提示条告知。
- **各状态（CLAUDE.md 强制要求，逐个定义）**：
  - loading：**有缓存时不显示骨架**，直接显示旧内容后台刷新；**无缓存时**才显示骨架/ProgressView。
  - empty：本地无缓存且服务器返回空 → 现有空状态文案不变。
  - error：本地无缓存且请求失败 → 才显示现有「Failed to load, please retry」。**有缓存则永不进 error 态。**
  - offline（读）：有缓存 + 请求失败 → 显示内容 + 顶部「You're offline」提示条。
  - offline（写，仅 Tab1）：断网时用户发送/生成 → 请求失败 → 用户消息仍显示为气泡，下方挂「未发送，点击重试」，输入不丢失（方案 A）。

## 3. 数据三问（L3 —— 脊柱）

- **读**：本地缓存文件（新增）+ 现有三个端点 `get-materials` / `get-vocabs` / `get-messages`。
- **改 / 产生**：新增本地缓存文件（把已解码的 `[Material]` / `[MessageRecord]` 序列化落盘）；删除/撤销时同步改本地缓存。
- **这些数据现在存在吗？**
  - 服务器数据、解码模型（`Material`/`MessageRecord`）：**存在手边**（便宜）。
  - 图片本地缓存：**已存在**（`ImageCache` 内存+磁盘，见 `CachedRemoteImage.swift`）。
  - **文本 JSON 的本地持久化：不存在，需新造**（这是本切片唯一的新结构，是脊柱所在）。

## 4. 它长什么样（L6 视觉）

仅需一个新元素：**离线提示条**（一行，顶部或列表顶）。文案 `You're offline · showing saved content`。样式让 AI 先出，PM 看实物再否决。不新增其他 UI。

## 5. 边界与冲突

- 断网：见上，保留缓存、不报错。
- 空：本地无缓存 + 服务器空 → 空状态。
- 删除：乐观删除后**必须同步从本地缓存移除**；撤销恢复后重新写回。否则幽灵素材。
- 陈旧：本地可能比服务器旧；一旦联网刷新成功即覆盖，可接受（素材不可变，唯一变化是「新增」和「删除」，不会有内容级冲突）。
- 冲突仲裁：本地 vs 服务器不一致时，**永远服务器赢**（正本）。

## 6. 已定 vs 待定

**已定（铁律）**：服务器正本；永久缓存；用户删才清；不做离线生成；不设容量上限（v1）。

**待 PM 确认的默认值**（见下方六步检查「找洞」）：存储位置、v1 范围先做哪一处、离线提示条要不要做。

## 1. 复述

把「已生成内容离线可读」落成一套**可复用的本地读缓存**：读页面时先显示上次存的、再后台刷新；断网就一直显示上次存的、不报错；删除同步清本地。服务器永远是正本。

## 2. 找洞（三个必须 PM 拍板的点）

**洞 A —— 「一个共享库」在真实代码里不成立，需纠正。**
我们之前说「Tab1 和 Tab2 读同一个共享本地库」。但代码现实是：
- Tab1 的数据是 `MessageRecord`（聊天时间线，来自 `get-messages`）。
- Tab2 的数据是 `Material`（素材，来自 `get-materials`/`get-vocabs`），且 **Material 是服务器异步生成的，Tab1 生成对话的那一刻它还不存在**。
- 二者是**两个不同结构、两个不同端点**，不是一份数据。
- ⟹ 正确做法不是「一个共享库」，而是「**一套通用缓存机制，套用在两处**」。对你（PM）的结论不影响——目标「两个 Tab 都能离线看」不变，只是底层不是一个库而是一个可复用的工具。这点必须纠正，否则会按错误假设建结构。

**洞 B —— 存储位置影响「永久」承诺，需选。**
iOS 的 `.cachesDirectory`（图片现在存这）在**手机存储紧张时会被系统自动清空**——这跟「永久缓存」有轻微矛盾。两种存法：
- 文本 JSON 放 `.documentDirectory`（系统绝不自动清、体积极小）→ 保证永久。
- 图片继续放 `.cachesDirectory`（体积大、清了能重新下载）→ 可接受被清。
- **✅ PM 拍板**：文本 JSON → **Application Support 目录**（不被系统自动清、标记排除 iCloud 备份、无需权限）；图片 → 继续留 Caches（可被清、能重下）。修正了初版"Documents"的说法：Application Support 语义更贴——这是"服务器数据的本地镜像"，不是用户手动文档。

**洞 C —— v1 先做哪一处？（垂直切片，别一次全做）**

## 3. 分层

## 4. 定脊柱

新增一个通用组件 `LocalCache`：把**服务器返回的原始 JSON 字节（`Data`）**按 key 存到 **`.applicationSupportDirectory`** 的文件，文件标记「排除 iCloud 备份」。读取时把这份 `Data` 用**现有的同一个 decoder**解码——和网络回来的走完全相同的解析路径。

**为什么存原始 `Data` 而不是存解码后的对象**：`MessageRecord` 现在只有 `Decodable`（能解不能存），且带自定义解码逻辑。如果改存对象，得让它和内嵌的 `AICard` 等一整套类型都变成 `Encodable`，改动大、易错。存原始字节则**完全不碰任何现有模型**，写=把响应体落盘，读=把落盘字节喂给现成 decoder。这是本切片唯一的新代码，且对现有代码零侵入。

不改服务器、不改 `MessageRecord`/`Material` 模型。
