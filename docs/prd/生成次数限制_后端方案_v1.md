# 生成次数限制 · 后端方案 v1

> 前端（`UsageLimitButton` / `UsageLimitSheet` / 顶栏入口）已完成，本方案不改前端视觉。
> 目标：把「每天 5 次」变成服务端强制执行的真实限制。

---

## 一、读代码得到的现状

| 事实 | 位置 |
|---|---|
| 鉴权：`authenticateCaller` 走 `/auth/v1/user` 拿 `userId`，无 uid 返回 401 | `generate/index.ts` ~1055 |
| 幂等：`resolveCommittedRequest(requestId)`，命中已提交则**直接 200 返回**，不再调模型 | ~1082、~1107 |
| 落库：commit 阶段调 RPC，用户由 JWT 在服务端解析（`auth.uid()`），不接受 user_id 参数 | ~809 |
| 成功响应体：`successBody()`，含 `request_id` / `already_committed` | ~1003 |
| 目前**没有任何**计数、额度或拦截逻辑 | 全局 grep 无 |

幂等这一层是关键：**同一个 `requestId` 重试命中后会在调用模型之前就返回**，所以"失败→重试→成功只算一次"在架构上天然成立，后端不需要额外去重。

前端侧要改一处：`UsageLimitSheet` 的 `.task` 目前读的是 `LocalCache.messages` 并按 `role == "user"` 统计。按你的口径这是错的（滞后、且统计的是用户消息不是成功生成）。改为读服务端返回的用量。

## 二、核心设计决策

### 决策 1 · 在哪里扣次数

拆成两个动作，位置不同：

- **校验**：放在**调用模型之前**（幂等判断之后）。这样超限时不会产生模型费用。
- **扣减**：放在**提交成功之后**，与落库在同一个 RPC 事务里。

这样才同时满足两件事：成本被真正挡住，且只有成功才消耗。

> 并发缺口：两个请求同时读到「已用 4」都会放行，最终变成 6。对 5 次/天的量级可以接受。如果不接受，就把校验也挪进 RPC 与扣减合成一步 —— 但那样模型费用已经花掉了。**建议接受这个缺口。**

### 决策 2 · "每天 0 点"是谁的 0 点 ★ 已拍板 2026-09-02

> **拍板结果：客户端传本地时区偏移，服务端据此算当地日期**（第 3 刀实现）。
> 方案 B（档案存时区）暂不采用。下文 A/B 分析保留作为决策依据。

前端展示的是设备本地时间，后端必须和它一致，否则用户会看到「显示还剩 2 次但被拒」。两个方案：

**A · 客户端传本地日期（改动小）**
请求体加 `client_date`（`YYYY-MM-DD`，设备本地）。后端校验它与 UTC 当日相差不超过 ±1 天，然后用它作为计数分桶。
- 优点：改动最小，跨时区自动正确
- 缺点：可被伪造，但最多偏移一天 —— 极限情况下额度翻倍一次。5 次/天的量级可以接受

**B · 用户档案存时区偏移（更稳）**
onboarding 时把设备时区写进 `profiles`，后端按它算当地日期。
- 优点：不可伪造
- 缺点：要改 onboarding 和 profiles，用户飞到别的时区后需要更新

**建议先用 A**，把「日期从哪来」封装成一个函数，将来换 B 只改这一处。

### 决策 3 · 上限存在哪 ★ 已拍板 2026-09-02（两层设计，取代初版 default 5）

不要写成常量。上限**既要能整体调整，也要能按用户单独放宽**，做成「全局配置 + 用户覆盖」两层：

- `app_config` 全局配置表，初始写入 `('daily_generation_limit', '5')`。
  调全局 = `update app_config set value = '8' where key = 'daily_generation_limit'`，
  立即对所有未被单独设置的用户生效。
- `profiles.daily_generation_limit int null` —— **是 null，不是 default 5**。
  null = 跟随全局配置；非 null = 这个用户被单独设置过。
  只有这样才能区分「继承默认」和「特意放宽」：改全局值不会覆盖掉单独放宽的人。
  （如果写成 default 5，已有行会被写死成 5，改全局就必须全表 UPDATE，而那会把单独放宽的人一起覆盖掉。）
- 生效上限统一由 `get_effective_daily_generation_limit(user_id)` 计算（见 §三.3）：
  `coalesce(profiles 覆盖值, app_config 全局值)`，profiles 用 LEFT JOIN 语义——
  用户可能还没有 profiles 行，那种情况也要能落到全局值。

三种运维动作：

- 调全局：`update app_config set value = '8' where key = 'daily_generation_limit'`
- 给某人放宽：`update profiles set daily_generation_limit = 20 where id = ...`
- 撤销特殊额度：把那一列设回 null，自动回到全局值

## 三、要建的东西

### 1 · 迁移：计数表 + 全局配置表

```
generation_usage
  user_id      uuid    not null  references auth.users(id) on delete cascade
  usage_date   date    not null
  used_count   int     not null default 0  check (used_count >= 0)
  updated_at   timestamptz
  primary key (user_id, usage_date)
```

- 启用 RLS，只允许本人 select，写入只走 SECURITY DEFINER 的 RPC（无任何写策略）
- 按 `usage_date` 建索引，便于将来清理历史
- ★ `on delete cascade` 是必须的：`delete-account` 删完业务表后调 `auth.admin.deleteUser`，
  靠级联清掉 profiles（同样写法）；不带 cascade 会让删号因外键冲突失败

```
app_config
  key         text    primary key
  value       jsonb   not null
  updated_at  timestamptz
```

- 初始写入：`('daily_generation_limit', '5')`
- RLS：authenticated 可读；写入不开放给客户端
- 调整全局上限 = 改这一行，立即对所有未被单独设置的用户生效

### 2 · 迁移：`profiles` 加列

```
alter table profiles
  add column daily_generation_limit int;  -- null，语义见决策 3
```

★ profiles 对客户端可写（自愈 upsert + 本人行 UPDATE 策略），所以新列必须保护——
否则任何登录用户都能把自己的额度改大。第一版方案用列级 REVOKE，**实测无效**：
PostgreSQL 的列级 ACL 只能在表级授权之上「加」权限、不能「减」（表级授权是 CI
权限契约要求的；撤销列级权限后 `attacl` 仍为空、更新照常成功）。
最终改用**保护触发器** `guard_daily_generation_limit_override()`（第 1 刀已落地）：
BEFORE INSERT OR UPDATE OF 该列时，非 postgres/service_role 的写入被静默剥离
（INSERT 置 NULL、UPDATE 还原原值）。选「静默剥离」而非「报错拒绝」：即使将来某个
客户端版本误把该列放进自愈 upsert 的 payload，整行保存也不会被拖垮，只有这一列由服务器控制。
放宽额度是运维动作，永远不是客户端动作。

### 3 · RPC：额度查询（两个入口，权限模型不同）

只读，都返回 `used_count`、`limit`（生效上限）、`allowed`。生效上限统一走
`get_effective_daily_generation_limit(p_user_id)`（SECURITY DEFINER，仅 service_role 可调）：

```
effective_limit = coalesce(
    profiles.daily_generation_limit,
    (select value::int from app_config where key = 'daily_generation_limit')
)
```

- **给前端**：`check_generation_quota(p_usage_date date)`
  不接受 user_id 参数，内部用 `auth.uid()`。★ 若允许传 user_id，任何登录用户都能查别人的用量。
- **给 Edge Function**：`check_generation_quota_for_user(p_user_id, p_usage_date)`
  仅 service_role 可执行，Edge 用 service key 经 RPC 调用。

两个入口都返回：`used_count`、`limit`（effective_limit）、`allowed`。

> **响应形状注意（2026-09-02 线上事故教训）**：两个 RPC 都是 `RETURNS TABLE`，
> PostgREST 对这类函数默认回 JSON **数组**（单行也是数组）。Edge 侧调用带
> `Accept: application/vnd.pgrst.object+json` 头取单对象、解析器同时容忍两种形状；
> 第 4 刀前端调 `check_generation_quota` 同样要 `.single()`（或同样的 Accept 头），
> 不要按裸对象解析——本次事故就是 Deno 假响应用了对象形状、真实 HTTP 回数组，
> 线上每次预检 502、app 把 502 显示成「No connection」。

### 4 · 扣减：并入现有的 commit RPC

在已有的落库 RPC 里，事务内加一步：

```
insert into generation_usage (user_id, usage_date, used_count)
values (p_user_id, p_usage_date, 1)
on conflict (user_id, usage_date)
do update set used_count = generation_usage.used_count + 1,
              updated_at = now();
```

**必须在同一个事务里**，落库回滚则计数一并回滚。

★ 幂等路径（`already_committed = true`）**不得**走到这里 —— 那条路在函数早期就返回了，天然不会执行到扣减，但改动时要确认这一点没被破坏。

**第 2 刀已落地（迁移 `20260902020000`），实际实现如下：**

- **扣减动作封装为 `consume_generation_quota(p_usage_date date)`**（SECURITY DEFINER）：
  `commit_generated_content` 是 SECURITY INVOKER，而 `generation_usage` 对客户端无任何
  写策略、无写授权 → 扣减 SQL 若直接写在 commit RPC 函数体里，会以登录用户身份执行
  被 RLS 拒绝。helper 内部用 `auth.uid()` 解析用户——**不设 user_id 参数**，客户端
  就算直接调它也只能推进自己的行（构造上自限，无法滥用）。authenticated 有 EXECUTE
  （commit RPC 以登录用户身份调用它），表级写权仍只属于函数 owner。
- **commit RPC 以 6 参数重载的形式新增两个入参**（原 4 参版本被 DROP，见下）：
  - `p_usage_date date DEFAULT NULL` —— 由调用方在入口算好后传下。
    ★ 不得在 RPC 内部用 now() 现算：否则前置校验在 23:59:59 算的是昨天、落库在
    00:00:02 扣到今天，两个桶对不上，用户当天凭空多出一次额度。
    旧调用方（不传日期的）→ NULL → 不计入，行为向后兼容。
  - `p_count_usage boolean DEFAULT true` —— false 时跳过扣减（onboarding）。
    两个参数都有默认值，不打断存量调用方（已全量排查：SQL 侧 0 个调用方；
    save-preset-card 走 PostgREST 按参数名传 4 个必填参数，靠默认值解析）。
- **DROP 旧 4 参签名而非并存**：两个重载并存会让所有 4 位置参数调用报
  42725「function is not unique」（带默认值的 6 参签名同样是候选），且 PostgREST
  对 save-preset-card 的 4 个命名参数选哪个重载会不确定。删掉后，旧调用统一经
  6 参默认值解析、无歧义。
- **扣减放在事务内、幂等早期返回之后**：`already_committed` 路径在函数开头就
  RETURN，能走到扣减的必然是新落库；与 INSERT 同事务，落库回滚则计数一并回滚。
  第 2 刀测试明确断言「幂等重试不消耗次数」。
- **豁免判定用服务端事实，不用客户端 source 字符串**（见 §四.2）：
  扣减成立的条件为 `COALESCE(p_count_usage, true) AND p_usage_date IS NOT NULL
  AND NOT (v_source = 'onboarding' AND COALESCE(v_not_yet_completed, false))`——
  「还没完成 onboarding」由 RPC 现查 `profiles.onboarding_completed_at` 得到。
  第 3 刀起 Edge 侧也用同一服务端事实自行判定，豁免时传 `p_count_usage = false`
  （见 §三.5 之 3.2）；RPC 内部仍独立再查一遍（防御纵深），伪造 source 无效。

### 5 · Edge Function 改动（`generate/index.ts`）★ 第 3 刀已落地

插入位置：**幂等判断之后、调用 Gemini 之前**（`missing_input` 等输入校验仍在前，
非法请求按合法性拒绝而不是按额度拒绝）。

**3.1 日期解析（单一函数 `resolveUsageContext`，`usageContext.ts`）**

- body 新增可选字段 `utc_offset_minutes`（整数，设备当前 UTC 偏移分钟数）。
  ★ 不让客户端直接传日期：传日期意味着客户端可以在 D-1 / D / D+1 三个桶里
  任选，轮着用能拿到三倍额度；传偏移量并校验范围后，可选桶只剩两个。
- 校验为整数且在 -720 ~ +840（真实时区范围），缺失/非法回退 UTC 当日
  （旧客户端正常工作）。
- 用偏移把请求时刻换算成当地日期 → `usageDate`；同时算出 `resets_at`
  （下一个当地 0 点的 ISO8601，含偏移后缀如 `2026-09-03T00:00:00+08:00`）。
- ★ 全部日期逻辑只在这一个函数里；将来改「按档案时区」只动这一处。
- 已知残留风险（已接受）：跨零点改设备时区可落到相邻桶，最多约两倍额度。

**3.2 onboarding 豁免 · 服务端判定**

- body 的 `source` 只作辅助信号；判定 = `source='onboarding'` **且**
  `profiles.onboarding_completed_at IS NULL`（Edge 用 service key 读 profile，
  与 commit RPC 的豁免门同口径——profile 行缺失按「不免」处理）。
- 一个判定结果同时驱动「跳过前置校验」与 `p_count_usage = !exempt`，
  不能各算各的。RPC 内部仍按自己的服务端判据再查一遍（防御纵深）。

**3.3 校验与失败模式**

- 豁免关闭时调 `check_generation_quota_for_user(p_user_id, p_usage_date)`
  （service key，仅 service_role 可执行）。
- `allowed == false` → 429；查询失败 → 502 `quota_check_unavailable`
  （fail closed：额度是硬限制，宁可本次失败也不静默放行）。
- 服务端分桶日期与落库共用同一取值瞬间：`lockedNowMs` 一次取值同时喂给
  日期解析与 user 行时间戳，校验与扣减不会跨桶。

**3.4 响应契约**

超限（429）：

```json
{
  "error": "daily_limit_reached",
  "used": 5,
  "limit": 5,
  "resets_at": "2026-09-03T00:00:00+08:00"
}
```

`successBody()` 追加一个字段，让前端每次生成后都能拿到最新用量（幂等命中
的响应同样携带；读取失败只省略该字段、绝不拖垮成功响应——否则客户端会
重试并卡死在幂等路径上）：

```json
"usage": { "used": 3, "limit": 5, "resets_at": "..." }
```

### 6 · 前端改动（最小）

- `UsageLimitSheet` 的 `.task`：不再统计 `LocalCache.messages`，改为调 `check_generation_quota`
- 每次 generate 请求带上 `utc_offset_minutes`（`TimeZone.current.secondsFromGMT() / 60`）；不带则回退 UTC 当日——功能可用，但重置时刻是 UTC 0 点而非设备当地 0 点
- 每次 generate 成功后，用响应里的 `usage` 更新本地展示
- 收到 429 `daily_limit_reached` 时，展示已有的「达标态」文案与 feedback 入口 —— UI 已经做好了，只需接上错误码
- **不要**在前端做拦截判断。前端只展示，服务端说了算

## 四、需要注意的边界

1. **旧客户端**：不传 `utc_offset_minutes` 的版本要能正常工作 —— 回退到 UTC 当日（第 3 刀已实现并测试）
2. **onboarding 路径**：`generate` 也服务 onboarding（代码里有 onboarding cleanup 分支）。onboarding 的生成不计入额度——否则新用户第一次用就消耗了当天的额度。
   **★ 豁免判定必须用服务端事实（第 2 刀已实现）**：客户端可伪造 `source`，所以不能
   只看 body 里的 `source` 字符串。第 2 刀的判定 = `source='onboarding'` **且**
   `profiles.onboarding_completed_at IS NULL`（RPC 在事务内现查）。完成过 onboarding
   的用户即使伪造 source 也会被计数。已知取舍：**永不完成 onboarding 的用户一直豁免**
   ——接受，因为 onboarding 流程本身就是真实使用的闸门，走不完流程的用户成不了正常用户。
   Edge 侧（第 3 刀起）用同一判据自行判定，豁免时传 `p_count_usage = false`；RPC 内部仍独立再查（防御纵深）。
3. **图片重试**：图片已上传到 Storage 但 commit 失败的场景，重试复用同一 `requestId`，走幂等路径，不重复扣减 —— 与现有逻辑一致
4. **RLS 与权限测试**：项目的 `docs/engineering/CI.md` 里有数据库权限测试的维护要求，新表要补上对应用例
