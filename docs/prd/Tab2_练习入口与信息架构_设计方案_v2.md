## 一、Tab2 的定位翻转

`CLAUDE.md` 已经写死：**Tab2 exists to make the user practise and grow.** 但现在的实现是一个词库，练习入口在第四层（Tab2 → 词 → 场景 → 开口）。定位和结构对不上。

翻转后：

```
Tab2 首屏     = 开口的入口（场景 + chat），整屏就这一件事
对话页        = Tab2 的子页，从首屏一层直达
Your words    = 推迟。定位改为"记单词工具"，场景是它的记忆辅助
```

### 1.0 本轮范围决定（产品负责人拍板）

**Tab2 首屏只放 chat 入口和场景，`Your words` 整块推迟。** 词库的定位从"练习清单"改为**记单词功能**，场景只是让用户更好记忆。

> ⚠️ **推迟的是界面，不是账本。** 记账链路（Slice 1 已上线）必须继续跑，且是对话页的**前置**而非可推迟项——三处硬依赖：
> - `§6.2.5 实时推荐` 要从账本挑"你手头有这些能用上"，没有账本 agent 就没有弹药；
> - `§6.3.3 breakthrough`（`spoken_count` 0→1）是**北极星指标**，靠 `lexicon_entries` 写；
> - `§7 成长层`只读这三张表。
>
> 如果把"Your words 以后再整"理解成记账也暂停，对话页本身就废了。

> ⚠️ **这是对上游的实质修改，需回写文档**：`PRD_v2 §5.5` 现在把词汇账本定义为"练习清单"，`CLAUDE.md` 写 "Tab2 is word-centred"。改为：**账本是记账与记忆层（面向用户的形态是记单词工具，MVP 暂不做界面）；练习清单的角色由场景承担。**

对话页仍然是 Tab2 的子页、仍然不是默认屏（符合 `整体架构_两个Tab与对话页_v1.md`），只是从"藏在第四层"变成"首屏可发起"。

### 1.05 Tab2 解锁制（已拍板）

**Tab2 不做空状态。** 素材不够时整个 Tab 是锁定态；首次捕获的引导责任归 **Tab0 onboarding**，不由 Tab2 兜。

#### 只有一条规则：**每个分类各自在 20 词时解锁**

Tab2 整体的"开门"不是第二条规则，**它是这条规则的副产品**——第一个分类达标的那一刻，Tab2 就有东西可展示了（再叠加一个全局门槛：Tab1 ≥5 次输入）。

```
分类 A  20/20  → 已开，出现在首屏卡片区
分类 B  13/20  → 未开，出现在底部「Still filling up」
分类 C   6/20  → 未开，同上
分类 D   0      → 不显示（见下）
```

三条推论：

- **解锁不是一次性事件**，是一个持续发生的过程。用户永远看得到"再拍点什么会长出新的"，成长循环不断。
- **待解锁页 = 首屏底部「Still filling up」区，是同一个组件在两个位置**。Tab2 未开门时它占满整页；开门后它降到底部、变灰、折叠。**实现上只做一个组件**，也天然保证两处的口径一致。
- **词数为 0 的分类不显示**。12 类里大多数对某个用户是空的，全列出来是噪音。至少有 1 个词才进「Still filling up」。

#### 解锁条件（两个都要满足）

| 条件 | 口径 |
|---|---|
| **某单个分类下 ≥20 个有效词汇** | 去重后的 `lexicon_entries`（同 lemma 只算一次），`status='active'`，按其 occurrences 的 `scene_category` 归属。**查词来的词条同样计入**（§1.05-3：词卡也判分类）；判不出分类而留 null 的不计入任何分类 |
| **Tab1 累计 ≥5 次输入** | **所有输入类型都算**，含查词卡 |

- **现成查询**：`get_lexicon_scenes` 已经是 `COUNT(DISTINCT entry_id) GROUP BY scene_category` 且已过滤 `active`，直接拿来判即可，不用新写统计。
- **解锁后永不回锁**，即使用户之后删掉素材。回锁是惩罚。

#### 为什么是这两条

- **按词汇数而不是素材条数**：三个短句可能只出 4 个词，按"3 条素材"就放行了，进去发现没东西可聊。**词汇量直接量的是 agent 手上有多少弹药**，素材条数只是它的代理指标。
- **20 的推算**：一场 10 分钟对话，agent 大约回推 5–8 个他的词（§6.2.5），手上有 20 个才有得挑、不会翻来覆去推同几个。
- **限定在单个分类内**：20 个词摊在 5 个分类里，每张卡都很薄，开场那句"是会议室那件还是客户电话"没得选——正是要避免的情况。
- **≥5 次输入是防单条素材通关**：一篇长文可能一次就出 20 个词。加这条防止"一篇文章解锁整个 Tab2"。
  > ⚠️ 因为查词卡也计入 5 次，仍存在"1 篇长文 + 4 次查词"就解锁的边界情况。已知并接受。

#### ⚠️ 阈值与抽词供给量是绑死的

`PRD §7.3.1` 已警告抽词可能抽得太少。**如果抽词偏保守，20 这个门槛会意外地变严**——用户拍了很多却解锁不了，而且完全不知道为什么。**两个数必须一起调，不能分开定。**
上线前要拿真实账号验一次：到 20 个词时跑一场测试对话，看是否还显得空。显得空就调数，不是调文案。

#### 待解锁页面

##### 1. 两个条件都要在页面上

解锁是「20 词 **且** 5 次输入」，页面就必须同时呈现两者，否则用户会以为只差词、拍够了却仍没开，无从解释。

```
INPUTS                                    3 of 5
▓▓▓▓▓▓▓▓▓▓▓▓░░░░░░░░

AREAS                        （任一满 20 即可）
Work & study                             14 of 20
▓▓▓▓▓▓▓▓▓▓▓▓▓▓░░░░░░
set up · run late · agenda · +11

Food                                      6 of 20
▓▓▓▓▓░░░░░░░░░░░░░░░
marinate · simmer · +4
```

- **输入次数一条全局**（它本来就是全局条件）；**词汇量每个分类各一条**（它是"任一满足"）。两种条件的形状不同，视觉上也要不同。
- 分类条里**最接近的用品牌色，其余灰色**；副标由数据算出（"再拍一件工作相关的就开了"），不写死。
- **不存在"我做了事但进度没动"**：任何一次输入必定推进输入条；有场景的输入还会推进某个分类条。

##### 2. 分类可展开，全部词都要能看到

> **原先写的"露 3 个词 + `+11`"是错的**——剩下 11 个仍然不可见，那不是"让不可见变可见"，那是勾一下就收手。

**分类行可点击展开**（就地展开，不跳页）：

```
Work & study                             14 of 20   ⌄
set up · run late · agenda · +11
   ↓ 点开
Work & study                             14 of 20   ⌃
  set up          phr.    📷 Meeting room, 8:40am
  run late        phr.    📷 Meeting room, 8:40am
  agenda                  📷 Meeting room, 8:40am
  invoice                 🔍 looked up
  marinate                ✏️ typed
  … 全部 14 个
```

- **收起态**保留 3 个词做预览，**展开态给全部**。收起态的 3 个取该分类下**最近入账的**，让他能对上"这是我前天拍的那张"。
- **每个词标出来源**，因为一个分类里本来就装着三种粒度的东西（`word` / `sentence` / `passage`）——展开这一层同时也让"分类是个容器"这件事变得可见。
- 这不是把 `Your words` 提前做了：**只读、不排序、不筛选、不进详情页**。它只回答一个问题——"这 14 个到底是哪 14 个"。

**为什么必须做到这一步**：`Your words` 推迟后，用户在整个产品里没有任何地方能看到自己积累了什么。进度条上的数字若无法查证，它就只是一个要求，不是一份资产。**能翻开看，数字才变成"我攒下的东西"。**

顺带还有个免费收益：抽词抽得离谱时用户会立刻发现——这是唯一一条不用埋点就能拿到的抽词质量反馈通道。

###### 词表每一行的标签怎么取（已核对代码，无需新字段）

右侧那个"它从哪来"的标签，直接用 **`lexicon_occurrences.sample_sentence`**——它已经在流水行上，**不用 join `materials`**（`generate/index.ts:706` 写入）。

> **曾经考虑过给「时刻」新增一个标题字段，结论是不需要。** `sample_sentence` 就够，且更精确——它是**这个词所在的那句**，而不是整张卡的名字。

| 输入形态 | 标签取什么 |
|---|---|
| 纯文字 sentence | `sample_sentence`（截断） |
| 图片 + 文字 | **小缩略图** + `sample_sentence`（截断） |
| 纯图片 | **小缩略图** + `sample_sentence`（此时它是 AI 对照片生成的英文描述） |
| passage | `sample_sentence`（**修完缺口 7 后**才是所在那一行；未修前是整篇，见 §8 缺口 7） |
| 查词（`material_type='vocabulary'`） | `looked up` |
| 对话（`source_type='dialogue'`） | 🎤 + `sample_sentence`（他实际说出来那句） |
| 连 `sample_sentence` 都为空 | 只留缩略图；图也没有则整个标签不渲染 |

**截断规则**（必须有：prompt 定义 sentence 的上限是 **300 字符**，不是"一句短话"）：

- 单行，全角约 18 字 / 拉丁约 30 字，尾部省略号。
- **优先在标点处断**，断不了再硬截。这一步很便宜，但可读性差别很大。

**一个连带的好处**：`sample_sentence` 取值优先 `target_expression`，所以它**基本都是英文**。于是词表里不会出现产品侧的中文，语言边界问题自动消失，还多一处目标语言曝光。代价是回忆钩子比用户自己的母语原句弱——但**有图的那些由缩略图补上了**，只有纯文字输入会弱一点。

##### 3. 查词计入分类词汇量（已拍板）

**词卡也判分类**，其抽出的词条照常计入该分类的词汇量。

- **实现**：在 `generate` 现有调用里顺带判（不新增调用）；**判不准就留 null**，null 的词不计入任何分类。
- **要改的**：Stage 2 现在对词卡显式跳过分类（`词卡无场景，category 为 null`），以及 `PRD §5.2.2`「孤立词情境为空」。
- **为什么可以接受判错**：错分类只影响这个词落在哪个桶里；而借锚时 agent 本来就是从 2–3 个候选情境里自己挑（§3.4），能挑掉不搭的那个。相比之下"用户查了 10 个词、产品毫无反应"的代价高得多。
- **连带好处**：孤立词在"只剩分类卡"的版面里有了落脚点，不用再单开一个"没地方去的词"区块。

##### 4. 语气、动效、首次解锁的价值感

**语气**：标题用 `Almost there` 一类，**把原因归给产品**（"东西够了才聊得起来"），不归给用户（"你还没攒够"）。

**动效**（已定：不弹窗，但要有动效）：

- 进入 Tab2 时，锁定态先短暂可见 → 进度条走满 → 锁图标淡出 → 第一张分类卡淡入并轻微上移落位。
- **一次性、≤0.6s、无粒子/彩带/音效**。用 `AppTheme.Motion` 现有 token，不新造曲线。
- 只在**首次**解锁播放；之后每个分类各自达标时不再播（否则变成刷分反馈）。
- *为什么不弹窗*：弹窗要用户按一下确认"我得到了奖励"，那是把游戏化框架坐实。动效只让变化被看见，不索取动作。

**价值感（已定：首次解锁要给用户价值感）**

动效只解决"被看见"，解决不了"值当"。价值感靠**首次专属的卡片文案**承载，不靠额外的屏或弹窗：

```
Work & study
You've got enough here to talk about it now.        ← 仅首次出现
Morning at the office · Client calls · Meeting room
set up · run late · agenda · +17
                                              [ 🎤 ]
```

三条规则：

1. **说能力，不说奖励。** `You've got enough here to talk about it now.`（你现在能聊它了），不是 `Unlocked!` / `You earned it` / 任何计分口吻。这是 §7「质变叙事，不用进度条不用打分」在解锁时刻的落点。
2. **价值指向他攒的东西，不指向产品的功能。** 主语是 `You've got`——被解锁的是**他的素材到了可用的量**，不是"你获得了一个新功能"。
3. **只出现这一次**，之后该卡恢复常规副标。

> **真正的价值感来自第一场对话，不来自解锁那一屏。** 所以这一屏唯一的任务是把人送进对话——不要在这里加"看看你都攒了什么"的回顾页，那会把人留在原地。

### 1.1 注意力预算（可当验收标准用）

| 层 | 用户在干什么 | 预算 |
|---|---|---|
| Tab2 首屏 | 挑一个方向 | 5–10 秒 |
| 词（查阅） | 认领"是这个词" | 1–3 秒 |
| 场景页 | 决定练不练 | 10–20 秒 |
| 对话页 | 练 | 全部 |

> **前三层加起来的注意力，应少于对话页的五分之一。**
> 反向判据：如果用户在 Tab2 里逛得津津有味、十分钟一次没开口，Tab2 就是失败的——它把自己变成了目的地。

## 二、场景的三层模型

"场景"其实是三个不同的东西。**先讲数据层面它们各自是什么、从哪来**，再讲各自派什么用场。

### 2.0 数据层面：三层分别是什么

| 层 | 数据上它到底是什么 | 现在有吗 | 内容长什么样 |
|---|---|---|---|
| **分类** | `materials.scene_category`，**12 个固定枚举**（家庭与人际 / 工作与学业 / 饮食 …）。由 `generate` 的 Stage 2 判定后写回；`lexicon_occurrences` 上冗余存一份 | ✅ 字段有，**但判定作业未上线**，所以线上全是「其他」 | 一个枚举值 |
| **子场景** | 一个**自由文本细标签**（"做晚饭""等公交"），描述这次捕获具体在干什么 | ❌ **没有这个字段**，要新增 `lexicon_occurrences.scene_detail text` | 一个短语，模型抽词时顺带输出 |
| **时刻** | **一条 `materials` 行**（`material_type='scene'`，即 granularity 为 sentence / passage）。`lexicon_occurrences.source_id` 指向它 | ✅ 已存在，不是新概念 | `raw_content` jsonb：原句、英文、key phrases、`learnable_units`；照片输入还有 `messages.image_url` |

**三层的包含关系（以及词挂在哪）：**

```
分类  工作与学业                          ← materials.scene_category
 ├── 子场景  晨会前                        ← occurrence.scene_detail（新增）
 │     ├── 时刻  7/26 会议室那张照片        ← materials 一行
 │     │     └── 词  set up / run late     ← lexicon_entries ← occurrences
 │     └── 时刻  7/19 桌子那条
 └── 词  invoice（查词来的，无子场景无时刻）  ← 词卡也判分类后直接挂在分类下
```

- **词永远通过 occurrence 挂上去**，occurrence 上同时带着分类、子场景、时刻三个坐标。
- **查词来的词只有分类坐标**，另外两个为空——这就是它在 §1.05-3 里"直接挂在分类下"的数据原因。
- 一个**子场景 = 多个时刻共享同一个（归并后的）`scene_detail` 值**。这也是"反复出现"能被算出来的原因：`COUNT(DISTINCT source_id) GROUP BY scene_detail`。

#### 2.0.1 那 word 粒度的素材呢（回答提问）

**它也是 `materials` 的一行，只是它不是"时刻"。** 表里两类素材，`material_type` 已经把它们分开了（`generate/index.ts` 第 595–609 行）：

| granularity | material_type | 是"时刻"吗 | 有图吗 | 在三层模型里的位置 |
|---|---|---|---|---|
| `sentence` / `passage` | `scene` | ✅ 是 | 可能有（照片输入） | 分类 → 子场景 → **时刻** |
| `word` | `vocabulary` | ❌ **不是** | 无（查词是打字来的） | 分类 → **词**（跳过中间两层） |

所以准确的说法是：**"时刻"只覆盖 sentence / passage 那一半。** word 素材不是三层里的任何一层，它是**挂在分类下的第四种东西**——一个没有情境的词。

这也解释了为什么它需要 §1.05-3 那个决定：不给词卡判分类的话，它连唯一那根绳子都没有，会从整棵树上掉下去。

### 2.1 各层派什么用场（已按拍板 8 更正）

> ⚠️ **本节原先写的是"练习单元必须是子场景"，已作废。**
> 后续拍板：**练习入口 = 大分类**（拍板 8），收窄发生在对话里。以下是更正后的分工。

| 层 | 用场 |
|---|---|
| **分类** | **练习入口**。首屏的卡就是它，一张卡 = 一个分类 = 一次对话的起点 |
| **子场景** | 两处：①分类卡的**描述行**（告诉用户这张卡里装着什么）；②进对话后 agent **让用户收窄的选项**（"是晨会那件，还是客户电话？"） |
| **时刻** | **seed 素材**。用户选定某个子场景后，agent 真正读的是它下面那几条时刻的 `raw_content`；也是记忆锚点（那张照片、那句原话） |

**为什么入口不是子场景**：入口越细，用户要挑的次数越多。放在分类这一层，用户只做一次粗选，剩下的收窄用嘴完成——**而"回答哪一个"本身就是一次最低门槛的开口**（见拍板 8）。

**那"反复出现"还有用吗**：有，但换了位置。它不再决定"能不能当入口"，而是决定**子场景在描述行里的排序**、以及 **agent 优先拿哪几个让用户选**。用户反复回去的地方，仍然是他更想聊的地方。

### 2.2 「其他」泛滥不是子场景解决的（回答提问）

**不是。这两件事互相独立。**

- 「其他」泛滥的原因是**分类判定作业没上线**，所有素材落在默认值。**修它的办法是把那个作业部署上线**，跟子场景没关系。
- 子场景是**另一个字段**，解决的是另一个问题：分类太粗，卡片描述行和对话收窄需要更细的话题名。

> 顺带保留一条更正记录：本节原先推断「其他」泛滥是因为"12 个固定桶形状不对"，并据此得出"细标签比粗分类稳"。**那个论证是错的**——归因错了。子场景该做的理由只剩 §2.1 那一条（描述行和收窄需要更细的粒度），分类本身没有被证伪。

### 2.3 子场景怎么产生

**MVP：模型标注。** 抽词那次调用里顺带让模型输出一个细标签（同一次调用，零额外成本），写进 `lexicon_occurrences.scene_detail`。

产生之后有一步**归并**：模型今天写"做晚饭"、明天写"做饭"、后天写"晚餐准备"，它们其实是同一个子场景。MVP 用字符串近似合并（阈值见 §十 待定 5），归并后才拿去算"出现了几次"。

> 关于"共现聚类"这条备选路径，见文末**附录 A**。它不影响本节结论。

#### 2.3.1 名字不稳怎么解决：生成后、写入前，先跟已有标签比一次

**两步，不是一步：**

```
第 1 步  抽词调用照常跑，模型自由输出一个细标签      → "做晚饭"
第 2 步  写入前，拿它跟该用户这个分类下的已有标签比一次
           已有：["做饭", "等公交"]
           判定：「做晚饭」≈「做饭」  → 沿用「做饭」
           写进 occurrence 的是「做饭」，不是「做晚饭」
```

**关键：比较发生在写入之前，所以旧数据一行都不用动。** 归一化在入账那一刻完成，流水账"只增不改"的原则不受影响。

**为什么是两步而不是把候选塞进抽词 prompt**：抽词 prompt **保持不变**。不用按用户拼装候选列表，请求内容稳定、可缓存、好测；比较这一步单独跑，出问题也好定位是哪一步错了。

**第 2 步怎么比**：候选一般只有 5–20 个，一次轻量调用即可（"这个新标签和以下哪个是同一件事？没有就答 NONE"）。不要用字符串相似度——它判不出「做晚饭」≈「做饭」，更判不出「晚餐准备」≈「做饭」。

**仍然保留一个兜底的合并作业**：比较那步偶尔会漏。做成可手动触发的脚本，不做 UI——与 `PRD §5.3.1` 已有的补账 / 对账作业放一起。

#### 2.3.2 粒度怎么定义（这是这一层真正的难点）

太粗 = 和分类重复（"工作"）；太细 = 每次捕获一个新标签、永不重复，**"反复出现"这个信号直接死掉**，而它正是子场景排序和 agent 选题的依据。

**给模型的判据（一句话，可直接写进 prompt）：**

> **子场景 = 一个会重复发生的日常活动。** 检验方法：把这个标签挪到下个月另一次捕获上，还说得通吗？说得通才写。

**不要用"粗 / 细"这种形容词给模型下指令**——那只给了方向没给标准，模型会一路粗到「日常」。用下面两条可机械检验的规则，两种碎片化各堵一种。

##### 规则 1 · 必须是完整活动，不能是活动里的一个环节

> **检验：这件事有没有开头和结尾？**

| 例 | 判定 | 说明 |
|---|---|---|
| `通勤` | ✅ | 有（出门 → 到达） |
| `等公交` | ❌ | 没有，它只是通勤中间的一小段 → 往上取 `通勤` |

`等公交` 属于**时刻**那一层：

```
出行交通（分类）
└── 通勤（子场景）
      ├── 等公交那次（时刻）
      ├── 地铁挤爆那次（时刻）
      └── 打车迟到那次（时刻）
```

##### 规则 2 · 是完整活动但带修饰词的，把修饰词去掉

> **检验：去掉某个词之后标签还成立吗？成立就去掉，去到不能再去。**

| 例 | 判定 |
|---|---|
| `做晚饭` | ❌ 去掉"晚" → `做饭` 仍成立 → 用 `做饭` |
| `等公交` | 去掉"公交" → `等` 不成立 → 但它被规则 1 拦下了 |
| `周二晚上做番茄炒蛋` | ❌ 日期 + 时段 + 一次性具体物，全去掉 → `做饭` |

**去到什么时候停**（上界，防止太粗）：

- 再去就不指向一个具体活动了（`做饭` → `吃` ❌）
- 或者已经接近分类名本身（饮食 → `吃饭` ❌）

**两条一起用**：是片段 → 往上找完整活动；是完整活动但带修饰 → 去修饰词。

##### ⚠️ 不允许返回 null

**模型必须永远给出一个标签。**

*为什么*（本项目自己的前车之鉴）：**`scene_category` 允许落到「其他」这个默认值，结果线上几乎全部落在了「其他」。** 给模型留逃生口，它就会一直走逃生口。

##### 用锚点例子校准，不用形容词

每个分类预置 **4–8 个示范子场景**，作为 few-shot 锚点（**不是白名单**，模型仍可新建），让新标签对齐同一高度。

```
饮食       做饭 · 外食 · 买咖啡 · 点外卖
出行交通   通勤 · 出门办事 · 旅行
工作与学业 开会 · 写东西 · 和同事聊
```

这是校准主观刻度最有效的办法——**用例子钉高度，不用形容词描述高度**。它和 §2.3.1 的"生成后比较"天然配合：比较那一步本来就要拿已有标签，锚点例子就是初始的那一批。

> ⏳ 12 个分类的锚点例子需要有人写一遍，尚未起草。

**可观测的健康指标**（用来判断粒度调对了没）：

> **活跃用户平均每个分类下的子场景数应在 5–12 之间。**
> 长期低于 3 → 太粗，和分类没区别；长期高于 15 → 太细，去看是不是日期和具体物没排除干净。

**还有一条自净机制**：只出现过 1 次的子场景**不进分类卡描述行、也不进对话的收窄选项**，只有出现 ≥2 次才浮出来。于是偶发的坏标签**不需要删也不会被看见**——它自己沉底。

### 2.4b Hero 卡：用他自己的原话，提问挪到点击之后

> ⚠️ **本节推翻上一版。** 上一版把 agent 的开场问题印在卡上，并写了"卡上那句就是对话第一轮"。**已作废**，原因见下。

#### 为什么把问题从卡上拿掉

| 理由 | 说明 |
|---|---|
| **索取感** | 用户打开 Tab2 时处在"随便看看"的松弛状态。一个问号怼上来，哪怕问得温柔，潜意识里也是在**索取答案**——浏览瞬间变成被提问 |
| **必然过期** | 印在卡上就必须提前生成 + 缓存。"昨天那个会议室"三周后还挂着；要修就得再加时间衰减和刷新策略 |
| **生成质量** | 提前生成时拿不到点击那一刻的上下文，翻车概率更高；而一句不搭调的问句破坏力很大 |

**挪到点击之后，三个问题一起消失**：不再索取（是用户先敲的门）、不再过期（实时生成）、不再盲生成（有明确触发点和当下上下文）。

> 顺带删掉一整套东西：缓存字段、刷新策略、时间衰减、"只有 hero 能有问题"这条限制。

#### 卡上放什么：他自己的原话，每个子场景一句

**不是清单，不是 AI 总结，是他说过的话逐字呈现。**

```
WORK & STUDY
[图] "我得在九点前把会议室弄好"
[图] "又要开会了，一天三个"
[icon] "这个文档还没写完"
+5 more
[ 🎤  Start talking ]
```

**为什么是原话**：用户不是在做选择题（打开 App 时通常没有议程），他是在**找共鸣**——看到"这是我"才会想说。按共鸣强度排：

> 他自己的原话 > 他拍的照片 > 他没注意到的模式（属成长层）> 子场景名 > 泛泛总结

`Client calls` 是我们给他的生活起的名字，他要**辨认**；`"又要开会了，一天三个"` 是他自己的话，他直接**认出**。

**一句原话代表整个大类会造成层级错位**——解法和缩略图一样：**用多个成员，不用单个代表**。三句各来自一个子场景，共鸣、交代范围、容器感一次做完。

#### 左槽固定：有图放图，没图放 icon

图和引文**来自同一个时刻**，所以配对成行，而不是做成两个独立元素。这样 0～很多张的图片数量问题自然消解——**每一行自己知道有没有图**，不需要为图片数量单独设计规则。

- **有图** → 缩略图（46×34）
- **无图** → **同位置放 icon**，槽位永不为空，引文左边缘始终对齐
- **零图的分类** → 整列仍保留 icon，不塌成纯文字列表

##### icon 按 granularity 单轴分（已拍板）

> ⚠️ 上一版写的「打字 / 查词 / 对话」**是错的**——把三个轴混在了一起：打字是**输入方式**、查词是**粒度**、对话是**来源类型**。这正是本文批评顶部六个镜头时说的同一个毛病。

**主轴 = `granularity`**：

| 值 | 含义 | 用在哪 |
|---|---|---|
| `word` | 查词 | 待解锁页词表 |
| `sentence` | 一句话素材 | 两处都有 |
| `passage` | 长文素材 | 两处都有 |

**外加一个 `dialogue` 标记（刻意的例外）**：它严格说属于 `source_type` 而非 `granularity`，破轴。但"这句是我**说出来**的"是本产品的核心区分（§7.1 用它定义什么算用户输出），值得单列。**这是有意为之，不是又混轴了。**

**两处surface需要的集合不同：**

- **hero 卡引文行**：引文来自子场景，而子场景只可能来自 `sentence` / `passage`（查词无子场景）→ **只需两种**，且有图时缩略图顶替 icon。
- **待解锁页词表**：四种都会出现。

#### 取句规则

1. **每个子场景只取一句**，避免三句全来自同一件事。
2. **太短的跳过**：「好累」「今天真忙」没有信息量，勾不住人。设下限（约 6 字），不够则取该子场景的下一条。
3. **纯照片输入没有原话** → 该行退回子场景名。
4. **最多三行**，不硬凑。刚满 20 词的分类只有一句就显示一句，也不显示 `+N more`。

#### 点击行为

- **整卡可点 + CTA 按钮可点 = 同一个动作**，都直接进对话页。
  > 卡片没有"详情页"这个去处。**这条要写进规范**，否则容易有人给"点卡片"另配一个行为（比如展开看词表），那等于又造了一个浏览目的地。
- CTA 文案 `Start talking`（不用 `Say something back`——卡上已无问句，没有 back 的对象）。
- **转场：卡片展开成对话页**（共享元素动画），让人觉得是"这张卡打开了"，不是"跳到了别处"。

#### 不做半屏浮层

考虑过"点卡片 → 底部升起浮层（agent 提问 + 话题 chips + 麦克风）→ 再进全屏"，**否掉**：

1. **它把收窄从"说"换成了"点"。** 我们定过：回答"是晨会还是客户电话"本身就是当天**最低门槛的第一次开口**。做成 chips，那口话被手指吃掉了。一次点击换两次选择，第二次还消灭了开口。
2. **和 `PRD §6.1.2` 冲突**：对话页已定为独立、沉浸的语音页。随手下滑就关掉的半屏面板与"沉浸"相反；一场 8–12 分钟的语音对话待在半屏里也不成立（转写往哪放？长到全屏就是加了步骤的整页）。
3. **麦克风权限**首次要弹系统授权框。在半屏面板上叠系统弹窗，收起后状态很难处理干净；整页是标准场景。

**chips 保留，但放在对话页里当兜底**（不想开口的人有路走），不是关口。

#### 待验

📊 **首屏卡片文案 → 进入对话的转化率**是个干净的单指标实验。hero 先按"原话"做，把"子场景名"版留作对照组。

### 2.4 非 hero 卡描述行的取值优先级（替换原"展示降级规则"）

> ⚠️ **原先这里是"首屏顶部展示子场景还是时刻"的降级表，已作废**——入口固定是分类卡，不存在展示什么的选择。
> 现在需要规则的只剩一件事：**这张分类卡的描述行写什么**（因为不同成熟度的分类，手上有的东西不一样）。

按优先级取，取到就停：

| 顺序 | 条件 | 描述行显示 | 例 |
|---|---|---|---|
| 1 | 该分类下有子场景 | **子场景名**（按出现次数排，取前 3） | `晨会前 · 客户电话 · 会议室` |
| 2 | 有时刻但还没有子场景 | **时刻标题**（按时间倒序，取前 3） | `会议室那张 · 楼下咖啡机` |
| 3 | 只有查词来的词 | **词本身**（按入账时间倒序） | `invoice · deadline · reimburse` |

- 第 2 档是过渡态：`scene_detail` 还没上线、或这个分类刚起步时会出现。
- 第 3 档只可能出现在很偏的分类（用户只在这个领域查过词、从没捕获过场景）。它仍然能开练——走**借锚**（§3.4）。

## 三、开练的门槛：有没有方向，不是有几个词

**已废弃的思路**：给场景定一个词数下限（"少于 5 个词就藏起来"）。

**废弃理由**：对话本身会产生新词，且数据层已支持——用户说出账本里没有的词，记账会新建 entry 并标 `origin='spoken'`（§7.2）。所以三个词的场景不是"内容不够"。

> **词是 agent 的弹药，不是用户的课表。**
> agent 用账本做实时再现（§6.3.3）；用户从头到尾不需要知道"这场要练 12 个"。

### 3.1 门槛改为：能不能找到一个用户有话可说的方向

| 方向来源 | 锚点强度 | 动机 |
|---|---|---|
| 反复出现的子场景 | 强 | 高（他自己回去过） |
| 最近的具体时刻 | 强 | 中高 |
| 分类（兜底） | 中 | 中 |
| **用户当场自己说的** | 无 | **最高** |
| 系统猜的 | 无 | 低 |

前四种任一成立即可开练。

### 3.1b 起手方式的分工（已拍板）

| | Tab1 语音 | Tab2 |
|---|---|---|
| 场景 | **默认不预设任何场景**，开放起手 | **必须选一个场景**，永远有锚 |
| 动机来源 | 用户此刻想说 | 用户过去的生活 |

**这条同时关掉了 `PRD_v2 §12` 的待定项**（无 seed 的"随便聊聊"起手往哪放）：**放 Tab1 的语音**，不是 Tab2 的降级形态。

*直接后果*：**Tab2 首屏不需要输入框。** 它的入口全部是场景卡。

### 3.1c 对话记录回写 Tab1（方向已定，**本轮不做**）

Tab2 的每次对话在 Tab1 留一条记录。于是分工是一句话：

> **Tab1 是发生过的，Tab2 是接下来要做的。**

*直接后果*：**Tab2 不做"最近的对话"列表**——历史归 Tab1，Tab2 只向前看。

**⏸ 本轮不实现**：Tab1 侧还没有承接这条记录的位置。对话本身照常落库（§6 要求服务端 session + 长期记忆），只是暂时没有面向用户的入口。

> ⚠️ **推迟带来一个必须知道的后果：总结卡成了唯一的闭环反馈。**
> `Your words` 推迟 + Tab1 记录推迟 = 用户练完之后，**在产品里再也看不到这次练习留下了什么**。
> 所以总结卡（§6.3.2）在本轮承担的分量比原计划重得多——它不是"顺便给个总结"，它是用户唯一能拿到的"我刚才做了一件事"的凭证。做 E1 时不能把它当边角料。

> ⚠️ 等 Tab1 侧开做时，**必须和 `§6.3.4` 分清两件事**：
> - **对话记录**（聊了什么话题、多久）→ **自动**写进 Tab1，它是事实；
> - **对话中提取的新素材**（值得留存的表达）→ **仍需用户确认才入库**（§6.3.4："按一下确认既是筛选也是确权"）。
>
> 不能因为"反正都回写 Tab1"就把后者也自动化了。

### 3.2 三个后果

1. **卡片上不显示词数。** `12 words · 9 not used yet` 是在说"这有一份清单等你完成"，与边学边练矛盾。改成用他自己的词给一口味道：`set up · run late · agenda …`
2. **词库从"输入"变成"输入 + 产物"。** 循环是 `捕获 → 方向 → 练 → 新词入账 → 下次弹药更多`。因此词库最有意义的时刻是**练之后**，不是练之前。
3. **风险类型变了。** 三个词加一张照片，靠 agent 把一场对话撑起来——这是 prompt/agent 质量的赌注，不是数据完备性的赌注。**验收标准必须是对话质量，不能用数据指标代替。**

### 3.3 没过门槛的内容，Tab2 展示吗

**唯一真正过不了门槛的是孤立词**（s1/s3 查词，无场景、无时刻，背后什么都没发生，§5.2.2）。任何一次捕获——哪怕只有三个词——都有一个时刻可以聊。

**分三档处理：**

| 内容 | Tab2 展示吗 | 形态 |
|---|---|---|
| 子场景 / 分类 / 时刻 | ✅ 主入口 | 方向卡，按出现次数排 |
| **孤立词** | ✅ 但**单独一档、放最下面** | `Start from a word` — agent 现编一个用得上它的情境 |
| 什么都没有（新用户） | ✅ | 引导去 Tab1 捕获 |

**为什么孤立词不该直接扔掉**：用户主动查了这个词，说明他想知道——动机是真的，只是缺锚点。扔掉它，只查词的用户会看到一个空 Tab2。

### 3.4 起手方式：直接锚 / 借锚 / 不起手（本轮更正）

> **原先写的是"无锚时 agent 构造一个虚构情境"，已作废。**
> 更正后的原则更硬也更简单：

> ## agent 永远不虚构用户的生活——但也永远不因此停下。
> 没有直接锚点就**借**一个；连借的都没有，就在对话里**问**出来。

于是三档，**没有一档是死路**：

| 档 | 条件 | seed 装配 | agent 干什么 |
|---|---|---|---|
| **直接锚 · express** | 他自己的时刻（拍的、想说的） | 那个场景的素材（原句、图片、key phrases） | 从他的真事往下聊 |
| **直接锚 · comprehend** | 他读过的内容（多为 passage） | 那篇内容 + 抽出的表达 | **聊他对这个内容的看法** |
| **借锚** | 这个词没有场景，但用户有别的语料 | 从其他素材里挑 2–3 个**可能容得下这个词**的情境，交给 agent 选 | 找一个容得下它的情境 |
| **引导锚** | 对话中途没锚可用 | 无 | **不是不起手**——问他此刻的处境，用户答出来的**当场变成锚** |

> **`comprehend` 起手是另一种对话，必须单独写。** seed 是一篇文章时，开场只能是"你怎么看那篇东西"——那是**讨论内容**，不是**描述生活**。它其实是更难的口语练习（要表达观点，不只是描述场景），所以不该砍，但**不能混在 express 那一档里悄悄跑**，好的开场句写法完全不同。
>
> **`direction` 用来排序，不用来卡门槛。** 只算 `express` 会造成"只读文章的用户永远解锁不了"——又是不封顶的失败模式。解锁后的分类卡按 express 占比高的排前面：**他自己的生活优先，读过的内容往后放，但不剥夺。**
>
> ⏳ **待确认事实**：`generate` 的 prompt 有 s5/s6 两条 passage 流程，但 `CLAUDE.md` 写"long-form content 计划中、未构建"。需确认 passage 现在是否已在跑——这决定上面这一档是当下问题还是未来问题。

> **引导锚是冷启动引擎，不是降级兜底。** 它没有违反"不虚构"——agent 是在**问**，不是在**编**；素材仍然来自用户。
> 而且它比"去 Tab1 拍张照再回来"更顺：用嘴就能提供素材，第一次开口的门槛反而最低。

**这条更正带来的三个变化：**

1. **不需要第二套提示词了。** 任务从头到尾都是"从用户的语料起手"，变的只是 seed 的组成。改成**一套提示词 + 两种 seed 装配**——比两套提示词好维护得多，也不会出现"为了能编而放松约束、结果拖垮主路径"。
2. **风险换了。** 原来的风险是"编得不像他的生活"；现在是"**借来的锚点和这个词不搭**"（把 invoice 硬塞进做饭的场景）。对策：不让代码去判相关性，**给 agent 2–3 个候选情境让它自己挑**——它比字符串匹配更懂哪个塞得进去，成本也只是 prompt 里多几行。
3. **借锚要读的东西比 §6.1.3 现在写的多。** §6.1.3 的开场准备是"拿 seed 场景 + 预读账本"；借锚还需要**用户最近的若干条 materials**。这是把读的范围放宽，不是新机制。

## 四、词详情：查阅不是目的地

### 4.1 为什么要降级

用户点开一个词的动机只有三种，都很弱：

- "这什么意思来着" —— 词典做得更好，何况这是他自己几天前捕获的；
- "我从哪儿碰到的" —— 真实但浅、且低频；
- "我想练这个" —— 那么这一页就是个减速带。

**词详情页存在的真正原因是"列表需要一个能点的东西"。** 那是满足 UI 惯例，不是满足需求。

### 4.2 结论

- **列表行默认点击 = 直接进它最近的场景。** 默认意图就是练。
- **想看档案的**：长按 / 右滑 / 就地展开，出一个半屏 sheet，不是 push 一整页。
- **sheet 里零 CTA**，唯一可点的是时间线的每一行 → 进那个场景。

### 4.3 关联词必须指向练习，不能指向阅读

关联词 chips 是全页最可疑的元素：好看、可点、有发现感，但点下去是**另一个词**，等于在用户往前走的路上开一条横向岔路。

**规则：点一个关联词，进它最近的场景，不进它的词页。** 关系是这个产品最独特的资产，不删；但必须让它通向开口。

## 五、词的标签体系

### 5.1 一条规则

> **凡是"要和别的词比较才有意义"的信息，都不属于词详情。**

排名、闲置、缺口画像、进步——全部归成长层（§7），因为它们都要跨词比较。这也是"用户的进步感不由单一词汇决定"在架构上的落点。

### 5.2 三层

| 层 | 回答 | 数据来源 | 变化方式 |
|---|---|---|---|
| **身份** | 这是个什么词 | `lexicon_entries` 静态列（lemma / entry_kind / pos / phonetic / tier） | 基本不变 |
| **经历** | 我和它之间发生过什么 | `lexicon_occurrences` 全部行 | 只增不改 |
| **关系** | 它和我别的词什么关系 | 跨 entry 的 join（intent / source / scene） | 派生 |

### 5.3 两处必须纠正的建模

1. **情境不是词的元属性，是经历层的。** 一个词会出现在多个场景。现在 `get_lexicon_entries_tab2` 只返回 `latest_scene`，等于假设一词一场景——建模错误。
2. **「同义词」和「同意图」是两种东西。**
   - 同意图 = 同一 `intent_text` 下用户自己用过的其他说法 —— 免费、是他的真实语料 → **进词档案**
   - 同义词 = 词典关系 —— 需外部词库或 AI，且已是成长层 §7.3.3「同义扩展」的职责 → **不进词档案**

### 5.4 使用情况不单开区块

`lexicon_occurrences` 里没有两种东西，只有一条流水加一个 `source_type`。用户说出来的那次就是时间线上的一行，靠图标区分。单开"使用情况"区块等于凭空造一个数据里不存在的区分，并且会长出「说过 2 次 / 正确率 50%」这类记分板。

聚合只留顶部一行、且**有才显示**：`Seen 6 · used 2 · since Jul 12`。

## 六、来源必须可分辨

三种来源在时间线上不能长成一样：

| 来源 | 那句话是谁产出的 | 行里必须有 |
|---|---|---|
| 文字输入 | 用户自己打的 | 句子 |
| 图片输入 | **AI 看图生成的** | **缩略图** + 句子（`messages.image_url` 已有） |
| 语音对话 | 用户自己说的 | 句子 + 时长/轮次 |

> 缩略图不是装饰，**它是"这句不是你写的"的标记**。把 AI 生成的描述和用户自己写的句子用同一种排版并列，用户会误以为那是自己说过的话——这直接污染 §7.1 对"什么算用户输出"的认知。

## 七、文案约定（已定）

| 位置 | 用 | 不用 | 理由 |
|---|---|---|---|
| 聚合行 | `Seen 6 · used 2` | ~~`said 2`~~ | 说出来这个区分已由时间线图标（🎤 / 📷）承担，标签不必重复；`used` 语气不像记分 |
| 同意图区 | `Your other expressions` | ~~`Other ways you've said this`~~ | 那些说法**可能从未说出口**，只是被捕获过——原文案在事实上是错的 |
| 首屏标题 | 动词（`Talk about something`） | 名词（`Your words`） | 第一句话要说明这一页让你干什么 |

**`Your other expressions` 只有紧贴在意图那行下面才读得通**（"你想说把…弄好 → 你的其他说法"），两块不得被其他区块隔开。

### 7.1 情境标签的中英映射（阻塞项）

`scene_category` 的值是中文（`其他`、`饮食`），被直接渲染进英文 UI，违反 `CLAUDE.md` 硬约束（产品 UI 一律英文，中文只能作为 AI 生成的学习内容）。

修法：固定枚举加一层 `code → English label` 静态映射，DB 存什么不动。**这是首屏、场景页、词档案三处的共同前置。**

## 七之二、对话页展示规划

> **行为**已由 `PRD_v2 §6` 定死（全目标语言、母语兜底、不打断、不判达标、空闲收尾、总结卡）。
> 本节只补 §6 没写的**呈现**，不改任何已定行为。

### A. 一条判据

> **屏幕存在的目的是让人开口，不是让人读。**
> 每个元素只回答一个问题：它降低了开口门槛，还是替代了开口？替代的，删掉或收起。

### A2. 开场白：点击那一刻生成，且第一句就是收窄问题

**上一版把开场问题印在卡上，已作废**（见 §2.4b）。现在它归对话页：

- **生成时机**：用户点卡片那一刻实时生成。不缓存、不预生成——于是不会过期，且拿得到当下上下文。
- **第一句 = 收窄问题**："这个分类里有晨会、客户电话，你想说哪个？"用户**用嘴回答**就是当天第一次开口——回答比开场容易得多，这是全流程门槛最低的一口。
- **必须有默认**：用户答"随便"或不答，**不许追问第二次**，直接挑最厚/最近的那个往下走。追问两次就把势头掐了。
- **chips 是兜底不是关口**：页面上给几个话题 chip 供不想开口的人点，但主路径是说。

#### 开场白的两条硬约束（从卡片文案迁移过来）

1. **问处境，不问结果。**
   - ✅ `You're in that office most mornings — what's it like when you get there?`
   - ❌ `Did you get that meeting room sorted in the end?`
   后者是查进度，预设了"你应该完成的任务"——**直接违反 §4.1 的 `never use coach voice`**。写进 prompt：不问完成情况、不问是否坚持、不问感受好坏。
2. **不用亢奋语气。** ❌`进入工作频道啦！` —— §4.1：不用感叹号承载情绪、warm but never loud。

### B. 四个状态（缺一不可，`CLAUDE.md` 硬约束）

| 状态 | 屏幕 |
|---|---|
| **权限未授予 / 被拒** | 说明为什么需要麦克风 + 去设置的引导。这是必经的第一屏，不是边缘情况 |
| **开场准备** | 话题名 + AI 开场白（有声 + 文字），麦克风已就位 |
| **对话中** | 见 C |
| **收尾** | 总结卡 |

### C. 对话中的版面（三区）

```
┌─────────────────────────────┐
│  ← 做晚饭                    │  顶部薄条：话题 + 退出，别的都不要
├─────────────────────────────┤
│                             │
│   AI 的话（目标语言，文字）    │  中部：对话流
│   你的话（转写，小字弱化）      │  点 AI 那句 → 出整句母语译文
│                             │
├─────────────────────────────┤
│   3 words you could use ⌄   │  收起态的实时推荐
│      🎤        中文说不出     │  底部：麦克风是主角
└─────────────────────────────┘
```

### D. 五个呈现决定

**1. 转写要有，但要弱。**
用户说的那句以小字灰色显示，AI 的话正常字重。
*理由*：转写必须存在——它是 `sample_sentence` 的证据（§6.3.1），也让用户确认 ASR 没听岔。但这是口语产品，用户不该在屏幕上读自己刚说过的话。**弱化是为了让视线离开屏幕。**

**2. 母语兜底按钮常驻，且不带羞耻感。**
文案是 `Say it in Chinese`，不是 `I don't know` / `Help`。
*理由*：母语兜底产出的是 `is_known_gap`——**全产品最高价值的语料**（高动机 + 高缺口，§6.2.6）。把它做成"求助"会让用户回避使用，等于亲手关掉最好的数据源。它应该像换挡一样自然。

**3. 兜底弹框 = 译文 + 重点词音标 + 一句轻提示，然后就闭嘴。**
不比对、不判"你念得对不对"（§6.2.3 已废除达标判定）。用户念完、说了变体、甚至说岔了，都推进。

**4. 实时推荐默认收起成一行，点开才看。**
`3 words you could use ⌄`
*理由*：§6.2.5 已定这个功能要有且可一键关闭；这里只定它的默认态。**词一直摊在屏幕上，用户会读，不会回忆——而回忆那一下才是学习发生的地方。** 收起态保留"我有后备"的安全感，展开是主动求助。
> ⚠️ 这是我的判断不是已定结论，建议在 Slice 3 里 A/B：默认展开 vs 默认收起，看 `spoken_count` 和 `native_fallback_used` 的差异。

**5. 屏幕上永远不出现纠错标记。**
没有红色下划线、没有 ❌、没有"再试一次"。§6.2.4 已定 AI 对话中绝不纠错——**这必须落成组件层面的硬约束**，否则以后很容易有人"顺手加个小提示"。正确性判定在后台写 `learning_events`，只在总结卡出现。

### E. 收尾与闭环

- **空闲轻推**：一句话（"慢慢来～"），不弹窗、不倒计时。倒计时是施压。
- **继续空闲 → 优雅收尾**：停止监听（耗电，§6.2.7）+ 出总结卡 + 记账落库。**任何自动结束都必须产出总结卡**，绝不静默丢弃。
- **总结卡三块条件展示**（§6.3.2）：用出了哪些你的词 / 待提高 1–2 条 / 进步。空的块不出现。
- **退出后回 Tab2 首屏，且首屏必须看得出变化**——刚练过的那个场景状态变了。没有这个变化，用户感觉不到自己刚才做的事留下了什么。这是闭环的最后一环，容易被漏掉。

### F. 这一节需要定的

| # | 问题 | 为什么现在就要定 |
|---|---|---|
| 1 | ASR 用什么（系统 `Speech` 框架 / 云端） | **延迟直接决定体验**，且影响"转写要不要实时逐字出现" |
| 2 | 要不要显示轮次或时长 | §6.2.7 已定不设最低时长；显示计时容易被读成 KPI |
| 3 | 总结卡是整页还是 sheet | 决定"退出"这个动作有几步 |
| 4 | 开场白要不要等 AI 生成完才进页 | 生成有延迟，先进页后出声 vs 转场等待，体感差别很大 |

### 8.2 缺口 7 详解：长文的 `sample_sentence` 存了整篇文章

**先说这两个字段是什么**（避免又用字段名说字段名）：

- `lexicon_entries` = **单词本**，一个词一行。`set up` 出现多少次，这里永远只有一行。
- `lexicon_occurrences` = **流水账**，每碰到一次记一笔。`set up` 出现 6 次，这里就有 6 行。
- **`sample_sentence` 是流水账上的一列**，记"这一次，这个词出现在哪句话里"。

正常情况（一句话的卡）：

```
用户打字：我得在九点前把会议室弄好
  → AI 生成 "I need to set up the meeting room before nine."
  → 抽出 set up、meeting room
  → 两条流水，sample_sentence 都是那句英文   ✅ 正确
```

**长文的情况（错的）：**

代码里这一列取的是 `target_expression ?? user_original`（`generate/index.ts:706`）。而 prompt 对长文卡的定义是 **`target_expression` = 整篇原文**（第 421 行）。于是：

```
一篇 800 字的文章 → 抽出 15 个词 → 15 条流水
每一条的 sample_sentence 都是那整篇 800 字
```

**两个后果：**

1. **存储浪费**：同一篇文章在库里存了 15 遍。
2. **Tab2 显示没法看**：词表里每个词旁边都是同一篇文章的开头，**截断成什么样都没意义**——三个词看起来一模一样。而这正是 §1.05-2 那个可展开词表的核心内容。

**修法（改动很小，字段现成）：** AI 生成长文卡时已经把文章切成一句一行存在 `passage_lines[]` 里。记账时把每个 unit 匹配到它所在的那一行，`sample_sentence` 存**那一行**。修完之后字段名和内容才对得上，显示也不用特殊处理。

> **归属**：这是抽词/记账那一层的问题，不是 Tab2 的展示问题。但**不修的话，Tab2 词表里长文来的词永远显示不好**，所以排进本轮（切片 A 一起做，反正都要动 `generate`）。
>
> 另附一条观察：`sample_sentence` 的建表注释写的是"用户实际说出来那句"，但对**素材来源**它其实是 AI 生成的目标语言表达，只有**对话来源**才符合注释原意。**注释和实现对不上**，建议顺手改注释，免得下一个人被误导。
