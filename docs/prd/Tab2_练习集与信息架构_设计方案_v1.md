## 〇、诊断：三个问题是同一个根因

当前 Tab2 把**词汇账本**直接当成了**练习页**。账本是数据结构，练习清单是产品形态，两者被画了等号，于是：

- 练习单位 = 账本的一行 = 一个词 → **问题 1**
- 详情页 = 那一行的字段回显（`total_count` / `spoken_count` / `latest_scene` 三个列各占一块）→ **问题 2**
- 顶部导航 = 把账本的几个查询条件平铺成等价 tab → **问题 3**

修复方向统一：**账本留在底层，Tab2 上层重新定义三样东西 —— 练习集（set）、词的档案（profile）、浏览的三个正交轴（筛 / 排 / 分组）。**

### 0.1 先修一个硬伤（不在你列的三条里，但截图里很显眼）

`scene_category` 的值是中文（截图里的 `其他`、`饮食`），被直接渲染进英文 UI —— 既出现在词详情的 FROM 区，也出现在列表右侧和 chips 上。

`CLAUDE.md` 硬约束：**产品 UI 文案一律英文，中文只能作为 AI 生成的学习内容出现**。情境标签是产品分类，不是学习内容，属于违规。

修法：情境是固定 12 类枚举，加一层 `code → English label` 静态映射（`SceneCategory.displayName`），DB 存什么完全不动。**这是下面所有方案的前置**——分组的 section header、chips、详情页的情境行都要用它。

## 一、练习单位：从"一个词"改成"一个练习集"

### 1.1 为什么"一个词"不成立

三条独立理由：

1. **对话形态撑不住**。MVP 对话页是语音、多轮（§6.1.2），一次开口最少是一句话；一个词开不起一场对话，只能变成"跟读单词"，那不是这个产品要的东西。
2. **PRD 定的入口本来就是集**。§6.1.1 写的是"点开一个词 → 看它的来源场景 → 在某个来源场景上和它聊聊"，seed 是**场景**，场景天然带一批词。现在的实现把中间那步吃掉了。
3. **成本荒谬**。用户要练 20 个词就要进 20 次对话页、点 20 次麦克风权限、等 20 次开场白生成。

### 1.2 练习集怎么组：四种成组规则

四种都能用现有字段直接算出来，不需要新表、不需要 AI：

| 成组方式 | 数据依据 | 用户心智 | 典型规模 |
|---|---|---|---|
| **情境集** Scene set | `occurrences.scene_category` 相同 | "把'工作'那批词练一下" | 8–30，需截断 |
| **意图集** Intent set | `occurrences.intent_text` 相同 | "想说'很累'时我手上有几种说法" | 2–6，天然小 |
| **同源集** Source set | `occurrences.source_id` 相同（同一张卡 / 同一次对话） | "那天拍的那张照片里的词" | 3–8，天然合适 |
| **策展集** For-review set | `tier` + `spoken_count` + `last_used_at` 加权 | "系统说我现在该练这些" | 固定取 6 |

**意图集是这四个里最独特的一个**——它是别的背单词产品做不出来的东西，因为只有这个产品记了 `intent_text`（用户当时想说的母语意图）。PRD §5.2.7 已经为它建了部分索引，但目前前端没有任何地方用到。建议它优先级最高。

### 1.3 落地建议：练习集是**临时装配**，MVP 不建表

发起练习时按规则现算出 `seed_entry_ids[]`，连同 seed 场景一起传给 `dialogue` 函数；不新建 `practice_sets` 表。

*为什么：* 成组规则还在调——§12 明说 `For review` 的排序权重"上线后按数据 tune"。过早把集固化成表，等于把还没验证的规则写进 schema，以后改一次要迁一次数据。以后真要做"我的自定义练习包"（用户手选并保存），再补表也不冲突，因为那时集有了明确的所有者和生命周期。

### 1.4 UI 后果

- Tab2 主页面出现**一个主 CTA**（悬浮或吸底），文案随当前视图变：`Practice these 6 words`。不是每一行都有按钮。
- 词详情页的按钮从 `Practice this word` 改成 **`Practice with 5 related words`**，点了把关联词一起带进对话。
- 建议每组 **5–8 个词**（一次 8–12 分钟对话大致能覆盖的量）。超出就截断，不要一次塞 30 个——用户练不完会产生"没练完"的负债感，违反 §7.2 的"不制造焦虑"。

## 二、词详情页：从"字段回显"改成"这个词的档案"

详情页要回答三个问题，现在一个都没答：

> 我什么时候、在哪碰到它的？我当时想说什么？它和我已经会的哪些词是一伙的？

### 2.1 版面（自上而下）

1. **Header** — word / kind·pos / phonetic / tier badge。`definition_native` 保持弱化（不做成词典页）。
2. **状态条（一行，不是两个大数字）** — `Seen 6 · Spoken 0 · First seen Jul 12`。
   > 现在的 `6×` / `—` 双大数字块占了首屏近一半，承载的信息却只有两个整数，权重严重失配；而且 `—` 这种"空"状态被放大到 48pt，视觉上像在提醒用户"你什么都没做"。
3. **Encounters（时间线，核心区）** — 每条 occurrence 一行：
   `日期 · 情境 · 来源图标（素材/对话）· sample_sentence`
   这就是 §5.2.3 说的"记忆锚点"。**它是详情页里唯一能让用户真的"想起来"的东西**，应该占最大面积。
4. **What you meant**（仅当 `intent_text` 非空）— "你当时想说的是：很累"；`is_known_gap = true` 时额外打一个 `Known gap` 标记。
5. **Related** — 分维度，见 2.2。
6. **CTA** — `Practice with this set`。

### 2.2 关联词的四个维度（都不需要新的 AI 调用）

| 维度 | 算法 | 展示标题 | 说服力 |
|---|---|---|---|
| **同意图** | 同 user 下 `intent_text` 相同的其他 entry | `Other ways to say this` | ★★★ |
| **同源共现** | 同 `source_id` 的其他 entry（同一张卡里一起出现的） | `Appeared together` | ★★★ |
| **同情境高频** | 同 `scene_category` 下 `total_count` 高的 entry | `Often used in <Work>` | ★★ |
| **词形相关** | `lemma` 子串匹配（meeting → meeting room / meeting agenda） | `Built on this word` | ★ |

优先级理由：前两个是**用户自己语料里的真实关系**（"这两个词你当时是一起用的"），后两个是统计兜底。截图里 `meeting room` 和潜在的 `meeting` 正好是第四维度的例子，但它只解释词形，不解释使用。

细节：每个维度取 3–5 条；**空的维度整段不渲染**，不要留空态占位（一个新用户点开会看到四个空框）。

### 2.3 数据缺口

`get_lexicon_entries_tab2` 只返回 `latest_scene`，喂不动上面的页面。需要新增只读 RPC：

```
get_lexicon_entry_detail(p_user_id uuid, p_entry_id uuid)
  → entry 全字段
  + occurrences[]  最近 20 条（含 sample_sentence / intent_text / source_type / created_at）
  + related[]      四维度各 5 条，带 relation 标签
```

一次请求打完，避免详情页发四个查询。**纯读，不碰写入链路**，风险低。

## 三、顶部导航：从"6 个 tab"改成"三个正交轴"

### 3.1 为什么现在难看——是信息架构问题，不是视觉问题

`For review / All / Not yet / Spoken / Recent / By scene` 这 6 个不是同一类东西：

| 标签 | 它其实是 |
|---|---|
| For review | **目的地**（策展队列） |
| All | 无筛选（= 默认态，不该是一个选项） |
| Not yet / Spoken | **筛选**（`spoken_count` 阈值的两个值） |
| Recent | **排序**（`last_used_at`） |
| By scene | **分组**（而且激活时还会长出第二行 chips） |

把"目的地 / 筛选 / 排序 / 分组"四类塞进一排长得一模一样的胶囊里，用户建立不了心智模型——他没法预期点下去会发生什么。三个具体症状：

- 横向滚动截断（截图里第 6 个已经被切掉半个），用户不知道右边还有什么；
- `By scene` 激活时顶部长出第二行，**页面高度跳变**，列表位置整体下移；
- 组合不了。想"只看没说过的、按场景分组"——做不到，因为它们是互斥的 tab。

### 3.2 方案 A（推荐）：Review / Library 两段 + 一个 Sort & Filter 菜单

```
┌────────────────────────────────────────────┐
│  [ Review │ Library ]              [ ⇅ ]   │  ← 分段控件 + 排序筛选入口（高度恒定）
├────────────────────────────────────────────┤
│  12 words · Not yet                 Clear  │  ← 条件摘要条（有条件时才出现）
├────────────────────────────────────────────┤
│  WORK                                      │  ← 分组打开时的 sticky section header
│    set up             phr.    ○ Not yet    │
│    run late           phr.    ○ Not yet    │
│  HOME                                      │
│    very sleepy               ● Spoken 2×   │
└────────────────────────────────────────────┘
        [  Practice these 6 words  ]           ← 吸底主 CTA
```

- **Review** = 策展队列（原 `For review`）。它是**目的地**不是筛选：进去就是一句话说明 + 6 个词 + 主 CTA，不提供排序分组。
- **Library** = 全量账本，可浏览、可组合查询。
- **⇅ 菜单**（iOS 原生 `Menu`，不用自造控件）三组：
  - `Sort by`：Frequency / Recent / Least practiced / A–Z
  - `Group by`：None / Scene / Word type / Tier
  - `Show`：All / Not yet / Spoken
- **第二行 chips 取消**，`By scene` 变成 `Group by = Scene`，用 sticky section header 表达。这同时解决了顶部高度跳变。

**优点**：三轴正交可自由组合；顶部高度恒定；用系统 Menu，代码量比现在的 `LensSelectorBar` 还小；以后加维度（`entry_kind`、`origin`、`input_lang`）只是往菜单里加一行，不会再撑爆顶部。

**代价**：排序/分组状态藏在菜单里，可见性下降 —— 所以必须有那条**条件摘要条**兜底，不能省。

### 3.3 方案 B（最小改动）：保留单排 tab，但只留"目的地"

只留 `Review / All / Not yet` 三个，`Spoken`/`Recent`/`By scene` 降级进 ⇅ 菜单。

视觉上立刻干净，改动一天以内。但本质仍是"筛选伪装成 tab"，以后加维度会再次膨胀成今天这样。**适合你想先小步验证"菜单化"用户接不接受**，之后再走方案 A。

### 3.4 方案 C（先不做，但预留）：Library 变成索引页

顶部只有一个维度切换器（`Scene ▾` / `Word type ▾` / `Tier ▾`），点开是**分组卡片矩阵**——每组一张卡，显示组名 + 词数 + 未练数，点进去才是词列表。

这是词量上千以后的正确形态。现在词量还小（截图里目测不到 30 个），做出来每张卡里只有两三个词，会显得很空。**建议：现在不做，但把方案 A 的 `Group by` 枚举设计成以后能平滑升级成这个形态。**

### 3.5 关于"按词性分组"——先看数据再决定

你提到还可以用词性分。数据层面要泼一点冷水：

- `lexicon_entries.pos` 允许为空，PRD §5.4.1 也承认"可能为空"；
- 截图里 `speak` / `receive` / `consequently` 后面**都没有词性标注**，只有 `entry_kind` 是 `phr.` / `coll.` 的行有内容。也就是说 pos 目前基本是空的。

所以：**`Group by = Word type` 先用 `entry_kind`（word / phrase / collocation / idiom / pattern），`pos` 作为二级。** 想真正按词性分组，得先补 pos 的供给——要么抽词 prompt 稳定返回，要么接一个静态词典查表。**这是一个独立的前置任务，不该混进导航改造**，否则会变成"改导航顺便改 prompt 顺便改记账"的三合一切片。
