# 功能需求表：使用额度 · 限流入口 v2

> 状态：**待评审 / 未开工。** 本版是 `UsageLimit_额度状态机与限流入口_PRD_v1.md` 的收窄版——PM 拍板：不做"默认/进行中/达标"三态联动，图标不随额度变化（图标只是入口，不承担状态提示的职责），配色不新开体系、沿用 App 现有视觉。唯一需要新设计的是**达标（用完）之后的一个方案**。v1 文档保留作为过程记录，以本版为准。

---

## 0. 一句话目标（用户视角）

我今天还能免费生成几次、用完之后还有没有办法继续用——这两件事讲清楚就够了，中途不需要额外提示打断我。

## 1. 产品哲学约束（L0，与 v1 一致）

- 限流发生在"是否允许发起新一轮生成"这一层，不影响已产出内容的可读性（历史仍可读，参考 `OfflineCache_PRD_v1.md`）。
- 达到上限**不是拒绝，是引导**：没有付费/配额系统的阶段，人工放量（Send Feedback / 邮箱）是唯一的"继续用"通道。
- 与 `TodayViewModel.send()` 里已有的 `isConsentGranted()` 同属"发送前置门槛"家族：不吞输入、不静默失败、拦截时明确告诉用户为什么。

## 2. 用户怎么用它（L2 交互）—— 收窄为两态

**这是本版和 v1 最大的区别**：不做"默认/进行中/达标"三态联动，只有两种情况：

| 情况 | 判定 | 图标 | Sheet |
|---|---|---|---|
| **正常使用**（含 v1 里的"默认"与"进行中"，合并） | `used < dailyLimit` | **不随额度变化**，任何时候都是同一个静态样子——图标只是入口，不是状态指示器 | 现有的卡片 + 进度条骨架照常显示"已用/上限"，不加任何额外提示文案，不换色。用量的变化就靠进度条自己说话 |
| **达标 / 用完**（唯一新增的设计） | `used >= dailyLimit` | 仍然**不变**（tap 行为不变，照常点开 Sheet） | 替换为达标专属版：进度条满格（用 App 现有色板里的强调色，不新开 token）+ 达标文案 + **Send Feedback** 按钮（复用现有 `FeedbackView`）+ 邮箱联系次要入口 |

**达标态的拦截行为**：点发送时若已达标，`send()` 直接短路、不发起网络请求，把用户引导到上表的达标态 Sheet（内联提示还是直接弹出，见"待定"）。

**恢复**：跨自然日计数回到 0，回到"正常使用"。`Calendar.current.isDateInToday`（`UsageLimitButton.swift:141`）已具备该语义，不需要新逻辑。

## 3. 数据三问（L3，比 v1 更小）

- **读**：本地 `LocalCache.shared.load(key: .messages)` 解出的 `[MessageRecord]`，按 `role == "user"` 且 `createdAt` 是今天计数——逻辑已存在（`UsageLimitButton.swift:137-142`），只是要从 Sheet 内部抽出来，供 Sheet 与 `TodayViewModel.send()` 共用同一份读数（图标本身不需要这份读数，因为图标不跟着变化，这点比 v1 简单）。
- **改 / 产生**：不新增持久化数据结构。唯一新增的是一个可调常量 `dailyLimit`（建议放进类似 `FeatureFlags.swift` 写法的 `UsageLimitConfig.swift`），不需要 v1 里提议的"进行中阈值"这类额外常量。
- **现在存在吗**：
  - 今日已用次数 → 存在手边（逻辑已写过，只是要挪个位置共用）。
  - 每日上限数字 → 存在但没送到位：Sheet 现在硬编码 `20`（`UsageLimitButton.swift:65`），本次要改成可调的 `5`，且只有一个唯一出处。
  - 达标态文案 + Feedback 入口 → 需要新造，成本低，是本次唯一真正的新设计工作。

## 4. 它长什么样（L6 视觉）—— 范围收得最窄的一节

**图标：不做状态变化，只做质感打磨。** 现状 `UsageGaugeIcon`（`UsageLimitButton.swift:21-60`）的问题不是"要不要随额度变形变色"（这次明确不做），而是这一个**静态**图标本身画得不够温润——直挺的指针线条偏硬，跟 App 整体暖纸质感的调性不太搭。打磨方向：保留"仪表"这个大意象（不用大改成全新隐喻），把生硬的直线指针换成一个更柔和的收尾——比如把指针末端从尖锐的直线改成一个圆头短杆 + 末端一个小圆点（像一颗温润的小豆/水滴，而不是一根冷硬的刻度针），线宽、比例对齐左侧 `SettingsMenuButton` 的 `DoubleLineMenuIcon`（同一套 `topBarMenuIconStroke`），弧线也可以再放松一点、减少"精密仪器"感。图标全程只有这一版视觉，不随额度变化。

**配色：不新开体系，沿用 App 现有视觉。** 达标态 Sheet 里的强调色（进度条满格、CTA 按钮）直接用 App 现有色板里已经在用的强调色（比如 `AppTheme.Color.danger` / `Primitive.errorDeep`，与 Feedback 页插画色系同源），不新增 warning 之类的中间态 token——因为已经没有"进行中"这个中间态需要单独配色了。

**Sheet 版式**：
- 正常使用：完全复用现有卡片 + 进度条骨架（`UsageLimitButton.swift:87-122`），不改。
- 达标：进度条满格（用上面选定的强调色）；标题下文案替换为达标专属文案（例如 "You've reached today's limit. Want more today?"）；卡片下新增主按钮 "Send Feedback"（直接 present 现有 `FeedbackView`）+ 一行次要邮箱联系方式。顺带一提：`FeedbackView.swift:253` 目前的邮箱是占位符 `name@example.com`，既然要在这里复用展示方式，建议一并换成真实邮箱。

## 5. 边界与冲突（与 v1 一致，收窄范围不影响这些判断）

- **带图消息算不算多一次？** 计数口径是"`role == "user"` 的消息条数"，不分是否带图，维持不变。
- **重试算不算新的一次？** `retrySend` 复用同一个 `requestId` 幂等键（`TodayViewModel.swift:390-398`）——提案：**重试不占用新次数**，需 PM 确认。
- **达标后还能干嘛？** 历史仍可读，仅"发起新生成"被拦。
- **本地读取失败时怎么办？** 现状读取失败会保留 `usedCount = 0`（`UsageLimitButton.swift:137-142` 无 else 分支）——即误判为"今天没用过"从而**误放行**而非误拦截，这是"宁可误放行、不可误拦真实用户"的兜底策略，v1/v2 都沿用，需 PM 明确表态接受。
- **卸载重装 / 换设备能否绕开限制？** 能，计数完全本地化、没有后端配额系统，是"v1/v2 阶段不做后端"的必然代价，写进已定。

## 6. 已定 vs 待定

**已定（本次拍板，比 v1 更明确）**：
- 每日生成次数限制要做，上限数字先按 **5**，做成可调常量，替换掉 `UsageLimitButton.swift:65` 现有的 `20`。
- **不做三态联动**：正常使用期间（含临近上限）图标和 Sheet 都不额外提示，靠现有进度条表达即可。
- **图标不随额度状态变化**，只是入口；本次只对这一个静态图标做质感打磨（软化指针），不换隐喻、不做多态配色。
- **配色不新开体系**，沿用 App 现有视觉色板，达标态直接用现成的强调色（如 `errorDeep`）。
- 唯一新增设计：**达标之后的方案**——Sheet 内替换文案 + Send Feedback 按钮 + 邮箱联系入口。
- v1/v2 都不做后端配额系统，计数继续走本地消息记录，接受"卸载重装可绕开"的已知代价。

**待你确认的默认值**：
- 达标拦截的呈现方式：提案"发送前在输入区做一次内联提示，引导点开额度 Sheet"，也可以直接强制弹出，需要你选一种。
- 达标态具体用哪个现成的强调色（`errorDeep` 还是别的），需要看实物确认。
- 重试不计入新次数——提案如上，需确认。
- 图标"温润化"打磨的具体形态（圆头短杆+末端小圆点 vs 其他更柔和的画法）：AI 先出稿、PM 看实物再否决。
- `FeedbackView.swift:253` 的占位邮箱：建议借这次机会换成真实邮箱，一并修正。

# 六步检查（AI 执行）

## 1. 复述

把"限制每天生成次数"落成一套最简的两态机制：正常使用期间完全不打扰（不加文案、不变色、图标不变），只有真正用完当天额度时，才在原来的 Sheet 位置换一版内容——满格进度条 + 达标文案 + Send Feedback / 邮箱联系入口，引导用户争取继续使用。图标本身全程视觉不变，这次只顺手把它画得更温润。上限数字做成可调常量。

## 2. 找洞

- 数字不一致：Sheet 硬编码 20，本次要 5——仍需统一到唯一出处（`UsageLimitConfig`），这一点和 v1 一样没变。
- 现状完全没有拦截逻辑：`send()` 从未真的挡过任何一次生成，这次要新增的不只是视觉，还有一道实打实的生成前置门槛——这一点也和 v1 一样没变，收窄的只是"状态该怎么呈现"，不是"要不要拦截"。
- 达标拦截的交互方式未定：内联提示还是强制弹窗，需要你选。
- 达标态强调色具体用哪个 token 未定，需要看实物。
- retry 是否计入新次数未定，提案不计入。
- 反馈邮箱是占位符，达标态会把它真正曝光给用户，建议一并换成真实地址。
- 图标"温润化"的具体画法是提案，不是拍板，需要看实物再定。

## 3. 分层

比 v1 轻：**L2**（新增"达标即拦截"这一步交互，且要决定内联提示 vs 强制弹窗）和 **L6**（达标态 Sheet 新增文案 + CTA；图标只做一次性静态打磨，不再需要"图标随状态联动"这层复杂度）。**L3** 只需新增一个 `dailyLimit` 常量，比 v1 提议的"两个常量 + 状态枚举"更小。L0/L1 不动。

## 4. 定脊柱

新增一个 `UsageLimitConfig.swift`（写法仿 `FeatureFlags.swift`），只放一个 `dailyLimit` 常量。`TodayViewModel.send()` 顶部加一道 guard：`used >= dailyLimit` → 不发起生成、触发达标态 Sheet。今日已用次数的读取逻辑从 `UsageLimitSheet.task` 抽成一个 Sheet 与 `send()` 共用的函数（图标不需要订阅这份读数，因为图标视觉不变，这是比 v1 更小的脊柱）。不改动 `MessageRecord` / `LocalCache` 任何现有结构，图标的 SVG 路径改动是纯视觉层面的独立小改动，不影响这条脊柱。

## 5. 排顺序（最小垂直切片）

**切片一**：新增 `UsageLimitConfig`（`dailyLimit = 5`）→ 抽出共用的今日已用次数读取逻辑 → `send()` 顶部加达标 guard，复用现有 Sheet 弹出方式 → Sheet 达标态换文案 + 满格进度条 + 跳转 `FeedbackView` 的按钮 → 手动验证：把上限临时改成 1，连续生成 2 次，确认第 2 次被拦截、弹窗文案正确、按钮能跳转。

**横向扩展（切片一验证通过后）**：图标质感打磨（软化指针，独立于拦截逻辑，可以并行做）；补邮箱联系入口并修正占位邮箱；视需要加输入区内联提示；把 `dailyLimit` 迁到真正的远程可配置来源（独立的后端配额 PRD，不在本次范围）。

## 6. 停

以上六步列完，**未写任何代码**。等你对"待确认的默认值"（尤其是达标拦截呈现方式、达标态强调色、retry 是否计次这三条）表态并说"确认执行"后再开始实施。
