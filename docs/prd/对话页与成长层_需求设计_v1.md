## 三、两个技术选型（你要我分析的两件事）

### 3.1 ASR：语音怎么变成文字

#### 三个候选

| | **A · iOS 系统 Speech 框架** | **B · 云端 ASR（Whisper 类）** | **C · 端到端语音模型自带** |
|---|---|---|---|
| 钱 | **免费** | 约 $0.006/分钟。一场 10 分钟对话里用户说话约 3 分钟 → **约 ¥0.13/场** | 打包在模型调用费里，单独算不出来 |
| 延迟 | **几乎为零**（本地，边说边出字） | 说完一句 → 上传 → 等 0.5–2 秒 | 最低（模型直接听声音） |
| 逐字实时转写 | **能** | 不能（只能整句出） | 不适用（没有转写这一步） |
| 中式英语口音 | **一般**——这是它最大的短板 | **好**，Whisper 类模型对非母语口音明显更强 | 好 |
| 中英混说 | 差（要预先指定识别语言） | **好** | 好 |
| 离线 | 部分机型可以 | 不行 | 不行 |
| 额外风险 | 苹果对**连续识别时长有限制**（一次约 1 分钟会自动断），要自己做重启拼接 | 网络抖动直接毁掉一轮对话 | 见 §3.2 方案二的整体风险 |

#### 延迟到底有多明显：**关键不是快多少，是慢在哪一刻**

一轮对话的等待由三段组成：**转写 + 模型思考 + 出声**。ASR 只是第一段。

**系统框架的延迟接近于零，但原因不是它算得快，是它和用户说话的时间重叠了。** 它边说边转写，等用户说完最后一个字，转写基本已经完成——这一段等待被"用户自己说话"这件事吸收掉了。

云端做不到这一点，它必须等一句说完才能上传。于是那约 1 秒的等待，**结结实实地落在"用户刚说完"这个时刻**。

> **而这恰好是全流程里最贵的一秒。**
> 一个初学者刚鼓起勇气说完一句磕磕巴巴的英语，屏幕一片死寂。他不会想"网络有点慢"，他会想**"我是不是说错了"**。

所以选 A 的理由不是"云端慢 1 秒可以忍"，而是**这 1 秒花在了最不该花的位置上**。同样一秒的延迟，如果发生在"AI 正在想"的阶段，用户是有耐心的——人对"对方在思考"天然容忍；发生在"我刚开口之后"，则会被读成对自己表现的否定评价。

**这条也反过来给了一个实现要求**：即使将来换成云端 ASR，也必须在用户说话时给出某种即时的视觉反馈（音量波形、听写指示灯），**不能让"刚说完"到"字出现"之间是完全静止的**。

#### 我的建议：**A（系统 Speech 框架），但把它当"可替换的一层"来写**

理由按重要性排：

**1. 这个产品最怕的不是识别不准，是用户不敢开口。**
逐字实时转写有一个 B 方案给不了的心理作用：**用户一开口，字就在动**。屏幕在"回应"他，他知道系统听见了。云端 ASR 那 1–2 秒的空白，在一个本来就紧张的初学者面前，会被读成"我说错了吧？它没听懂"。而 `Tab2_v2 §七之二 D-1` 已经定了转写要弱化、要让视线离开屏幕——**弱化的前提是它可靠且即时**，一个延迟 2 秒才蹦出来的转写反而会把视线拽回屏幕。

**2. 识别不准这件事，在这个产品里的代价比通常小。**
因为 `PRD §6.2.3` 已经废除了"达标判定"——**我们不拿转写去判用户说得对不对**。转写有两个用途：给用户看（确认被听见）、当 `sample_sentence` 存进账本。识别偏一点，第一个用途不受影响，第二个用途影响的是账本里那句例句略有出入，**不影响任何判定和统计**。

> ⚠️ 但这条有一个例外必须点破：**正确性判定（`used_correctly`、语法错误）是基于转写文本做的**。转写错了 → 判成语法错误 → 写进 `learning_events` → 出现在总结卡的"待提高"里 → **用户看到一条自己根本没说过的错误**。这是 A 方案最真实的风险，对策见下面第 4 条。

**3. 免费和零延迟在 MVP 阶段的复利很高。**
你现在需要的是**快速验证 agent 的对话质量**（`Tab2_v2 §3.2` 说得很对：这一轮的赌注是 prompt 质量，不是数据完备性）。让 ASR 变成一个要付钱、要调延迟、要处理网络失败的模块，会分走本该花在 prompt 上的注意力。

**4. 对策：给 ASR 包一层协议，并给"待提高"设置信心门槛。**

```
protocol SpeechRecognizing {   // 前端定义
    func start() async throws
    var partialText: AsyncStream<String> { get }   // 逐字
    func stopAndFinalize() async throws -> String  // 整句
}
```

系统实现 `AppleSpeechRecognizer`，将来换云端只加一个 `CloudSpeechRecognizer`，**对话页一行不用改**。这与 `CLAUDE.md` 里"AI provider 不写死"的思路一致。

同时在服务端加一条硬规则：**转写文本置信度低于阈值时，这一轮只记 `spoken_count`，不写 `learning_events`。** 宁可少报一条待提高，也不能报一条假的——因为假的那条会直接破坏用户对整个产品判断力的信任。

**什么时候该换成 B**：上线后看两个数——① 用户重说率（同一轮内连续说两次），② 母语兜底使用率异常高（可能不是不会说，是说了没被听懂）。任一明显偏高就换。

> **⏳ 待你拍板**：接受建议 A，还是要我按 B 重写这一节。

### 3.2 AI 链路：一场语音对话在后台是怎么跑的

你问的三个方案，逐个讲清楚它们**到底是什么**，再比。

#### 方案一 · 三段拼装：ASR → 文本大模型 → TTS

**它是什么：** 把一场语音对话拆成三个独立零件。用户说话 → 手机把声音转成文字 → 文字发给 Gemini（就是现在 `generate` 用的同一个模型）→ Gemini 回一段文字 → 再把文字转成声音播出来。

**打个比方：** 像一个不会说话但会写字的老师，配了一个翻译员和一个朗读员。老师全程只处理文字。

**它的决定性优势：中间那段文字是干净的、可以随便加工的。**
这在本产品里不是"顺便的好处"，是**刚需**——因为你有一整套要在每一轮做的事：

- 判这句语法对不对 → 写 `learning_events`
- 从这句里抽出用了哪些账本里的词 → `spoken_count += 1`
- 判是不是第一次说出口 → 写 `first_spoken_at` + `breakthrough` 事件
- 重新推断当前话题 → 给实时推荐重排候选

**这四件事全部需要一段规整的、分好轮次的文本。** 方案一天然就有。

**代价：** 每轮延迟约 1–2 秒（转文字 + 模型思考 + 转声音）。这个延迟是可感的，但可以用"AI 开口前先出一个思考中的轻微动效"缓解——用户对"对方在想"是有耐心的。

---

#### 方案二 · 端到端实时语音模型（Gemini Live / OpenAI Realtime 类）

**它是什么：** 不拆零件。你把麦克风的声音直接**流式**送进模型，模型直接**流式**吐出声音。中间没有文字这一站。

**打个比方：** 直接给你接了一个真人电话。

**它的优势是体验上的，而且是真优势：** 延迟能压到几百毫秒，可以打断、可以插话、能听出你语气里的犹豫。**作为"陪练"，它是三个方案里最像人的。**

**但它和你这个产品的架构有一处硬冲突：**

> 你要的不只是"聊得爽"，你要的是**这场对话在账本里留下痕迹**。而端到端模型的输出是声音流，**没有干净的分轮文本**。

想拿到文本，有两条路，都不好：
- 让模型**同时**输出文字轨（部分模型支持）——但这份文字是它自己说的话的稿子，**不等于用户说了什么**，而 `spoken_count` 记的恰恰是用户那句。
- 在旁边**再挂一路 ASR** 专门听用户 → 那你其实又回到了方案一，只是多花了一份钱。

**另外三条现实代价：**
1. **贵**，且按音频秒数计费，一场 10 分钟对话的成本比方案一高一个量级。
2. **它会打断人**。真人般的实时性意味着模型会在你停顿时接话——而 `PRD §6.2.4` 是拍死的："AI 在对话进行中绝不打断"。要压住它反而要额外调教。
3. **"母语兜底"这个核心机制难做**。兜底要的是：用户说中文 → **不推进剧情** → 弹一个译文框 → 等他用英文再说一遍。这是一个需要**拦截并中断**模型正常反应的流程，在端到端的连续流里很难干净实现。

---

#### 方案三 · 先做文本对话，语音后置

**它是什么：** 先按聊天界面做，用户打字，AI 回文字。验证 prompt 和 agent 逻辑，语音之后再加。

**它的优势：** 最快、最便宜、最容易调 prompt。你能在两三天内知道"这个 agent 到底聊得行不行"。

**但它违反两条已定原则**，且违反得很实质：

- `PRD §6.1.2`：MVP 无文本聊天模式。
- `PRD §7.1`：**打字明确不算"用户输出"**——原文是"打字能绕过'开口'这道坎，对口语产品不算数"。

所以文本版跑出来的 `spoken_count` **全是假的**，`breakthrough`（北极星指标）也是假的。你会得到一堆数据，但一个都不能用来判断产品是否有价值。

> **不过它有一个合法的变体，我建议采纳**：**不做面向用户的文本模式，但做一个内部的文本调试入口**（Debug 菜单里的隐藏页，或者干脆一个后端测试脚本）。**同一套 prompt、同一套记账逻辑，只是把语音这一层短路掉。** 这样你可以在真机语音跑通之前就把 agent 的对话质量调到位，而不需要每改一句 prompt 就对着手机说十分钟话。它不写数据到正式账本（或者写进一个测试用户下）。

---

#### 方案一 vs 方案二 的差距到底有多大

**差距是真实的，而且是本次选型里唯一明显的体验代价。不淡化它。**

粗略量级（**待实测校准，不是实验数据**）：

| | 方案一 | 方案二 |
|---|---|---|
| 整轮等待 | 约 1.5–2.5 秒 | 约 1 秒以内 |
| 体感 | 对讲机 | 打电话 |

上手就能感觉到，不是玄学差异。**但有三件事让这个差距没有听起来那么致命：**

**1. 这个差距可以砍掉一大半，靠两个实现细节。**

- **流式播报**：别等模型把整段话生成完再开口，**生成出第一句就开始播**。
- **本地 TTS**：省掉一次网络往返。

两条加起来能把体感压到 1 秒出头——落在"对方在想"的正常范围里，而不是"这机器卡了"。**这两条要写进 E1a 的验收标准**，否则很容易先做成"等全部生成完再播"的简单版本，然后拿那个版本去否定方案一。

**2. 你的用户不在做快速对答。**

端到端低延迟优势最大的场景是抢话、插话、一言一语的快速来回。而一个紧张的初学者，说完一句之后自己也要缓一两秒组织下一句。**1 秒的延迟在快节奏对话里很刺眼，在这个场景里几乎被用户自己的节奏吸收掉了。**

**3. 方案二有一个反向副作用，而且撞的是已定原则。**

它像真人，意味着它**会在你停顿时接话**——而 `PRD §6.2.4` 拍死了"AI 对话中绝不打断"。对一个说得磕磕巴巴、中间要停下来想词的用户，**一个会抢话的陪练造成的伤害，比慢 1 秒大得多**。选了方案二，你反倒要额外花力气把它的实时性压住。

> **一句话总结这个取舍：**
> 体验上方案二赢，但**赢的幅度约 1 秒，且赢在这个产品最不需要的维度上**；
> 而它输掉的是分轮文本——**那不是幅度问题，是有和没有。**

**什么时候该重新评估**：E1 跑通、prompt 稳定之后。那时你已经知道对话质量的天花板在哪，能判断"更像真人"值不值那个成本 + 那套记账的重做。**现在评估这件事的信息不够。**

#### 建议：**方案一，加方案三的内部调试入口**

| | 为什么 |
|---|---|
| 主链路走**方案一** | 你的记账、正确性判定、母语兜底、实时推荐，四件事都要求干净的分轮文本。这不是偏好，是架构约束 |
| **不用方案二** | 它在体验上确实更好，但它拿走的正好是这个产品赖以成立的东西。**等 E1 跑通、prompt 稳定之后再评估**——那时你已经知道对话质量的天花板在哪，能判断"更像真人"值不值那个成本 |
| 补一个**内部文本调试入口** | 把"调 prompt"和"调语音"两件事解耦。这两件事的失败模式完全不同，混在一起你分不清是 agent 笨还是麦克风没听清 |

**具体的模型选择：** 主对话用与 `generate` 相同的 provider（Gemini 3.7 Flash）起步——**理由不是它最好，是它已经接好了、你已经知道它的脾气、且 `CLAUDE.md` 明确要求 provider 可换。** 对话对模型的要求（多轮一致性、不跑题、不说教）比生成卡片高，**上线前必须专门验一次**，如果达不到就换更强的模型，只改 Edge Function 里的一个常量。

**TTS：** MVP 用 iOS 内置的 `AVSpeechSynthesizer`（免费、零延迟、离线可用）。它的声音明显是机器音，但在"AI 说英语给你听"这个场景里可接受。若上线后反馈声音出戏，再换云端 TTS——同样包一层协议，可替换。

> **⏳ 待你拍板**：主链路方案一 + 内部文本调试入口，是否通过。

## 四、对话前：从点卡片到 AI 开口

### 4.1 入口（裁决 C1）

**唯一入口：Tab2 首屏的分类卡。** 整卡可点 = CTA 按钮可点 = 同一个动作，都直接进对话页（`Tab2_v2 拍板 11c`）。

- 代码上就是把 `MineView.swift:58` 的 `ConversationStubView(sceneCategory: cat)` 换成 `ConversationView(sceneCategory: cat)`。
- **传参只传 `sceneCategory`**，不传 seed。理由见 §1.3。
- 转场用卡片展开（共享元素动画），让人觉得"这张卡打开了"。

**~~PRD §6.1.1 的"从词详情发起"作废~~**，需回写 PRD（§9）。

### 4.2 Seed 装配（裁决 C2：进页时只知道分类）

因为收窄发生在对话第一轮，seed 装配分成**两段**：

```
第 1 段 · 进页时（只知道分类）
  服务端拿 user_id + scene_category，组装"分类级 seed"：
    ├─ 该分类下的子场景列表（按 occurrence_count 降序，取前 3–5，只取出现 ≥2 次的）
    ├─ 每个子场景的一句用户原话（≥6 字）
    └─ 该分类下的候选词（供实时推荐用，见 §6.3）
  → agent 用它生成第一句：收窄问题

第 2 段 · 用户答完第一轮（知道具体子场景了）
  服务端按选中的子场景，追加"子场景级 seed"：
    ├─ 该子场景下最近 2–3 条 materials 的 raw_content（原句、英文、key phrases）
    └─ 有图片的话，图片的英文描述（不是图片本身，除非模型支持）
  → agent 从这里开始聊真事
```

**为什么分两段而不是一次性全塞进去：**
一个分类下可能有 5 个子场景 × 每个 3 条素材 = 15 条原始内容。全塞进 prompt 会：① 上下文膨胀、贵且慢；② 模型注意力被稀释，容易把不相关的事混着说。**第一轮它只需要知道"有哪几个话题可选"，不需要知道每个话题的细节。**

**用户答"随便"或不答怎么办**（`Tab2_v2 §A2` 已定不许追问第二次）：
按下面顺序自动挑一个，直接进第 2 段：

| 顺序 | 挑哪个 |
|---|---|
| 1 | 出现次数最多的子场景（他常回去的地方） |
| 2 | 最近有素材的子场景 |
| 3 | 该分类下任意一条最近的 material（连子场景都没有时） |

**用户答了一个不在列表里的东西**（"我想聊上周出差"）：
**跟着他走。** 这是"引导锚"（`Tab2_v2 §3.4`）——用户当场说出来的处境，直接当锚点用，不需要账本里有。此时第 2 段 seed 为空，agent 就从他这句话往下聊。**这不违反"agent 不虚构用户的生活"——素材是用户嘴里出来的。**

### 4.3 开场白：先进页，后出声（拍板待定项 4）

**决定：立即进页，页面先显示话题名 + 一个"准备中"的轻状态，AI 的第一句生成完再出声 + 出字。**

*为什么不等生成完再转场*：卡片展开动画是这个交互的情绪高点，让用户对着 Tab2 首屏干等 1–2 秒，那个"这张卡打开了"的感觉就没了。**先给空间、再给内容**，是移动端的常规做法，用户对"页面已到、内容在加载"完全能接受；对"点了没反应"则不能。

*"准备中"长什么样*：不要转圈菊花（那是技术味的）。用麦克风图标的呼吸动效 + 一行淡字（`Getting your topics…`），≤2 秒。超过 3 秒仍未返回 → 降级为**本地兜底开场白**（用子场景名拼一句固定句式），**绝不让用户对着空屏等**。

### 4.4 麦克风权限：这是必经的第一屏，不是边缘情况

`CLAUDE.md` 硬约束 + `Tab2_v2 §七之二 B` 都点了名。具体三态：

| 态 | 屏幕 | 文案方向 |
|---|---|---|
| **未请求** | 进页后、AI 开口前请求。**不要在 Tab2 首屏提前请求**——那时用户还不知道要干嘛，拒绝率高 | 系统弹窗前给一句自己的说明："Practice happens out loud — we'll need your mic." |
| **已拒绝** | 整屏说明 + 一个跳系统设置的按钮 | 说用途，不说"你必须允许"。给一条退路（返回 Tab2） |
| **已授权** | 直接进 §4.3 | — |

> **语音识别在 iOS 上是两个权限**：麦克风（`NSMicrophoneUsageDescription`）+ 语音识别（`NSSpeechRecognitionUsageDescription`）。两个都要在 Info.plist 里写用途，**少一个会直接崩溃**，不是报错。

## 五、对话中：数据侧要做的事

> 呈现侧（三区版面、转写弱化、推荐收起、无纠错标记）在 `Tab2_v2 §七之二 C/D` 已经定完，本文不重复。本节只写它没写的**数据流**。

### 5.1 补 `learning_events` 表（E1 第一件事）

这是 §〇-2 说的那个坑。建议 schema（沿用两张 lexicon 表的既有范式）：

```sql
CREATE TABLE IF NOT EXISTS learning_events (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id      uuid NOT NULL,
  session_id   uuid,                    -- 哪一场对话（见 §5.3）
  entry_id     uuid REFERENCES lexicon_entries (id) ON DELETE RESTRICT,
                                        -- 可空：语法类问题不属于某个词（PRD §6.2.6 明确）
  event_type   text CHECK (event_type IN ('gap','error','breakthrough','correction')),
  aspect       text CHECK (aspect IN ('vocab','grammar','collocation','pronunciation')),
  detail       jsonb,                   -- 用户说的那句 + 建议说法 + 错在哪
  created_at   timestamptz NOT NULL DEFAULT now()
);
```

**四个 `event_type` 分别谁写：**

| 类型 | 什么时候写 | 谁触发 |
|---|---|---|
| `gap` | 用户用了母语兜底（想说但不会） | 母语兜底流程，**必写** |
| `error` | 判定这轮有语法/用法错误 | 每轮的正确性判定 |
| `breakthrough` | 某个 entry 的 `spoken_count` 由 0 变 1 | **记账 RPC 内部自动写**，不靠模型判断 |
| `correction` | 同一 entry / 同一 aspect 出现"先错后对"的翻转 | 记账时查历史 |

> **`breakthrough` 必须由数据库触发，不能让模型判。** 它是北极星指标，必须百分之百可靠、可复现。`spoken_count` 从 0 变 1 是一个确定的数据事实，写在 RPC 里就永远不会漏、不会重复。

**RLS 与安全**：照抄 lexicon 两张表的范式（Edge 用 service key 写、表上开 RLS 兜底、无 uid 直接 401）。

### 5.2 新增对话侧记账 RPC

新建 `record_lexicon_dialogue_units`，**不改现有的 material 版**（它已上线验证，动它是没必要的风险）。

它比 material 版多做四件事：

```
1. source_type = 'dialogue'，source_id = 对应的 message/turn id
2. spoken_count += 1；若原本为 0 → 写 first_spoken_at + 插一条 breakthrough 事件
3. 账本里没有这个词 → 新建 entry，origin = 'spoken'（而不是 'captured'）
4. 接受 used_correctly (bool?) 和 is_known_gap (bool)
```

**必须继承 material 版的两个既有行为：**
- **枚举容错**：模型漂移的值强制转成 valid-or-null，一条脏数据不能中断整批（现有 RPC 已这么做）。
- **防复活**：入账前查 `status`，命中 `'excluded'` 就跳过，不重建（`PRD §6.3.5`）。**这条现在还没实现**（因为删除功能没做），但对话侧记账是第二个入口，**在这里一并加上，免得将来两处都要补**。

### 5.3 对话 session 要落库（Tab1 的内存 session 不能复用）

`PRD §6.0` 已经点明：Tab1 的 `ConversationSession.swift` 是**纯内存**的工作记忆，App 被杀即丢。对话页需要**服务端 session**，因为：

- 用户中途接电话、切出去、App 被系统回收 → 回来要能接着聊；
- 记账要知道"这几轮属于同一场"（`learning_events.session_id`）；
- 总结卡是对"一场"的总结，没有 session 就没有边界。

最小 schema：

```sql
CREATE TABLE IF NOT EXISTS dialogue_sessions (
  id             uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id        uuid NOT NULL,
  scene_category text,
  scene_detail   text,          -- 第一轮收窄后回填
  turn_count     int  NOT NULL DEFAULT 0,
  ended_at       timestamptz,   -- null = 进行中
  end_reason     text CHECK (end_reason IN ('user_exit','idle_timeout','error')),
  created_at     timestamptz NOT NULL DEFAULT now()
);
```

**轮次本身存不存？** 建议存（一张 `dialogue_turns`，记 role / text / created_at）。理由：① 恢复会话要重放上下文；② 转写质量、agent 质量都要靠翻真实记录来判断，没有它你只能靠用户口述；③ 将来"对话记录回写 Tab1"（已定方向、本轮不做）直接读它。
**但要写进隐私说明**——这是用户的口语记录，敏感度高于素材。默认全私有、按 `user_id` 隔离，与 `PRD §8` 一致。

### 5.4 母语兜底的完整数据流（全产品最高价值的语料）

`PRD §6.2.2` 说它产出 `is_known_gap`，`Tab2_v2 D-2` 说按钮文案要不带羞耻感。串起来：

```
用户点 [Say it in Chinese] 或直接说了中文
   ↓
① 弹框：目标语言译文 + 重点词音标 + 一句轻提示（"念念看"）
② 立即写一条 learning_events：event_type='gap', aspect='vocab'
③ 剧情不推进——AI 不回话、不评论、不接梗
   ↓
用户用目标语言说出来（照念 / 变体 / 说岔了都算）
   ↓
④ 正常记账：这些词的 occurrence 上 is_known_gap = true
⑤ 剧情推进，AI 回话
```

**第 ③ 步是最容易实现错的一步。** "不推进"不等于"没反应"——屏幕上要有明确的、非评判的信号表示"我在等你说英文"（比如麦克风保持激活 + 译文停留）。如果什么都不发生，用户会以为卡住了。

**用户念完之后一直不说 / 直接跳过怎么办**：不追、不拦、不弹二次提示。`gap` 事件已经记下了（那才是数据价值所在），剧情用一句自然的话推进过去。**卡住用户会让他下次不敢按这个按钮，那等于亲手关掉最好的数据源。**

### 5.5 每轮要判什么（给 prompt 的清单）

每一轮 AI 回复时，同一次调用**顺带**输出一个结构化的判定块（不是额外调用，`PRD §6.2.6` 已明确"每轮顺手记"）：

```json
{
  "reply": "AI 说的话（目标语言）",
  "used_entries": ["set up", "run late"],       // 用户这句用到的、账本里已有的词
  "new_expressions": [{"lemma":"…","kind":"…"}],// 账本里没有、值得记的
  "correctness": { "ok": true, "issues": [] },  // 或 issues: [{aspect, said, suggested}]
  "current_topic": "晨会前"                      // 重新推断的话题，给推荐重排用
}
```

**三条硬约束写进 prompt：**
1. `reply` 里**绝不包含纠错内容**。`issues` 只进数据，不进 `reply`。这是 `PRD §6.2.4` 的落点，**也要在前端组件层再拦一道**（`Tab2_v2 D-5`：纠错标记必须是组件层面的硬约束）。
2. `issues` **最多 2 条**，且只报有把握的。宁少勿滥——总结卡只显示 1–2 条，报十条也是浪费，还增加误报概率。
3. 转写置信度低时（§3.1），**丢弃 `issues`，保留其余**。

## 六、对话后：总结卡与收尾

### 6.1 总结卡三块（`PRD §6.3.2` 已定，本文补"数据从哪来"）

| 块 | 数据来源 | 空了怎么办 |
|---|---|---|
| **用出了哪些你的词** | 本场 session 内 `spoken_count` 被 +1 的 entries，且 `origin='captured'` | 不显示这一块 |
| **待提高 1–2 条** | 本场 `learning_events` 里 `event_type IN ('gap','error')`，按 aspect 去重后取 1–2 条 | 不显示 |
| **进步** | 本场 `breakthrough` + `correction` 事件 | 不显示 |

**为什么它能即时、几乎零成本**：三块全部是"把已经攒好的笔记按类拼一下"，不是重新分析整段对话。所以用户点退出的那一刻直接拼卡，无需等待。

> 若想加一句 AI 生成的温暖收尾语——**异步补，不挡卡片先出**。卡片必须立刻可见。

### 6.2 文案口气（三块各一条硬规则）

| 块 | 用 | 不用 |
|---|---|---|
| 用出的词 | `You used these today` | ~~`5/12 words used`~~（比例即打分） |
| 待提高 | `You could also say…` | ~~`Mistakes`~~ / ~~`Corrections`~~ / 任何红色 |
| 进步 | `First time you've said this out loud` | ~~`+1 progress`~~ / 任何计数器 |

**贯穿的一条**：`PRD §7.3.5` 定的"用质变叙事，不用进度条不用打分"。**总结卡是这条原则最容易破功的地方**——因为它天然想报数。守住。

### 6.3 实时推荐的数据来源（对话中，但写在这里因为它和账本耦合）

`PRD §6.2.5` 定了五个排序信号。**MVP 建议只实现前两个**：

| 信号 | MVP 做吗 | 理由 |
|---|---|---|
| 动态相关性（按 `current_topic` 重排） | ✅ | 不做的话推荐会一直锚死开场，很快就不搭 |
| 已知缺口优先（刚兜底暴露的） | ✅ | 免费——`is_known_gap` 就在手边，且这是当下最想说的 |
| tier 缺口加权 | ⏸ | 依赖成长层的缺口画像，本轮成长层只有骨架 |
| 闲置储备激活 | ⏸ | 需要足够的历史数据才有意义 |
| i+1 + 多样性 | ⏸ | 调优项，先看基础版效果 |

**候选池**：该分类下 `status='active'` 的 entries，**优先 `spoken_count=0` 的**（还没说过的才值得推）。取 10–15 个进 prompt，模型从里面挑 3 个显示。

> ✅ 这里原本会撞上"长文 `sample_sentence` 存整篇"的问题（推荐词要带例句进 prompt，整篇会撑爆上下文）。**该问题已在 `generate/index.ts` 修复**（§1.4 坑 2），无需额外处理。

### 6.4 总结卡的形态：暂不定（按你的意思）

你要先上机体验再决定。两者的差别写在这里，体验时对着看：

| | **整页** | **半屏 sheet** |
|---|---|---|
| 退出步数 | 2 步（结束 → 看卡 → 关闭回 Tab2） | 1 步（下滑即走） |
| 被看见的概率 | 高，必须处理它 | 低，容易被顺手划掉 |
| 情绪 | 像"一场练习的结算" | 像"顺便给你看一眼" |
| 风险 | 想走的人被拦一下 | **本轮唯一的闭环凭证被划掉了** |

**我的倾向是整页**，理由只有一条：`Your words` 和 Tab1 回写都推迟了，这张卡是用户唯一能拿到的"我刚做了一件事"的证明。**但这个判断值得你亲自体验一次再定**——如果实际用下来"被拦住"的不适感很强，那说明它对当下的用户不是奖励而是障碍，那就该改成 sheet。

**实现建议**：**先按整页做，但把它做成一个独立的 View**，改成 sheet 只是换一层 presentation modifier，不用重写内容。这样体验完再改的成本接近零。

### 6.5 空闲与收尾（拍板待定项 6）

| 阶段 | 时间 | 做什么 |
|---|---|---|
| 静默 | **20 秒** | 什么都不做。人思考本来就要时间，20 秒内插话是打断 |
| 轻推 | **20 秒时** | AI 说一句短的（"Take your time."）。**一次，只一次** |
| 收尾 | **再 60 秒**（累计 80 秒） | 停止麦克风监听 → 生成总结卡 → 记账落库 → 出卡 |

**为什么停止监听是必须的而不是可选的**：`PRD §6.2.7` 已经写了——持续监听麦克风耗电，且用户已经离开了，还在录他周围的声音，隐私上也不合适。

**收尾时的记账不能省。** 硬规则：`end_reason` 无论是 `user_exit` 还是 `idle_timeout`，走的是**同一段收尾代码**。不要为"主动退出"和"自动收尾"写两条路径——那必然有一条会漏记账。

### 6.6 退出后 Tab2 首屏必须有变化（`Tab2_v2 §七之二 E`）

这是闭环最后一环，最容易漏。具体做什么：

- 退出时 `MineView` 的 `vm.load()` 必须被触发（现在有 30 秒的 stale 判定 `loadIfStale()`——**从对话页返回要强制刷新，不能走 stale 逻辑**）。
- 刚练过的分类卡上要看得出变化。**本轮 `Your words` 推迟了，所以不能靠"说过 N 次"的数字。** 建议最小做法：该分类卡上出现一行 `Talked about this today`，或 hero 卡换成刚练过的那个分类。
- **这一条不做，用户会觉得刚才那 10 分钟没有发生过。**

### 6.7 新素材确认（`PRD §6.3.4`）

对话里冒出的、账本里没有的表达 → 打包成预览卡问"要不要加入你的素材"。

**本轮建议：做，但做成总结卡里的一小块，不单开一屏。**
理由：单开一屏 = 退出多一步，而退出路径上每多一步，总结卡被看见的概率就掉一截。放在总结卡底部，勾选 + 一个确认按钮，默认全不勾（"素材是用户的"，需要主动认领）。

> ⚠️ 注意区分两件事（`Tab2_v2 §3.1c` 的警告）：**对话记录**是事实、自动落库；**新素材入 materials** 需要用户确认。不要因为都在一场对话里就把后者也自动化了。

## 七、成长层：本轮只做骨架

### 7.1 本轮做什么、不做什么（裁决 C3）

| | 本轮 |
|---|---|
| 数据口径确定下来（三种状态、两种差距） | ✅ 做，§7.2 |
| `learning_events` 建表并开始积累 | ✅ 做（E1 已含） |
| **独立的成长/侧写页** | ❌ **不做** |
| Tab2 首屏的成长层入口 | ❌ **不做**——首屏是"开口的入口"，加一个"看看你的分析"会把它变回浏览目的地 |
| 总结卡带成长层链接 | ❌ 本轮无处可链 |
| 周期性推首页 | ❌ 不做 |

**为什么成长层现在只做骨架，理由要说清楚：**

> **成长层是对数据做减法的产物，而现在数据还没有。**
> 它的五个角度（高频表达、更地道的说法、同义扩展、语法薄弱点、闲置与进步）**全部依赖多场对话累积出来的分布**。用户练了 2 场，"你最常用的表达"是一个用过 2 次的词——那不叫洞察，那叫噪音。
> 更糟的是，**一个说不出洞察的成长页，会让用户认定这个产品没东西**，而这个第一印象很难扭转。**宁可晚出，不可早出。**

**什么时候该开做：** 一个活跃用户累计 **≥10 场对话**、账本里 `spoken_count>0` 的词 **≥30 个** 之后。到那时先拿你自己的账号手工看一遍数据，**看得出洞察再做界面**。

### 7.2 数据口径（现在就定死，因为它决定字段怎么写）

**三种状态**（`PRD §7.2` 已定，此处只是把判定条件写成可查询的形式）：

| 状态 | SQL 条件 | 含义 |
|---|---|---|
| 碰过没说过 | `origin='captured' AND spoken_count=0` | 练习目标 |
| 碰过也说过 | `origin='captured' AND spoken_count>0` | 你真能用的 |
| 没碰过直接说出来 | `origin='spoken'` | **他在长新东西** |

**两种差距：**
- **正向** = `origin='spoken'` 的词条 + `breakthrough` 事件。
- **负向** = 有但没说过的词（闲置）+ `learning_events` 里反复出现的 `error`（按 `aspect` 分，**语法是重点**）。

> **这三种状态的正确性完全取决于 `origin` 字段写对。** 对话侧记账 RPC 里那句"账本里没有 → 新建 entry 且 `origin='spoken'`"（§5.2 第 3 条）如果写错成 `'captured'`，**正向差距就永远是空的**，成长层会失去它最重要的一块内容，而且不会报错、你也看不出来。**这条必须写单元测试。**

### 7.3 什么算"用户输出"（`PRD §7.1`，重申一遍因为它极易被放松）

= **用户在对话里用目标语言说出来的话。**

**明确不算的**：AI 生成的内容、母语原话、查词、**以及 Tab1 打字捕获的英文句子**。

> 最后那条最容易被"顺手放松"——打字捕获的英文看起来也是英文、也在账本里、统计进去数字还更好看。**但打字绕过了"开口"这道坎。** 一旦放松，`spoken_count` 就不再有意义，北极星指标也跟着废掉。**在 RPC 层面守住：只有 `source_type='dialogue'` 的记账才动 `spoken_count`。**

### 7.4 "卡顿 → 流畅"算不算第三种进步：**本轮不做**

`PRD §6.3.3` 留了这个待确认项。结论：

**不做，但把数据先攒上。** 理由：
- 它需要一套现在完全没有的数据：每轮的停顿时长、语速、犹豫次数（"um"、重启句子）。
- 这些数据**只有在录音/转写那一刻才拿得到**，事后无法补算。

所以建议：**在 `dialogue_turns` 上加两个便宜的字段**——`duration_ms`（这一轮用户说了多久）和 `word_count`。语速 = 两者相除。**先攒着，不做任何呈现。** 攒三个月后如果看得出规律，那时再决定要不要做成第三种进步；如果那时才想起来加字段，历史数据就永远补不回来了。

**为什么只加这两个而不是全套**：它们从 ASR 那里免费就能拿到，零额外成本。停顿检测、犹豫词识别要额外的信号处理，那是有成本的，不在"先攒着"的范围内。

#### D 的配套：隐私说明必须同步写

`dialogue_turns` 存的是**用户的口语原话逐轮全文**，敏感度高于 `materials`（素材是他主动写下的，口语是他随口说的）。存可以，但三件事要一起做，**不能等上线后补**：

| 要做的 | 具体 |
|---|---|
| **技术上** | 照抄 lexicon 两张表的范式：`user_id` 强隔离 + RLS 兜底 + Edge 层无 uid 直接 401。**任何情况下不跨用户可见**（`PRD §8`） |
| **告知上** | 隐私说明里写清楚：**存什么**（对话的文字记录）、**为什么**（用来统计你说过哪些词、生成练习总结）、**存多久**、**怎么删** |
| **音频不存** | **只存转写文本，不存录音音频。** 音频的敏感度和存储成本都高一个量级，而本产品所有功能（记账、判定、总结）用文本就够——存音频拿不到任何额外价值 |

> **"音频不存"这条建议现在就写死。** 它是那种一旦开了口子就很难收回的决定：将来若有人为了"改进 ASR 准确率"想留音频，会发现用户协议和用户预期都不支持，改起来很贵。
