## 〇、一句话结论

**这份 PRD 的核心洞察是对的，两个关键决策是可疑的，七处事实描述已经过期。**

- **对的**：「系统里没有『词』这个可聚合的独立对象，所以 agent 规划里六条诉求全部落空」——这个诊断准确，`lexicon_entries` + `lexicon_occurrences` 的建模也是标准做法，没有过度设计。**这一层建议照做。**
- **可疑的两个决策**：① 把 Tab2 从"以场景为中心"翻转成"以词为中心"（§3.4）——这推翻了 `Tab2_PRD_v1` 里**专门论证过并否决过**的方案，而给出的理由（"和 Tab1 重复"）指向的其实是另一个问题；② 开发排期把「Tab2 换主体」放在「对话层」之前（Slice 3 早于 Slice 4-6）——这会交付一个**六个标签里三个是死的**界面，同时砍掉现在能用的功能。
- **过期的事实**：PRD 第九节的"前置欠账"和第二节的"现状盘点"，引用的是 2026-07-04 那版审计报告的结论。**那之后代码已经修了一大批**，照文档施工会重复劳动。

## 一、事实层：文档描述与当前代码不符的 7 处

> 这一类问题最危险，因为它不会引发讨论，下一个 agent 会直接照着做。

### 事实-1 🔴 `messages` / `profiles` 的迁移文件**已经补好了**，不是欠账

**文档怎么说**：§9.1 把"补 messages / profiles 迁移文件"列为**必须先清的欠账**，§13 Slice 0 也把它列为前置。

**代码实际**：仓库里已有

- `supabase/migrations/20260704010000_create_messages_table.sql` —— 完整 DDL + 两条索引 + RLS 策略（select/insert own）
- `supabase/migrations/20260707000000_create_profiles_table.sql` —— 完整 DDL + `handle_new_user` 触发器 + RLS
- 之后还有 4 个针对 `messages` 的增量迁移（`image_url`、`preset_card_id` 并扩了 CHECK、`source`、drop `parent_message_id`）

**为什么要改**：Slice 0 有两件事，其中一件已经完成。照文档做会让下一个 agent 去"补"一份已经存在的迁移，轻则浪费一轮，重则写出和线上冲突的 DDL。**Slice 0 应缩减为只剩 `source_message_id` 回填一件事。**

### 事实-2 🔴 用户数据隔离**已经修完了**，不是"代码里已在修复"

**文档怎么说**：§2.1 表格里写"审计报告①的高危项，代码里已在修复"——语气是"进行中"。

**代码实际**：三层都已落地。
- `generate/index.ts` 通过 `/auth/v1/user` **验签**后取 uid，写入 `materials.user_id`（不是自己 base64 解 token，这点做得对）
- `get-materials` / `get-vocabs` 拿不到 uid **直接返回 401**，查询强制 `user_id=eq.<uid>`
- `20260704000000_add_rls_materials.sql` 给 materials 开了 RLS 四条策略，messages 的 RLS 在建表迁移里

**为什么要改**：这不是措辞问题。**地基比文档以为的更结实**，意味着 lexicon 那两张新表可以直接照抄这套模式（Edge 用 service key + 表上开 RLS 做纵深防御），文档应该把它写成"已验证的既有范式，新表照此办理"，而不是留一个模糊的"在修"。

### 事实-3 🟡 §2.3 的 `materials` 表结构盘点漏了 `source` 列

**代码实际**：`20260709000000_add_source_to_materials.sql` 加了 `source text NOT NULL DEFAULT 'tab1' CHECK (source IN ('tab1','onboarding'))`，`generate` 每次写入都带它。

**为什么这不是小事**：它逼出一个 PRD 完全没回答的问题——**引导页（onboarding）生成的那条素材，要不要记进账本？**

- 记：用户第一次打开 Tab2 就有词，不空；但那条素材可能是"预制卡片"，不是用户真实生活，会污染"从你自己生活取材"的账本和后续的语言习惯分析。
- 不记：账本纯净，但 Tab2 换成账本主视图后**新用户第一眼是空的**——而 `Tab2_PRD_v1` §5 专门论证过"走完引导后 Tab2 不该有真空态"。

这条必须在 PRD 里明确，否则下一个 agent 会随手决定。

### 事实-4 🔴 每条场景素材实际**最多只产出 1 个词条**，不是"一批 key_phrases"

**文档怎么说**：§5.1「s2/s4 抽 `key_phrases` 里的词组」——复数，读起来像一次能抽好几个。

**代码实际**：
- `SYSTEM_PROMPT` 里 s2 / s4 的输出 schema 是 **`key_phrase`（单数，object 或 null）**，只让 AI 挑"最地道的那一个"
- `buildRawContent` 落库时写的是 `key_phrases: kp ? [kp] : []` —— 一个数组，但里面**最多一个元素，也可能是空数组**

**为什么这是这份 PRD 最大的落地风险**（详见逻辑-4）：账本的全部卖点是"能数频率"。但供给端一次输入最多进 1 个词，且 AI 每次挑的都是"最地道的那个"、天然倾向挑新鲜的，**同一个词被重复挑中的概率很低**。§3.1 举的例子"set up 你其实已经用过 7 次了"，按当前供给可能要几个月才攒得出来。

### 事实-5 🟡 `source_message_id` 该指向哪一条 message，文档没定义

**文档怎么说**：§9.1「`saveMaterial` 时回填 `source_message_id`」。

**代码实际的困难**：一次 `generate` 请求写了**两条** message —— user 行（原始输入，图片挂在这里）和 assistant 行（AI 卡片，素材由它提取）。而且 `insertMessage` 用的是 `'Prefer': 'return=minimal'`，**根本不返回 id**。

**所以要回填，必须先决定两件事**：
1. 指向 user 行（能反查原始输入和图片）还是 assistant 行（能反查生成的卡片）？
2. `insertMessage` 要改成 `return=representation` 并把 message 写入从"并行 fire-and-forget"改成"串行等 id"——这会**给主响应加一次 DB 往返的延迟**。

这是 Slice 0 唯一剩下的一件事，却是文档里最含糊的一句话。

### 事实-6 🟡 纯图片素材落库即失真的老 bug 仍在，账本链路没有考虑它

**代码实际**：`buildRawContent` 的 s4 分支仍是 `chinese_original: String(content.chinese_original ?? '')`——纯图输入时 AI 返回 `null`，被压成**空字符串**；`ai_scene_guess` 不在 `SceneRawContent` 结构里，**直接丢弃**（审计③，至今未修）。

**为什么和账本有关**：§5.1 抽词要用场景内容做上下文，而纯图素材的上下文（AI 的场景猜测）已经在落库那一刻丢了。**引导页的纯图路径是新用户的第一条素材，第一条就命中这个 bug。**

### 事实-7 🟢 s2 素材的 `chinese_original` 里装的是 AI 中译，不是用户原文

**代码实际**：`buildRawContent` 的 s2 分支 `chinese_original: String(content.chinese_translation ?? '')`（审计④指出过，仍未修）。

**和账本的关系**：§5.2.6 要给每条 occurrence 记 `input_lang`（区分母语 vs 目标语言）。s2 的素材，用户输入的是**英文**，但落库的 `chinese_original` 字段是**中文 AI 译文**——如果抽词或语言判定读了这个字段，`input_lang` 会判错。

## 二、逻辑层：内部不自洽或依据薄弱的 11 处

### 逻辑-1 🔴🔴 Tab2 翻转成"以词为中心"，推翻了已论证否决过的方案，而给出的理由指向的是另一个问题

**这是整份文档最需要重新讨论的一条。**

**文档的论证链**（§3.4）：
> Tab2 和 Tab1 重复 → 因为 Tab2 详情页直接复用 Tab1 的回复卡 → 所以场景卡这个单位错了 → 所以把 Tab2 换成词条列表，场景降为"词的来源背景"

**三个问题**：

**① 结论推翻了已定的产品根基。** `Tab2_PRD_v1` 第一节写死的三条根基之一是：**"场景是根，词汇是叶——词汇脱离场景会失去处境感和记忆价值"**。§3.2 还专门列过一个否决方案：

> **3.2 为什么不做"场景/词汇并列 Tab"（否决方案）**：词汇一旦从场景里被抽出来单独管理，用户的注意力就从场景转移到了单词本身，处境感变弱——而处境感正是这个产品记忆效果的来源。

新方案做的正是当初被否决的事，而且**走得比被否决的方案更远**：当初否决的只是"词汇和场景并列"，新方案是"词汇为主体、场景退居第二层"。推翻一条论证过的原则是可以的，但**得用比原论证更强的理由**，而现在给的理由（见②）比原论证弱。

**② 论证链中间断了一环。** 文档自己指出了"重复"的真实成因：Tab2 的场景详情页**直接复用 Tab1 的回复卡组件**。那是**呈现层没做**，不是**组织单位错了**。

而且 `Tab2_PRD_v1` §4.2 本来就定义了 Tab2 场景卡应该长得不一样：

> s2/s4 流转进 Tab2 后应统一按"英文优先、中文弱化"展示，不延续 Tab1 那套不对称逻辑——因为 Tab2 只关心一件事：这段经历能不能被说出来。

**也就是说，"Tab2 和 Tab1 重复"的解法早就写好了，只是没实现。** 用"换掉整个组织单位"来解决"呈现层偷懒"，代价大得不成比例。

**③ 新方案自己也承认处境感重要，却把它降级了。** §3.4 写"点开一个词还能看到『帮妈妈弄手机』那一幕，记忆锚点还在"——这是承认锚点有价值，但把它从**默认可见**改成了**要多点一次才可见**。产品根基说的恰恰是"词脱离场景会失去记忆价值"，多一次点击就是在制造这个脱离。

**我的倾向（供你判断，不替你决定）**：真正的问题是 **Tab1 和 Tab2 的呈现层没有分化**，不是**组织单位选错了**。更小代价的做法是：
- Tab2 主体**仍是场景卡**，但按"能不能说出来"的练习视角重做呈现（英文优先 / 中文弱化 / 标出哪些词你还没说过），和 Tab1 的"刚生成的卡"明确不同；
- 账本作为**第二个镜头**存在（顶部一个 `Words` 切换，或情境词汇汇总条升级成真账本），承担"跨输入聚合"这件 Tab1 结构上做不到的事；
- 这样既拿到账本的全部数据价值，又不推翻已论证的根基。

**这条必须你拍板，我不替你决定。** 见第五节问题 1。

### 逻辑-2 🔴 "Tab2 = 我在积累什么" 与 "Tab2 不做数字积累" 直接冲突

`Tab2_PRD_v1` 第一节：

> 用户打开这个页面，应该产生的第一反应是"**我想把这个说出来**"，而不是"**我有多少内容**"。
> 进步感知的本质是**质变**（说不出来 → 说出来了），不是**数字积累**（场景数、词汇数）。

新 PRD §3.4 把 Tab2 定义成 **"我在积累什么"**，主视图是**按 `total_count` 排序的词条列表**，每行带频率数字，顶部六个筛选标签。

**这在体验上就是"我有多少内容"的界面。** 而 §7.3 又写"数字只作工具性信息，不作评价指标"——但当数字成了主列表的**默认排序依据**，它就是这个页面的主逻辑，不可能只是"工具性信息"。

这不是措辞问题，是**同一个页面被两份文档赋予了互斥的目标**。要么承认 Tab2 的定位变了（并说清为什么变），要么保留原定位、让账本以别的形态存在。

### 逻辑-3 🔴 排期倒置：Slice 3 会交付一个"六个标签三个是死的"界面，且净减少功能

**文档的排期**：Slice 3（Tab2 换成账本主视图）→ Slice 4-6（对话层）。
**文档自己定的原则**（§13 结尾）：「**任何一片都不依赖后面的片，可随时停在一个完整可用的状态。**」

**但 Slice 3 违反了这条原则**：

| Tab2 的六个镜头 | 依赖什么 | Slice 3 上线时的实际状态 |
|---|---|---|
| `For review`（默认） | `spoken_count` + 缺口画像 | 两者都来自对话层 → **退化成"最近新增"** |
| `All` | `total_count` | ✅ 可用 |
| `Not yet`（`spoken_count=0`） | 对话层 | 所有词都=0 → **等于 All，无意义** |
| `Spoken`（`spoken_count>0`） | 对话层 | **恒为空** |
| `Recent` | `created_at` | ✅ 可用 |
| `By scene` | occurrences | ✅ 可用 |

也就是说，Slice 3 交付的界面里**六个标签有三个是死的**（其中一个还是默认选中的那个），**同时**砍掉了现在线上能用的场景卡浏览和词汇本。这一片是**净负收益**。

**这条和逻辑-1 是同一个根：如果 Tab2 保持场景为主、账本作为第二镜头，这个问题自动消失**——账本镜头可以等对话层就绪后再点亮，中间不砍任何现有功能。

### 逻辑-4 🔴 账本的核心卖点（频率）在 MVP 数据量下可能长期等于 1

接**事实-4**。把供给量算一遍：

- 一次 Tab1 输入 → 最多 1 个词条（s2/s4 的单个 `key_phrase`，或 s1/s3 的 1 个主词）
- 假设活跃用户一天输入 5 条 → 账本一天最多长 5 行
- 而这 5 个词**几乎不重复**：AI 每次挑的是"这条内容里最地道的那个表达"，本身就倾向挑新鲜的、不常见的

**结果**：账本长得很慢，而且 `total_count` 长期是 1。**"按频率排序"和"看见你最常用的表达"这两个核心体验，在数据上是空的。**

这直接影响：`All` 镜头（按频率）、§7.3 角度 1（高频表达）、§6.7 实时推荐（挑高频可用词）——**三个功能同时失效**。

**PRD 完全没有评估这个风险。** 要么扩大提取（让 AI 一次输出多个可学单元 / Stage 3 独立再抽一遍全文），要么承认 MVP 阶段"频率"不是主排序维度、改用别的（最近 / 情境 / 未说出）。这是必须现在决定的，因为它决定了 §5.1 提取规则怎么写。见第五节问题 2。

### 逻辑-5 🟡 `tier` 的"双信号判定"在首次写入时无法成立

§5.2.1 说 tier 用「通用高频词表（静态）**+ 跨情境扩散度修正**」。

**矛盾**：跨情境扩散度是**后验的**——要等这个词在多个情境里出现过才算得出来。但 `tier` 是 `lexicon_entries` 上的一列，**在词条第一次创建时就要写一个值**。第一次出现时扩散度恒为 1，这个信号提供不了任何信息。

文档写了"可后台重算"，但**没有这个重算作业的任何设计**：谁触发（定时？还是每次 occurrence 写入时检查）？多久跑一次？重算后用户在 Tab2 看到的分层标签会不会**当着他的面跳变**（昨天还是"场景词"，今天变"框架词"）？

**建议**：MVP 只用静态词表判 tier（确定性、零成本、可测试），把扩散度修正明确标为"迭代项"，并写清重算作业的触发方式和对 UI 的影响。

### 逻辑-6 🟡 "不判达标"与 `used_correctly` / 错误检测的边界没划清

§12 已定死原则：**"不拿用户说的去比对 AI 译文、不判达标——用户实际说出来什么就记什么"**。

但 §5.4 的 occurrences 保留了 `used_correctly` 字段，§6.9 写"用错一个词 → `used_correctly=false` + 生成 gap 事件"。

**"用错了"本身就是一次判定。** 文档没有说清这两件事的界线，下一个 agent 会困惑。实际上它们是两件不同的事：

- **达标判定**（已废除）：你说的和 AI 给你的译文一样吗？—— 这是拿"照不照抄"当标准，废除是对的。
- **正确性判定**（保留）：你说的这句英语，语法/用法有错吗？—— 这是学习产品的基本功能，不废除。

**建议在 §6.5 明确加一段把这两条分开**，否则"不判达标"很容易被理解成"什么都不判"，那 `learning_events` 整张表就没有数据来源了。

### 逻辑-7 🟡 `spoken_count` 的记法会打破"已使用账本 ⊂ 输入账本"的框架

§7.2 的框架是：**输入账本（碰过）**⊇**已使用账本（说过）**，"两者不是两张表，是同一份 lexicon 的两个视图"。

**但按 §5.3 的记账规则**，用户在对话里说出一个**账本里从来没有的词**时，系统会**新建一个 entry**（`total_count=1`, `spoken_count=1`）。于是出现第三种状态：**说过、但从来没"碰过"**。

这不只是状态多了一个，它让"两个账本"这个叙事框架失效：已使用账本不是输入账本的子集，两者是**交叉**的。而 §7.2 的正向差距分析、Tab2 的 `Not yet` / `Spoken` 两个镜头，都建立在"子集"这个假设上。

**要么**给 entry 加一个 `origin`（'captured' / 'spoken'）区分来源，**要么**重述这个框架为"三种状态"。

### 逻辑-8 🟡 "进步"有两个互相冲突的定义，北极星指标可能长期为 0

同一份文档里，"进步"被定义了两次，触发器完全不同：

- §6.9：**"同一个 entry 出现『先错后对』的翻转"** → 生成 progress 事件
- §7.2 / §3.4：**"从说不出到说出来"**（`spoken_count` 由 0 变 1）

**这两个是完全不同的事件**，而且第一个在 MVP 数据量下**几乎不会发生**：它要求同一个词在**两次不同的对话里都被用到、且都被判定过对错**。按逻辑-4 算出来的供给量，这个概率极低。

**后果很严重**：§11 明确把 `progress_event_created` 定为 **"最该盯的北极星类指标"**。如果用的是"先错后对"的定义，**这个指标可能几个月都是 0**，你会以为产品没有价值，其实是触发器定得太窄。

**建议**：把"进步"拆成两级——**突破**（说不出→说出来，`spoken_count` 0→1，高频发生，可日常反馈）和**纠正**（先错后对，稀疏，作为高光时刻）。北极星盯前者。

### 逻辑-9 🟡 成长层的"正向差距"在数据上恒为空集

§7.2：**正向差距 = "用户输出里冒出了账本里没有的表达"**。

**但按 §5.3，用户在对话里说出的词会立刻入账。** 入账之后它就"在账本里"了——等成长层去读的时候，账本里已经有它了，**差集永远是空的**。

这不是措辞问题，是机制缺失：要实现"冒出新东西"，需要区分**"这次对话之前的账本"**和**"这次对话之后的账本"**。可行做法是给 entry 打首次出现的来源和时间（`first_seen_at` 已有，但没有"这次会话新增"的标记），或者直接读 `learning_events` 里的突破事件而不是做差集。

### 逻辑-10 🟢 对话里产生的 occurrence，情境标签继承谁，两处说法相反

- §5.2.2：情境**继承自来源场景**
- §6.7：话题会进化，相关性**不锚死开场场景**，每隔几轮重新推断当前话题

那一次对话聊到第 10 轮时冒出的词，`scene_category` 记的是**开场 seed 场景的情境**，还是**当前推断出的话题**？两处给了相反暗示。这直接影响 `By scene` 镜头和"在最贴近的场景再现"的准确性。

### 逻辑-11 🟢 两份文档对"Tab1 语音"一个说已定、一个说待定

- 本 PRD §6.2：「冷起手住 Tab1（**Tab1 输入入口以后迭代成语音对话**）」——当成已定前提在用
- 《输入到成长_链路现状与待敲定_v1》§1.2.3：「语音输入、语音对话都**未上线**……进 Tab1 后怎么处理**还没定**，先占位」

同一件事，一份文档拿它当地基，另一份说它是空白。**§6.2"一个引擎两种起点"的整个论证依赖 Tab1 语音存在**，这个依赖要么标注清楚，要么把冷起手也放进 Tab2。

## 六、本轮讨论已定的决策（2026-07-25）

### 已定-1 ✅ 提取供给量：**卡片仍是一次输入一张，账本按抽取规则"有多少抽多少"**

- Tab1 卡片视觉**不动**（仍只高亮最地道的那 1 个），这是展示层。
- 账本是另一层：记账时**按抽取规则把这句话里所有可学单元都抽出来入账**，不设固定条数。
- **代价与前提**：这意味着记账要对原文再跑一次抽词（每条素材多一次 AI 调用），或者把抽词并进主 generate 的 prompt。哪种走法在写提取规则时一起定。
- **随之升级为头号问题的**：既然是"有多少抽多少"，那**"什么算一个可学单元"这条判断标准就是整条链路的闸门**。理论上 "I was in meetings all day — completely drained." 能抽出 `be in meetings`、`all day`、`completely drained`、`drained`、`meeting` …… 抽满了账本会被稀释成一本流水单词表，`For review` 就失去意义。停用词表只挡得住 the/is/of，挡不住这类"是词但不值得学"的东西。**"学习性"的判定标准必须在提取规则里写死，这是《输入到成长》§二 批次一的第一道题。**

### 已定-2 ✅ 对错判定：**判，但只在总结卡里轻触**

- 对话进行中：AI **绝不打断、不纠错**（保护表达欲，这是语音口语产品的命门）。
- 对话结束的总结卡：用「也可以这么说」的口气给 **1–2 条**，不打分、不列错误清单。
- 因此 `learning_events` 表**保留**，`aspect='grammar'` 保留，成长层的"语法/结构薄弱点"保留。
- **必须在 §6.5 补一段划清界线**：不判「你说的和 AI 译文一样吗」（达标判定，已废除）≠ 不判「这句英语有没有语法错」（正确性判定，保留）。两者混为一谈会让下一个 agent 把整张表删掉。
