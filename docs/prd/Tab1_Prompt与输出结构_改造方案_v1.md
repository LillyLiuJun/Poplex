## 〇、这份文档解决什么

现在 Tab1 的提示词是**一个 `SYSTEM_PROMPT` 包打天下**：五种卡片类型、三种输入形态（纯文/图文/纯图）全挤在一份提示词里，输出结构是四套互不相干的字段。

由此长出四个具体问题：

| 问题 | 表现 |
|---|---|
| **排版乱** | 两件事：可空字段没内容时留大块**空白**（s2 最明显）；内容多时**溢出**、没有折叠机制 |
| **命名漂移** | 同一个概念四个名字（目标语言主表达 = `word` / `native_polish` / `english_translation` / `native_translation`） |
| **语义槽位错配** | s2 的用户英文原句没有独立字段，和 AI 润色版挤在一起，落库后**分不开** |
| **人设无标尺** | 代码里 `TONE` 只有三行泛泛之词，与已定的人设规范和品牌调性都不一致 |

本方案分两层解决：**架构层**（有几个 prompt、每个输出什么）和**内容层**（提示词十块逐块处置）。

## 一、Tab1 的定位：即时解惑 + 生成素材

**这是本轮新增的上位定义。**

**即时解惑 = 按「有没有非目标语言成分」分流处理**，不是简单的"翻成目标语言"，也不是"中文 vs 英文"的二分。

### 1.1 三步判定（顺序不能颠倒）

```
第一步  这是不是元问题？（用户在问关于某个语言片段的事）
        是 → 抽出被问的对象 X，后面只处理 X
        否 → 处理整条输入
              ↓
第二步  （对象）里有没有非目标语言的成分？
        没有 → comprehend  修正形式 + 用母语解释
        有   → express     译成目标语言
              ↓
第三步  粒度：word / sentence / passage
```

**为什么判定依据是「是不是目标语言」而不是「中文还是英文」：** 这样第三种语言自动被覆盖，不用单开分支。用户输入日文「お疲れ様です」，意图和输入中文完全一样——**"这个意思用英语怎么说"**。

```
输入是目标语言        → comprehend
输入含非目标语言成分  → express
   ├─ 母语（中文）
   ├─ 第三种语言（日文 / 法文 …）   ← 同一条路，零额外规则
   └─ 混合
```

**混合输入的规则：只要存在非目标语言成分，就是 express。** 纯目标语言才是 comprehend。三种混合情况：

| 类型 | 例 | 判定 | 用户在干什么 |
|---|---|---|---|
| 母语为主，嵌目标语言词 | `今天工作好 stress` | express | 用中文思维表达 |
| **目标语言为主，嵌母语词** | `I have a 会议 at 3pm` | **express**（补全成完整英文） | 在写英文、卡在一个词 |
| 元问题 | `overtime是什么意思` | 由第一步抽出的对象定 | 问关于某个片段的事 |

> 第二种（`I have a 会议 at 3pm`）在现有规则里**一个字都没有**。而它恰好证明"主体是什么语言"这个判据不够——主体是英文，但用户明明在表达、缺一块。

**为什么顺序不能颠倒——可以直接验证：**

| 输入 | 跳过第一步 | 按三步 |
|---|---|---|
| `overtime是什么意思` | 含中文 → express ❌ | 抽出 `overtime` → 纯目标语言 → comprehend ✅ |
| `摸鱼怎么说` | 含中文 → express ✅（碰巧对） | 抽出「摸鱼」→ 非目标语言 → express ✅ |

> ⚠️ **现在提示词里这三块（`SELF-REFERENCE EXTRACTION` / `LANGUAGE INTENT RULE` / `GRANULARITY RULE`）是平行罗列的，没有任何顺序关系——这就是它会判错的原因。** 不是规则写得不对，是没告诉模型先做哪一步。

### 1.2 不对称：修正只发生在目标语言侧

**`comprehend` 侧才有"修正 / 润色"，`express` 侧没有。** 因为非目标语言（母语或第三语言）是用户的自然表达，没有"错"可言——他要的是"帮我变成英语"，不是"帮我改中文"。

> 承自《Tab1_AI回复卡片需求设计_v1》决策 4（以"用户的表达意图语言"判路径）与情境 2（`native_polish` 仅当有错才出）。

### 1.3 三档粒度各自的流程

```
word · comprehend     ① 判形式：词形变化 / 拼写错 / 正常
                      ② 卡片主体给【规范词条】，弱化一行说明"你输入的是什么形式"
                      ③ 给音标、词性、母语释义、例句

word · express        直接译成目标语言 + 音标、词性、例句（与上对称）

sentence · comprehend ① 判断有没有表达错误
                      ② 有错 → 先润色，再翻译【润色版】
                      ③ 没错 → 直接翻译【原句】

sentence · express    直接译成目标语言
                      （含"目标语言为主、嵌母语词"的补全，见 1.1）

passage · comprehend  概览 + 可学点列表。【不做整篇润色】——那不是用户写的。
                      文中若有不地道表达，作为【可学点的一种】挑出来（2.4）

passage · express     待定（§七 待-7）
```

> **`sentence` 那道流程现在的提示词里没有**——s2 是平行输出"中译 / 语法点 / 润色"四个字段，没有任何先后与条件关系。落到字段上的具体后果见 3.1②。
> **`word` 那道形式判定现在完全没有**——落到字段上见 3.1③。

**两个目标不对立，是同一个动作的两个时间面：**

| | 即时解惑 | 生成素材 |
|---|---|---|
| 什么时候兑现 | 现在这一秒 | 以后在 Tab2 练习时 |
| 用户感知 | 我懂了 / 我知道怎么说了 | 无感，后台发生 |
| 同一个产物的哪一面 | 卡片上看到的内容 | 落库的结构 + `learnable_units[]` |

所以 Tab1 **不需要为两个目标做取舍**——把输入准确地变成目标语言内容、并且结构化地存下来，一件事同时满足两个。

> 由此推出一条呈现原则：**卡片展示什么，由内容本身决定，不由"服务哪个目标"决定。** 见 2.5。

## 二、架构层

### 2.1 按输入来源拆 prompt

**五条路，各自独立提示词。** 拆分理由：不同输入形态是不同性质的任务，混在一份提示词里会互相污染（纯图是确定性任务，它的规则挤进文字路只会让文字路更不稳）。

| 路 | 状态 | 输入 | 说明 |
|---|---|---|---|
| **文字路** | 已上线 | 短文本 | 本轮主要改造对象。**仍分四类卡，但改为两个维度**（2.2） |
| **图片路** | 已上线 | 纯图 / 图文混合 | 纯图是确定性任务（固定出场景卡），单独拆出；**图文混合仍走文字路**（图片作上下文），因为它本就文字主导 |
| **长内容路** | 未开发 | 粘贴长文 / 文件 / 邮件 / 聊天记录 | 产出"概览 + 可学单元列表"，见 2.4 |
| **语音路** | 未开发 | 语音输入 | **待定**：转写后并入文字路，还是独立提示词（§七 待-1） |
| **对话路** | 未开发 | 语音对话 | 不属 Tab1，归对话页（见架构文档） |

> **重要澄清**：「按输入来源拆 prompt」和「按输出形态分四类卡」是**两个正交的维度**，不能互相替代。文字这一路里面仍然会有词/句/中/英四种情况——拆了 prompt 不等于取消了四类卡。

### 2.2 输出结构：一套字段 + 两个维度（取代四个独立 schema）

**保留四类卡的差异，但不再用四套字段名。**

真正的差异只有两个维度，**但两者的地位不同**：

| 维度 | 取值 | 决定什么 | AI 要判吗 |
|---|---|---|---|
| `granularity` 粒度 | `word` / `sentence` / `passage` | **讲多细**——字段的多少、解惑流程走哪条 | ✅ **这是 AI 唯一真正的分类任务** |
| `direction` 方向 | `comprehend` 理解 / `express` 表达 | 哪边是源 | ❌ **推导得出，不是分类题** |

**为什么 `direction` 是推导的、不是判的：** 它由 1.1 第一、二步的结果直接得出——定位到对象、看它有没有非目标语言成分，方向自然就有了，不需要模型再做一次"这属于哪类"的分类。这也是 `LANGUAGE INTENT RULE` + `SELF-REFERENCE EXTRACTION` 两块真正在做的事。

**word 卡最能说明这一点——两个方向的字段完全相同，只是哪一栏是用户给的不同：**

| | 用户给英文词 | 用户给中文词 |
|---|---|---|
| `user_original` | overtime | 摸鱼 |
| `target_expression` | overtime（同一个） | slack off |
| `native_meaning` | 加班 | 摸鱼（同一个） |
| `phonetic` / `pos` / `examples[]` | 同 | 同 |

> **由此简化：CARD SELECTION 从"五选一"降为"判一个粒度"**（word / sentence / passage），`direction` 由定位到的翻译对象自动填。判一件事比判五件事稳得多。

对照原来的四类卡：

| 原卡型 | granularity | direction | 用户在干什么 |
|---|---|---|---|
| s1 轻词典 | `word` | `comprehend` | 给了个英文词，想知道什么意思 |
| s2 句子分析 | `sentence` | `comprehend` | 给了个英文句，想知道对不对 / 更地道怎么说 |
| s3 地道翻译 | `word` | `express` | 给了个中文词，想知道英文怎么说 |
| s4 场景手帐 | `sentence` | `express` | 给了段中文经历，想变成地道英文 |
| **（新）长内容** | `passage` | 二者皆可 | 给了一大段，想知道里面有什么值得学 |

**为什么这样改而不是简单统一命名：**

1. **CARD SELECTION 从"选一个类型"变成"标两个维度"**——AI 判两个二元问题比判五选一稳得多，也更少踩"到底算 s2 还是 s4"这类边界。
2. **落库从四个 case 变成一个映射**，`buildRawContent` 不再需要为每种卡型写一份。
3. **前端从四套组件变成一套按维度显隐**，同一个字段在四张卡上必然同字号同颜色——《输入到成长》§1.4 那笔"同字段字体字号不统一"的旧账从根上消失（**根因就是字段名不统一，所以各写各的**）。
4. **`passage` 天然承载"越短越细、越长越粗"**（2.3），不用另发明一套规则。

### 2.3 粒度决定详细程度

> ⚠️ **"粒度"在需求里有两个意思，必须拆开命名，否则提示词会自相矛盾：**
> - **输入粒度**（现有 `GRANULARITY RULE` 说的）：这个输入是词还是句 → 已并入 `granularity` 字段。
> - **输出详细度**（新需求"越短越细、越长越粗"说的）：讲多细 → 由 `granularity` 的取值**决定**，不是另一个独立规则。
>
> 二者其实是同一个字段的因与果，所以合成一个维度，不设两条规则。

| granularity | 一次输入产出 | 详细程度 |
|---|---|---|
| `word` | 1 个学习单元 | **最细**：音标、词性、释义、例句全给 |
| `sentence` | 1 个学习单元 | **细**：中译、语法点、更地道说法 |
| `passage` | **N 个学习单元** | **粗**：一句话概览 + 可学单元列表，不逐句翻译 |

### 2.4 长内容卡：概览 + 单元列表

**长内容不是"一张更大的卡"。** 长文本里没有"一个"重点，有很多个；用户对它的诉求也不是逐句翻译（太长没人看），而是"这里面有什么值得我学的"。

- **收起态**：一句话概览（这段讲了什么）+ "N 个可学点"。
- **展开态**：可学单元列表，**可勾选剔除**——只有用户留下的才进账本（延续"素材是用户的"，见《输入到成长》§1.2.2）。

**（已定）不做整篇润色——润色降级为「可学点的一种」。**

理由：长内容大概率**不是用户写的**（邮件、文章、聊天记录），润色别人的内容毫无价值，而且很冒犯。但文中若确有不地道的表达，它可以作为**一个可学单元**被挑出来：

```
可学点 · "I am looking forward to hear from you"
        → 更常见的是 "hear back from you"
```

**这个设计的好处：不需要判断"这段是你写的还是你收到的"。** 是用户自己的草稿，他会从可学点里看到该改的地方；是别人的邮件，那些可学点就是他能学的表达——**同一份产出，两种需求都接住了**，省掉一个不可靠的意图判定。

**与短卡共享同一个 `learnable_units[]` 结构**，区别只在数量：短卡 1–3 个、长卡 10+ 个。这正是「可学单元数量随输入体量而定」的落地（见 `Agent PRD v2` §2.3(2)）。

### 2.5 卡片呈现：由内容体量决定

**排版其实是两个独立的问题，解法不同，不能混着解：**

| 问题 | 表现 | 解法 |
|---|---|---|
| **空白** | 可空字段没内容时留下大块空（s2 最明显） | **区域随字段为 null 自动隐藏**。这条 `Tab1_AI回复卡片需求设计_v1` §330 已定过（"极简翻译 → `key_phrase` 返回 null，前端区域自动隐藏"），**只是没贯彻到所有可空字段**——本次要贯彻 |
| **过长 / 溢出** | 内容太多，一张卡装不下 | **收起 + 展开** |

**所以「收起 / 展开」是长度的解法，不是每张卡都有的固定两态。** 短卡强行加展开态纯属多余。

| granularity | 内容体量 | 是否需要展开 | 收起态给什么 |
|---|---|---|---|
| `word` | 天然短 | ❌ 不需要，直接全展示 | —— |
| `sentence` | 多数短，偶尔长 | ⚠️ **超过阈值才折叠** | 目标语言表达 + 中文侧 |
| `passage` | 必然长 | ✅ 必须 | 一句话概览 + "N 个可学点" |

> **待定**：`sentence` 的折叠阈值怎么定（按行数？按字符数？还是让前端按可用高度自适应）。留到视觉稿阶段，不阻塞提示词改造。见 §七 待-6。

## 三、统一字段表（核心交付物）

一套字段，四类卡按维度取用。`—` = 该类型不产出此字段。

| 字段 | 含义 | word+comp (s1) | sent+comp (s2) | word+expr (s3) | sent+expr (s4) | passage |
|---|---|:--:|:--:|:--:|:--:|:--:|
| `granularity` | 粒度维度 | word | sentence | word | sentence | passage |
| `direction` | 方向维度 | comprehend | comprehend | express | express | 二者皆可 |
| `user_original` | **用户原样输入**（不加工） | ✅ | ✅ | ✅ | ✅ | ✅ |
| `user_original_lang` | 用户输入的语言（**任意语言码，不限中英**） | target | target | 非 target | 非 target | 判定 |
| `target_expression` | **AI 产出的目标语言表达** | ✅ **规范词条**（见 3.1③） | 可 null＝原句已够地道 | ✅ 英译 | ✅ 地道英文 | — |
| `native_meaning` | 中文释义 / 译文 | ✅ 释义 | ✅ 译文 | ✅ 概念 | 可选 | — |
| `phonetic` | 音标 | ✅ | — | ✅ | — | — |
| `pos` | 词性 | ✅ | — | ✅ | — | — |
| `examples[]` | 例句 `{en, zh}` | ✅ 1–2 | 可选 | ✅ 1 | 可选 | — |
| `grammar_note` | **形式 / 语法说明** | 可 null（形式说明） | 可 null（语法点） | — | — | — |
| `ai_scene_guess` | AI 对图片的场景描述 | — | — | — | 仅纯图 | — |
| `summary` | 一句话概览 | — | — | — | — | ✅ |
| `learnable_units[]` | **可学单元数组** | ✅ | ✅ | ✅ | ✅ | ✅ 数量多 |
| `scene_trigger` | 追问 | ✅ | ✅ | ✅ | ✅ | ✅ |

### 3.1 三处必须说清的语义

**① `user_original` 与 `target_expression` 必须分开存，这是本次改造最重要的一条。**

现在 s2 落库写的是 `native_english: native_polish ?? userText`——用户自己写的英文和 AI 润色版**挤在同一个字段里，落库后分不开**。而这恰恰是 Tab2 要守的那条线：**AI 生成的 ≠ 用户能说出来的**。

拆开之后：
- `user_original` 永远是用户原样输入。
- `target_expression` 永远是 AI 产出。s2 的 `null` 有明确语义 = **"你原句已经够地道，我没改"**，不再是"没有值"。
- 下游取"这条素材的目标语言表达"统一用 `target_expression ?? user_original`，规则一条，不用分卡型。

**② `native_meaning` 翻译的是「正确版本」，不是用户原句——这条必须在提示词里写死。**

对应第一节 sentence 的解惑流程（先判错 → 有错先润色 → 再翻译）。落到字段上就是一条规则：

```
zh_meaning = 对 (target_expression ?? user_original) 的翻译
```

拿 `I am very sleep today` 举例：

| | 翻用户原句 | **翻正确版本（本方案）** |
|---|---|---|
| `native_meaning` | "我今天很睡觉"（荒谬）；或 AI 悄悄按正确意思翻成"我今天很困"——**但用户不知道自己错了** | "我今天很困" |
| 用户得到 | 一个不知从何而来的翻译 | 先看到错在哪，再看到正确版本和它的意思 |

**不需要额外的"有没有错"字段**：`target_expression` 是否为 null 天然表达了这件事——有值 = 我改了，`null` = 你原句没问题。

**顺带废弃 `chinese_original`**：它在 s2 里装 AI 中译、在 s3/s4 里装用户原文，四种语义挤一个位置，这就是落库填错槽的直接原因。拆成 `user_original`（用户的）和 `native_meaning`（AI 的），各自语义单一。

**③ word 侧：卡片主体永远给「规范词条」，用 `grammar_note` 说明用户输入的形式。**

用户查词时输入的不一定是规范形式，三种情况分开处理：

| 情况 | 例 | `user_original` | `target_expression` | `grammar_note` |
|---|---|---|---|---|
| **词形变化** | 输入 `spoken` | spoken | **speak** | "spoken 是过去分词，用在完成时（I have spoken to him）和被动（English is spoken here）" |
| **拼写错** | 输入 `recieve` | recieve | **receive** | "你写的是 recieve，正确拼写是 receive" |
| **正常** | 输入 `overtime` | overtime | overtime | `null` |
| **用词不当** | 想说"加班"却输入 `overwork` | overwork | overwork | `null` —— **不处理** |

最后一种明确不做：没有上下文，AI 无从知道用户想表达什么，硬猜会错得离谱。

> `grammar_note` 因此从"仅 sentence 的语法点"扩展为"**形式 / 语法说明**"——word 侧讲形式、sentence 侧讲语法，本质都是"关于你写的这个形式的说明"，不新增字段。

**⚠️ 归原型的判定，必须和账本的 lemma 归一化共用同一套规则。**

`Agent PRD v2` §5.1.3 定的"词形还原：meetings → meeting"就是这件事。**如果卡片和账本各判各的，用户在卡片上看到 `speak`、账本里存的却是 `spoken`，两边对不上。**

而且不是所有词形都能归原型——**只有当这个词形没有独立词义时才归；有独立词义就当独立词条**：

| 输入 | 归原型？ | 为什么 |
|---|---|---|
| `spoken` / `meetings` | ✅ | 纯屈折变化，无独立词义 |
| `glasses`（眼镜） | ❌ | 与 `glass`（玻璃/杯子）语义完全不同 |
| `drawing`（图画） | ❌ | 名词义独立于 `draw` |
| `used to` | ❌ | 固定结构，不是 `use` |
| `spoken English` 里的 spoken | ❌ | 此处是形容词，有独立用法 |

这条规则同时约束提示词和记账层，**要写进两份文档**。

**④ `ai_scene_guess` 必须真正落进结构。**

现在提示词**确实输出了**它，但落库用的 `SceneRawContent` 结构里没有这个字段，写库那一刻就丢了；同时 `chinese_original` 被 `String(null ?? '')` 压成空字符串。纯图素材的上下文因此在落库瞬间消失——**而引导页的纯图路径是新用户的第一条素材，第一条就命中**。

> ⚠️ **拆 prompt 必须连带落库结构一起拆。** 只换提示词、不改 `raw_content` 的结构，②③ 两处失真不会消失——它们的根在落库映射层。

### 3.2 `learnable_units[]` 的结构

```
learnable_units: [
  {
    form:      "set up",           // 表达原形
    kind:      "phrase",           // word|phrase|collocation|slang|idiom|pattern
    note:      "帮别人配置/装好",    // 一句话说明
    is_primary: true               // 是否卡片主推（收起态高亮那个）
  },
  ...
]
```

- **数量随输入体量而定，不在提示词里写死。** 短句 1–3 个，长文 10+ 个。
- `is_primary` 让"卡片展示什么"和"账本收什么"在**同一次输出**里分开——卡片只高亮 `is_primary`，账本吃全部。**这样记账不需要另跑一次 AI 调用**（对应 `Agent PRD v2` §5.1.1 路径 A）。
- **筛选标准（什么算一个可学单元）不在本文档定**，那是《输入到成长》§二 批次一的头号问题。本文档只定**结构**——结构稳定、标准可换，这样才能拿真实数据对照着试几版标准。

### 4.1 persona 与 TONE 重做

#### 现状：三方打架

| 来源 | 说的是 |
|---|---|
| **代码** `TONE` | "Warm and encouraging, like a knowledgeable friend" + 简洁实用 —— 只有三行泛泛之词 |
| `Tab1_AI回复卡片需求设计_v1` 决策5 | 口语化、可用网络梗、先认同再延伸、可开小玩笑、**正反例里带 emoji** —— **这套东西从未进入提示词** |
| `Tab0_onboarding_PRD_v1` §150 | **克制美学**：不要卡通陪伴感、无 Emoji、要"笃定" |

三者互斥。而且代码里那句 `Warm and encouraging` 恰恰**鼓励了**决策5明令禁止的"夸奖用户"。`AI协作手册` 也早把"AI 语气无标尺"列为已知缺口。

#### 已定基调：温润极简（Warm Minimalism）+ 注重效率

对应品牌：主色 `#FF7622` 暖橙（饱和度保持，不降调）、中性色是暖纸灰（H 24–30°）——**暖但不喧，克制但不冷**。语气要和这套视觉是同一个人。

**翻译成可执行的规则：**

- **温润 ≠ 热情。** 不冷淡，但也不亢奋。温度体现在**懂用户的处境**（"开了一天会那种累"），不体现在情绪词（"太棒了！""加油！"）。
- **极简 = 不铺垫。** 用户要的东西第一句就给到，不写"Great question!"、不写"Let me explain…"、不描述自己在做什么。
- **注重效率 = 能一句说完不说两句。**

**保留决策5的三条禁止项**（它们和新基调完全一致，不是要推翻的部分）：

```
❌ 不夸奖用户输入（"Great input!" / "很好的问题！"）
❌ 不用教练腔（"这是个学习的好机会…" / "你可以尝试…"）
❌ 不说教、不主动给人生建议（除非用户明确问"我该怎么做"）
```

**废弃决策5的允许项**（与新基调冲突的部分）：

```
✗ 网络梗
✗ emoji
✗ "先认同再延伸"的情绪铺垫（改为：直接给内容，共情藏在措辞里）
```

**新增：**

```
❌ 不自我描述（"作为你的英语伙伴…"）
❌ 不用感叹号堆情绪
✅ 共情通过"准确描述处境"实现，不通过情绪词
```

#### 正反例（同一条输入，三种语气对照）

用户输入：**「今天地铁挤死我了」**

| | 文案 | 判定 |
|---|---|---|
| 现在的代码（warm and encouraging） | "Great that you're sharing! The subway was packed today — that sounds tough! 😅 Would you like to learn more commuting expressions?" | ❌ 夸奖用户 + emoji + 教练腔，三条全踩 |
| 决策5（接地气带梗） | "The subway was packed — did you manage to squeeze off at your stop without a fight? 😅" | ❌ emoji；情绪铺垫偏多 |
| **温润极简（本方案）** | "The subway was packed today." / 追问："Was it the whole ride, or just getting off?" | ✅ 直给表达；温度在"问到了具体的那一下"，不在情绪词 |

### 4.2 `scene_trigger` 分化（延续《输入到成长》§1.1 已定）

| 卡型 | 追问什么 | 为什么 |
|---|---|---|
| `sentence`（s2/s4） | **场景细节** | 本来就有情境，追问细节是顺势加深 |
| `word`（s1/s3） | **"什么场景遇到 / 会用到"** | 词是孤立的，追问处境补上语境，也呼应账本"词 → 场景"的继承链 |
| `passage` | **待定**（§七 待-2） | 长内容已经有一堆单元，追问可能是干扰 |

沿用决策5对 `scene_trigger` 的三条约束（仍然有效）：必须顺着用户的**具体细节**延伸、禁止泛问（"Tell me more" 无效）、最多 2 句。
