## 〇、一句话读懂这份文档

你的 agent 规划想做的三件事——**把用户的词句整理分层、用对话陪练、让用户看见自己的成长**——本质上是**同一份数据在三个地方被使用**。而现在的代码，恰恰缺的就是这份数据。

打个比方：现在的 App 像一个**只会往盒子里扔纸条的机器**。用户每输入一次，它生成一张卡片、往 `materials` 盒子里塞一张纸条。盒子里纸条越来越多，但机器**从来没有统计过"set up 这个词你其实已经用过 7 次了"**——因为每张纸条是独立的，词埋在纸条内部的文字里，没有被单独拎出来数过。

agent 规划里所有让人眼前一亮的能力（按频率展示词汇、区分常见词/专业词、看见"从不会到会"的进步、对话里实时推荐你的高频词），**全都建立在"能把每个词拎出来数"这一件事上**。所以这份文档的核心，不是加三个花哨功能，而是先补上这个**"词汇账本"（lexicon）数据地基**，再在上面长出三层体验。

这份文档的结构就是这个逻辑：
1. 先盘点**已经建好了什么**（第二节），避免重复造轮子。
2. 说清**为什么现在这个地基撑不起 agent 规划**（第三节）——这是整份文档的转折点。
3. 给出**三层架构总图**（第四节），让你一眼看到整理层/对话层/成长层怎么串。
4. 逐层展开需求（第五、六、七节），每层都含数据模型。
5. 处理你标注的**两个难题**（第八节：一词多义、知识产权）。
6. 落到**和现有代码的具体整合改造点**（第九节）、数据模型总览（第十节）、埋点（第十一节）、待确认清单（第十二节）、垂直切片开发计划（第十三节）。

## 一、这份文档要解决的问题

你的原始 agent 规划（《语言学习Agent规划.md》）写了四段：内容来源、内容整理、AI 对话、用户成长。它是一份**思路草稿**——每一段都点出了正确的方向，但都停在"要做这个"的层面，没有回答"数据怎么存、和现有代码怎么接、MVP 先做哪一刀"。

同时，仓库里已经有一套**跑起来的代码**：Tab1 能把输入变成卡片并落库，Tab2 能展示场景卡和词汇本。但《全局数据架构审计报告_v1》已经指出，这套代码的数据地基有几处结构性缺口。

**这份文档做的事，就是把"草稿的方向"和"代码的现实"对齐**：保留草稿里对的判断，补上它没说的数据结构，改掉代码里挡路的地方，最后给出一条能一片一片开发出来的路径。

### 2.3 数据模型——已实现

只有 `materials` 一张业务表真正承载内容（`analytics_events` 是埋点）：

```
materials
├── id, user_id, source_message_id（声明了但从不写）
├── material_type   'scene' | 'vocabulary'
├── status          'pending' | 'categorized'
├── scene_category  12 类固定枚举之一
├── raw_content     jsonb —— 两种结构：
│     scene:  { native_english, chinese_original, key_phrases[{phrase,note}], source_image_path }
│     vocab:  { word, phonetic, pos, definition, example_en, example_zh }
├── related_material_ids[]  （声明了但从不写）
├── deleted_at
└── created_at
```

**记住这张表的两个特征，它们是第三节的全部矛盾所在**：
1. 一个"词"在系统里有两种完全不同的存在方式：要么是一整行 `vocabulary` 素材（s1/s3 查的词），要么是**埋在某行 scene 素材 `raw_content.key_phrases` 里的一个 JSON 片段**（s2/s4 场景里高亮的词组）。
2. 这两种方式**都不支持"把同一个词跨内容聚合起来数一遍"**。

## 三、核心洞察：为什么现在的地基撑不起 agent 规划

这一节是整份文档的转折点。请慢读。

### 3.1 agent 规划的每一个亮点，都要求"能按词聚合"

把你草稿里的诉求逐条翻译成"它需要什么数据能力"：

| 你在草稿里写的 | 翻译成数据能力 | 现在能做到吗 |
|---|---|---|
| 区分常见词汇（框架词汇）和专业词汇（场景词汇） | 每个词要有一个"层级"标签，且能全局判定 | ❌ 词没有独立身份，无处挂标签 |
| 对不同的词汇展示频率 | 要能查"这个词用户一共用了几次" | ❌ 词分散在 N 行素材的 JSON 里，数不出来 |
| 分析用户的高频表达、表达习惯 | 要能对用户所有词做排序统计 | ❌ 同上 |
| 词汇还有哪些同义表达 | 要能定位一个词、挂上它的同义词 | ❌ 词没有独立身份 |
| 记录"之前不会/错误、现在正确"的进步 | 要能对同一个词记录多次使用、每次对错 | ❌ 素材是一次性快照，没有"同一个词的多次使用"概念 |
| 对话里实时推荐用户的高频可用词 | 要能实时查用户词库里的高频词 | ❌ 没有词库 |

**六条诉求，六个 ❌，卡在同一个点：系统里没有"词"这个独立、可聚合、可累计的对象。**

### 3.2 根因：词汇是"一次性快照"，不是"可累计的账本"

现在的模式是：用户每输入一次 → 生成一张卡 → 存一行素材。这行素材是那一刻的**快照**。同一个 "set up"，用户在"帮妈妈弄手机"的场景里用过一次（埋在 scene A 的 key_phrases）、在"配置新电脑"的场景里又用过一次（埋在 scene B 的 key_phrases），系统里就是**两个毫不相干的 JSON 片段**，没有任何东西告诉系统"这俩是同一个词"。

要回答"set up 你用过几次"，你得把用户所有 scene 素材拉出来、把每行的 `key_phrases` 数组解开、逐个字符串比对——这既慢又不准（"set up / sets up / setting up" 算不算一个？），而且**同义扩展、对错记录这些根本无从谈起**。

### 3.3 结论：先补一层"词汇账本"（lexicon），三层体验才立得住

解法是引入一个**规范化的词汇层**，把"词"从素材里拎出来，变成有独立身份、能累计、能挂标签的对象。这一层就是后面所有设计的地基。它不替代 `materials`（场景素材仍然是场景素材），而是**在旁边并行长出一份"用户个人词库"**，记录"用户这辈子在这个 App 里碰过的每一个学习性词条，以及每一次碰它的记录"。

有了这一层：
- **整理层**（第五节）= 往账本里正确地记账（分层、去重、继承）。
- **对话层**（第六节）= 一边陪练一边往账本记新账、并读账本做实时推荐。
- **成长层**（第七节）= 不只是把账本读给用户看，更是把**用户的实际输出**和账本做对比、找差距（正向=进步/新表达，负向=闲置的词/反复的错），让用户认识自己、进而提升。（这一条按你的新输入调整，详见第七节。）

三层是**同一个账本的写入端和读取端**，这就是你草稿里"三者耦合"的本质。下面逐层展开。

### 3.4 顺势而为：这个账本直接成为 Tab2 的主视图（重塑 Tab2）

> 这一节采纳你的新判断（"现在 Tab2 那套呈现要推翻，账本直接承接 Tab1 输入"），并给出我的推荐方向，标为**提案**，你可推翻。

**为什么现在的 Tab2 是错的、且和 Tab1 重复——我同意你的判断，并能说清错在哪：** 现在 Tab2 的场景详情页，按《Tab2_PRD_v1》第九节，是**直接复用 Tab1 的 AI 回复卡组件**。用户在 Tab2 点开一个场景，看到的东西和他在 Tab1 生成那一刻看到的一模一样——Tab2 没有提供任何 Tab1 给不了的新价值，这就是"重复"的根源。

**Tab1 和 Tab2 应该结构上互补，不是同一份东西看两遍：**
- **Tab1 = "我说过什么"**：即时输入、即时生成、按时间排列的表达/场景历史。单位是"一次输入 / 一段对话"，流水式。
- **Tab2 = "我在积累什么"**：跨所有输入聚合出来的词汇账本。单位是"一个词条"，累计式。**这个"跨输入聚合"恰恰是 Tab1 结构上做不到的事**（Tab1 是单次的），所以让账本做 Tab2 的主体，天然不和 Tab1 重复。

**账本直接承接 Tab1 输入**：Tab1 每输入一次，记账动作（第五节 Stage 3）就把词记进账本，Tab2 立刻可见——这就是你说的"词汇账本直接承接 Tab1 的输入"。

**那场景去哪了？（提案，可讨论）** 场景不删，但**从"独立卡片"降为"词的来源背景"，继承链方向翻转**：
- 旧 Tab2：场景 → 词（先看场景卡，词埋在里面）。
- 新 Tab2：**词 → 场景**（先看词，点开一个词才看到"它在你哪些场景里出现过"）。
- 这同时满足两件看似矛盾的事：**消除与 Tab1 的重复**（用户不再浏览场景卡），又**保住情境温度**（"set up"点开还能看到"帮妈妈弄手机"那一幕，记忆锚点还在）。想整段回看某次场景/对话本身，那属于 Tab1 的历史，不在 Tab2。

**"词条"是一个泛化的词汇单元，不只是单词。** 账本收的是各种**词汇项 / 表达单元**：单词 / 短语 / 词伙（搭配，如 "run late"）/ 俚语（如 "hit the sack"）/ 习语 / 固定句型（如 "It takes sb. some time to do sth."）。用一个 `entry_kind` 标签区分类型（见 5.4 数据模型），它既是展示时的一个筛选维度，也让"框架词 / 场景词 / 句型"的分层能落在任何粒度上。

**Tab2 前端怎么展示这些词（回应你"2/3/4 都需要 + 可筛选"，且澄清不是把页面切两半）：**
- **就是一个词条列表 + 顶部一排"镜头"标签**，不是上下两块区域。"值得关注（For review）"只是**默认选中的第一个标签**，不是单独的一块。
- **每个标签 = 一个镜头，点哪个就按哪个维度重排这份列表**：`For review`（默认，策展"现在该看的词"：场景词 + 最近新增 + 还没说出来的 + 高频但不够地道的口头禅词）/ `All`（全量，按频率）/ `Not yet`（碰过但还没自主说出来，`spoken_count=0`）/ `Spoken`（已说出＝**已使用账本**，`spoken_count>0`）/ `Recent`（最近）/ `By scene`（按来源场景）。这正是你说的"用顶部导航分类、不同筛选项做不同导航标签"；`Not yet` 和 `Spoken` 正好把"输入账本 vs 已使用账本"两个视图摆在一起。
- **`By scene` 点开会再展开情境小标签**（家庭 / 工作 …，复用现有 `ContextFilterBar` 那套），所以"按来源场景分组（维度3）"落在同一套结构里，不另起炉灶。
- 这样 `All` 覆盖你的**维度2（全量按频率）**、`By scene` 覆盖**维度3**、这排镜头标签本身就是**维度4（多维切换）**，再叠 `entry_kind` / 分层做二级筛选。**一句话：默认镜头帮用户聚焦，切换镜头兜住多维全量。**
- 默认 `For review` 的具体排序权重是可调细节，留待上线后按数据 tune（列入第十二节待定）。

## 四、整体架构：三层怎么串起来

```
                        用户产生语言的两个入口
        ┌──────────────────────────┐   ┌──────────────────────────┐
        │  Tab1 捕获生成（部分实现） │   │  对话陪练（Layer 2 新增）  │
        │  输入 → 卡片 → materials  │   │  一来一回的练习对话        │
        └────────────┬─────────────┘   └─────────────┬────────────┘
                     │                                │
                     │      两个入口都往同一个账本记账 │
                     ▼                                ▼
        ╔═══════════════════════════════════════════════════════════╗
        ║   Layer 1 · 内容整理层 = 词汇账本（lexicon）= 新 Tab2 主视图  ║
        ║                                                           ║
        ║  lexicon_entries      每个词条一行（去重后的"概念"）         ║
        ║    · 分层 tier         框架词 / 场景词                      ║
        ║    · 累计 total_count  总使用次数                           ║
        ║    · 词义 sense_key    一词多义拆分依据                     ║
        ║                                                           ║
        ║  lexicon_occurrences  每次使用一行（记账流水，只增不改）      ║
        ║    · 来自哪条素材/哪次对话  · 属于哪个情境  · 这次用对了吗    ║
        ╚═══════════════════════════════════════════════════════════╝
                     │                                ▲
                     │  成长层读账本 + 读用户输出，找差距 │ 对话层实时读账本
                     ▼                                │ 做高频词推荐
        ┌───────────────────────────────────────────────────────────┐
        │   Layer 3 · 用户成长层（读账本 + 读用户输出，做差距分析）      │
        │   把"用户实际输出的" 和 "账本里应该会的" 对比：                │
        │     正向差距 = 进步 / 冒出的新表达                            │
        │     负向差距 = 闲置没用的词 / 反复犯的错                       │
        │   目的：让用户认识自己 → 优化提升（不是展示数字）              │
        └───────────────────────────────────────────────────────────┘
```

**读这张图只需记住四件事：**
1. **账本（Layer 1）是中心，而且它就是新 Tab2 的主视图（见 3.4）。** 上面两个入口只管往里写，下面成长层往外读并做对比。旧 Tab2 的场景卡呈现被它取代。
2. **两张账本表分工明确**：`lexicon_entries` 是"去重后的词"（set up 只有一行），`lexicon_occurrences` 是"每一次用到"（set up 在场景 A 一行、场景 B 一行）。频率 = 数 occurrences；词本身的属性 = 存在 entry。**这是标准做法：一个"字典条目"配一份"使用流水"。**
3. **对话层既是写入端也是读取端**——它一边把对话里的新词记进账本，一边实时读账本给用户推荐高频词。这就是为什么"频率来自对话中的使用"，也是三层无法拆开的根本原因。
4. **成长层不是账本的镜子，是"账本 vs 用户输出"的差集。** 它读用户实际说出/写出的英文，和账本里"应该会的"对比：正向差距是进步（说出了新东西），负向差距是待提升点（有词不用、反复犯错）。它的目的是让用户认识自己，不是展示积累了多少。（详见第七节。）

> **两处备注（回应你这次的提醒）：**
> 1. **Tab1"捕获生成"目前只是部分实现。** 现有代码只覆盖文字 / 图片 / 语音的**短输入**；长内容、connectors（从邮件 / 文档 / 日程等提取）怎么接入**还没规划**。这不影响本文档的账本设计——无论输入来自哪，记账动作（第五节 Stage 3）是同一套；但要记得 Tab1 的输入面还会继续长，账本要能接住新来源。
> 2. **Tab2 已被重塑为账本主视图**（见 3.4）。第九节（9.4）、第十三节（Slice 3）已同步改为"换主体"，不再沿用旧场景卡呈现。

## 五、Layer 1 · 内容整理层 = 提取机制（含数据模型）

**这一层的目的（按你的纠正）：不是"把词存好看"，而是从用户输入里把语言素材提取出来、打上标，好让系统能分析这个用户的语言习惯、进而定制化地提升他的表达能力。** "以后在最贴近的场景把词推回给用户"是这个目的的一种交付方式（再现），不是全部。

整层是一条链——**提取 → 打标 → 累计与再现**：
- **提取（5.1）**：从两个、且只有两个来源（Tab1 输入 + 对话过程）把学习性词条拉出来、清洗归一。这是你说的"最重要的那件事"。
- **打标（5.2）**：给每个词条打几个维度的标；每个维度存在的唯一理由，都是"它能支撑对用户语言习惯的分析、或决定这个词该在什么场景/时机再现"。
- **累计与再现（5.3）**：把每次使用记成流水，累计成这个用户的语言画像；再据此在对的时机把词推回、或在成长层告诉用户他的习惯与缺口。

> 术语：下文"词条"是泛化的**词汇单元**（词/短语/词伙/俚语/习语，见 5.2.5）；"账本" = lexicon 两张表。

### 5.1 提取与清洗（"怎么把用户的输入提取出来"——你说这最重要）

**两个来源，一套提取动作：**
- **Tab1 输入** → 从生成的卡片里抽：s1/s3 抽主词（word / english_translation）；s2/s4 抽 `key_phrases` 里的词组。
- **对话过程** → 从用户用英文产出的话里抽词组/搭配（见第六节）。
- Tab1 的输入面以后会随长内容 / connectors 变宽，但抽词这一套不变——无论素材从哪来，提取动作同一套。

**提取要过两道清洗，否则账本会脏、后续一切分析全废：**
1. **规范化（normalization）→ 去重**：入账前统一成一个 `lemma`（转小写、去首尾标点；词形还原：setting up / sets up / set up → `set up`，meetings → meeting）。MVP 用轻量规则 + 一次极廉价的模型调用给原形，不追求语言学完美。**目的：同一个东西在账本里只有一行，频率才数得准。**
2. **过滤（停用词）**：纯功能词（the, a, is, of, 的, 了）**不入账**——它们不是学习目标，入账只会稀释一切榜单。维护停用词表，命中即跳过。
   - *为什么过滤是生死线：* 不过滤的话，"高频词 Top 10"全是 the/is/to，习惯分析直接作废。

**一句话：提取 = 从 Tab1 + 对话里拉出学习性词条，规范化去重、过滤功能词，得到干净的 `lemma`。** 拿到干净的 lemma，才能进入打标。

### 5.2 打标：给词条打上"决定分析什么、何时/何地再现"的几个维度

每个维度存在的唯一理由，都是"它能支撑对用户语言习惯的分析、或决定这个词该在什么场景/时机再现"。

#### 5.2.1 分层：框架词 / 场景词 / 固定句型（两个作用，不是推送开关）

**先作废更早一版的错误定位：分层不是"框架词少推、场景词多推"的展示频率开关。** 它的依据，是你确认并补全的语言模型假设：

> 人的表达 ≈ **基础高频词（框架，尤其是动词）** + **场景词** + **固定句型**。
> 固定句型 = 可复用的句子骨架，如 "Too... to..."、"It takes sb. some time to do sth."。
> 不会表达时，卡点有三种：不知道用什么**动词**（框架缺口）、不知道用什么**场景词**（场景缺口）、不知道用什么**句型**把意思架起来（句型缺口）。
>
> 假设评估（已做）：**基本成立**——高频核心词覆盖大部分用量、动词是二语学习者最尖的卡点，都有语言学依据。补充：框架侧不止动词，还含搭配 / 介词 / 轻动词；"词都会但不知道怎么搭"归入词伙（collocation）；"固定句型"作为第三支，用 `entry_kind='pattern'` 承载（见 5.2.5）。

**分层有两个作用（你的纠正）——不只是诊断：**
1. **在对话中：引导用户输出。** 对话 agent 知道用户手上有哪些框架词 / 场景词 / 句型，就能顺势搭台子、推着他把这些主动用出来（落地见 6.5）。这是"帮他说出来"的一环，发生在当下。
2. **在成长层：诊断缺口。** 把用户的框架 / 场景 / 句型库存和他的实际输出一比，看出他偏哪种缺口（如"场景词丰富、但句型单一"），据此定制化提升。这发生在回看时。

- 定义：**框架词** = 跨话题的通用词（get, make, set up…）；**场景词** = 绑定领域的词（invoice, marinate…）；**固定句型** = 可复用句子骨架（entry_kind='pattern'）。

**怎么判层、怎么从输入提取（含句型识别）——具体逻辑你要晚点再定，这里先占位。** 明确回答你的担心：这些是 5.1 / 5.2.1 格子里的**实现细节，不影响"提取→打标→再现"这条主链**——判定方法怎么调、句型怎么识别，换的是这一格的算法，链路结构不变。MVP 参考方案（非最终）：分层用通用高频词表（NGSL/CEFR，静态、不调 AI）+ 跨情境扩散度修正；句型识别靠抽词那次 AI 调用顺带标注。`tier` 存最终结果，可后台重算。

> 对 Tab2 展示的影响（修正 3.4）：默认 `For review` 不是"场景词优先"，而是**三类缺口都照顾**——没用起来的场景词、贫乏 / 不地道的框架动词、单一的句型。权重列入待定（第十二节）。

#### 5.2.2 情境（scene_category）：决定"在哪个场景再现"

继承自来源场景的话题标签（家庭/工作/…，沿用现有 12 类）。它是"在最贴近的场景再现"的直接依据：用户下次进入相似情境、或在对话里聊到该话题时，系统据此把这个情境下的词推回。孤立词（查词无场景）情境为空，不参与情境再现。

#### 5.2.3 来源 / 继承链（词 → 场景）：记忆锚点

每条 occurrence 带 `source_id`（来源素材 / 对话）。于是词能反查"它来自哪些场景"——"记得住 set up 是因为记得帮妈妈弄手机"就是这条链的价值。它也是 Tab2"点词看来源场景"和情境词汇聚合的数据基础，补上审计⑧ `related_material_ids` 空转的洞。

**边界（延续 Tab2_PRD 3.0）：孤立词汇（s1/s3 查的、无场景的词）`scene_category` 为空，不参与情境再现。** 它在账本里照样有 entry、照样计频率，只是不挂情境。

#### 5.2.4 一词多义（sense）：MVP 不做，字段预留，留待迭代

**你的决定：一词多义（schedule 日程 → 赛程）放到迭代版本，MVP 先不做。** 这里说清"以后怎么加不折腾"。

先切清概念（留给迭代时用）：词扩散到多场景有两种——**意思没变**的扩散（set up 到处用）由 5.2.1 升级 + 5.2.3 来源处理；**意思变了**的扩散才是一词多义。

**"以后直接加字段就行吗？"——比加字段更省：字段现在就留好，MVP 只是不启用逻辑。**
- 数据层：`lexicon_entries` 的唯一键**现在就定成** `(user_id, lemma, sense_key)`，`sense_key` 默认 `'default'`。MVP 抽词不判义项，所有 entry 的 sense_key 恒为 'default'——等于同一个词只有一份，行为和"没有分义"完全一样。
- 迭代开启时：只需打开"抽词顺带判义项 + 义项不一致就新建一个 sense 的 entry + 一词多义卡呈现"这套逻辑，**不用改表、不用改唯一键、不用回填老数据**。
- *为什么现在就把 sense_key 放进唯一键、而不是以后再加列：* 若 MVP 唯一键只有 `(user_id, lemma)`、以后再把 sense_key 加进唯一键，那是一次约束变更 + 可能要把已合并的多义词拆开回填，折腾且有风险。现在留好、只是不填非 default 值，才是真正的"以后无痛加"——和项目里 `visibility`、`reply_style` 那些"预留字段先不启用"是同一套做法。

迭代版本的完整方案（sense 判定、一词多义卡呈现）等立项时再展开，此处不细化。

#### 5.2.5 entry_kind：词汇单元类型

word / phrase / collocation(词伙) / slang / idiom / **pattern(固定句型)**，抽词时 AI 顺带标注。既是展示筛选维度，也承载 5.2.1 假设的两支：**collocation** 对应"词都会但不知道怎么搭"，**pattern** 对应"固定句型"（如 "It takes sb. some time to do sth."，`display_form` 存模板本身）。

> 建模选择（**已定**）：句型用 `entry_kind='pattern'` 承载、`tier` 默认按框架处理（句型是通用骨架），**不把 tier 扩成三值**——形态归 entry_kind、通用度归 tier，两轴分开、互不污染。

#### 5.2.6 输入语言 与 已知缺口（第 5/6 接缝，补充）

（回应第六节：母语 vs 目标语言的区别、多语言复用、"已知缺口"。标为补充，MVP 轻量实现。）

**记录每条输入 / occurrence 的语言（`input_lang`）**，三个理由：
- **多语言复用**：用户的母语表达是"想说什么"的意图载体，跨目标语言可复用——今天学英语、明天学日语，同一个意图能重新生成。
- **区分脚手架**：母语轮 vs 目标语言轮本来就要分（6.5），语言字段是实现基础。
- **账本过滤**：母语内容不混进目标语言的高频榜。

**"已知缺口（known gap）"——母语兜底暴露的最高价值学习目标。** 当用户用母语说了个意思（= 他承认"这句我不会用目标语言说"），对应的目标语言表达同时满足**高动机（真想说）+ 高缺口（还不会）**，学习优先级高于系统猜测的泛泛高频词。数据上：母语兜底时记一条"用户想表达 X（母语）、对应 Y（目标语言）、尚未掌握"的**已知缺口标记**，供 6.7 推荐和成长层优先攻克。
> MVP 轻量实现（**已定**）：在 occurrence 上加 `input_lang` + 一个"来自母语兜底缺口"的布尔标记即可，**不单开 expression_needs 表**（避免和现有记录重复一张几乎一样的表）；等要围绕"表达需求"做更多功能时再升级。

### 5.3 累计与再现：把使用记成流水，累计成语言画像，再据此再现 / 提升

**累计（记账）：** 每次在任一来源产生词条，就往 `lexicon_occurrences` 追加一行（带来源、情境、对错、例句）；`total_count` 是频率缓存，真值永远是流水。流水只增不改——它是分析用户语言习惯的**全部证据**（频率、来源、对错、进步都从这里长出来）。

**记账动作（在 `generate` 新增 Stage 3，见第九节）：** 抽词（5.1）→ 规范化过滤（5.1）→ 顺带取义项与 kind（5.2）→ 查该用户是否已有此 lemma+sense：没有则新建 entry（判 tier、存音标词性释义）、有则 `total_count += 1`；无论新旧都 append 一行 occurrence。

**再现 / 提升（这层目的的落地，三种交付）：**
1. **对话里实时再现**：聊到某话题时，把该情境下用户的高频可用词推回（6.5）。
2. **Tab2 主动再现**：`For review` 把"该看的词"按缺口浮到眼前（3.4）。
3. **成长层分析**：把画像和用户实际输出对比，告诉他习惯与缺口（第七节）——这才是"分析语言习惯、定制化提升"的正主。

**为什么流水 / 缓存分开：** 流水是证据（支撑一切分析），缓存是给列表快速排序用的。既能秒出高频榜，又能回溯每一次原始上下文。

### 5.4 数据模型设计（Layer 1 新增两张表）

> 术语先统一（回应审计报告④"命名跨层漂移"）：一个概念只用一个名字，贯穿 DB / Edge / Swift。下面字段名即最终名。

## 六、Layer 2 · AI 对话层（陪练 + 记账 + 记忆）

**这一层解决的问题：素材躺在库里不等于会说。用户需要一个能一来一回、从他自己的经历出发、在他卡壳时接住他的陪练对象——并且这个陪练全程在往词汇账本记账、在记住他的强弱项。**

### 6.1 定位：对话陪练 ≠ Tab1 的生成

必须先划清和已实现的 Tab1 的界线，否则会做重。

| | Tab1 捕获生成（已实现） | 对话陪练（Layer 2 新增） |
|---|---|---|
| 交互形态 | 单次：输入一条 → 出一张卡 | 连续：一来一回的多轮对话 |
| 目的 | 把生活片段变成学习素材 | 用已有素材/话题练"说出来" |
| 产物 | materials 卡片 | 一段对话；**副产物**是新词条 + 新素材（需确认） |
| 记忆 | 30 分钟短期上下文，纯内存（《多轮对话设计_v1》） | **长期记忆**，落 DB，跨 Session 持续 |

**关键区分：Tab1 的 `ConversationSession` 是"工作记忆"（说完就忘），对话层的记忆是"长期记忆"（记住你哪个词总说错）。** 两者都叫"记忆"但完全不同，不要混用同一套机制。

### 6.2 对话入口与主题：一个引擎，两种起点（不新建 tab）

对话不是新 Tab，而是**现有入口的进化**——现有入口本来就产素材，进化成对话后自然继续产素材。两个起点，各管一件不重叠的事：

- **从素材出发（主推）**：Tab2 点开一个词 → 看它的来源场景 → 在某来源场景上"和它聊聊" → dialogue 函数拿这个场景内容（native / 中文原句 / key_phrases）当 seed，生成贴合的开场。话题是用户真事，锚强、有话说。
- **冷起手（补充）**：Tab1 输入入口以后迭代成语音对话，无 seed，AI 泛开场或"你想聊啥"。这是"我此刻想说什么"，冷启动也走这条（聊出的东西照样回流账本）。

**为什么不做单独的自由 chat 入口、也不在 Tab1 加"从场景开始"（§12 问题7 已定）：** 每个入口只应有一个不重叠的职责——场景住在 Tab2 就从 Tab2 发起，冷起手住在 Tab1。正好对上 Tab1（我说过什么）/ Tab2（我在积累什么）的分界，避免两个入口做同一件事。

**两种起点 ≈ 同一个引擎，只差开场 seed：**

| | 相同（引擎建一次） | 不同（只差这里） |
|---|---|---|
| chat 流页 / 语音 / 语言规则 / 实时推荐 / 记账 / 新素材确认 / 对话记忆 / 结束总结 | ✅ 全同 | — |
| 开场 seed | — | 从素材出发以 seed 场景生成开场；冷起手无 seed |
| 相关性锚 | — | 从素材出发一开始有情境锚；冷起手靠对话推断（前几轮锚弱） |
| 产出继承链 | — | 从素材出发继承 seed 场景情境（强）；冷起手靠推断（像冷输入，弱） |

工程含义：**引擎建一次、seed 参数化**，先做哪个都行，加另一个几乎零成本。排期建议先做"从素材出发"（有 seed、数据质量高），Tab1 语音对话随后加"空 seed"分支。

### 6.3 交互形态：独立 chat 流页 + 首页总结卡

- **首页不铺对话详情**：点击进入一个**独立的 chat 流页面**（沉浸、**语音对话——MVP 无文本聊天模式**、不干扰首页时间线）。这解决了"单次捕获（输入→卡）"和"持续对话"两种形态的冲突——前者留首页时间线，后者搬进独立页。
- **对话结束在首页留一张"总结卡"**：轻量回顾（用出了几个你的词、哪处可更地道、哪个从不会到会），点开看详情。这张卡 = 6.9 的即时小结，也是对话向成长层沉淀的入口。
- 待定小点：从 Tab2 场景发起的对话，总结卡落首页时间线还是贴回场景？倾向**统一落首页时间线**（首页 = "我说过什么"的历史），只有一个地方找。

### 6.4 Agent 用什么语言：全目标语言 + 点击翻译

- **AI 全程用目标语言**（MVP 是英文，但架构 / 文案不写死英文，以后可能别的语种），营造沉浸语境。
- **点击翻译兜底**：用户主动点某句 → 看整句母语译文（默认不显示，保沉浸）。
- **MVP 只做整句翻译**：点单个词弹"单词卡 + 查账本显示'你已经有它'"复杂度更高（词查询 + 账本联查 + 生成卡），列为后续增强；短期看整句译文足够。

### 6.5 用户用什么语言：母语兜底 + 实时翻译带音标 + 必须说目标语言才推进

用户可用母语或目标语言。规则：
- **母语兜底**：卡壳时用母语说出想表达的意思 → **弹框实时翻成目标语言，对重点词带音标**（降开口门槛 + 练发音）。
- **必须用目标语言说出来 AI 才推进**：母语轮只给"翻译 + 音标"帮助、不推进剧情；用户用目标语言说出来（哪怕照译文念）AI 才回复、这轮才计入 occurrence。守住"说出来才算数"。
- **母语兜底的语料是最高价值的"已知缺口"**：用户用母语说的，是他"承认自己不会说、却明确想说"的东西——同时满足高动机 + 高缺口。它有两面，都要记（详见 5.2.6）：
  - 内容层：学习优先级最高（推荐 / 成长层优先攻克它）。
  - 产出层：**不判"达标"、不比对 AI 译文——用户嘴里说出来什么就记什么**（照译文念也好、说了自己的变体也好、说岔了也好，记的都是他实际那句），照样计入 `spoken_count`。AI 译文只是屏幕上的脚手架，不是被记录的内容。**不设 `assisted` 字段**（是不是照念既不可靠又不必要）；"用户用了多少次母语兜底"改用 `native_fallback_used` 埋点在聚合层看。

*为什么这么设计：* 母语兜底降低开口门槛，又严格区分"我替你说的"和"你自己说出来的"，只有后者算成长——这是产品诚实性的底线。

### 6.6 对话时长与空闲退出：不设最低时长，做优雅的空闲收尾

**最低时长：不做（已定）。** 硬性"聊满 N 分钟才能走"偏暗黑模式、和"有温度、不施压"冲突；而且收获按"是否产出"而非时长——4 轮产出 2 个表达 = 有收获，10 轮全 yes/no = 没收获。要引导就用**产出型软目标**（"用出 3 个你的词"），完成有正反馈但随时能走；总结卡如实反映"这次收获了啥"，少时自然勾"再聊两句"。

**空闲退出：做，但优雅。** 这和最低时长正相反——不是"逼你留下"，是"你已经走了就体面放手"。主流做法分层、有预告、结束不销毁：语音助手（听几秒无声→轻问"还在吗"→仍无声关闭）、客服 chatbot（空闲弹"X 分钟后结束"→到点关闭）、会话分析惯例（30 分钟无活动 = session 结束，本项目 Tab1 已用）。
- **本产品**：空闲一小会先轻推一次（"慢慢来～"），不退；继续空闲（1–2 分钟，阈值待定）→ **优雅收尾：生成总结卡 + 记账落库 + 回首页**。
- **本产品对话是语音的（没有文本聊天模式）**：在持续监听麦克风、耗电，所以空闲超时停止监听 + 收尾是**必要的、不是可选的**。切后台又回来复用现有 30 分钟 session 逻辑（短时回来续、超时收尾）。
- **硬规则：任何自动结束都必须产出总结卡 + 记账，绝不因用户分心就静默丢掉他练的东西。**

### 6.7 实时推荐："最需要"的多信号排序（动态相关性 + 已知缺口 + tier 个性化）

对话中实时给"你手头有这些能用上"（从账本挑，可一键关闭）——这是 5.2.1 分层第一个作用（对话中引导输出）的落地。"最需要"= 综合排序：
1. **动态相关性**：话题随对话进化，相关性**不锚死开场场景**，而是每隔几轮从最近对话内容重新推断"当前话题"、重排候选，持续刷新。
2. **已知缺口优先**：用户刚母语兜底暴露的"想说但不会"的表达 → 最高权重（当下正卡在这）。
3. **按 tier 个性化加权**：从成长层拿用户缺口画像（偏缺框架动词还是场景词），把他弱的一侧加权——tier 不只是筛选，是个性化。
4. **可激活的闲置储备**：账本里有、最近没用、当下用得上的词，推一把促成复习式产出。
5. **够得着（i+1）+ 多样性**：略高于当前水平不超纲；别老推同几个。

排序：动态相关性 ×（已知缺口 > 闲置储备 > 新词）× tier 缺口加权 × 够得着。
*为什么推自己的词而非通用推荐：* 激活已有、快忘的储备 = 复习式产出；灌通用新词认知负担高、也背离"从你生活取材"。

### 6.8 新素材提取与确认（不自动入库，可删除）

对话里冒出值得留存的内容，agent **打包成预览卡问"要不要加入你的素材？"**，确认才入 materials + 记账，否则丢弃。

- **提取规则（什么值得提）**：用户产出的、**账本里还没有的**表达（新词 / 搭配 / 句型）；母语兜底转出的地道英文；AI 纠错后用户采纳的更地道说法；够到"场景级"的完整表达更该存。**排除**：AI 单方面说、用户没接住的；纯寒暄；账本已有的重复。
- **为什么必须确认**：延续"素材是用户的"，自动塞会污染库；按一下确认既是筛选、也是"我认领了"的确权。
- **可手动删除**：软删除这个数据能力（`deleted_at`）和 Tab2 长什么样无关、一直都在。重塑成账本视图后，**删除对象是词条**——左滑一个词就把它从账本移除（**连词汇 / 词条都能删**），对话确认入库的素材同样能删。

### 6.9 对话记忆与总结卡：边聊边攒，退出即时展示

**对话记忆是什么（先讲清）：** 系统在对话过程中一边听你说、一边记两种笔记——**待提高**（你没说出来、或说错的地方）和**进步**（以前不会 / 错、这次说对了的地方）。这些笔记**不是对话结束才重新分析整段对话得来的，而是每一轮顺手记下的**（AI 本来每轮就在纠错、判对错，顺手落成一条 `learning_event`）。所以它不是一个要你点开的独立功能，是**对话自动产生、喂给总结卡和成长层的一叠笔记**。

**总结卡为什么能即时、成本低：** 因为它是"把已攒的笔记归类拼卡"，不是"重新分析整段对话"。所以**在用户退出那一刻（主动退出 或 空闲收尾）直接拼卡即可，几乎零延迟、零额外成本**（回收 6.6"任何结束都产出总结卡"）。若想加一句 AI 生成的温暖总结语，那是一次轻量调用，可异步补、不挡卡片先出。

**总结卡总结什么（三块）：**
1. **这次用出了哪些"你的词"**：从账本调用了几个已有词条——正向、有成就感。
2. **待提高**：可以更好的地方，**分两类，语法是一等公民**——
   - 词 / 表达：想说没说出、或用得不地道。
   - **语法**：时态、单复数、语序、冠词等结构问题。**（按你的判断，语法甚至比词更重要：词错了对方常还能猜懂，语法错了容易听不懂或误解，而"被听懂"是口语第一目标。）**
3. **进步**：哪个以前不会 / 错的，这次说对了。
   措辞延续 7.2：进步正向呈现，待提高用"可以更…"而非"你错了"。

**这三块不是必备栏位，是"有才出现"（条件展示）：** 没进步就不显示进步块、没错就不显示待提高块，避免硬凑空栏，也不给用户"每次都被挑毛病"的压迫感。

**去处：** 当下拼成总结卡；长期汇进成长层（第七节）。两类记忆落到数据：

- **待提高**（不会的、说错的）：用户没说出来、或用错的点，记为一条 `learning_event`（event_type='gap' 或 'error'）+ `aspect` 标明是词还是语法等；若牵涉某个词，同时在该 entry 的 occurrence 上标 `used_correctly=false`（**语法类问题不属于某个词，entry_id 可空**）。
- **进步**（之前不会/错、现在对了）：同一个 entry（或同一 aspect 的问题）出现"先错后对"的翻转，生成一条 `learning_event`（event_type='progress'）。这正是"进步感知的本质是质变（说不出→说出来了），不是数字积累"——现在它有了数据触发器。

**新增第三张表 `learning_events`（成长层也读它）：**

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | uuid PK | |
| `user_id` | uuid NOT NULL | |
| `entry_id` | uuid FK→lexicon_entries | 关联词条（**可空**：语法等结构问题不属于某个词，entry_id 为空） |
| `event_type` | text CHECK ('gap','error','progress') | 弱点 / 错误 / 进步翻转 |
| `aspect` | text CHECK ('vocab','collocation','grammar','pattern','pronunciation') | 这条是关于哪方面（词 / 搭配 / 语法 / 句型 / 发音）。让成长层能把"语法薄弱点"单独拎出，不混在词里。**语法是重点** |
| `detail` | text | AI 的一句话说明（"过去式用错，说成 goed"） |
| `source_message_id` | uuid | 来自哪次对话 |
| `created_at` | timestamptz DEFAULT now() | |

*为什么单开一张表而不塞进 occurrences：* occurrences 是"每次使用"的机械流水，learning_events 是"有意义的学习节点"（犯错、突破）。前者量大、机械；后者稀疏、是成长层要重点展示的高光时刻。分开存，成长层查"进步高光"时不用在海量流水里捞。

## 七、Layer 3 · 用户成长层（读账本 + 读用户输出，做差距分析）

**这一层的目的，按你的定义，是让用户"知道自己的现状"——把"用户实际输出的英文"和"账本里已经有的"放在一起对比，让用户看清自己现在站在哪。** 它不产生新存储（读 lexicon / occurrences / learning_events + 读用户输出），但比"只读账本"多了一个关键动作：**找差距**。

### 7.1 什么是"用户输出"（按你的定义收紧为"口语"）

成长层要读的"用户输出" = **用户在对话里用目标语言"说出来"的话（口语）**，来自两个对话入口——Tab1 冷起手对话 + Tab2 场景对话。
- 母语兜底后说出来的（照念也好、说了别的也好），都算输出——**记的是用户实际说出来那句**，不判达标、不比对 AI 译文（见 6.5）。
- **明确不算"输出"的**：AI 生成的内容、母语原话、查词（s1/s3 被动查询）；以及 **Tab1 打字捕获的英文句子——那是"输入 / 捕获"，不是"说出来的输出"**（打字能绕过"开口"这道坎，对口语产品不算数）。

*为什么收紧到口语：* 产品核心是练口语、对话是语音的，"能说出来"才是成长的度量——守住"AI 生成 / 打字 ≠ 用户能说出来"的边界。

### 7.2 差距分析：正向 / 负向，都只是陈述现状

**先立框架：其实是"两个账本"的差（这就是"已使用账本"的位置）。**
- **输入账本（碰过）** = lexicon 全部条目：你收集 / 遇到过的表达（`total_count`）。
- **已使用账本（说过）** = 其中 `spoken_count > 0` 的子集：你在对话里**实际说出来**过的（记的是用户真说的那句，不判达标）。
- 两者**不是两张表，是同一份 lexicon 的两个视图**——一个词"碰过"和"说过"是它的两种状态，不复制身份。凡说出来的都已过记账进了 lexicon，所以"已说出"数据天生就在。
- **两个账本的差 = 成长的全部故事**：碰过没说过 = 练习目标；说过的 = 你真能用的。

把这两个账本（＋用户输出、learning_events）对照，就得到两种差距：
- **正向差距**：用户输出里冒出了账本里没有的、或比账本更地道的表达 → 他在长新东西。
- **负向差距**：账本里有、但没说出来的词（`spoken_count=0`，闲置资产）；或反复用错的点（learning_events 的 error，按 `aspect` 分——**含语法薄弱点，语法是重点**）。

**（硬原则，按你的要求）成长层只陈述现状，不评价。** 负向差距也只是**谨慎地告知现状**，不带评判、不制造焦虑。措辞是"你有这些词还没怎么用起来"，不是"你这些词学得不好"；是"schedule 你还没在'赛程'这个意思上用过"，不是给你打个低分。**目的是让用户认识自己、自己决定要不要提升，而不是让产品替他下判断。** 这既是你的产品意图，也避免强化用户的负面自我认知。

### 7.3 呈现的五个角度（都是上面差距分析的切面，全部只读）

1. **高频表达 / 表达习惯**：读 `lexicon_entries` 按 `total_count` → "你最常用的表达"。分框架词/场景词展示（呼应 5.2.1）。这是现状的正面镜子。
2. **更地道的说法**：某个高频表达其实不够地道 → 对照历史 `native_polish`，"你常说 X，也有更 native 的 Y 可选"。**给选项，不判优劣。**
3. **同义扩展**：针对高频依赖的词，推它**没用过的**同义词（AI 生成候选，比对 lexicon 里没有的），"想说这个意思，你还可以用这些"。
4. **语法 / 结构薄弱点**：读 `learning_events` 里 `aspect='grammar'`（及 pattern）的反复项，"时态是你最近反复出现的点"。**这是待提高的重点**——语法错比词错更影响"被听懂"。谨慎告知、给可练方向，不打分。
5. **闲置与进步**：负向侧 = 闲置的词（有但不用，谨慎告知）；正向侧 = 读 `learning_events` 的 `progress` 事件，"这些是你从说不出到说出来的词 / 语法点"。**用质变叙事，不用进度条/打分。**

**呈现原则（继承 Tab2 + 你的非评价要求）：** 成长页第一反应应该是"哦，我原来是这样"和"我想再练"，不是"我被评了几分"或"我攒了多少词"。数字只作工具性信息，不作评价指标。

## 八、知识产权保护（难题②，给出方案建议）

你草稿的原问：**"怎么保护知识产权，对外怎么展示。"** 这里的 IP 有两层含义，要分开处理。

**第一层：用户的个人素材是用户的隐私资产。**
用户的场景素材取材于真实生活（照片、"帮妈妈弄手机"、情绪），这是最敏感的部分。方案：
- **默认全私有**：lexicon 和 materials 严格按 `user_id` 隔离，任何情况下不跨用户可见（代码已在做，继续强约束 + 补 RLS 作纵深防御）。这是底线，不是功能。
- **图片等原始输入**存私有 bucket、按需签发短期 URL（已实现），不生成公开链接。

**第二层：如果将来要"对外展示"（分享/社区），展示什么、不展示什么。**
建议引入一条清晰的分界，正好复用第五节的分层概念：
- **可分享的 = 去人格化的语言产物**：一个词条、一句地道英文、一个语法点——这些是"通用学习内容"，本身不含个人隐私，类似字典条目。
- **不可分享的 = 人格化的场景背景**：照片、中文原话、时间地点、这段经历本身——默认剥离，除非用户逐条主动勾选公开。
- 换句话说：**分享时，把"帮妈妈弄手机"这段私事抽掉，只留 "set up" 这个词和它的地道用法。** 用户获得"我学的东西可以晒"的价值，又不暴露私生活。

**这层的落地建议：分享功能本身标为 MVP 后置**（现在没有社区场景，不必提前建）。但**数据模型现在就为它留好接口**：给 `materials` 预留 `visibility` 字段（'private' 默认 / 'shareable_derived'），lexicon 天然是去人格化的可共享层。这样将来做分享时不用重构，只需开开关。

*为什么现在只留字段不做功能：* 遵循"垂直切片、不提前铺框架"的工作方法。但 IP 分界的**原则现在就定死**（个人场景私有、语言产物可去人格化分享），避免将来做分享时才发现数据混在一起、拆不开。

## 十一、埋点设计（延续 analytics_events 表）

| 事件名 | 触发 | 附加属性 | 能回答什么 |
|---|---|---|---|
| `dialogue_started` | 进入一次对话陪练 | `{ seed_type: 'scene'\|'free', scene_category? }` | 对话入口有没有人用、从素材起手还是自由聊更受欢迎 |
| `native_fallback_used` | 用户在对话里切母语兜底 | `{ }` | 卡壳有多普遍、母语依赖度（**取代 per-word assisted**）；也是"已知缺口"产生量 |
| `dialogue_ended` | 一次对话结束 | `{ turns, produced_count, native_fallback_count, known_gap_count, end_reason: 'user_exit'\|'idle_timeout' }` | 每次对话的"收获"（产出多少、用了几次母语兜底、暴露多少缺口）+ 怎么结束的——支撑 6.6 用产出而非时长衡量、并看空闲退出占比 |
| `vocab_suggestion_shown` / `_tapped` | 实时高频词展示 / 被点用 | `{ entry_id }` | 推荐词有没有真的被用起来（tapped/shown 转化率） |
| `material_confirmed` / `_discarded` | 对话新素材确认/丢弃 | `{ }` | 确认率——太低说明提议质量差 |
| `tab2_word_tapped` | 点一个词条查看来源 | `{ entry_id, tier }` | 账本列表有没有激起"点进去看"的欲望；哪类词更被点 |
| `tab2_lens_switched` | 切换顶部镜头标签 | `{ lens }` | 哪个镜头用得多、默认 For review 够不够用 |
| `growth_viewed` | 打开成长页 | `{ top_word_count }` | 成长页活跃度，作其他埋点分母 |
| `synonym_adopted` | 采纳一个同义扩展 | `{ entry_id }` | 同义扩展有没有价值 |
| `progress_event_created` | 系统生成一条 progress 翻转 | `{ entry_id }` | "从不会到会"发生的频率——产品核心价值的硬指标 |

`progress_event_created` 是这套产品**最该盯的北极星类指标**：它直接度量"说不出→说出来"的质变，正是全产品的价值主张。
