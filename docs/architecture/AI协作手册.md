# AI 协作手册 —— 产品经理与 AI 搭建软件的方法与模版

> 本文档由 2026-06-27 的一次完整协作沉淀而成。
> 它回答三个问题：① 我（产品经理）和 AI 沟通时该给什么？② 怎么给得有结构？③ 给完怎么让 AI 帮我检查？
> 文档分四部分：背景与原始记录 → 核心方法论 → 沟通模版 → 检查提示词。

---

# 第一部分：背景与今日原始记录

## 1.1 需求背景

- **产品**：AI native 英语学习 App，从用户生活取材，帮用户「把想说的话说出来」。
- **当前阶段**：Tab1（内容捕捉与生成）的文字输入链路。
- **今天的目标**：把「用户只输入文字」时，AI 的 4 种输出情形（PRD 的 2×2 矩阵）端到端跑通。
- **协作者画像**：产品经理，市场背景，零编码。需要每个技术决策都有「为什么」。

## 1.2 我今天给 AI 的原始提示词（逐条留存）

> 留存原始提示词的目的：日后回看「我当时是怎么提的、哪里提得好、哪里提得不够」，对照本手册改进。

**① 开工指令**
> 先检查目前的分支是否commit，然后根据PRD和Claude.md文件带着我，把用户输入文字后所有的输出情形跑通，先只做用户只输入文字的情形，目前PRD文档列出了4种情形下AI的回复，你先复述下我的详细需求应该怎么做，然后我确认后再执行

**② 追问实施细节**
> 可以commit一下。合规/有效性审查怎么实施呢？目前的系统提示词我可以在哪个代码文件里看？最新的几个补充场景是通过结构化提示词实现的么？

**③ 给出安全规则提示词**（我自己写的一段，用于合规/有效性审查，AI 评价并采纳后嵌入后端）
> 核心安全指令：评估语义 → 不合规返回 compliance 错误 → 胡言乱语返回 meaningless 错误（含具体 JSON 文案）

**④ 确认执行**
> 好的，决策点A正确，决策点B正确，你可以执行了

**⑤ 方法论追问**（本手册的起因）
> 我理解任何软件都是由一个自上而下的规则一点点叠加的……上层逻辑更具全局性……我想知道你是怎么一点点加逻辑的？这些规则（UX/交互/视觉/后端）怎么联系到一起？我该怎么给你规则？我缺什么？

**⑥ 功能与数据之问**
> 功能是一个一个叠加的，功能和数据什么关系？我说的数据都很散很乱，但功能是有层次和整体的，怎么通过明确数据来加功能？

# 第二部分：核心方法论

> 这部分是「为什么这么搭」的底层逻辑。看懂这部分，你才知道模版里每一栏为什么存在。

## 2.1 软件是「一圈套一圈」的规则，越外层越稳、越能否决里面

```
L0 产品哲学      最外层｜最少变｜冲突时它赢      「帮用户说出来」「先给答案再追问」「不拒绝」
L1 信息架构      ↓                            Onboarding→Tab1→Tab2；Tab1只生成不分类
L2 交互/状态机   ↓                            输入→loading→卡片→追问；变体A/B/C；凌晨4点分天
L3 数据契约 ★    ↓  脊柱：所有规则在此交汇      4种scenario的JSON形状、字段可空规则
L4 后端/前端逻辑 ↓                            后端流水线：合规→意图→生成→打标；前端send()顺序
L5 组件结构      ↓                            TimelineRow路由→4卡片；字段null就隐藏
L6 视觉token     最内层｜最易变｜被隔离        颜色/间距/字体/圆角
```

**关键纠正**：不是「上层兼容下层」，而是 **「下层服从上层，冲突时上层赢」**。
例：安全规则（产品性质）必须放提示词最前面，**否决**「永远先给答案」——这就是用文字顺序固化了「上层赢」。

## 2.2 「先后顺序」有三种，别混成一个

| | 回答什么 | 方向 |
|---|---|---|
| **① 优先级顺序** | 两规则打架谁赢？ | 自上而下（稳定→易变）|
| **② 搭建顺序** | 先敲哪行代码？ | **先定脊柱（L3数据契约），再两头展开** |
| **③ 验证顺序** | 先确认哪块对？ | 一条最窄端到端链路先跑通（垂直切片）|

**搭建顺序为什么从数据契约开始**：因为数据契约是前后端唯一的握手点。脊柱立住，两头才能各做各的、最后在中间对上。

## 2.3 功能与数据：动词与名词

- **数据是名词，功能是动词。每个功能 = 读数据 → 处理 → 改/产生数据。**
- **数据看起来散乱，是因为你在用「用户视角」数它**（一张张卡片、一句句话）。换成「结构视角」，十几个功能其实只挂在两三个核心结构上（本项目：一条时间线记录、一个AI响应、将来一个Tab2素材）。
- **功能的整体性是用户给的（用户旅程天然连续）；数据的整体性是你设计出来的（你为一组功能找共享结构）。你的活儿就是设计后者去支撑前者。**

**判断一个新功能贵不贵——问数据三问：**
1. 它要 **读** 哪些已有数据？
2. 它会 **改/产生** 哪些数据？
3. 这些数据 **现在存在吗**？
   - 存在手边 → 便宜（如语音、翻译）
   - 存在但没送到位 → 中等，是「连接」问题（如追问：历史已在前端，没传给后端）
   - 需要新造结构 → 大事，动外层，慎重（如 Tab2 素材库落库）

# 第三部分：沟通模版（每加一个功能，填一份）

> 复制下面这张表，每要做一个新功能就填一份发给 AI。填不出来的栏，正是你需要先想清楚、或明确「让 AI 猜默认值」的地方。

```markdown
# 功能需求表：【功能名称】

## 0. 一句话目标（用户视角）
这个功能帮用户做到什么？一句话。

## 1. 产品哲学约束（L0）
它必须兼容哪些已定的产品原则？（如「先给答案再追问」「不拒绝」）
它会不会和某条原则冲突？

## 2. 用户怎么用它（L2 交互）
- 触发：用户做什么会启动它？
- 过程：一步步会发生什么？（包括：等待时？出错时？为空时？）
- 成功：用户看到什么算成功？

## 3. 数据三问（L3 —— 最重要，决定这功能贵不贵）
- 它要【读】哪些已有数据？
- 它会【改 / 产生】哪些数据？
- 这些数据现在存在吗？
  □ 存在手边（便宜）
  □ 存在但没送到位（中等，是连接问题）
  □ 需要新造数据结构（大事，慎重）

## 4. 它长什么样（L6 视觉）
（可留白。建议写「让 AI 先做出来，我看着实物再否决」）

## 5. 边界与冲突
- 异常情况：出错 / 空 / 超长 / 网络断 …分别怎么办？
- 和哪条已有规则可能打架？打架时听谁的？

## 6. 已定 vs 待定
- 我已经定死的（铁律，不可违反）：
- 让 AI 猜默认值并标记出来给我确认的：
```

**填表小贴士（对照方法论）**：
- 第 1、3、5 栏是你的强项（产品判断、数据流向、冲突仲裁），**要给准**。
- 第 4 栏（视觉）是你的弱项，**别硬憋，交给 AI 提案、你否决**。
- 每条规则尽量标注：属于哪层、是铁律还是默认、冲突时谁赢——这是你目前最容易漏的。

# 第四部分：检查提示词（填完表后，粘贴这段给 AI）

> 填完功能需求表后，把表和下面这段一起发给 AI。它会强制 AI 在写代码前先暴露问题、对齐理解，避免「闷头写错一大片」。

```
我填了一份功能需求表（见上）。请你在动手写任何代码之前，先按下面六步做，全部列完后停下，等我回复「确认执行」你再开始：

1. 复述：用你的话把我的需求复述一遍，让我确认你理解对了。

2. 找洞：指出我这份表里【没说清楚】或【自相矛盾】的地方，重点查：
   - 数据三问有没有答不上来的（尤其「这数据现在存在吗」）
   - 有没有和已定产品原则、或已有功能冲突的地方
   - 哪些我没定、你只能猜默认值——把你打算用的默认值逐条列出来让我确认

3. 分层：告诉我这个功能牵动了哪几层（L0哲学/L1架构/L2交互/L3数据/L5组件/L6视觉），其中哪一层改动最大、风险最高。

4. 定脊柱：告诉我这个功能落在哪个数据字段/结构上，需不需要新增或修改数据结构。如果需要改数据结构，单独提醒我（因为那是动外层、容易返工）。

5. 排顺序：给我一个最小垂直切片——先做哪一条最窄的端到端链路就能验证它成立，剩下的怎么横向扩展。

6. 停：以上五步列完，先别写代码，等我回复「确认执行」。
```

# 附：一次标准协作的完整流程

```
1. 我填【功能需求表】
2. 我粘【检查提示词】，AI 复述+找洞+分层+定脊柱+排顺序
3. 我补齐 AI 指出的洞 / 确认默认值 → 回「确认执行」
4. AI 按垂直切片先做最窄链路 → 编译 → 测试 → 报结果
5. 我在真机看实物，对视觉等弱项栏做否决/微调
6. 稳定后 AI 写单元测试锁住 → commit
7. 每 2~3 个切片，AI 做一次 token 卫生审计
```

> 配套文档：`CLAUDE.md`（最外层稳定规则）、`PRD.md`（中间层产品规格）、`待决策清单.md`（当前待补的洞）。
> 本手册是「怎么协作」，那三份是「协作什么」。
