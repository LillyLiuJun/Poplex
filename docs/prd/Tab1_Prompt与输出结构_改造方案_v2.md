## 〇、这份文档解决什么

现在 Tab1 的提示词是**一个 `SYSTEM_PROMPT` 包打天下**：五种卡片类型、三种输入形态全挤在一份里，输出结构是四套互不相干的字段。

| 问题 | 表现 |
|---|---|
| **规则没有顺序** | `SAFETY` / `SELF-REFERENCE` / `LANGUAGE INTENT` / `GRANULARITY` 平行罗列，模型不知道先做哪一步——**这是判错的根因** |
| **排版乱** | 两件事：可空字段没内容时留大块**空白**（s2 最明显）；内容多时**溢出**、没有折叠机制 |
| **命名漂移** | 同一个概念四个名字（目标语言主表达 = `word` / `native_polish` / `english_translation` / `native_translation`） |
| **语义槽位错配** | s2 的用户英文原句没有独立字段，和 AI 润色版挤在一起，落库后**分不开** |
| **人设无标尺** | 代码里 `TONE` 只有三行泛泛之词，与已定的人设规范和品牌调性都不一致 |

本方案分两层解决：**架构层**（有几个 prompt、每个输出什么）和**内容层**（提示词十块逐块处置）。

## 一、Tab1 的定位

**word / sentence = 即时解惑 + 生成素材**（双目标）
**passage = 只有生成素材，没有即时解惑**（见第八节，本轮不做）

即时解惑不是"翻成目标语言"这么简单，也不是"中文 vs 英文"的二分——是按**有没有非目标语言成分**分流。

### 1.1 四步判定（顺序不能颠倒）

```
第零步  SAFETY / 有效性过滤
        不安全 / 无意义 → error 卡，流程终止
              ↓
第一步  这是不是元问题？（用户在问关于某个语言片段的事）
        是 → 抽出被问的对象 X，后面只处理 X
        否 → 处理整条输入
              ↓
第二步  （对象）里有没有非目标语言的成分？
        没有 → comprehend  修正形式 + 用母语解释
        有   → express     译成目标语言
              ↓
第三步  粒度：word / sentence（passage 见第八节）
              ↓
        按 1.3 走对应档位的流程，末尾统一提取 learnable_units[]
```

> **第零步是新增的（v1 漏了）**：SAFETY 不是一条平行的规则，是**流程的入口**——先判要不要处理，再谈怎么处理。错误状态的完整定义见第五节。

**为什么第二步的判据是「是不是目标语言」而不是「中文还是英文」：** 这样第三种语言自动被覆盖，不用单开分支。用户输入日文「お疲れ様です」，意图和输入中文完全一样——**"这个意思用英语怎么说"**。

```
纯目标语言            → comprehend
含非目标语言成分      → express
   ├─ 母语（中文）
   ├─ 第三种语言（日文 / 法文 …）   ← 同一条路，零额外规则
   └─ 混合
```

**混合输入的规则：只要存在非目标语言成分，就是 express。**

| 类型 | 例 | 判定 | 用户在干什么 |
|---|---|---|---|
| 母语为主，嵌目标语言词 | `今天工作好 stress` | express | 用中文思维表达 |
| **目标语言为主，嵌母语词** | `I have a 会议 at 3pm` | **express**（补全成完整英文） | 在写英文、卡在一个词 |
| 元问题 | `overtime是什么意思` | 由第一步抽出的对象定 | 问关于某个片段的事 |

> 第二种在现有规则里**一个字都没有**。而它恰好证明"主体是什么语言"这个判据不够——主体是英文，但用户明明在表达、缺一块。

**为什么顺序不能颠倒——可以直接验证：**

| 输入 | 跳过第一步 | 按四步 |
|---|---|---|
| `overtime是什么意思` | 含中文 → express ❌ | 抽出 `overtime` → 纯目标语言 → comprehend ✅ |
| `摸鱼怎么说` | 含中文 → express ✅（碰巧对） | 抽出「摸鱼」→ 非目标语言 → express ✅ |

### 1.2 不对称：修正只发生在目标语言侧

**`comprehend` 侧才有"修正 / 润色"，`express` 侧没有。** 非目标语言是用户的自然表达，没有"错"可言——他要的是"帮我变成英语"，不是"帮我改中文"。

> 承自《Tab1_AI回复卡片需求设计_v1》决策 4（以"用户的表达意图语言"判路径）与情境 2（`native_polish` 仅当有错才出）。

### 1.3 各档流程

```
word · comprehend      ① 判形式：词形变化 / 拼写错 / 正常
                       ② 卡片主体给【规范词条】，弱化一行说明"你输入的是什么形式"
                       ③ 音标 + 词性（最多 3 个常见词性）+ 母语释义 + 双语例句
                       ④ 提取 learnable_units[]

word · express         ① 译成目标语言
                       ② 音标 + 词性（最多 3 个）+ 双语例句（与上对称）
                       ③ 提取 learnable_units[]

sentence · comprehend  ① 判断有没有问题，并区分【错误】还是【不够地道】
                       ② 有 → 先修正/润色，再翻译【修正版】；标 revision_type
                       ③ 没有 → 直接翻译【原句】
                       ④ 提取 learnable_units[]

sentence · express     ① 译成目标语言
                          （含"目标语言为主、嵌母语词"的补全，见 1.1）
                       ② 提取 learnable_units[]
```

> **每档的最后一步都是提取 `learnable_units[]`——这是账本的唯一进料口。** 现在代码里 `key_phrase` 是单数、一条素材最多 1 个词，本次一并整合掉（见 3.2）。
> **`sentence` 那道流程现在的提示词里没有**（s2 是平行输出四个字段，没有先后与条件关系）；**`word` 那道形式判定完全没有**。落到字段上见 3.1。

## 二、架构层

### 2.1 按输入来源拆 prompt

| 路 | 状态 | 输入 | 说明 |
|---|---|---|---|
| **文字路** | 已上线 | 短文本 | **本轮唯一改造对象** |
| **图片路** | 已上线 | 纯图 / 图文混合 | 单独拆出，理由见下 |
| 长内容路 | 未开发 | 长文 / 文件 / 邮件 / 聊天记录 | **第八节** |
| 语音路 | 未开发 | 语音输入 | **第八节** |
| 对话路 | 未开发 | 语音对话 | 不属 Tab1，归对话页 |

**图片路为什么单独拆（v2 修正）：**

v1 写的"纯图是确定性任务、固定出场景卡"**是错的**。图片输入的产出同样可能落在三档粒度上——拍一个单词、拍一句话、拍一整页文字。

真正的拆分理由是：**判定依据不同**。文字路的四步判定第一步是"看文本"，图片路要先"看图里有什么"——是一个词、一句话、一段文字，还是一个没有文字的场景。这一步的性质和文字路完全不同，混在一份提示词里会互相污染。

**但输出仍然走同一套**：判出粒度和方向之后，后续流程与字段结构与文字路完全一致。图片只是多了"从图里读出待处理内容"这一前置步骤。

> 纯图（图里没有文字，只有场景）是 `sentence · express` 的一个特例：用 `ai_scene_guess` 承载 AI 对场景的描述，再译成目标语言。

**待定（待-8①）**：图文混合走哪条——决策4 说"无论有无文字统一进情境 4"，代码是"图文混合按文字分类"。两份说法冲突，要挑一边。

> **重要澄清**：「按输入来源拆 prompt」和「按输出形态分粒度」是**两个正交的维度**。文字路里面仍然有 word/sentence、comprehend/express 四种组合——拆了 prompt 不等于取消了这些区分。

### 2.2 输出结构：一套字段 + 两个维度

**保留四类卡的差异，但不再用四套字段名。** 真正的差异只有两个维度，**但两者地位不同**：

| 维度 | 取值 | 决定什么 | AI 要判吗 |
|---|---|---|---|
| `granularity` | `word` / `sentence` /（`passage` 预留） | 讲多细、走哪条流程 | ✅ **AI 唯一真正的分类任务** |
| `direction` | `comprehend` / `express` | 哪边是源 | ❌ 由 1.1 第一、二步**推导得出** |

**word 卡最能说明这一点——两个方向的字段完全相同，只是哪一栏是用户给的不同：**

| | 用户给英文词 | 用户给中文词 |
|---|---|---|
| `user_original` | overtime | 摸鱼 |
| `target_expression` | overtime（同一个） | slack off |
| `native_meaning` | 加班 | 摸鱼（同一个） |
| `phonetic` / `pos[]` / `examples[]` | 同 | 同 |

对照原来的卡型：

| 原卡型 | granularity | direction |
|---|---|---|
| s1 轻词典 | word | comprehend |
| s2 句子分析 | sentence | comprehend |
| s3 地道翻译 | word | express |
| s4 场景手帐 | sentence | express |

**为什么这样改而不是简单统一命名：**

1. **CARD SELECTION 从"五选一"降为"判一个粒度"**——判一件事比判五件事稳，也不再踩"到底算 s2 还是 s4"这类边界。
2. **落库从四个 case 变成一个映射**，`buildRawContent` 不再为每种卡型写一份。
3. **前端从四套组件变成一套按维度显隐**，同一个字段在四张卡上必然同字号同颜色——《输入到成长》§1.4 那笔"同字段字体字号不统一"的旧账从根上消失（**根因就是字段名不统一，所以各写各的**）。

### 2.3 粒度决定详细程度

> ⚠️ "粒度"有两个意思，必须拆开：**输入粒度**（这是词还是句）已并入 `granularity`；**输出详细度**（讲多细）由 `granularity` 的取值**决定**，不是另一条独立规则。二者是同一字段的因与果。

| granularity | 一次输入产出 | 详细程度 |
|---|---|---|
| `word` | 1 个学习单元 | **最细**：音标、最多 3 个词性、释义、双语例句 |
| `sentence` | 1 个学习单元 | **细**：译文、修正/润色、语法说明 |
| （`passage`） | N 个学习单元 | 见第八节 |

### 2.4 卡片呈现：由内容体量决定

**排版是两个独立的问题，解法不同，不能混着解：**

| 问题 | 表现 | 解法 |
|---|---|---|
| **空白** | 可空字段没内容时留下大块空（s2 最明显） | **区域随字段为 null 自动隐藏**。`Tab1_AI回复卡片需求设计_v1` §330 已定过（"`key_phrase` 为 null 时前端区域自动隐藏"），**只是没贯彻到所有可空字段**——本次要贯彻 |
| **过长 / 溢出** | 内容太多，一张卡装不下 | **收起 + 展开** |

**所以「收起 / 展开」是长度的解法，不是每张卡都有的固定两态。**

| granularity | 内容体量 | 是否需要展开 |
|---|---|---|
| `word` | 天然短 | ❌ **不需要**，直接全展示 |
| `sentence` | 多数短，偶尔长 | ⚠️ **超过阈值才折叠**（阈值见待-6） |

> **明确回答"word + sentence 需要展开态么"**：word 不需要；sentence 只在超长时需要，不是常态。短卡强行加展开态纯属多余。

### 2.5 版式统一：都突出目标语言

**comprehend 和 express 两种卡片，版式统一——都突出目标语言，不按"输入语言 vs 翻译语言"各排一套。**

**为什么：**
1. 产品是练英语，用户要练的永远是**目标语言那一侧**，不管它是他写的还是 AI 给的。
2. `Tab2_PRD_v1` §4.2 已经定过同样的原则（"s2/s4 进 Tab2 后统一按英文优先、中文弱化展示，不延续 Tab1 那套不对称逻辑"）。**Tab1 也这么排，两个 tab 才一致**——否则同一条素材在两处长得不一样。
3. 两套版式意味着两套组件，回到"字段名不统一 → 各写各的"的老路。

**但要用弱化的方式标出哪一栏是用户输入的。** 这正是 `user_original` / `target_expression` 分开存的意义（3.1①）——版式统一不等于抹掉"这是你写的 / 这是我给的"这条界线，那是 Tab2 的立身之本。

```
comprehend（用户给英文）        express（用户给中文）
┌────────────────────┐         ┌────────────────────┐
│ set up      ← 突出  │         │ set up      ← 突出  │
│ /set ʌp/            │         │ /set ʌp/            │
│ v. 安装；建立        │         │ v. 安装；建立        │
│ ─────────────       │         │ ─────────────       │
│ 你输入的：set up ← 弱│         │ 你输入的：安装 ← 弱  │
└────────────────────┘         └────────────────────┘
```

## 三、统一字段表

一套字段，按维度取用。`—` = 该组合不产出此字段。

| 字段 | 含义 | word+comp | sent+comp | word+expr | sent+expr |
|---|---|:--:|:--:|:--:|:--:|
| `granularity` | 粒度 | word | sentence | word | sentence |
| `direction` | 方向 | comprehend | comprehend | express | express |
| `user_original` | **用户原样输入**（不加工） | ✅ | ✅ | ✅ | ✅ |
| `user_original_lang` | 用户输入的语言（**任意语言码**） | target | target | 非 target | 非 target |
| `target_expression` | **AI 产出的目标语言表达** | ✅ 规范词条（3.1③） | 可 null＝原句无问题 | ✅ 译文 | ✅ 地道表达 |
| `revision_type` | **修正性质**（3.1④） | — | `error`／`polish`／null | — | — |
| `native_meaning` | 母语释义 / 译文 | ✅ 释义 | ✅ 译文 | ✅ 原概念 | 可选 |
| `phonetic` | 音标 | ✅ | — | ✅ | — |
| `pos[]` | 词性，**最多 3 个常见词性** | ✅ | — | ✅ | — |
| `examples[]` | 例句 `{en, zh}`，**双语** | ✅ 1–2 | 可选 | ✅ 1 | 可选 |
| `grammar_note` | **形式 / 语法说明** | 可 null（形式） | 可 null（语法） | — | — |
| `ai_scene_guess` | AI 对图片场景的描述 | — | — | — | 仅纯图 |
| `learnable_units[]` | **可学单元数组**（3.2） | ✅ | ✅ | ✅ | ✅ |
| `follow_ups[]` | **追问，1–2 个，不落库**（3.3） | ✅ | ✅ | ✅ | ✅ |

### 3.1 五处必须说清的语义

**① `user_original` 与 `target_expression` 必须分开存，这是本次改造最重要的一条。**

现在 s2 落库写的是 `native_english: native_polish ?? userText`——用户自己写的英文和 AI 润色版**挤在同一个字段里，落库后分不开**。而这恰恰是 Tab2 要守的那条线：**AI 生成的 ≠ 用户能说出来的**。

拆开之后：
- `user_original` 永远是用户原样输入。
- `target_expression` 永远是 AI 产出。`sentence+comp` 的 `null` 有明确语义 = **"你原句没问题，我没改"**。
- 下游取"这条素材的目标语言表达"统一用 `target_expression ?? user_original`，规则一条，不分卡型。

**② `native_meaning` 翻译的是「正确版本」，不是用户原句——必须在提示词里写死。**

```
native_meaning = 对 (target_expression ?? user_original) 的翻译
```

拿 `I am very sleep today` 举例：

| | 翻用户原句 | **翻正确版本（本方案）** |
|---|---|---|
| `native_meaning` | "我今天很睡觉"（荒谬）；或 AI 悄悄按正确意思翻成"我今天很困"——**但用户不知道自己错了** | "我今天很困" |
| 用户得到 | 一个不知从何而来的翻译 | 先看到问题在哪，再看到正确版本和它的意思 |

**顺带废弃 `chinese_original`**：它在 s2 里装 AI 中译、在 s3/s4 里装用户原文，四种语义挤一个位置，这就是落库填错槽的直接原因。

**③ word 侧：卡片主体永远给「规范词条」，用 `grammar_note` 说明用户输入的形式。**

| 情况 | 例 | `user_original` | `target_expression` | `grammar_note` |
|---|---|---|---|---|
| **词形变化** | 输入 `spoken` | spoken | **speak** | "spoken 是过去分词，用在完成时（I have spoken to him）和被动（English is spoken here）" |
| **拼写错** | 输入 `recieve` | recieve | **receive** | "你写的是 recieve，正确拼写是 receive" |
| **正常** | 输入 `overtime` | overtime | overtime | `null` |
| **用词不当** | 想说"加班"却输入 `overwork` | overwork | overwork | `null` —— **不处理** |

最后一种明确不做：没有上下文，AI 无从知道用户想表达什么，硬猜会错得离谱。

> `grammar_note` 因此从"仅 sentence 的语法点"扩展为"**形式 / 语法说明**"——word 侧讲形式、sentence 侧讲语法，本质都是"关于你写的这个形式的说明"，不新增字段。

**⚠️ 归原型的判定，必须和账本的 lemma 归一化共用同一套规则。** `Agent PRD v2` §5.1.3 定的"词形还原：meetings → meeting"就是这件事。**卡片和账本各判各的，就会出现用户在卡片上看到 `speak`、账本里存的却是 `spoken`。**

而且不是所有词形都能归原型——**只有当这个词形没有独立词义时才归**：

| 输入 | 归原型？ | 为什么 |
|---|---|---|
| `spoken` / `meetings` | ✅ | 纯屈折变化，无独立词义 |
| `glasses`（眼镜） | ❌ | 与 `glass` 语义完全不同 |
| `drawing`（图画） | ❌ | 名词义独立于 `draw` |
| `used to` | ❌ | 固定结构，不是 `use` |
| `spoken English` 里的 spoken | ❌ | 此处是形容词，有独立用法 |

这条规则同时约束提示词和记账层，**要写进两份文档**。

**④ `revision_type`：区分「错」和「不够地道」（v2 新增）**

sentence+comprehend 侧的修正有两种性质，**对用户的意义完全不同，呈现语气也该不同**：

| `revision_type` | 例 | 性质 | 怎么呈现 |
|---|---|---|---|
| `error` | `I am very sleep today` → `I'm very sleepy today` | 语法/用词**错了**，不说他会一直错下去 | **明确指出**，`grammar_note` 必出（"sleep 是动词，这里要用 sleepy"） |
| `polish` | `I very like it` → `I really like it` | 语法没错，只是**不够地道** | **轻触**，用"也可以说 X"的口气，不判优劣 |
| `null` | 原句没问题 | —— | `target_expression` 为 null，不显示修正区域 |

*为什么必须分开：* 两种都塞进同一个呈现里，要么把"不地道"说重了变成挑刺（撞上 persona 的"不说教"），要么把"错"说轻了用户根本没注意到。**一个字段解决，不新增结构。**

**⑤ `ai_scene_guess` 必须真正落进结构。**

现在提示词**确实输出了**它，但落库用的 `SceneRawContent` 结构里没有这个字段，写库那一刻就丢了；同时 `chinese_original` 被 `String(null ?? '')` 压成空字符串。纯图素材的上下文因此在落库瞬间消失——**而引导页的纯图路径是新用户的第一条素材，第一条就命中**。

> ⚠️ **拆 prompt 必须连带落库结构一起拆。** 只换提示词、不改 `raw_content` 结构，②⑤ 两处失真不会消失——它们的根在落库映射层。

### 3.2 `learnable_units[]`：账本的唯一进料口

```
learnable_units: [
  {
    form:       "set up",          // 表达原形
    kind:       "phrase",          // word|phrase|collocation|slang|idiom|pattern
    note:       "帮别人配置/装好",   // 一句话说明
    is_primary: true               // 是否卡片主推（高亮那个）
  },
  ...
]
```

- **数量随输入体量而定，不在提示词里写死。** 短句 1–3 个。这一并整合掉现在"`key_phrase` 单数、一条素材最多 1 个词"的限制（`Agent PRD v2` §2.3(2)）。
- **`is_primary` 让"卡片展示什么"和"账本收什么"在同一次输出里分开**——卡片只高亮 `is_primary`，账本吃全部。**这样记账不需要另跑一次 AI 调用**（`Agent PRD v2` §5.1.1 路径 A）。
- **筛选标准（什么算一个可学单元）不在本文档定**，那是《输入到成长》§二 批次一的头号问题。本文档只定**结构**——结构稳定、标准可换，才能拿真实数据对照着试几版标准。

### 3.3 追问：移出卡片，1–2 个，不落库（v2 改动）

**追问不再是卡片内的一个字段，改为：**

| | v1 / 现状 | **v2** |
|---|---|---|
| 位置 | 卡片内的 `scene_trigger` | **卡片外，对话流下方** |
| 数量 | 1 个字符串 | **1–2 个**（`follow_ups[]`） |
| 持久化 | 随卡片落库 | **不落库、不留历史记录**——用完即失 |

*为什么改：* 追问是**当下的引导**，不是这条素材的一部分。留进历史记录只会让老卡片上挂着一堆早已过期的提问；移到卡外、不落库，卡片本身就更干净，也不必为它设计"历史里的追问要不要还能点"这种边界。

**追问内容按粒度分化（延续《输入到成长》§1.1 已定）：**

| 粒度 | 追问什么 | 为什么 |
|---|---|---|
| `sentence` | **场景细节** | 本来就有情境，追问细节是顺势加深 |
| `word` | **"什么场景遇到 / 会用到"** | 词是孤立的，追问处境补上语境，也呼应账本"词 → 场景"的继承链 |

沿用决策5的三条约束：必须顺着用户的**具体细节**延伸、**禁止泛问**（"Tell me more" 无效）、最多 2 句。

### 4.1 persona 与 TONE 重做

#### 现状：三方打架

| 来源 | 说的是 |
|---|---|
| **代码** `TONE` | "Warm and encouraging, like a knowledgeable friend" + 简洁实用 —— 只有三行泛泛之词 |
| `Tab1_AI回复卡片需求设计_v1` 决策5 | 口语化、可用网络梗、先认同再延伸、可开小玩笑、**正反例里带 emoji** —— **从未进入提示词** |
| `Tab0_onboarding_PRD_v1` §150 | **克制美学**：不要卡通陪伴感、无 Emoji、要"笃定" |

三者互斥。而且代码里那句 `Warm and encouraging` 恰恰**鼓励了**决策5明令禁止的"夸奖用户"。`AI协作手册` 也早把"AI 语气无标尺"列为已知缺口。

#### 已定基调：温润极简（Warm Minimalism）+ 注重效率

对应品牌：主色 `#FF7622` 暖橙（饱和度保持，不降调）、中性色是暖纸灰（H 24–30°）——**暖但不喧，克制但不冷**。语气要和这套视觉是同一个人。

**可执行的规则：**

- **温润 ≠ 热情。** 不冷淡，也不亢奋。温度体现在**懂用户的处境**（"开了一天会那种累"），不体现在情绪词（"太棒了！""加油！"）。
- **极简 = 不铺垫。** 用户要的东西第一句就给到，不写 "Great question!"、不写 "Let me explain…"、不描述自己在做什么。
- **注重效率 = 能一句说完不说两句。**

**保留决策5的三条禁止项**（与新基调完全一致，不是要推翻的部分）：

```
❌ 不夸奖用户输入（"Great input!" / "很好的问题！"）
❌ 不用教练腔（"这是个学习的好机会…" / "你可以尝试…"）
❌ 不说教、不主动给人生建议（除非用户明确问"我该怎么做"）
```

**废弃决策5的允许项**（与新基调冲突）：

```
✗ 网络梗
✗ emoji
✗ "先认同再延伸"的情绪铺垫（改为：直接给内容，共情藏在措辞里）
```

**新增：**

```
❌ 不自我描述（"作为你的英语伙伴…"）
❌ 不用感叹号堆情绪
✅ 共情通过"准确描述处境"实现，不通过情绪词
```

#### 正反例（同一条输入，三种语气对照）

用户输入：**「今天地铁挤死我了」**

| | 文案 | 判定 |
|---|---|---|
| 现在的代码 | "Great that you're sharing! The subway was packed today — that sounds tough! 😅 Would you like to learn more commuting expressions?" | ❌ 夸奖用户 + emoji + 教练腔，三条全踩 |
| 决策5（接地气带梗） | "The subway was packed — did you manage to squeeze off at your stop without a fight? 😅" | ❌ emoji；情绪铺垫偏多 |
| **温润极简（本方案）** | 卡片："The subway was packed today."<br>追问："Was it the whole ride, or just getting off?" | ✅ 直给表达；温度在"问到了具体的那一下"，不在情绪词 |

## 八、迭代（暂不做，正文不体现）

以下全部**本轮不做**，字段/枚举值预留，正文不展开设计。

### 8.1 `passage`（长内容）

- **定位不同**：`passage` **只有"生成素材"的需求，没有"即时解惑"的需求**——用户粘一大段进来不是要看懂每一句，是要"这里面有什么值得我学的"。所以第一节的双目标对它不成立。
- **产出方向**（已有共识，待细化）：收起态一句话概览 + "N 个可学点"；展开态可学单元列表，**可勾选剔除**，只有用户留下的才进账本。
- **不做整篇润色，润色降级为「可学点的一种」**：长内容大概率不是用户写的（邮件、文章、聊天记录），润色别人的内容毫无价值。文中若有不地道表达，作为一个可学单元挑出来（"这里用了 X，更常见的是 Y"）。**好处是不需要判断"这段是你写的还是你收到的"**——同一份产出，两种需求都接住。
- **重点是提取规则**（`learnable_units[]` 从长文本里挑什么），归《输入到成长》§二。
- 待细化：`passage + express`（粘一大段中文）产出什么；`passage` 要不要追问；三种语言情况各自的产物。
- **正文保留 `granularity` 的 `passage` 枚举值作为预留**，不实现。

### 8.2 长内容路 / 语音路 prompt

- 长内容路（粘贴长文 / 文件 / 邮件 / 聊天记录）：独立提示词，随 8.1 一起做。
- 语音路：**待定**转写后并入文字路，还是独立提示词。语音上线时才阻塞。

### 8.3 `coach_mode`（按 english_level 分化语气）

`Tab0_onboarding_PRD_v1` §354 设计过按 `english_level` 映射一个内部标签（teach / retrieve / destigmatize / polish）控制语气侧重，**代码从未实现**（`SYSTEM_PROMPT` 是常量、不读 level）。

**MVP 废弃**。理由：一个语气基线都还没定准，先谈按人分化太早；且 `english_level` 现在几乎全是默认 B1，实际没有区分度。

### 8.4 其他后置项

- 单词级点击翻译 / 单词卡。
- 语言展示切换（让偏好母语优先的用户把词卡切成母语为主）——与 `reply_style`、`interest_tags` 等预留字段同批。

| 8 | `scene_trigger` 是卡片内字段、1 个 | **移出卡片**：卡外对话流下方、**1–2 个**（`follow_ups[]`）、**不落库不留历史** | 批注 |
| 9 | `coach_mode` 列在待定、倾向废弃 | **确认废弃**，移入第八节迭代 | 批注 |
| 10 | 长内容路 / 语音路列在架构表 | 移入第八节迭代 | 批注 |
| 11 | 施工顺序 7 刀 | 拆为 9 刀，**新增第 4 刀「把 2–6 五块改写成有顺序的四步流程」**——只改提示词组织顺序、不动字段和前端，是收益最高的一刀 | 顺延 |
