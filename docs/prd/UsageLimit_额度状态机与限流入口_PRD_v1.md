# 功能需求表：使用额度 · 状态机与限流入口 v1

> 状态：**待评审 / 未开工。** 现状只有 `UsageLimitButton` 图标 + `UsageLimitSheet` 一个视觉版本，且**完全没有拦截逻辑**——`TodayViewModel.send()` 里不存在任何次数判断，Sheet 里的 20 只是一个展示用的硬编码数字（`UsageLimitButton.swift:65`），和本次需求"暂定 5 次"不一致。这份文档把「限流本身」「状态机」「图标视觉」三件事拍板到同一份规格里，避免三处各自臆测。

---

## 0. 一句话目标（用户视角）

我今天还能免费生成几次、什么时候会被拦、被拦了还能不能想办法继续用——这三件事在同一个入口（右上角额度按钮）看得明明白白，而不是点开才发现进度条已经满了却什么都没发生。

## 1. 产品哲学约束（L0）

- 限流发生在"是否允许发起新一轮生成"这一层，不影响已产出内容的可读性：历史消息永远可查看（与 `OfflineCache_PRD_v1.md` 的"服务器为正本、本地永久可读"原则不冲突）。
- 达到上限**不是拒绝，是引导**：产品目前没有付费/配额系统，人工放量（看 Feedback / 邮箱）是唯一的"继续用"通道，这条要在文案和交互上体现出"我们愿意让你继续"，而不是一堵硬墙。
- 这是产品里第二个"发送前置门槛"：第一个是 `TodayViewModel.send()` 里已有的 `isConsentGranted()` AI 数据处理同意拦截（`TodayViewModel.swift:351-356`）。两者应该是同一个家族的行为模式——不吞输入、不静默失败、拦截时明确告诉用户为什么。新的次数拦截要照着这个已验证的模式加，不要另起一套。

## 2. 用户怎么用它（L2 交互 / 状态机）

**触发**：每次调用 `send()` 生成前先判断「今日已用次数 vs 每日上限」；右上角图标与其 Sheet 任何时候都应反映当前所处状态，而不是只有点开 Sheet 才知道。

**三态定义**（这是本次要补的核心缺口——现状只有一个视觉，没有区分）：

| 状态 | 判定 | 图标表现 | Sheet 表现 |
|---|---|---|---|
| **默认 Default** | `remaining` 远大于 0（现状已有，仅套壳） | 常态线性图标，无强调色 | 常规进度条 + "refresh every day at midnight" 文案 |
| **进行中 Running Low**（缺） | `remaining` 落在临近上限的区间（阈值待拍板，见"待定"） | 图标切到强调色，提示"快用完了" | 进度条变强调色 + 追加一行"You're running low today" |
| **达标 Reached**（缺） | `used >= dailyLimit` | 图标切到警示态（不同于进行中） | 进度条满格（警示色）+ 达标专属文案 + **Send Feedback 按钮**（复用现有 `FeedbackView`）+ 邮箱联系次要入口 |

**达标态的拦截行为**：点发送时若已达标，`send()` 直接短路、不发起网络请求；同时把用户引导到上表的达标态 Sheet（具体是"内联提示+引导点开"还是"直接弹出"，见"待定"）。

**恢复**：跨自然日后计数回到 0、状态回到 Default。现状 `Calendar.current.isDateInToday` 已经是这个语义（`UsageLimitButton.swift:141`），复位不需要新逻辑，只是三态要能正确地"退回默认"。

## 3. 数据三问（L3 —— 决定这功能贵不贵）

- **读**：本地 `LocalCache.shared.load(key: .messages)` 解出的 `[MessageRecord]`，按 `role == "user"` 且 `createdAt` 是今天来计数。这段逻辑现在只写在 `UsageLimitSheet.task` 里（`UsageLimitButton.swift:137-142`），是**唯一一处**，按钮图标本身并不知道这个数字——这也是为什么图标现在做不出"进行中/达标"两态：状态压根没被提升到按钮层。
- **改 / 产生**：不新增任何持久化数据结构。今日已用次数完全由现有本地消息记录推导，v1 阶段刻意不做后端配额表（见"已定"）。唯一新增的是**配置常量**，不是数据：一个类似 `FeatureFlags.swift` 的 `UsageLimitConfig.swift`，把「每日上限」「进行中阈值」收敛到一处，改数字不用满仓库搜。
- **这些数据现在存在吗**：
  - 今日已用次数 → **存在手边**（计数逻辑已经写过一遍，只是位置不对、要从 Sheet 里抽出来给按钮和 `send()` 共用）。
  - 每日上限数字 → **存在但没送到位**：Sheet 硬编码 20，本次要 5，且没有唯一定义来源——是"有值但值错、没有单一出处"的连接问题，中等成本。
  - 三态判定 + 达标态 CTA → **需要新造**，但都是小常量/小文案，成本低，只是必须先拍板才能画图。

## 4. 它长什么样（L6 视觉）

**图标要改的根因**：现状 `UsageGaugeIcon`（`UsageLimitButton.swift:21-60`）画的是一个"仪表盘 + 指针"，一个完整的写实读数隐喻。对照左侧 `SettingsMenuButton` 的 `DoubleLineMenuIcon`（`SettingsMenuButton.swift:22-49`）——两根圆头线段，零具象隐喻，注释里明确写着"不复用实心图标，避免与内容竞争注意力"——右边这个仪表指针虽然线宽复用了同一套 `topBarMenuIconStroke`，但视觉重量和抽象层级比左边重一整级。这就是"写实了不高级"的根：不是画得不精致，是隐喻选得太具象，跟顶栏其余极简线性语言不是一个系统。

**提案方向**（AI 先出稿、PM 看实物再否决，按项目惯例"视觉栏别硬憋"）：把仪表指针换成**分段圆环 / 刻度胶囊**——比如按 `dailyLimit` 分出等量的短弧段，随已用次数依次点亮/熄灭。这个图形本身就是"额度"该有的样子（一份一份被消耗），而不是"测量仪器"，而且天然能一图带三态：

- 默认：少数几段点亮，描边色 `AppTheme.Color.textPrimary`（与现状一致）。
- 进行中：仅剩最后一段时，那一段变强调色。
- 达标：全部点亮且整体切到警示色。

配色候选：达标态用 `Primitive.errorDeep`（`AppTheme.Color.danger` 同源，也和 Feedback 页插画色系 `feedbackIllustrationAccent` 呼应——图标变这个颜色恰好在暗示"这里能跳去反馈"）；进行中候选 `Primitive.warning900`，但本项目 warning 色族整体饱和度偏低（`warning950` 才 `#C8B11B`），警示力可能不够，是否需要单开一个更醒目的强调 token，等实物出来再判断。

**Sheet 版式**：默认/进行中复用现有卡片+进度条骨架（`UsageLimitButton.swift:87-122`），进行中只是换色+加一行小字。达标态：进度条满格用警示色；标题下文案替换为达标专属文案（例如 "You've reached today's limit. Want more today?"）；卡片下新增主按钮 "Send Feedback"（直接 present 现有 `FeedbackView`）+ 一行次要邮箱联系方式。顺带一提：`FeedbackView.swift:253` 目前的邮箱是占位符 `name@example.com`，既然要在这里复用展示方式，建议一并换成真实邮箱。

## 5. 边界与冲突

- **带图消息算不算多一次？** 现状计数口径是"`role == "user"` 的消息条数"，不区分是否带图——一条带图的 user 消息也只算 1 次，与"限制输入 N 次"的表述一致，维持不变，但要写清楚避免后续被误解为"每张图另算"。
- **重试（`retrySend`）算不算新的一次？** `retrySend` 复用同一个 `requestId` 幂等键，服务端不会重复落库（`TodayViewModel.swift:390-398` 注释）——提案：**重试不占用新次数**，因为它对应的是已经计数过的同一条用户消息。需 PM 确认。
- **达标后还能干嘛？** 历史仍可读（不受影响）；仅"发起新生成"被拦，与 `OfflineCache_PRD_v1` 的"服务器为正本、本地永久可读"不冲突。
- **本地读取失败时怎么办？** 现状 `.task` 静默失败时 `usedCount` 保留初值 0（`UsageLimitButton.swift:137-142` 没有 else 分支）——也就是说本地缓存一旦读取失败，用户会被**误判为"今天还没用过"从而被误放行**，而不是被误拦截。这是"宁可误放行、不可误拦付费用户"的兜底策略，v1 是否接受需要 PM 明确表态（我倾向于接受：产品早期，误放行的代价远小于误拦截真实用户）。
- **卸载重装 / 换设备能否绕开限制？** 能——因为计数完全本地化，没有后端配额系统。这是"v1 不做后端"这个前提下的必然代价，建议明确写进"已定"，避免以后被当 bug 提出来返工。

## 6. 已定 vs 待定

**已定（本次拍板）**：
- 每日生成次数限制要做；起始数字**必须做成可调常量**，不需要动视觉/交互结构就能改数字。
- 需要三态：默认 / 进行中 / 达标；达标态要在 Sheet 原位提供 Send Feedback / 邮箱联系入口，而不是硬拒绝。
- 图标去掉写实仪表指针隐喻，改成与左侧汉堡图标同一抽象线性语言、且自身能表达三态的新图形。
- v1 不做后端配额系统，计数继续走本地消息记录，接受"卸载重装可绕开"的已知代价。

**待你确认的默认值**（AI 先按下面这版做，你看实物再否决）：
- 每日上限的具体数字：本文档示例先按 **5** 写，落地时收进新建的 `UsageLimitConfig`，替换掉 `UsageLimitButton.swift:65` 现有的 `20`。
- "进行中"阈值：提案为**剩余 ≤ 1 次**（总数只有 5，比例阈值太琐碎，不如整数阈值直给）。
- 达标拦截的呈现方式：提案为"发送前在输入区做一次内联提示，引导点开额度 Sheet"，比每次点发送都强制弹出 Sheet 更不打断；也可以反过来直接强制弹出——两种都不难做，需要你选一种。
- 三态强调色：进行中提案 `warning900`，达标提案 `errorDeep`；若 warning 色族饱和度压不住，看实物后可能改开新 token。
- 重试不计入新次数——提案如上，需确认。
- `FeedbackView.swift:253` 的占位邮箱：建议借这次机会换成真实邮箱，一并修正。

# 六步检查（AI 执行）

## 1. 复述

把「限制每天生成次数」落成一套可随时调数字的限流机制：右上角图标 + Sheet 从现在的"只有一个默认视觉、且完全不拦截"，升级为"默认/进行中/达标三态联动、达标时真正拦住生成并引导去 Feedback 或邮箱联系"。上限数字本身收进一个配置常量，以后改多改少不用碰视觉和交互代码。

## 2. 找洞

- **数字不一致**：Sheet 硬编码 20（`UsageLimitButton.swift:65`），本次需求要 5——必须先统一到一个唯一出处（`UsageLimitConfig`），否则两边各写各的会继续分叉。
- **现状完全没有拦截逻辑**：`TodayViewModel.send()` 里没有任何次数判断（只有 `isConsentGranted()` 和 `isLoading` 两道 guard），Sheet 里的数字目前只是"展示"，从未真的挡过任何一次生成。这次要新增的不只是视觉，还有一道实打实的生成前置门槛。
- **状态没有被提升**：今日已用次数的计算现在完全锁在 `UsageLimitSheet.task` 内部，按钮图标本身拿不到这个值——所以图标做不出"进行中/达标"两态，得先把这个读数抽成三处（图标、Sheet、`send()`）共用的东西。
- **"进行中"阈值未定义**：需求里提到要有这个状态，但没给具体触发点，本文档提案"剩余 ≤ 1"，需要你确认或改。
- **达标拦截的交互方式未定**：是内联提示还是强制弹窗，直接影响改动范围，需要你选一种再动手。
- **读取失败时的兜底策略是隐含的"误放行"**：现状代码路径决定了本地缓存读取失败 = 当作用户今天没用过，这是可接受的默认值，但之前没人明确拍过板。
- **retry 是否计入新次数未定**：提案不计入，需要确认。
- **卸载重装能绕开限制是必然代价**：不是本次能解决的洞，但要写进已定，免得以后被误当 bug。
- **反馈邮箱是占位符**：`FeedbackView.swift:253` 的 `name@example.com` 目前不是真实地址，若要在达标态露出邮箱联系方式，这个占位符会被真正曝光给用户，建议这次一并换成真实邮箱。

## 3. 分层

- 改动最大 / 风险最高：**L4**（把"今日已用次数"从 Sheet 内部私有状态提升为图标 + Sheet + `send()` 三处共用的状态，是本次唯一有"状态分叉"风险的部分）与 **L6**（图标要重画，且要在同一图形里表达三态，需要反复看实物）。
- 其次 **L2**（新增"达标即拦截"这一步交互，且要决定内联提示 vs 强制弹窗）。
- **L3** 改动小但必须先定：新增 `UsageLimitConfig` 常量文件，统一 dailyLimit / runningLowThreshold 两个数字的唯一出处。
- L0/L1 不动。

## 4. 定脊柱

新增一个小型可观察状态（例如 `enum UsageLimitState { case normal, runningLow(remaining: Int), reached }`）和一个统一的"读取今日已用次数"函数，从现有 `UsageLimitSheet.task` 里的逻辑（`UsageLimitButton.swift:137-142`）搬出来，供 `UsageLimitButton`（图标着色）、`UsageLimitSheet`（正文 + CTA）、`TodayViewModel.send()`（拦截）三处共用同一份口径。同时新增 `UsageLimitConfig.swift`（写法仿照 `FeatureFlags.swift`），收敛 `dailyLimit` 和 `runningLowThreshold` 两个数字为可调常量。不改动 `MessageRecord` / `LocalCache` 任何现有结构——今日已用次数依旧从本地消息记录推导，这是本次唯一的新增结构，且对现有数据模型零侵入。

## 5. 排顺序（最小垂直切片）

**切片一（最窄核心：先跑通"真的会被拦"，视觉先将就）**：
1. 新增 `UsageLimitConfig`：`dailyLimit = 5`，`runningLowThreshold = 1`（先写死本地常量，不做远程配置）。
2. 把"今日已用次数"计算逻辑从 `UsageLimitSheet.task` 抽成共用函数/状态。
3. `TodayViewModel.send()` 顶部加一道 guard：达标 → 不发起生成，触发一个新的 `showUsageLimitReached` 状态，复用现有 Sheet 的弹出方式呈现（先不做输入区内联提示，收窄本轮范围）。
4. Sheet 按三态切换文案 + 进度条颜色；达标态加一个跳转 `FeedbackView` 的按钮（先不做邮箱次要入口）。
5. 手动验证：把 `dailyLimit` 临时改成 1，连续生成 2 次，确认第 2 次被拦截、弹窗文案正确、点 Send Feedback 能正常跳转到 `FeedbackView`。

**横向扩展（切片一验证通过后）**：
1. 图标本身按三态换形/换色（分段圆环重绘）。
2. Sheet 达标态补上邮箱联系次要入口，同时修正 `FeedbackView.swift:253` 的占位邮箱。
3. 输入区内联提示（如果切片一确认要走"内联提示"这个交互方向）。
4. 把 `dailyLimit` / `runningLowThreshold` 迁到真正的远程可配置来源——这会是独立的后端配额系统 PRD，不在本次范围内。
