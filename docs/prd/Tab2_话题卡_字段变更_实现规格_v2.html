#发现处置状态
1 最终 ORDER BY 断链。基线结尾为 ORDER BY cw.word_count DESC, cw.last_material_at DESC，删该字段后 SQL 不合法已复核：hero_v4.sql:276 cat_words 保留 MAX(lo.created_at) 作纯排序键，不输出到 JSON。不用 last_talked_at 兜底（它是 LEFT JOIN，NULL 排序语义不清） 已定

3 Edge Function 回写陷阱。不改 signImagePaths 时裸路径原样透传（不是 null）；重建 cover 会丢 material_id 见 §3。收集侧深入一层；回写用展开语法保留 material_id；签名失败只置空 image_url，不丢整条 activity 已定
4 dialogue_sessions.ended_at 无任何写入方，按它过滤会恒为 null 口径改用 dialogue_turns 的用户轮次时间。取数路径见 §4（唯一待定项） 部分
5 索引论据错误。idx_lexicon_entries_user_spoken 与该聚合无关（cat_words 驱动表是 occurrences，entries 按主键 JOIN） 论据已更正，见 §5。结论「不需新建索引」不变 已定
6 「列表排序键」无 SQL 支撑。排序实际在客户端 moreCategories() 从字段用途描述中删除该说法。RPC 不做该排序 已定
7 cover LATERAL 无可用索引，谓词 (user_id, scene_category, scene_detail) 上无索引，执行 N 次 先排序、后取 cover：排名 → 取前 5 → 只对前 5 跑 LATERAL。N 压到常数 5 已定
8 tiebreak 不应用封面时间（无图活动永远垫底，且语义与活动新鲜度无关） scene_counts 加 MAX(lo.created_at) FILTER (非 word) 作 activity_last_at，与有无图解耦 已定

02最终 SQL 规格

2.1 cat_words

cat_words AS (
  SELECT
    lo.scene_category,
    COUNT(DISTINCT lo.entry_id)::int AS word_count,
    COUNT(DISTINCT lo.entry_id) FILTER (WHERE le.spoken_count = 0)::int
                                     AS not_spoken_count,
    MAX(lo.created_at)               AS sort_last_at,   -- 纯排序键，不输出 JSON
--  MAX(lo.created_at) AS last_material_at,  -- 不再输出
--  ( preview_words 子查询 )                 -- 整段删除
  FROM   lexicon_occurrences lo
  JOIN   lexicon_entries     le ON le.id = lo.entry_id
  WHERE  lo.user_id = p_user_id
    AND  lo.scene_category IS NOT NULL
    AND  le.status = 'active'
  GROUP  BY lo.scene_category
)

DISTINCT 是必须的

驱动表是 lexicon_occurrences，一个词条在多条 occurrence 里出现会被数多次。 COUNT(*) FILTER 得到的是「出现次数」而非「词条数」。 同一个坑本项目已中过一次——scene_counts 的注释原文： 「旧为 COUNT(*)（词条行数，虚高）」。 spoken_count 是 NOT NULL DEFAULT 0，不存在 NULL 掉出 FILTER 的问题。

2.2 scene_counts —— 加 tiebreak 列

scene_counts AS (
  SELECT
    lo.scene_category, lo.scene_detail,
    (COUNT(DISTINCT lo.source_id)
      FILTER (WHERE lo.source_granularity <> 'word'))::int AS occurrence_count,
    MAX(lo.created_at)
      FILTER (WHERE lo.source_granularity <> 'word')        AS activity_last_at
  FROM …  -- 其余不变
)

2.3 activities —— 先排名、取前 5、再取 cover

ranked_activities AS (
  SELECT sc.*,
         ROW_NUMBER() OVER (
           PARTITION BY sc.scene_category
           ORDER BY sc.occurrence_count DESC, sc.activity_last_at DESC
         ) AS rn
  FROM   scene_counts sc
  WHERE  sc.occurrence_count > 0
),
activities AS (
  SELECT r.scene_category,
         jsonb_agg(
           jsonb_build_object(
             'scene_detail',     r.scene_detail,
             'occurrence_count', r.occurrence_count,
             'cover',            cover.obj        -- null = 该活动无带图素材
           ) ORDER BY r.rn
         ) AS items
  FROM   ranked_activities r
  LEFT   JOIN LATERAL (
    SELECT jsonb_build_object(
             'material_id', m.id,
             'image_url',   m.raw_content->>'source_image_path'
           ) AS obj
    FROM   lexicon_occurrences lo
    JOIN   materials m ON m.id = lo.source_id
    WHERE  lo.user_id        = p_user_id
      AND  lo.scene_category = r.scene_category
      AND  lo.scene_detail   = r.scene_detail
      AND  lo.source_type    = 'material'          -- 多态外键，未来防线
      AND  m.deleted_at IS NULL                    -- 软删素材的流水被有意保留
      AND  m.raw_content->>'source_image_path' IS NOT NULL
    ORDER  BY m.created_at DESC
    LIMIT  1
  ) cover ON true
  WHERE  r.rn <= 5                                 -- 卡面用 3，多给 2 作兜底余量
  GROUP  BY r.scene_category
)

activity_count 仍由 moment_counts 全量计算，不受这里的 rn <= 5 截断影响。

2.4 featured / hero_photos —— 整段删除

连同 featured 的五键排序 DISTINCT ON 与 hero_photos 的 ROW_NUMBER() 窗口一并移除。最终 SELECT 的两个 LEFT JOIN 同步删除， ORDER BY 改为 cw.word_count DESC, cw.sort_last_at DESC。

需写进变更记录的三处口径

① occurrence_count 的定义。「Cooking ×7」的 7 是 COUNT(DISTINCT source_id) FILTER (source_granularity <> 'word')： 一条素材 = 一次出现；source_granularity 为 NULL 的行（枚举容错产物）被静默排除； comprehend 方向的英文输入也计为一次。这是本次改动对外的产品承诺，必须写死。

② activities 新增了 occurrence_count > 0 过滤。 旧 sub_scenes 不过滤，会包含 0 计数的纯查词组。这是「复活 + 收窄」之外的第三处行为变化。 好处是 activities 与 activity_count 的口径从此一致（旧的两者不一致）。

③ 加 deleted_at 过滤会降低照片覆盖率。 某活动的图若全被软删，cover 变 null 退兜底图。行为正确，但与「图对不上宁可退兜底」的规则叠加后， 预设图出现频率会高于原估计。

03Edge Function 改动

与 RPC 同发。漏改是静默失败，且有两种不同表象。

  • 收集侧：从 sub_scenes[].image_url / featured.image_url / hero_photos[].image_url 三处，改为 activities[].cover.image_url 一处，多一层嵌套。
  • 回写侧：必须 cover: {...cover, image_url: signed}， 不能把 cover 整体替换成 URL——否则 material_id 丢失， 客户端缓存 stableKey 与去重失效。
  • 签名失败时只置空 image_url，不能像现在的 hero_photos 那样把整条丢掉—— activity 的 scene_detail 和 occurrence_count 没有图也要展示。
  • 两种失败表象：完全不改收集侧 → activities 不被重写， 裸 Storage 路径原样透传（非法 URL）；改了收集但签名失败 → image_url 为 null（无图）。 排查时注意区分。

04唯一待定项：last_talked_at 的取数路径

口径已定：「最后一次对话」= 最后一次用户开口，取 dialogue_turns 中 role = 'user' 的最新时间。天然排除 0 轮 session、Gemini 失败的孤儿行、以及杀进程遗留的 ended_at = NULL 行；也修掉了「用 session.created_at 会把 40 分钟的一场对话报成 40 分钟前」的低估。

未定的是怎么取。下面两条路二选一。

方案 A 直接扫 turns —— 存在热路径成本问题

last_talked AS (
  SELECT s.scene_category, MAX(dt.created_at) AS last_talked_at
  FROM   dialogue_turns dt
  JOIN   dialogue_sessions s ON s.id = dt.session_id
  WHERE  dt.user_id = p_user_id
    AND  dt.role = 'user'
    AND  s.scene_category IS NOT NULL   -- 否则产出一个 NULL 分组
  GROUP  BY s.scene_category
)

dialogue_turns 是全系统写入量最大的表（每句话一行）。 唯一可用的索引是 idx_dialogue_turns_user——单列 (user_id)， 且建表注释写明用途是「数据审计 / 隐私删除用」，是罕用管理路径的索引，不是热路径索引。

这意味着每次打开 Library 都要扫描该用户的全部对话轮次，且基数随使用时长快速增长。 这与本次对 cover LATERAL 提出的成本要求是同一标准，应同等对待。

已复核：20260801000000_create_dialogue_tables.sql:51-52

方案 B 物化到 sessions —— 推荐

在 dialogue_sessions 上加 last_turn_at timestamptz， 由 handleTurn 在写入用户轮次时顺手更新（写入侧 O(1)）。 RPC 回到对 dialogue_sessions 做 MAX(last_turn_at) 分组， 走现成的 idx_dialogue_sessions_user_created，读取成本与 sessions 行数同阶。

代价：多一列 + 一处写入逻辑，且存量测试数据需要一次回填（或直接不回填——反正是测试数据）。 换来的是首页 RPC 不再依赖最大表的全用户扫描。

折中方案 C：维持方案 A，但给 dialogue_turns 加复合索引 (user_id, session_id, created_at DESC)。比 B 改动小，但索引本身在最大表上有写入放大成本。

05成本与索引（论据已更正）

  • 不需要为 not_spoken_count 新建索引——但理由不是 idx_lexicon_entries_user_spoken 存在（该索引与本查询无关， cat_words 驱动表是 occurrences，entries 按主键 JOIN）。 真实理由是：这个聚合搭在已有的扫描上，新增成本为 0。
  • 净成本为负。删掉的 featured（五键排序 DISTINCT ON） 与 hero_photos（窗口 + 嵌套 DISTINCT ON）是整个函数最贵的两段， 新增的是一个 MAX、一个 ROW_NUMBER 和 ≤5 次 LATERAL。
  • 唯一的成本增量取决于 §4 的选择。选方案 A 则引入一次最大表的全用户扫描， 可能抵消掉上面全部收益。
  • 权限不变：仍为 SECURITY DEFINER， REVOKE FROM PUBLIC/anon/authenticated + GRANT TO service_role。

06本刀范围外、但需另立事项

dialogue_sessions.ended_at 是一个空承诺

该列有 CHECK (end_reason IN ('user_exit','idle_timeout','error')) 约束、 有「NULL = 进行中」的注释，但全仓没有任何写入方——schema 承诺了代码没兑现的语义。 本刀绕开它即可，但它会继续误导下一个读表的人。建议单开一个 issue：要么接线，要么删列。
